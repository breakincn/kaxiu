# 4. 核心分支功能完整性评估与开发计划 (Roadmap)

本章节对 Kabao 当前代码库中的各个功能分支进行闭环度评估，识别由于业务发展导致的潜在缺失点，并重点给出**预约机制的专项深度融合开发计划**。

## 4.1 各分支功能完整性与闭环分析
 经过架构审查，当前主干系统的闭环度如下：
 *   **高闭环度（稳定运行）**：
     *   **客服模式 / 叫号模式**：两条模式在当前代码实现下运行时互斥（是否进入叫号链路以 `support_customer_service_mode` 为关键前置条件），但二者的服务会话生命周期均已收敛至 `ServiceSession` 统一状态机，避免了历史上跨入口导致的状态推进不一致与重复分配问题。
    *   **结单核销（Usage/Card）**：基于事务的余额扣减与基于 `usage_revoke` 的反结单机制运转良好。
*   **中闭环度（有待增强容错）**：
    *   **房间/手牌管理**：核心的发牌锁定、分配房间机制有效，且已实现“手牌未归还 -> 锁卡”的兜底闭环：
        - `hand_card_scheduler` 会在“首次分配手牌后超过时间窗口仍未归还”时自动锁定卡片并写入 `locked_reason`。
        - 支持归还手牌后自动解锁（若仍有未归还手牌则更新锁卡原因），并提供商户强制解锁接口。
      **仍需增强**：手牌丢失/补办转移（将原卡的未归还手牌责任迁移到新手牌或记录挂失追溯）、以及房间/手牌在极端异常下的更完整补偿工作流（例如跨日未归还的长期追踪与处理规范）。
    *   **技师考勤**：忙闲推导机制准确。**缺失点**：对临时请假或紧急下钟的处理相对生硬，可能会导致部分排队用户“卡死”在等待池中。
*   **低闭环度（亟需重构/补全）**：
    *   **预约系统 (Appointment)**：当前逻辑较为独立，尚未完全融入整体排队与调度体系，面对线下真实并发冲突（如顾客迟到、技师拖堂）缺乏足够的弹性和自动流转能力。

## 4.2 专项升级：预约与排队叫号机制的深度融合方案

### A. 预约到店场景与“必须结合排队”的必要性分析
在线下实体门店（推拿、美容等），资源的实际耗用时间永远无法100%精确。这导致了以下冲突场景：
1. **技师拖堂/上一个服务未结束**：即使当前时间已到顾客 B 的预约时间（下午2点），但技师服务顾客 A 时加钟，导致技师在2点时仍处于 `busy / serving` 状态。
2. **顾客迟到/早到**：顾客未在精确的预约时间点出现。

**核心论断**：如果系统试图让预约单“到店后立刻生硬强切转入服务(`serving`)”，将不可避免地导致前一个订单被迫中断，或产生并发事务崩溃。因此，**预约到店后，在资源未释放前，必须进入排队缓冲池**。这决定了**预约机制必须与叫号机制结合**。

### B. 架构设计：复用现有叫号模式机制
为了防止系统退化为“两套平行状态机”，**绝不能为预约单单独实现一套排队或叫号轮询逻辑**。必须全面复用当前 `QueueTicket` （叫号模式）底层的排队与转化引擎。

**改造融合方案**：
1. **模型转化（漏斗化）**：当用户在商户端出示预约码“核销到店”时，将该 `Appointment` 标记为 `arrived`，同时系统自动为您生成一张**隐藏或特殊的 `QueueTicket`**。
2. **优先级字段增强**：在 `QueueTicket` 表中增加 `priority_level` 或 `appointment_time` 字段。普通取号为 `0`，预约转化为的 Ticket 设置为 `高优先级(10)`，并绑定原预约指定的 `technician_id`。
3. **入队与叫号复用**：该特殊的 Ticket 直接进入现有的排队系统。一旦目标技师的上一单结单释放（状态回到 `free`），大屏叫号/商户端队列会自动将此**高优先级 Ticket 置顶**，并触发叫号流程转入 `ServiceSession`。

### C. 极端冲突与边缘场景的处置预案 (Actionable Steps)

| 冲突场景 | 现象描述 | 处理方案与工作流 |
| :--- | :--- | :--- |
| **1. 技师拖堂占用** | 顾客准时到店，但预约技师的 `ServiceSession` 未结束 | 顾客到店核销 -> 生成高优 `QueueTicket` -> 进入该技师的专属等待队列 -> 告知顾客排队号并安抚。技师前序结单后，系统秒级唤醒该 Ticket 并叫号。 |
| **2. 顾客迟到过号** | 顾客晚于预约时间到达 | 引入**“宽容期”(Grace Period)** 机制。如设定迟到15分钟内，到店生成 Ticket 仍保留高优先级。超出宽容期，视为“过号”。此时商户端可选择：A. 降级为普通号继续排队；B. 人工授权插队（通过商户端按钮强行修改 Ticket 的 `priority_level` 置顶）。 |
| **3. 预约时段并发超卖** | 用户A和B同时请求下午2点的唯一技师档期 | 在 `appointment.go` 创建订单的 Handler 层，补充更为严格的事务控制。使用 `SELECT id FROM appointments WHERE technician_id=? AND time_slot=? FOR UPDATE` 进行时段锁定，防止超卖产生。若发生极端异常导致的重叠，商户端提供“一键改签/换技师”能力，重定向 `QueueTicket` 指向另一名空闲技师。 |

### D. 未来开发排期建议
1. **Step 1 (Schema 层)**：为 `QueueTicket` 增加 `source_type` (预约转化/现场取号) 与 `priority` 字段。
2. **Step 2 (Handler 层)**：重写预约核销接口，对接并复用 `CreateQueueTicket` 核心逻辑，完成降维转化。
3. **Step 3 (UI 层)**：商户端排队列表 UI 支持显示“高优预约号”的特殊标识，并增加调整优先级的操作按钮。

## 4.3 其它分支中长期补充计划

*   **手牌流转健壮性提升**：
    *   **挂失机制**：增加 `HandCard` 挂失 API。标记手牌为 `lost`，并将原 `ServiceSession` 关联绑定至新发放的手牌 ID 上，保证结单链路不中断。
    *   **超时与跨日补偿**：在现有“未归还手牌锁卡”的基础上，补充跨日/长时间未归还的运营处理与告警（例如超过 N 小时/跨日仍未归还，提示商户处理并保留追溯记录），并明确人工解锁的权限边界与审计。
*   **多房间拆合单结算**：
    *   针对包厢/多人同行场景，设计在 `usage.go` 中的账单聚合视图（由一个主干用户发起统结，但内部扣减对应不同的 Session）。目前系统底层事务支持单次请求内处理多个 Usage，只需在 UI 和聚合 API 层开放此能力。
