# 调度器健康检查使用说明

日期：2026-03-25

## 1. 目标

用于检查以下三个调度器是否仍在持续产生 tick：

- 服务会话调度器
- 预约调度器
- 手牌锁卡调度器

健康状态基于“最近一次心跳时间”计算，而不是只看进程是否存在。

## 2. 心跳写入方式

调度器运行时会周期性把最近 tick 写入 `system_configs`：

- `scheduler_heartbeat_service_session`
- `scheduler_heartbeat_appointment`
- `scheduler_heartbeat_hand_card`

写入内容包括：

- 调度器名
- 来源服务名
- 进程 PID
- 主机名
- 最近 tick 时间

## 3. 使用方式

### 3.1 命令行检查

在 `backend/` 目录执行：

```bash
GOCACHE=/tmp/kabao-go-build-cache go run ./cmd/check_scheduler_health --stale-minutes=3
```

说明：

- `--stale-minutes=3` 表示超过 3 分钟没有新 tick 就判定异常

返回示例：

```json
{
  "generated_at": "2026-03-25T21:27:34+08:00",
  "stale_threshold_minutes": 3,
  "overall_status": "degraded",
  "overall_message": "存在调度器尚未上报心跳",
  "items": [
    {
      "key": "service_session",
      "label": "服务会话调度器",
      "status": "missing"
    }
  ]
}
```

退出码规则：

- `0`：整体健康
- `2`：存在超时、缺失或异常

因此该命令可以直接接到：

- cron
- supervisor
- CI/CD 健康检查
- 进程托管平台探针

### 3.2 HTTP 接口检查

商户端接口：

```http
GET /merchant/system/scheduler-health
```

管理端接口：

```http
GET /admin/system/scheduler-health
```

可选参数：

- `stale_minutes`

示例：

```http
GET /merchant/system/scheduler-health?stale_minutes=5
```

## 4. 状态说明

- `healthy`：最近 tick 正常
- `stale`：超过阈值时间未检测到新 tick
- `missing`：从未检测到该调度器心跳
- `error`：心跳数据损坏或读取失败

整体状态：

- `healthy`：三个调度器都正常
- `degraded`：至少一个调度器为 `stale / missing / error`

## 5. 开发环境如何理解结果

如果当前只是开发调试，且没有启动后端服务，那么健康检查返回：

- `overall_status = degraded`
- 各调度器通常是 `missing`

这是正常现象，不代表代码故障，只代表：

`当前没有调度器进程在跑`

这时仍有另外一层兜底：

- 预约读接口自愈会在读取到跨日卡死预约时自动收口

## 6. 商户端展示位置

商户首页看板已加入“调度器健康状态”卡片，会展示：

- 整体状态
- 每个调度器最近 tick 时间
- 来源服务
- 来源 PID
- 距现在多久未 tick

## 7. 推荐接入方式

推荐至少做一条定时检查：

```bash
*/2 * * * * cd /path/to/kabao/backend && GOCACHE=/tmp/kabao-go-build-cache go run ./cmd/check_scheduler_health --stale-minutes=3
```

如果退出码非 `0`，则触发报警。

## 8. 注意事项

- 开发环境没启动服务时，出现 `missing` 是正常结果
- 如果只有某一个 API 进程启动，也可能只有该进程持续上报心跳
- 该机制检测的是“调度器最近是否真的在跑”，不是“进程端口是否存在”

## 9. crontab 完整配置示例

适用于普通 Linux 服务器。

仓库内示例文件：

- `backend/ops/cron/kabao_scheduler_health.cron`

### 9.1 仅做健康检查并写日志

```cron
*/2 * * * * cd /Users/will/Projects/Go/kabao/backend && GOCACHE=/tmp/kabao-go-build-cache go run ./cmd/check_scheduler_health --stale-minutes=3 >> /tmp/kabao_scheduler_health.log 2>&1
```

说明：

- 每 2 分钟执行一次

或：

## 11. 企业微信 / 飞书 webhook 报警脚本模板

建议在 `backend/scripts/alert_scheduler_health.sh` 放一个统一脚本，通过参数区分报警平台。

```bash
#!/bin/zsh
set -euo pipefail

CHANNEL="${1:-wecom}"
HOSTNAME="$(hostname)"
NOW="$(date '+%Y-%m-%d %H:%M:%S')"
TEXT="Kabao 调度器健康检查异常
主机: ${HOSTNAME}
时间: ${NOW}
请登录服务器执行:
cd /Users/will/Projects/Go/kabao/backend && GOCACHE=/tmp/kabao-go-build-cache go run ./cmd/check_scheduler_health --stale-minutes=3"

if [[ "${CHANNEL}" == "wecom" ]]; then
  : "${WECOM_WEBHOOK_URL:?WECOM_WEBHOOK_URL is required}"
  curl -sS -X POST "${WECOM_WEBHOOK_URL}" \
    -H 'Content-Type: application/json' \
    -d "{
      \"msgtype\": \"text\",
      \"text\": {
        \"content\": \"${TEXT}\"
      }
    }"
  exit 0
fi

if [[ "${CHANNEL}" == "feishu" ]]; then
  : "${FEISHU_WEBHOOK_URL:?FEISHU_WEBHOOK_URL is required}"
  curl -sS -X POST "${FEISHU_WEBHOOK_URL}" \
    -H 'Content-Type: application/json' \
    -d "{
      \"msg_type\": \"text\",
      \"content\": {
        \"text\": \"${TEXT}\"
      }
    }"
  exit 0
fi

echo "unknown channel: ${CHANNEL}" >&2
exit 1
```

## 12. 推荐最终落地方式

推荐组合如下：

1. `supervisor` 守护三个后端服务常驻
2. `cron` 每 2 分钟执行一次 `check_scheduler_health`
3. 非 `0` 退出码时调用 webhook 报警脚本

这样可以同时解决：

- 服务进程意外退出
- 调度器线程未运行
- 调度器长时间无 tick
