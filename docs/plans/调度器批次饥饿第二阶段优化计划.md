# 调度器批次第二阶段优化计划

本计划用于评估并（在确有需求时）对 `service_session_scheduler` 做“活跃状态内部仍可能饥饿”的第二阶段优化，目标是在不改变状态语义的前提下提升公平性与可观测性。

## 现状结论（基于代码核对）

- 主批次已剥离 `finished`，且 `releaseFinishedSessionTechnicians` 独立批次执行；该问题已有回归测试：`TestRunOnce_FinishedNotStarveActiveSessions`。
- 主批次当前仍为：`ORDER BY id asc LIMIT 200`，状态集包含 `room_selecting/room_locked/staff_selecting/start_pending/delay_pending/serving/auto_finishing/timeout_waiting/timeout_failed`。
- 因此，“finished 挤占主批次”的核心饥饿已解决；第二阶段优化仅针对：活跃状态之间仍可能互相挤占（例如某一状态堆积导致 `serving/auto_finishing` 延迟推进）。

## 什么时候需要做第二阶段优化（判断标准）

满足任一即可认为“现阶段需要优化”（建议先观察 1-3 天）：

1. 线上出现“仍活跃但长时间不推进”的投诉或日志：
   - 同一 `service_session` 在 `staff_selecting/start_pending/serving/auto_finishing/timeout_waiting` 等状态停留显著超过预期阈值（例如 >5min、>start_pending_timeout、>auto_finish_delay 等），且 DB 中 `updated_at` 长期不变。
2. 调度器 debug 统计显示主批次 200 条中某一状态占比长期极高（例如 `timeout_waiting` 或 `staff_selecting` 长期接近 200），同时存在其他状态的待处理会话。
3. 商户量/并发提升后，出现“尾部商户/高 ID 会话”推进延迟（不是 finished 导致），例如某些商户的 session 几乎不进入批次。

如果以上均未出现：不建议现在优化（会引入排序/取数策略的复杂度与潜在回归）。

## 优化目标与不变量

- 不变量：
  - 不改变既有状态机语义与迁移条件；只调整“扫描与挑选批次”的策略。
  - 保持幂等、短事务；避免全表扫描。
- 目标：
  - 保证 `serving/auto_finishing/timeout_*` 等“时间敏感状态”不会被 `staff_selecting/room_*` 等大量堆积状态长期挤出。
  - 提升可观测性：可以回答“本轮为什么没处理到某个会话”。

## 实施方案（分级，尽量可回滚）

### Phase 0（必做，低风险）：增加可观测性与验收用例

- 增加批次分布统计日志（仅 debug 开关下）：
  - 本轮主批次各状态计数、min/max id、min/max updated_at。
- 增加“活跃状态内部饥饿”回归测试（sqlite）：
  - 构造 200+ 条低 ID `timeout_waiting`（或 `staff_selecting`） + 1 条高 ID `serving/auto_finishing`，验证下一轮能处理时间敏感状态（需要新的取数策略才可能通过）。

### Phase 1（优先推荐，低复杂度）：主批次按“最需要处理”排序

将主批次从 `ORDER BY id asc` 调整为更接近“下一步应处理时间”的排序（示例策略，二选一即可）：

- 方案 1：`ORDER BY updated_at asc, id asc`
  - 优点：简单，能优先处理“最久未被推进”的会话。
  - 风险：若某些状态频繁写 `updated_at` 可能导致排序偏移；仍需观察。

- 方案 2：状态优先级 + 时间 + id
  - 例如：`timeout_waiting/auto_finishing/serving` 优先，再是 `start_pending/delay_pending`，最后 `staff_selecting/room_*`。
  - 可实现为 CASE WHEN 排序，不改表结构。

回滚：改回原排序即可。

### Phase 2（中等复杂度）：拆分主批次为“多批次配额”

把主批次拆成 2-3 个小批次，每个批次不同状态集合与 limit：

- 批次 A（时间敏感）：`timeout_waiting/timeout_failed/auto_finishing/serving`，limit 80
- 批次 B（排队与准备）：`start_pending/delay_pending`，limit 80
- 批次 C（选择阶段）：`staff_selecting/room_locked/room_selecting`，limit 40

优点：硬性保证每类状态都有配额，不会互相挤占。
风险：代码更长，但语义清晰、可测试。

### Phase 3（高复杂度，通常不需要）：按商户分桶/游标分页

当商户量很大、单表热点明显时再考虑：

- 按 `merchant_id` 轮询取样（避免单商户堆积吞掉批次）
- 引入游标（last_id / last_updated_at）分页，保证全局公平

## 验收标准

- 活跃状态内部饥饿构造用例通过（新增测试）。
- 线上观察：关键状态（`serving/auto_finishing/timeout_*`）的“停留过久”占比下降；调度推进延迟收敛。
- 调度耗时不显著增加（debug 日志可观测）。

## 需要你确认的两个问题

1. 你现在线上是否出现：活跃会话卡住推进（非 finished 造成）的现象？主要卡在哪些状态（`timeout_waiting` / `staff_selecting` / `serving` 等）？
2. 你更倾向的优化强度：
   - 只做 Phase 0 + Phase 1（更轻）
   - 直接做 Phase 0 + Phase 2（更硬配额、更确定）
