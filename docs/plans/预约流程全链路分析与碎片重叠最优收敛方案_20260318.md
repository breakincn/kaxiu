# 预约流程全链路分析与碎片重叠最优收敛方案

## 1. 目标

本文基于当前代码现状，梳理预约全链路，并给出一套能最大化解决以下问题的方案：

- 预约时间段碎片
- 预约时间段重叠
- 未指定客服预约导致的未来产能超卖
- 查询、创建、确认、改签、自动分配五处规则不完全一致

## 2. 当前预约全链路

### 2.1 商户基础配置

当前预约能力依赖三类配置：

1. 商户营业时间
2. 商户预约参数
3. 项目时长与服务间歇时间

其中：

- 商户预约设置包含：
  - `appointment_reserve_buffer_minutes`
  - `appointment_grace_window_minutes`
  - `appointment_max_wait_minutes`
  - `appointment_prediction_buffer_minutes`
  - `appointment_slot_granularity_minutes`

- 项目设置包含：
  - `duration`
  - `service_gap_minutes`
  - `start_delay_seconds`

### 2.2 用户查询可预约时段

入口：

- `GET /merchant/merchants/:id/available-slots`

当前实现：

1. 按商户统一粒度生成候选时段
2. 计算当前项目占用长度：
   - `duration + service_gap_minutes`
3. 对每个候选时段做：
   - 客服可预约校验
   - 未指定客服冲突校验
   - 碎片保护校验

现状优点：

- 不再按项目时长直接滚动出 slot
- 用户只能从后端 `time_slots` 中选，不会前端手输任意分钟

现状问题：

- 客服模式下，未指定客服预约的未来共享容量没有被严格预占
- 因此时段查询仍可能偏乐观

### 2.3 用户创建预约

入口：

- `POST /user/appointments`

当前实现：

1. 校验卡片归属、商户支持预约、项目有效性
2. 只允许预约明天
3. 校验营业时间内可容纳
4. 进入事务
5. 复用 `validateAppointmentPlacementRules(...)`
6. 创建 `pending` 预约

现状优点：

- 创建时已二次校验
- 已纳入碎片保护

现状问题：

- 在客服模式下，若预约未指定客服，仍只是“找一个理论可接客服”，而不是“锁住一份未来容量”

### 2.4 商户确认预约

入口：

- `PUT /merchant/appointments/:id/confirm`

当前实现：

1. 读取 `pending` 预约
2. 事务内重新执行 `validateAppointmentPlacementRules(...)`
3. 更新为 `confirmed`
4. 入预约队列

现状优点：

- 已修复“确认不重校验”的旧问题

### 2.5 自动分配客服

入口：

- `scheduler/appointment_scheduler.go`

当前实现：

1. 对 `pending + technician_id IS NULL` 且创建超过 10 分钟的预约尝试分配客服
2. 对 `confirmed + technician_id IS NULL` 的预约持续回补分配
3. 若 `pending` 长时间无可分配客服，则标记 `failed`

现状问题：

- 自动分配是事后补偿
- 不是在预约创建时就做真实资源锁定
- 因此前面仍可能积累未来共享容量冲突

### 2.6 到店核销与预约接入服务会话

入口：

- 核销 -> `detectServiceSessionSource(...)`

当前实现：

1. 命中 `confirmed/arrived` 且落在预约到店窗口的预约
2. 识别为 `appointment` 来源
3. 若原预约客服仍忙，进入 `appointment_waiting`
4. 否则进入正常服务流程

现状优点：

- 已把预约到店并入服务会话主链

### 2.7 改签

入口：

- 查询改签时段
- 创建改签提议
- 接受改签提议

当前实现：

- 已与 `validateAppointmentPlacementRules(...)` 共用主规则

现状优点：

- 普通预约与改签不再完全两套口径

### 2.8 失约

入口：

- `runAppointmentNoShowOnce(...)`

当前实现：

- `confirmed` 且超过宽限未到店，置为 `no_show`

## 3. 当前系统已解决的问题

### 已解决

1. 用户不能手输任意时间
2. 时段不再按项目时长直接递增生成
3. 创建预约会做事务级重校验
4. 确认预约会做事务级重校验
5. 改签已经并入同一套主规则
6. `pending` 已指定客服预约已纳入未来产能保护

## 4. 当前系统仍然存在的问题

### 4.1 最大问题：未指定客服预约没有真实占住未来共享容量

这会导致：

- 查询时段可能可约
- 创建时也可能通过
- 但未来某个时段其实已经被多条“未指定客服预约”共同消耗过量
- 最终只能在后续自动分配或人工处理时暴露冲突

这是当前“预约重叠/超卖”最核心的剩余问题。

### 4.2 当前碎片保护只是局部启发式，不是全局最优排期

现在拦的是：

- 内部碎片

没有做的是：

- 整天级别最优排布
- 跨客服的全局最优装箱
- 不同项目组合下的收益最优排序

所以碎片会减少，但不会消失。

### 4.3 未来预约之间仍允许“条件性挤占”

当前 `evaluateBookingTechnicianAvailability(...)` 允许：

- 若未来预约 A 对未来预约 B 的预计等待不超过 `appointment_max_wait_minutes`
- 则返回 `conditional`
- 仍视为可约

这意味着：

- 从严格排程视角看，未来预约之间仍不是绝对零重叠
- 系统允许一种“可接受等待”的预约重叠语义

如果目标是“最大化消灭预约时间段重叠”，这一点还不够严格。

### 4.4 预约预测缓冲同时参与了未来预约硬阻塞

当前公式把：

- `service_gap_minutes`
- `appointment_prediction_buffer_minutes`

都叠到预约预测完成时间上。

问题在于：

- `service_gap_minutes` 是硬占用
- `prediction_buffer_minutes` 更像软风险缓冲

如果软缓冲也参与未来预约硬阻塞，会：

- 变得更保守
- 放大碎片
- 降低时段利用率

## 5. 最大化解决碎片与重叠的最优方案

下面这套方案，不是最小改动，而是“最大化解决问题”的方案。

### 5.1 核心原则一：把未来预约拆成“硬占用”和“软风险”

定义两套口径：

1. `hard_reserved_minutes`
   - `duration + service_gap_minutes`
   - 用于未来预约硬排程

2. `soft_risk_buffer_minutes`
   - `appointment_prediction_buffer_minutes`
   - 用于风险提示、现场派单保护、到店等待预测

不要再把 `soft_risk_buffer_minutes` 当作未来预约硬占用的一部分。

收益：

- 可减少假性冲突
- 可减少假性碎片
- 让预约排程和现场风险管理分层

### 5.2 核心原则二：未来预约默认严格不重叠

未来预约之间应采用：

- 严格 no-overlap

也就是：

- 两条未来预约不能依赖“最大等待阈值”去允许彼此重叠

`appointment_max_wait_minutes` 只保留给：

- 现场单压预约
- 到店后前序服务拖堂
- 动态执行阶段的等待承诺

而不是用于：

- 未来预约和未来预约之间的预排期

收益：

- 最大化减少预约时间段重叠
- 预约一旦落单，未来日程更稳定

### 5.3 核心原则三：未指定客服预约必须占用“共享未来容量”

这是最关键的一步。

方案上有两种可选落地方式：

#### 方案 A：创建时立即给预约分配一个真实客服

即使用户没选客服，系统也在创建/确认时做一次最佳客服选定，并直接写入 `technician_id`。

优点：

- 逻辑最简单
- 未来容量最清晰
- 不再有“未指定客服悬空占位”

缺点：

- 商户后续若想手动换客服，需要改派能力

#### 方案 B：保留未指定客服，但创建共享容量预占记录

新增类似：

- `appointment_capacity_holds`

记录内容：

- merchant_id
- appointment_id
- date
- slot_start
- slot_end
- required_capacity = 1

校验时先算：

- 该时段活跃客服总容量
- 已指定客服已占容量
- 未指定客服共享预占容量

只有剩余容量足够才允许通过。

优点：

- 保留“先不指定客服”的产品体验

缺点：

- 实现复杂度更高

结论：

- 若目标是“最大化解决重叠和超卖”，优先推荐 **方案 A：创建时立即锁定客服**。

### 5.4 核心原则四：碎片优化改成“最佳拟合”而不是单纯过滤

当前碎片保护是：

- 会制造碎片就隐藏

最优方案应升级成：

- 在所有可放置位置中找“最小碎片成本”的位置

评分建议：

- `fragment_penalty`
- `load_balance_penalty`
- `late_slot_penalty`
- `technician_switch_penalty`

最终对每个候选位置计算总分，优先展示分数最优的一组时段。

收益：

- 不只是避免坏 slot
- 而是主动把用户往更优排布引导

### 5.5 核心原则五：显式定义“可公开预约项目集合”

当前策略 B 用的是“当前商户所有启用项目”。

最优方案应增加项目字段：

- `bookable_online`

只有：

- `is_active = true`
- `bookable_online = true`

的项目，才进入：

- 核心预约项目集合
- 碎片保护口径
- 可预约时段计算

收益：

- 避免边缘项目污染碎片规则
- 让项目集合真正贴近经营目标

## 6. 推荐最终架构

建议新增一层统一领域服务：

- `AppointmentPlacementService`

对外提供：

1. `BuildSlots(...)`
2. `ValidateCreate(...)`
3. `ValidateConfirm(...)`
4. `ValidateReschedule(...)`
5. `AssignTechnicianOrReserveCapacity(...)`

内部统一依赖：

1. `ProjectOccupancyPolicy`
2. `FragmentPolicy`
3. `CapacityPolicy`
4. `ReservationPolicy`

这样就不会继续在：

- `available-slots`
- `create`
- `confirm`
- `reschedule`
- `scheduler`

这几个入口里分散复制规则。

## 7. 下一步直接可执行的落地计划

### P0：先解决未来重叠/超卖

1. 取消“未来预约之间 conditional 也可约”的语义
2. 把未来预约改成严格 no-overlap
3. 处理未指定客服预约：
   - 优先采用“创建时立即锁定客服”
   - 若业务必须保留不指定客服，再做共享容量预占表

### P1：把预约硬占用和软风险缓冲拆开

1. 新增统一硬占用计算
   - `duration + service_gap_minutes`
2. `appointment_prediction_buffer_minutes` 退出未来预约硬阻塞
3. 仅在现场执行阶段继续使用软风险缓冲

### P2：升级碎片治理

1. 新增项目字段 `bookable_online`
2. 核心预约项目集合改为显式可配置
3. 碎片规则从“坏 slot 过滤”升级到“最佳拟合评分”

### P3：统一领域服务

1. 抽出 `AppointmentPlacementService`
2. 所有预约相关入口统一走该 service
3. scheduler 也复用同一套放置规则

### P4：补测试

至少补以下场景：

1. 未来预约之间严格 no-overlap
2. 两条未指定客服预约争抢同一未来时段时，第二条创建失败
3. 改签与普通预约在相同条件下得到相同结果
4. 预约确认前后结果一致
5. 自动分配不会推翻创建时已经占住的未来容量
6. 核心项目集合变化后，碎片评分结果按配置变化

## 8. 最终结论

如果只追求“小修补”，当前系统已经比之前稳定很多；
但如果目标是：

- 最大化解决预约时间段碎片
- 最大化解决预约时间段重叠
- 让未来预约资源判断真正稳定

那最关键的下一步不是继续调碎片过滤阈值，而是先做：

1. 未来预约严格 no-overlap
2. 未指定客服预约的真实未来容量预占
3. 硬占用与软风险缓冲拆层

这三件事做完，预约系统才会从“规则看起来统一”真正升级到“未来产能被正确建模”。
