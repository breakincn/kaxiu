# 1. 文档定位

本文档不是业务方案讨论稿，而是基于已冻结主方案输出的 `AI 启动执行清单`。

用途只有一个：

- 供下一步 AI 编程工具启动后，按既定顺序持续执行，直到实现最终版本。

执行原则：

- 不再回到“人工多团队分工”模式。
- 不再按“先讨论、再拆多人协作、再人工排期”的方式推进。
- 允许按 `P0 -> P1 -> P2` 的顺序持续开发，但这只是 `AI 连续执行顺序`，不是人工阶段切换点。
- 除非遇到真实阻塞（例如现网依赖缺失、历史数据不可识别、关键接口语义与现有代码完全冲突），否则 AI 启动后应持续执行，不中断等待人工派工。

# 2. 冻结说明

以下文档自本清单生成时起，视为开发基线，后续不再继续修改业务原则：

- 主方案基线：`预约新规与预约资源锁定补偿一体化方案_20260319.md`
- 启动执行清单：`预约新规与预约资源锁定补偿一体化方案_研发启动执行清单_20260322.md`

冻结内容包括：

- `D-1 16:00` 取消截止
- `D-1 16:00-18:00` 次日未约满补开
- 用户主动改签截止到 `D` 营业开始前
- 第一版普通用户主动改签不得跨日
- `bookable` 是派生语义，不是新增状态
- `balanced` 第一版固定为系统规则，不做商户配置化
- 商户违约补偿最终只收敛到 `merchant_breach` 或 `merchant_failure_offset`
- `merchant_breach_pending` 必须在 `breach_decision_at` 前后收敛
- `protected_repair_slots` 必须优先保护受影响预约修复，不得被普通新预约或普通改签占用

# 3. 最终交付目标

AI 启动开发后的最终目标，不是只完成局部功能，而是完成以下一体化版本：

- 次日排班发布 + 已发布排班驱动预约可售
- 预约创建即完成扣减/冻结
- 到店只做签到建单，不重复扣减
- 三阶段改签统一落地
- 商户保护性改签落地
- 请假触发后的异常修复模式落地
- 商户取消、取消申请、抗辩闭环落地
- `merchant_breach_pending -> merchant_breach / merchant_failure_offset` 闭环落地
- 预约结算迁移与快照回写落地
- 拖堂账本与兑现链路落地
- 前后端与测试全部对齐最终规则

# 4. AI 连续执行总顺序

AI 启动后，严格按以下顺序执行，不要跳步。

## 4.1 总顺序概览

1. 先完成数据结构与主流程骨架
2. 再完成预约创建、排班发布、改签、取消、请假修复这些主链路
3. 再完成签到、结算、违约补偿、责任归账
4. 最后完成拖堂账本、补偿兑现、补充页面、补齐测试

## 4.2 强依赖关系

执行时必须遵守以下依赖：

- 没有排班发布与 `bookable` 可售判断前，不要改预约自动确认逻辑
- 没有预约锁定字段前，不要改自动派单保护逻辑
- 没有 `protected_repair_slots` 前，不要落请假修复模式
- 没有结算主表前，不要落完整签到后迁移与退款/转扣逻辑
- 没有 `merchant_breach_pending` / `breach_decision_at` 前，不要落最终补偿收敛任务
- 没有延迟账本前，不要做拖堂补偿兑现

# 5. 所有阶段的真正可执行研发任务清单

## 5.1 P0：先把预约保护主链跑通

### 5.1.1 P0 开发目标

P0 不是做“半套新规”，而是先把最核心的风险关掉：

- 禁止压预约
- 已发布排班控制可售
- 新预约自动确认基于正式排班
- 用户主动改签基于统一窗口
- 系统优化性改签保持默认关闭，但推荐链路需按主方案预留
- 商户保护性改签可提议不可强改
- 请假后进入异常修复模式
- 商户取消与取消申请分流明确

### 5.1.2 P0 开发顺序

1. 新增数据库字段与表（仅 P0 必需项）
2. 落排班发布模型与读取逻辑
3. 改造可售时段生成逻辑，接入已发布排班与 `bookable` 派生语义
4. 改造预约创建逻辑，落预约锁定字段、自动确认、资产扣减/冻结
5. 改造用户主动改签资格校验、候选查询、正式提交
6. 预留系统优化性改签推荐链路，保持默认关闭且只输出推荐结果
7. 新增商户保护性改签提议链路
8. 落请假确认后的受影响预约扫描、`protected_repair_slots` 与高质量修复方案判定结果
9. 改造商户取消接口，分离 `5` 小时前单方面取消与 `5` 小时内取消申请
10. 清理自动派单与压预约路径，确保不穿透预约锁定
11. 补齐 P0 前端页面与 P0 测试

### 5.1.3 P0 可交付完成定义

满足以下条件才算 P0 完成：

- 次日预约只基于已发布排班生成可售时段
- 新预约成功即完成扣减/冻结
- 普通新预约和普通用户主动改签都不得挤占已确认预约
- 普通用户主动改签第一版同日、一次成功机会、失败可重试
- 系统优化性改签默认关闭，开启后也只能推荐不能自动改写预约
- 商户保护性改签必须用户确认后生效
- 请假后可扫描受影响预约、预留修复容量并输出高质量修复方案判定结果
- 商户取消规则按 `5` 小时阈值分流

## 5.2 P1：把签到、结算、商户违约补偿闭环打通

### 5.2.1 P1 开发目标

P1 负责把“预约已经被锁定”进一步推进到“能正确履约、退款、转扣、归责、补偿”。

### 5.2.2 P1 开发顺序

1. 新增 `appointment_settlements` 与预约侧快照/归责字段
2. 落预约签到接口与服务会话入口改造
3. 明确 `appointment_checkin` 与 `walk_in_verify` 两条入口的职责边界
4. 落取消后退款/解冻、未到店自动转扣、改签迁移结算
5. 落 `merchant_breach_pending` 风险标记进入规则
6. 落在线动作后的归责重评估逻辑
7. 落 `runMerchantBreachCompensation` 定时收敛任务
8. 落客服月度免责次数与内部责任账本
9. 落不可抗力撤销链路
10. 明确 `appointment_waiting` 仅保留为异常兼容分支，不再作为预约正常履约主链
11. 补齐 P1 前端页面与 P1 测试

### 5.2.3 P1 可交付完成定义

满足以下条件才算 P1 完成：

- 到店只签到建单，不重复扣减
- 预约结算能覆盖扣次、冻结、退款、转扣、改签迁移
- 旧 `appointment_waiting` 不再作为预约正常主链，只允许保留在异常兼容路径
- `merchant_breach_pending` 能正确进入与退出
- `breach_decision_at` 到达后能收敛到最终状态
- 用户可看到补偿与结算结果
- 商户可查看客服月度责任与违约承担情况

## 5.3 P2：补齐拖堂账本、补偿兑现与末端体验

### 5.3.1 P2 开发目标

P2 负责补齐“不是预约主链，但属于最终版本必需”的拖堂补偿和财务化兑现能力。

### 5.3.2 P2 开发顺序

1. 新增 `appointment_delay_ledgers`
2. 新增项目级拖堂补偿参数
3. 落拖堂检测任务
4. 落账本累计与兑现规则
5. 落补偿查询与审计接口
6. 补齐用户端与商户端的拖堂展示
7. 补齐 P2 测试

### 5.3.3 P2 可交付完成定义

满足以下条件才算 P2 完成：

- 商户责任导致的拖堂能形成正式账本
- 账本能按项目规则兑现
- 用户端和商户端均可查询账本与兑现结果
- 补偿不再依赖人工补录

# 8. 调度器与核心算法开发顺序

## 8.1 P0 调度器顺序

1. 次日排班预热与发布校验
2. 预约可售时段生成只读已发布排班
3. 自动派单复用预约锁定规则
4. 清理条件性压预约路径
5. 请假确认后扫描受影响预约
6. 先输出高质量修复方案判定结果，再生成保护性改签候选
7. 预留 `protected_repair_slots`
8. 系统优化性改签默认关闭；即使开启，也只允许输出推荐且不得占用修复容量
9. 在异常修复模式下调整优先级为：
   - 受影响预约修复
   - 商户保护性改签
   - 普通用户主动改签
   - 普通新预约自动确认

## 8.2 P1 调度器顺序

1. 预约结算状态推进
2. 改签迁移结算
3. 取消后退款/解冻
4. 未到店超窗自动转扣
5. 预约签到后的会话推进中，将 `appointment_waiting` 降级为异常兼容分支
6. 在线动作后的 `merchant_breach_pending` 重评估
7. `breach_decision_at` 到达后的最终归责任务
8. 客服责任账本推进
9. 不可抗力撤销推进

## 8.3 P2 调度器顺序

1. 拖堂分钟检测
2. 拖堂账本生成
3. 按项目规则兑现补偿
4. 补偿审计查询

   - 支持在 `5` 小时阈值内发起取消申请

# 10. 测试用例清单

以下测试清单按执行顺序排列，AI 开发时应同步补齐，不得把测试留到最后一次性补写。

## 10.1 P0 单元测试

### 预约窗口与可售规则

- `D-1 00:00-16:00` 允许预约创建
- `D-1 16:00-18:00` 仅在次日未约满时允许继续预约
- `D-1 18:00` 后关闭新预约
- `cancel_deadline_at` 前允许用户取消
- `cancel_deadline_at` 后不允许用户取消
- 用户主动改签一直开放到 `D` 营业开始前
- 普通用户主动改签第一版不得跨日
- `bookable` 仅是已发布排班上的派生语义
- 未发布排班不得出现在候选时段中

### 预约创建与锁定

- 新预约成功后写入 `reserved_start_at` / `reserved_end_at` / `occupied_end_at`
- 次卡预约创建后直接实扣
- 额度卡预约创建后进入冻结
- 普通新预约自动确认不得穿透已确认预约
- 自动派单不得把预约窗口内客服派给现场单

### 用户主动改签

- 用户主动改签仅允许成功一次
- 失败申请在窗口关闭前可重复发起
- 候选必须满足硬冲突校验
- 候选必须满足碎片保护
- 候选必须满足不劣于当前或更优于当前
- 成功改签后沿用 `booking_root_id`

### 商户保护性改签与请假修复

- 商户保护性改签不占用用户主动改签次数
- 商户保护性改签必须用户确认后才生效
- 请假确认后必须扫描受影响预约
- 请假后必须输出高质量修复方案判定结果
- 请假后必须预留 `protected_repair_slots`
- 普通新预约不得占用 `protected_repair_slots`
- 普通用户主动改签不得占用 `protected_repair_slots`
- 系统优化性改签不得占用 `protected_repair_slots`
- 修复候选不得引入第二个受影响预约

### 系统优化性改签推荐

- 默认关闭时不返回推荐结果
- 开启后仅返回推荐，不自动改写预约
- 异常修复模式下不得与保护性改签争抢修复容量
- 推荐结果必须与当前候选评分和碎片保护口径一致

### 商户取消与取消申请

- 商户在服务开始前 `5` 小时以上可单方面取消
- 商户单方面取消必须填写理由
- 商户在服务开始前 `5` 小时及以内只能发起取消申请
- 用户可同意或拒绝取消申请
- 非用户主动取消成功的预约记录必须保留
- 商户单方面取消后用户可提交抗辩意见

## 10.2 P0 集成测试

- 新预约 -> 自动确认 -> 用户取消
- 新预约 -> 自动确认 -> 用户主动改签成功
- 新预约 -> 自动确认 -> 用户主动改签失败后重试成功
- 次日排班发布 -> 可售时段变化正确
- 系统优化性改签默认关闭 -> 不返回推荐结果
- 系统优化性改签开启 -> 仅返回推荐不自动改签
- 客服请假 -> 受影响预约扫描 -> 保护性改签提议生成
- 客服请假 -> 高质量修复方案判定 -> 保护性改签提议生成
- 用户接受保护性改签 -> 旧占用释放 + 新占用锁定
- 用户拒绝保护性改签 -> 继续尝试其他候选或进入取消/补偿分流
- 商户在 `5` 小时前取消 -> 取消成功并保留记录
- 商户在 `5` 小时内发起取消申请 -> 用户同意 -> 取消成功
- 商户在 `5` 小时内发起取消申请 -> 用户拒绝 -> 保留原预约或继续保护性改签

## 10.3 P1 单元测试

### 签到与结算

- 预约签到成功写入 `actual_arrived_at`
- 实际开始服务写入 `actual_start_at`
- 到店签到不重复扣减资产
- 取消后次卡正确返还
- 取消后额度卡正确解冻
- 改签成功时结算正确迁移
- 未到店超窗后正确转扣

### 商户违约归责

- 满足进入条件时标记 `merchant_breach_pending`
- 在线动作后正确重新评估是否退出风险标记
- 到达 `breach_decision_at` 时正确收敛
- 用户到店且商户未能开始服务 -> `merchant_breach`
- 用户未到店但商户已正式取消/改签提议且用户未接受 -> `merchant_failure_offset`
- 用户未到店且商户未正式发起取消申请/保护性改签 -> 不进入 `merchant_failure_offset`
- 用户未到店且仅有商户整窗未恢复事实 -> 不自动判定 `merchant_breach`
- 商户取消正式生效且确认无法履约时 -> 同事务完成退款/解冻、补偿落账与终态收敛
- 已恢复可履约且用户未到店 -> 不触发商户违约
- 同一预约重复执行归责任务不重复补偿

### 责任承担与不可抗力

- 客服第 `1` 次临时请假且改签失败 -> 商户承担
- 客服第 `2` 次及之后 -> 客服承担
- 保护性改签成功时不计入当月次数
- 跨自然月自动重置免责次数
- 不可抗力申请必须双方确认后生效
- 不可抗力撤销后补偿状态正确回滚或标记撤销

## 10.4 P1 集成测试

- 新预约 -> 自动确认 -> 到店签到 -> 服务开始 -> 完成
- 新预约 -> 自动确认 -> 商户异常 -> 保护性改签失败 -> 风险进入 `merchant_breach_pending`
- 用户到店且商户未服务 -> 收敛到 `merchant_breach`
- 用户未到店且商户已正式履行取消/改签提议流程 -> 收敛到 `merchant_failure_offset`
- 用户未到店且商户未正式留痕取消/改签提议 -> 不触发商户补偿
- 商户取消成功时同步完成退款/解冻与补偿落账
- 取消申请、保护性改签、签到成功后均触发归责重评估

## 10.5 P2 单元测试

- 拖堂超过阈值生成账本
- 拖堂未超过阈值不生成账本
- 按项目固定值模式正确计算补偿
- 按项目比例模式正确计算补偿
- 账本兑现后状态正确推进
- 重复执行兑现任务不重复发放

## 10.6 P2 集成测试

- 新预约 -> 到店 -> 延迟开始 -> 生成拖堂账本
- 拖堂账本 -> 补偿兑现 -> 用户查询结果
- 商户查询补偿审计结果
