# 核心业务重构缺口检查报告（除预约外）

根据对 `docs/wiki` 和 `docs/plans` 下核心设计文档的审查，并结合项目当前代码（handlers/models/scheduler 等）的实际落地情况，除“预约”相关改造外，以下是关于模式隔离及业务流程重构的完成度及待办缺口清单。

## 一、 已完成的核心重构项

1. **模式隔离与状态前缀 (P1 级复核通过)**
   - `session_mode` 统一校验守卫（`ValidateSessionModeForEntry`）已实现并覆盖核心推进入口（起单、选房、选人、叫号推进等）。
   - 状态扩展（`ExpandStatusWithKnownPrefixes`）与前缀剥离（`NormalizeSessionStatus`）已全局应用，解决了裸状态串用导致的状态机污染。
2. **自动叫号单窗口 (qs_) 过号与插队**
   - 固定 3 个窗口的过号等待（`timeout_waiting`）与插队规则已完全落地。
3. **手动叫号 (qms_/qmm_) 推进一致性**
   - 扫码上号、结单触发下一号等已适配多前缀兼容。
4. **超时常量统一**
   - 扫码上号超时等硬编码已重构为 `config.StartScanTimeout()` 统一下发。

## 二、 尚未完成的重构需求（待办缺口）

### 1. 客服模式（CS）子模式缺失：手动结单场景未闭环
*出处：《8.重构修复验证总结.md》*
- **当前状态**：`ResolveSessionMode` 对客服模式的判断不够细化。当前仅实现了“自动结单”（`cs_无房间自动` 和 `cs_房间自动`）。
- **遗留缺口**：
  - ❌ **`cs_手动结单`** (`SupportCSMode && SupportOrderComplete && !SupportRoom`)
  - ❌ **`cs_房间手动`** (`SupportCSMode && SupportOrderComplete && SupportRoom`)
- **风险**：若商户开启“客服模式”并配置“手动结单”，由于后端和 Scheduler 缺乏相应的状态流转（不会自动从 `serving` 进入 `auto_finishing`），会话可能会卡死在 `serving` 状态，无法正常结单。

### 2. 技师考勤：紧急离岗/下钟的队列补偿机制
*出处：《4.核心分支功能完整性与开发计划.md》*
- **当前状态**：技师状态变更为 `rest` 或手动 `paused` 时，调度器依赖“其他在岗空闲技师”推进，或者等 `start_pending` 超时自动退回。
- **遗留缺口**：缺少对“紧急下钟/离岗”的显式队列补偿动作。
- **待重构项**：需要将该技师名下处于 `start_pending`（待上号）的会话立即转入 `timeout_waiting` 并 `uncall`（释放占用），或触发重分配机制。同时，商户端需提供“改派/跳过/一键重新分配”的标准操作入口。

### 3. 房间/手牌管理：异常场景的兜底工作流
*出处：《4.核心分支功能完整性与开发计划.md》*
- **当前状态**：已实现发牌锁定和“手牌未归还 -> 锁卡”的 `hand_card_scheduler` 超时兜底。
- **遗留缺口**：对于手牌丢失、补办转移（跨卡转移责任）、以及跨日未归还等极端异常情况的完整补偿工作流尚未实现。

## 三、 遗留用例未覆盖

## 四、 后续行动建议
1. **最高优**：补齐客服模式的手动结单能力（区分 `ResolveSessionMode` 的返回值，适配对应处理流程），防止特定商户配置下的流程卡死。
2. **中优**：落地技师紧急离岗的并发补偿，释放被锁定的会话与叫号资源。
