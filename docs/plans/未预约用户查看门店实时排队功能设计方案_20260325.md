# 未预约用户查看门店实时服务状态与排队进度功能设计方案

日期：2026-03-25

## 1. 修订结论

根据本次补充需求，这个能力的正确落点不是“新增一个实时排队系统”，而是：

- 不新增新的排队功能
- 不新增额外队列
- 不新增新的 `QueueType`
- 不新增新的排队表或异步排队链路

而是在现有项目代码基础上，直接利用当前两种既有模式的服务进度事实做推算：

1. 客服模式  
   根据 `核销 -> 选房 -> 选客服 -> 起单 -> 结单 -> 客服签到/忙闲状态` 推算门店当前服务负载。

2. 叫号模式  
   根据 `核销 -> 排队/叫号 -> 上号 -> 结号 -> 暂停叫号 -> 客服叫号状态` 推算门店当前服务负载。

最终提供的是一个“只读展示能力”，让未预约用户在门店公共页看到：

- 当前门店忙不忙
- 现在到店大概是否需要等
- 大概等多久
- 什么时候来更合适

不要求绝对准确，但要求基于现有服务流转，做到基本准确、稳定、可解释。

## 1.1 本轮复核结论

结合现有代码再次复核后，结论是：

1. 这份方案能够覆盖需求预期的主体目标  
   即：让未预约用户直观看到门店当前服务状态、当前进度、是否建议现在到店，以及一个基本准确的等待预测。

2. 完全基于现有服务流转状态做推算是可行的  
   当前 `service_sessions + technician_attendances + technicians.queue_paused + merchant.queue_paused + queue.Default` 已经足够支撑“状态展示”和“基础等待预测”。

3. “状态展示”准确度高于“等待分钟预测”  
   当前代码里的状态机是真实业务事实，因此：
   - 当前忙闲、当前多少人在待服务/服务中、当前是否暂停叫号，这类展示准确度较高
   - 等待分钟预测属于读时估算，准确度中等，适合做“决策辅助”，不适合承诺级展示

4. 下一步可以一次执行完成一期目标  
   但这里的“一次执行完成”，应理解为：
   - 一次开发完成“公共只读接口 + 用户门店页展示 + 基础预测 + 测试”
   - 不是一次开发就达到“所有门店、所有模式、所有历史数据都高精度预测”

5. 若按本文档补充后的口径执行，一期可以达到需求中的“基本准确预测与展示”  
   若目标是“接近实际叫号系统的分钟级精确预测”，则现有状态事实还不够，需要后续线上校准，不属于一期承诺范围。

## 2. 需求边界

### 2.1 本次明确不做的事情

以下内容不在本方案范围内：

- 不新建任何新的排队业务对象
- 不新增“用户公开排队号”
- 不新增“预约排队”
- 不新增 Redis 队列类型
- 不新增快照表、读模型表作为一期前提
- 不改造现有预约/核销/叫号主流程为另一套流程

### 2.2 本次允许做的事情

为了把现有状态展示给未预约用户，允许新增：

- 一个新的只读公共接口
- 门店公共页上的一个新的展示模块
- 基于现有表和现有状态的聚合计算逻辑

这里新增的是“读接口和展示”，不是“新排队能力”。

## 2.3 一期验收目标

为了避免下一步执行时目标发散，一期验收建议定义为：

1. 用户打开门店公共页，能看到门店当前服务状态
2. 能区分客服模式与叫号模式下的不同进度摘要
3. 能看到当前待服务人数、服务中人数、空闲/忙碌状态
4. 能看到一个“基本准确”的预计等待分钟数
5. 能看到建议是否现在到店、是否建议先预约
6. 在门店暂停叫号、打烊、无可服务人员时，能正确降级展示

不作为一期验收项：

- 精确到单个用户的真实开单先后顺序
- 精确到分钟的承诺级等待时间
- 覆盖所有历史脏数据下仍然完全准确

## 3. 现有代码事实

### 3.1 当前公共门店页入口

- `frontend/src/views/user/Shop.vue`

- 收款配置
- 在售卡片

当前并没有把门店实时服务状态展示给未预约用户。

### 3.2 当前项目已经有统一的服务事实载体

现有项目里，最关键的实时事实不是某个“公开排队表”，而是：

它已经统一承载：

- 现场单

- 叫号模式会话

关键字段包括：

- `session_mode`
- `source_type`
- `status`
- `room_id`
- `technician_id`
- `predicted_ready_at`
- `scheduled_start_at`
- `scheduled_finish_at`
- `duration_minutes`

### 3.3 当前模式识别已经存在

见：

- `backend/models/session_mode.go`
- `backend/models/status_compat.go`

当前代码已经明确区分：

- `cs`：客服模式
- `qs`：自动叫号单窗口
- `qm`：自动叫号多窗口
- `qms`：人工叫号单窗口
- `qmm`：人工叫号多窗口

也已经支持通过 `NormalizeSessionStatus(...)` 统一读取裸状态。

这意味着：本方案完全可以基于“现有模式 + 现有状态机”推算，而不需要创造新的状态体系。

### 3.4 当前代码复核后发现的关键实现约束

这次复核后，需要把以下约束明确写入方案，否则下一步实现很容易高估准确度。

1. 不能只看 `technician_attendances.status`

原因：

- 客服模式下，用户选客服后，考勤会立即从 `idle -> busy`
- 多窗口自动叫号模式下，`start_pending` 阶段可能已经绑定技师，但技师考勤仍然是 `idle`

这说明：

- `attendance.status = busy` 不能简单等价于“服务中”
- `attendance.status = idle` 也不能简单等价于“立刻可接新客”

因此实现时必须采用：

- `service_sessions` 决定当前服务占用与阶段
- `technician_attendances` 只作为“可服务资格 / 在岗状态 / 暂停状态”的辅助事实

2. 不能只看 Redis 队列长度

原因：

- Redis 里只有现有 `QueueTypeOnsite`
- 它只能表达叫号模式中的现场等待顺序
- 无法表达客服模式中的选房、选客服、待起单
- 也无法完整表达预约到店等待

因此实现时：

- 叫号模式可以用 `queue.Default` 做排序参考
- 但门店服务状态的主体事实仍然必须来自 `service_sessions`

3. 客服模式没有显式“公开排队顺序”

原因：

- 客服模式是“选房/选客服/待起单/服务中”的状态推进
- 当前代码没有一个明确的全店统一排队号

因此客服模式的等待预测本质上是：

- 对当前工作量的加权推算

而不是：

- 对真实排队顺序的精确还原

4. 当前状态读模型对历史脏数据敏感

例如：

- 活跃会话未收口
- 技师考勤没有及时回空闲
- 房间锁未释放

这些问题不会否定方案可行性，但会直接拉低某些门店的展示准确度。

## 4. 两种模式的现有服务推进链路

## 4.1 客服模式现有链路

从当前代码看，客服模式核心链路是：

1. 核销后创建 `service_session`
2. 若商户启用房间，则进入 `room_selecting`
3. 选房后进入 `staff_selecting`
4. 选客服后进入 `start_pending`
5. 起单扫码后进入 `serving`
6. 结单后进入 `finished`

对应代码主要在：

- `backend/handlers/service_session_factory.go`
- `backend/handlers/service_session_user.go`
- `backend/handlers/service_session.go`
- `backend/sessionflow/finish.go`

客服模式下，以下操作本身就是“门店服务进度”：

- 核销
- 选房
- 选客服
- 起单
- 结单
- 客服签到与忙闲变化

也就是说，客服模式不需要额外排队对象，本身就已经有服务进度可读。

## 4.2 叫号模式现有链路

从当前代码看，叫号模式核心链路是：

1. 核销后创建 `service_session`
2. 现场单进入现有 `queue.Default` 的 `QueueTypeOnsite`
3. 会话初始状态为 `staff_selecting`
4. 根据模式不同推进：
   - 单窗口人工叫号：`staff_selecting -> delay_pending -> serving -> finished`
   - 多窗口叫号：`staff_selecting -> start_pending -> serving -> finished`
5. 结号/结单后通过 `sessionflow.FinishServiceSession(...)` 收尾
6. 暂停叫号由：
   - 商户级 `merchant.queue_paused`
   - 技师级 `technicians.queue_paused`
   控制

对应代码主要在：

- `backend/handlers/queue_status.go`
- `backend/handlers/service_session.go`
- `backend/handlers/technician_attendance.go`
- `backend/queue/queue.go`
- `backend/queue/redis_store.go`

因此，叫号模式下也不需要新增队列，只要读取现有：

- 核销后的 `service_sessions`
- 现有 `queue.Default`
- 叫号暂停状态
- 技师签到/忙闲状态

就能推算门店当前的服务压力。

## 4.3 现有技师状态已经足够表达服务供给

见：

- `backend/models/technician_attendance.go`
- `backend/models/models.go`
- `backend/handlers/technician_attendance.go`

当前项目已有：

- `technician_attendances.status = idle / busy / paused / rest`
- `technicians.queue_paused`
- `merchant.queue_paused`

这三类状态已经足够推断：

- 当前可立即承接服务的人数
- 当前服务中的人数
- 当前暂停接待的人数
- 叫号模式下新客能否继续被推进

## 5. 当前问题不在于“没有队列”，而在于“没有对外展示口径”

当前门店公共页缺的不是底层事实，而是一个面向未预约用户的只读解释层。

当前缺口有两个：

1. 没有公共接口把现有状态聚合成“门店实时服务状态”
2. 没有把这些状态翻译成用户能看懂的文案和等待预测

因此，本次方案重点应从“新排队设计”改成“现有服务状态的读时推算与展示”。

## 5.1 准确度评估

本方案的准确度应拆开评估，而不是笼统地说“准确”或“不准确”。

### 5.1.1 高准确度部分

以下信息基本属于现有业务事实直出，准确度预期高：

- 当前是否营业 / 是否打烊
- 当前是否暂停叫号
- 当前有多少会话处于待服务
- 当前有多少会话处于服务中
- 当前多少工作人员处于暂停/下班
- 当前门店主要卡在哪个阶段

建议预期准确度：

- `85% ~ 95%`

前提：

- 没有严重历史脏数据残留

### 5.1.2 中等准确度部分

以下信息属于推算，不是直接事实：

- 未预约用户现在到店预计等待几分钟
- 建议几点后到店更合适
- 是否建议先预约

建议预期准确度：

- 叫号模式：`70% ~ 85%`
- 客服模式：`55% ~ 75%`

差异原因：

1. 叫号模式已有现成队列顺序，等待关系更明确
2. 客服模式没有显式公开队列，只能根据状态阶段和资源占用估算

### 5.1.3 准确度最低的场景

以下场景下，等待预测准确度会明显下降：

- 客服模式下大量用户同时处于 `room_selecting / staff_selecting`
- 商户人工操作习惯不稳定，起单/结单不及时
- 历史活跃会话未正确收口
- 技师签到状态与真实服务状态短时不一致
- 预约到店后插入较频繁

因此文案必须使用：

- `预计等待`
- `建议到店时间`

而不能使用：

- `准确等待`
- `保证 xx 分钟内开始服务`

## 6. 设计目标重构

### 6.1 对用户的目标

未预约用户打开门店页时，希望直接看到：

- 当前空闲还是忙碌
- 现在去大概要不要等
- 当前是卡在选客服、待起单、服务中，还是叫号暂停
- 建议什么时候去更容易快速开始服务

### 6.2 对实现的目标

实现上要做到：

- 完全复用现有状态机
- 同时兼容客服模式与叫号模式
- 结果可解释
- 精度不要求绝对准确，但不能明显失真
- 对现有业务链路零侵入或低侵入

## 7. 统一的实时服务状态读模型

建议不要再把这个能力继续命名为“live queue”。

更准确的语义应是：

- `门店实时服务状态`
- 或 `门店实时服务负载`

因此建议公共接口命名为：

- `GET /user/merchants/:id/live-service-status`

如果后续为了兼容旧文档必须保留 `live-queue` 叫法，也建议只作为兼容别名，内部语义仍然按“服务状态推算”处理。

## 7.1 下一步能否一次执行完成

复核结论是：

- 可以一次执行完成“一期落地”
- 但不能把“一期落地”等同于“一次把预测精度做到最佳”

### 7.1.1 可以一次完成的范围

下一步如果直接开工，可以在一次实现中完成：

1. 新增公共只读接口
2. 聚合现有状态并输出统一读模型
3. 用户门店页展示实时服务状态
4. 输出基础等待预测和建议文案
5. 补齐单元测试/联调场景

### 7.1.2 一次完成后可达到的效果

可以达到：

- 用户能看懂门店当前是否忙
- 用户能看懂当前进度主要卡在哪
- 用户能拿到一个基本靠谱的到店建议

不能承诺：

- 所有门店都分钟级精确
- 所有历史遗留数据都已自动修正
- 所有模式下都和人工现场感知完全一致

### 7.1.3 若想“一次实现后直接上线”，需满足的前提

建议在文档中把上线前提写清楚：

1. 至少补齐关键单测
2. 至少用 2 类真实门店做联调：
   - 客服模式门店
   - 叫号模式门店
3. 至少人工验证以下场景：
   - 打烊
   - 暂停叫号
   - 无空闲技师
   - 有预约到店插入
   - 服务中会话释放后自动回空闲

否则虽然功能能做完，但未必适合直接上线。

## 8. 状态口径与公开展示含义

建议统一基于 `NormalizeSessionStatus(...)` 处理基础状态。

| 基础状态 | 客服模式含义 | 叫号模式含义 | 计入到店 | 计入待服务 | 计入服务中 | 对等待预测影响 |
|---|---|---|---|---|---|---|
| `room_selecting` | 已核销待选房 | 历史兼容态 | 是 | 是 | 否 | 弱 |
| `room_locked` | 已选房待选客服 | 迁移兼容态 | 是 | 是 | 否 | 中 |
| `staff_selecting` | 已核销待选客服 | 待叫号/待分配 | 是 | 是 | 否 | 中到强 |
| `appointment_waiting` | 预约到店优先等待 | 历史兼容态 | 是 | 是 | 否 | 强 |
| `start_pending` | 已分配客服待起单 | 已分配客服待上号 | 是 | 是 | 否 | 强 |
| `delay_pending` | 待开始服务兼容态 | 已叫号待上号 | 是 | 是 | 否 | 强 |
| `serving` | 服务中 | 服务中 | 是 | 否 | 是 | 强占用 |
| `auto_finishing` | 待自动结单 | 待自动结号 | 是 | 否 | 是 | 强占用 |
| `timeout_waiting` | 不推荐公开展示 | 过号等待 | 否 | 否 | 否 | 默认不计入主预测 |
| `finished` | 已完成 | 已完成 | 否 | 否 | 否 | 不计入 |
| `canceled` | 已取消 | 已取消 | 否 | 否 | 否 | 不计入 |
| `timeout_failed` | 失败 | 过号失效 | 否 | 否 | 否 | 不计入 |

### 8.1 计数实现上的补充约束

为了保证实现不偏离真实业务，计数时需要额外遵守以下规则：

1. `present_count` 不应直接等于 Redis 队列长度  
   必须以活跃 `service_sessions` 为主。

2. `busy_staff_count` 不应直接等于 `technician_attendances.status = busy` 的人数  
   应优先按“存在活跃占用会话的技师人数”计算，再与考勤状态交叉修正。

3. `idle_staff_count` 不应直接等于 `technician_attendances.status = idle` 的人数  
   需要排除：
   - 已绑定 `start_pending / delay_pending / serving / auto_finishing` 会话的技师
   - 已暂停叫号的技师

4. `queue_waiting_count` 只在叫号模式下输出  
   且以 `staff_selecting` 且命中现有 `QueueTypeOnsite` 的会话为主，不单独从 Redis 裸票据推人数。

## 9. 推算原则

### 9.1 客服模式：基于服务推进状态推算

客服模式不使用任何额外排队对象，直接基于现有服务进度推算。

核心输入：

- `service_sessions`
- `technician_attendances`
- `rooms`
- `merchant_projects.duration`

推算逻辑：

1. `serving / auto_finishing` 表示当前产能已被占用
2. `start_pending` 表示已经接近开始服务，对新客等待影响最大
3. `staff_selecting / room_locked` 表示仍在完成服务前置步骤，对等待有中等影响
4. `room_selecting` 表示已到店但还未完成前置动作，对等待有弱影响
5. `appointment_waiting` 表示预约已到店，应优先消化

因此，客服模式预测不需要真实排队顺序，而是按“现有服务进度阶段”估算阻塞程度。

### 9.2 叫号模式：基于现有叫号推进状态推算

叫号模式只读取现有 `queue.Default`，不新增任何队列。

核心输入：

- `service_sessions`
- `queue.Default` 现有 `QueueTypeOnsite`
- `technician_attendances`
- `merchant.queue_paused`
- `technicians.queue_paused`

推算逻辑：

1. `staff_selecting` + 现有队列票据 = 当前仍在排队中的现场客
2. `delay_pending` = 已叫号待上号，已经非常接近占用服务能力
3. `start_pending` = 多窗口模式下已分配客服待上号
4. `serving / auto_finishing` = 当前实际服务中
5. `queue_paused` = 新客虽然能核销，但推进速度会显著下降，应显著上调等待建议

### 9.3 预约到店事实要参与预测，但不单独形成新队列

预约到店后，当前代码会创建：

- `usage`
- `service_session(source_type=appointment)`

并进入：

- `appointment_waiting`
- 或 `start_pending`

因此它们已经是现有服务状态的一部分。

本方案只把这些状态视为“应优先处理的现有工作量”，不新建任何“预约排队队列”。

## 9.4 对需求预期的匹配评估

结合当前需求描述，方案与需求的匹配度可总结为：

### 9.4.1 能满足的需求预期

1. 未预约用户直观看到门店当前实时服务状态
2. 用户能区分门店当前是“服务中多”还是“待服务多”
3. 用户能看到客服模式和叫号模式下不同的服务进度摘要
4. 用户能得到基本准确的等待预测
5. 用户能据此判断：
   - 现在要不要去
   - 稍后什么时候去更合适

### 9.4.2 不能完全满足的预期

如果需求预期被理解为以下内容，则现有状态事实不足以完全满足：

1. 精确推断每一个未预约用户实际何时被服务
2. 精确还原客服模式下全店统一排队顺序
3. 精确反映用户自己的真实等待名次

这些不是因为方案设计不完整，而是因为现有代码里本来就没有这些显式事实。

因此，本方案匹配的是：

- `门店实时服务状态展示 + 基本等待预测`

不是：

- `公开级精确排队系统`

## 10. 预计等待时间的推算方案

本能力只要求“基本准确”，不追求排班系统级别的精确预测，因此建议采用“服务槽位 + 现有工作量”推算法。

### 10.1 第一步：计算当前有效服务槽位

服务槽位来源于当前门店真实供给。

规则：

1. 只统计当日已签到、未签退的技师
2. `status = idle / busy` 视为可服务体系内的人
3. `status = paused / rest` 不计入当前可承接产能
4. 叫号模式下若 `technicians.queue_paused = true`，该技师不计入新客承接产能
5. 若商户开启房间：
   - 最终并发上限取 `min(有效技师数, 可用房间数)`
6. 单窗口人工/自动叫号：
   - 即便存在多个技师，也按当前实际模式把可承接窗口数收敛到 1

### 10.2 第二步：计算每个服务槽位的释放时间

对每个当前占用中的技师，计算 `available_at`：

优先级：

1. `predicted_ready_at`
2. `scheduled_finish_at`
3. `started_at + duration_minutes`
4. 兜底 `now + baseline_service_minutes`

这样可以避免仅凭人数估算导致偏差过大。

### 10.3 第三步：把当前未完成的工作量转成“阻塞项”

对于尚未进入 `serving` 但已经形成到店事实的会话，不直接当作“完整一单”，而是按当前阶段给予不同权重。

建议权重：

- `appointment_waiting / start_pending / delay_pending`：`1.0`
- `staff_selecting / room_locked`：`0.8`
- `room_selecting`：`0.5`

说明：

- 越接近真正开始服务，权重越高
- 越早期的前置步骤，对新客实际等待影响越弱
- 这比“所有等待中的人都算完整一单”更接近真实情况

### 10.4 第四步：模式化排序

#### 客服模式

按以下顺序视为优先被消化：

1. `appointment_waiting`
2. `start_pending`
3. `staff_selecting / room_locked`
4. `room_selecting`

同一阶段内按：

- `created_at asc`

兜底。

#### 叫号模式

按以下顺序：

1. `delay_pending / start_pending`
2. `staff_selecting`

其中 `staff_selecting` 若存在现有 `queue.Default` 号序，则按现有队列号排序；取不到号时按 `created_at asc` 兜底。

### 10.5 第五步：把“新来的未预约用户”插入末尾

不创建任何真实队列记录，只在内存计算中增加一个“虚拟新用户”。

然后根据：

- 当前服务槽位释放时间
- 当前待消化工作量
- 当前阶段权重

推导他可能轮到开始服务的时间，得到：

- `estimated_wait_minutes`

### 10.6 第六步：门店基准服务时长

为了做基本准确的预测，建议采用门店的“基准项目时长”作为虚拟新客的服务占用时长。

建议口径：

1. 优先取当前启用项目 `merchant_projects.duration` 的中位数
2. 若项目为空：
   - 叫号模式兜底 `15`
   - 客服模式兜底 `50`

这个兜底直接复用当前 `createServiceSessionForUsage(...)` 的默认值，和现有代码口径一致。

### 10.7 第七步：建议到店时间

设一个可接受等待阈值：

- 一期默认 `10` 分钟

规则：

- 若 `estimated_wait_minutes <= 10`，建议立即到店
- 若 `estimated_wait_minutes > 10`，建议时间为 `now + (estimated_wait_minutes - 10) 分钟`

这样给用户的是“什么时候来更容易在 10 分钟内开始服务”，比纯展示等待时间更有决策价值。

### 10.8 预测结果的展示策略

为了让“基本准确”更稳，前端展示建议增加保守处理：

1. 如果 `estimated_wait_minutes <= 5`
   - 显示 `大概率可较快开始服务`
   - 可不强调具体分钟数

2. 如果 `estimated_wait_minutes` 在 `6 ~ 20`
   - 可以展示具体分钟数

3. 如果 `estimated_wait_minutes > 20`
   - 同时展示：
     - 预计等待分钟数
     - 建议到店时间
     - 建议先预约

4. 如果系统发现数据不稳定或无法估准
   - 降级展示：
     - `当前较忙，建议稍后查看或先预约`
   - 不强行输出具体分钟数

## 11. 忙闲等级与文案

建议统一规则：

- `idle`：`0 ~ 5` 分钟
- `light`：`6 ~ 15` 分钟
- `busy`：`16 ~ 30` 分钟
- `crowded`：`> 30` 分钟

## 17. 最终建议

这份方案修订后的核心方向是：

- 不再把问题理解为“给未预约用户再造一个排队系统”
- 而是把现有客服模式、叫号模式里的真实服务进度，整理成一个统一的公开展示视图

一期最佳落地路径是：

1. 基于现有 `service_sessions` 读取当前服务进度
2. 基于现有 `technician_attendances` 和房间配置计算真实供给
3. 仅在叫号模式下读取现有 `queue.Default` 作为排序参考
4. 输出 `门店实时服务状态`
5. 在用户门店页展示“状态 + 进度 + 基本等待预测”

这样既满足你“不要新增排队功能及额外队列”的约束，又能利用当前项目已有代码快速落地，并保持方案可解释、可执行。
