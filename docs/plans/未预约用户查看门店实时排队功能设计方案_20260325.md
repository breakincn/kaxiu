# 未预约用户查看门店实时排队功能设计方案

日期：2026-03-25

## 1. 目标

目标不是给未预约用户展示一个“排队号”，而是让用户在打开门店页时，直接判断：

- 这家店现在忙不忙
- 现在去大概要不要等
- 大概等多久
- 什么时候去更容易更快开始服务
- 当前是否更适合先预约

结合当前代码，建议一期直接在用户端门店公共页新增“门店实时排队”模块，并提供一个独立公共读接口，基于现有 `service_sessions + technician_attendances + queue.Default + merchant_projects + appointments` 聚合，不新增表先落地。

## 2. 当前代码基线

### 2.1 用户入口现状

当前未预约用户进入门店页的公共入口是：

- `backend/routes/routes.go`
- `backend/handlers/shop.go`
- `frontend/src/views/user/Shop.vue`

现状上，`GET /user/s/:slug`、`GET /user/s/id/:id` 只返回：

- 商户基础信息
- 收款配置
- 在售卡片

`frontend/src/views/user/Shop.vue` 也只展示门店头图和在售卡片，没有任何实时排队、忙闲或预计等待信息。

### 2.2 当前排队接口无法满足需求

当前和排队相关、但不能直接用于未预约用户决策的接口有两类：

1. 商户端摘要接口 `GET /merchant/merchants/:id/queue`

当前 `backend/handlers/appointment.go` 中的 `GetQueueStatus` 只返回：

- `pending_appointments`
- `today_verify_count`

这不是“当前到店人数 / 当前等待人数 / 当前预计等待时间”，不能支持用户决策。

2. 商户端/内部排队接口

- `GET /merchant/queue/pending-list`
- `GET /merchant/internal/merchants/:id/queue/onsite`

它们要么需要商户权限，要么依赖 internal token，而且只反映“现场叫号队列号序”，没有把预约到店等待、技师可服务状态、预计释放时间合并成用户可读的门店负载结论。

### 2.3 现有代码里已经具备的事实来源

虽然没有现成的“用户实时排队”接口，但现有项目已经有足够的数据事实可复用：

1. 服务会话 `service_sessions`

见：

- `backend/models/service_session.go`
- `backend/handlers/service_session_factory.go`
- `backend/handlers/service_session.go`

这里已经统一承载了现场单与预约单的实时履约状态：

- `source_type = walk_in / appointment`
- `status`
- `technician_id`
- `room_id`
- `duration_minutes`
- `predicted_ready_at`
- `scheduled_finish_at`

2. 现场队列号快照 `queue.Default`

见：

- `backend/queue/queue.go`
- `backend/queue/redis_store.go`
- `backend/handlers/usage.go`
- `backend/handlers/queue_status.go`

现场核销单已经会进入 `QueueTypeOnsite`，并能实时读取：

- 当前仍在队列中的 ticket
- 号码顺序
- 是否已叫号

3. 技师/工作人员实时可服务状态

见：

- `backend/models/technician_attendance.go`
- `backend/handlers/technician_attendance.go`
- `backend/models/models.go` 中 `technicians.queue_paused`

当前系统已经有：

- `idle`
- `busy`
- `paused`
- `rest`

并且已经区分：

- 商户全局暂停叫号 `merchant.queue_paused`
- 技师个人暂停叫号 `technicians.queue_paused`

4. 预约到店等待事实

见：

- `backend/handlers/appointment.go` 的 `CheckInAppointment`
- `backend/handlers/appointment_policy.go` 的 `estimateAppointmentArrivalDelay`

预约到店后，会创建：

- `usage`
- `service_session(source_type=appointment)`

并在技师忙碌时进入 `appointment_waiting` 或写入预测等待，这对未预约用户的“现在去会不会被预约用户挤占”判断很关键。

5. 项目时长配置

见：

- `backend/models/merchant_project.go`
- `backend/handlers/project_timing.go`

当前已存在：

- `duration`
- `service_gap_minutes`

可作为预计等待时长的基础输入。

## 3. 一期设计原则

### 3.1 不做“预约排队号”展示

未预约用户需要的是门店负载，不是某个抽象排队号。

所以一期只展示：

- 当前到店总人数
- 当前待服务人数
- 当前服务中人数
- 现在到店预计等待
- 建议到店时间
- 是否建议先预约

不展示：

- 你的前面有几号
- 当前叫到几号
- 某个具体用户的排队明细

### 3.2 一期不新增表

一期直接使用现有事实聚合：

- `service_sessions`
- `technician_attendances`
- `technicians`
- `rooms`
- `merchant_projects`
- `queue.Default`

先做“实时读模型”，避免为了一个只读页面先引入新表和异步链路。

### 3.3 一期优先新增独立公共接口，不污染现有预约接口

建议不要继续扩展：

- `GET /merchant/merchants/:id/queue`
- `GET /user/s/:slug`

而是新增一个独立的用户公共接口，专门服务门店页实时排队模块，避免和预约摘要、售卡详情耦合。

## 4. 用户侧产品方案

### 4.1 展示位置

在 `frontend/src/views/user/Shop.vue` 的门店头部下面、在售卡片上面，新增卡片：

- 模块名：`门店实时排队`

### 4.2 展示内容

建议展示：

- 忙闲等级：`空闲 / 稍忙 / 忙碌 / 拥挤 / 暂不可服务`
- 当前到店人数
- 当前待服务人数
- 当前服务中人数
- 预计到店等待分钟数
- 建议到店时间
- 建议文案

推荐 UI 文案示例：

- `当前稍忙`
- `到店中 6 人，待服务 2 人，服务中 4 人`
- `现在到店预计等待 12 分钟`
- `建议 14:30 后到店，等待更短`
- `当前较忙，建议先预约`

### 4.3 展示规则

1. 如果门店当前打烊或不在营业时段内：

- 显示 `暂停接待`
- 不展示预计等待分钟数
- 展示 `当前不在营业时段，建议营业后再来`

2. 如果没有可服务技师：

- 显示 `暂不可服务`
- 展示 `当前暂无可服务人员，建议先预约或稍后查看`

3. 如果当前几乎无等待：

- 显示 `空闲`
- 展示 `现在到店更容易立即服务`

## 5. 指标定义

建议一期读模型统一返回以下字段。

### 5.1 核心字段

- `enabled`：当前门店是否启用此能力
- `business_state`：`open / closed / off_hours`
- `load_level`：`idle / light / busy / crowded / unavailable`
- `present_count`：当前到店总人数
- `waiting_count`：当前待服务总人数
- `walk_in_waiting_count`：现场待服务人数
- `appointment_waiting_count`：预约到店待服务人数
- `serving_count`：当前服务中人数
- `idle_technician_count`：当前空闲可接待技师数
- `active_technician_count`：当前在岗可服务技师数
- `estimated_wait_minutes`：未预约用户若现在到店的预计等待分钟数
- `recommended_arrival_at`：建议到店时间
- `recommend_appointment`：是否建议先预约
- `advice_text`：最终展示文案
- `snapshot_at`：本次快照时间
- `refresh_after_seconds`：前端建议刷新秒数

### 5.2 指标口径

`present_count`

- 口径：当前已经形成到店事实且尚未结束的有效服务对象数
- 计算：`waiting_count + serving_count`

`waiting_count`

- 状态口径使用现有活跃等待态：
  - `room_selecting`
  - `room_locked`
  - `staff_selecting`
  - `appointment_waiting`
  - `start_pending`
  - `delay_pending`

`walk_in_waiting_count`

- `source_type = walk_in`
- 状态属于等待态

`appointment_waiting_count`

- `source_type = appointment`
- 状态属于等待态

`serving_count`

- 状态属于：
  - `serving`
  - `auto_finishing`

### 5.3 一期不计入的人群

以下对象不进入用户侧公开人数口径：

- `finished`
- `canceled`
- `timeout_waiting`
- `timeout_failed`
- 明显脏数据/陈旧活跃会话

建议增加陈旧数据过滤规则：

- 若 `COALESCE(predicted_ready_at, scheduled_finish_at, updated_at, created_at) < now - 8h`
- 且状态仍是活跃态

则从公开快照中剔除，并打 warn 日志，避免历史脏单污染门店实时负载。

## 6. 接口方案

### 6.1 新增公共接口

建议新增：

- `GET /user/merchants/:id/live-queue`

原因：

- `Shop.vue` 现有流程本来就会先取门店信息，再拿到 `merchant.id`
- 用 `merchant.id` 拉实时排队，最稳定
- 不依赖 slug，避免后续 slug 变更或不同入口重复适配

### 6.2 返回示例

```json
{
  "data": {
    "enabled": true,
    "business_state": "open",
    "load_level": "busy",
    "present_count": 7,
    "waiting_count": 3,
    "walk_in_waiting_count": 2,
    "appointment_waiting_count": 1,
    "serving_count": 4,
    "idle_technician_count": 1,
    "active_technician_count": 4,
    "estimated_wait_minutes": 18,
    "recommended_arrival_at": "2026-03-25T14:30:00+08:00",
    "recommend_appointment": true,
    "advice_text": "当前较忙，建议先预约或 14:30 后到店",
    "snapshot_at": "2026-03-25T13:52:10+08:00",
    "refresh_after_seconds": 20
  }
}
```

### 6.3 错误/降级返回

1. 门店不存在：`404`

2. 门店未开启相关服务能力：

```json
{
  "data": {
    "enabled": false,
    "business_state": "open",
    "load_level": "unavailable",
    "advice_text": "当前门店未开启实时排队展示"
  }
}
```

3. 无法估算但仍可返回人数时：

- `estimated_wait_minutes = null`
- `recommended_arrival_at = null`
- `advice_text = "当前人数已更新，等待时间暂无法精确估算"`

## 7. 等待时间计算方案

一期不建议继续使用“人数 * 固定分钟数”的粗算方式，而是做一个轻量级排队仿真。

### 7.1 技师服务槽构建

从 `technician_attendances + technicians` 构建当前可参与服务的技师槽位：

1. 只取：

- 当天已签到
- 未签退
- `technicians.is_active = true`
- 非 `queue_paused`

2. 如果技师状态为：

- `idle`：可立即承接
- `busy`：需要看其当前会话何时释放
- `paused / rest`：不参与一期用户等待估算

3. 并发上限修正：

- 若门店是单窗口叫号模式：`support_queue = true && support_multi_customer_service = false`
  - 一期并发槽位数按 `1` 处理
- 若门店支持多客服/多窗口：
  - 按有效技师数处理
- 若门店启用房间 `support_room = true`
  - 最终并发上限取 `min(有效技师数, 启用房间数)`

### 7.2 技师释放时间

对每个可服务技师，先算 `available_at`：

1. 如果该技师当前有 `serving / auto_finishing` 会话：

优先取：

- `predicted_ready_at`
- 否则 `scheduled_finish_at`
- 否则 `started_at + duration_minutes`
- 否则 `now + baseline_service_minutes`

2. 如果当前没有服务中会话：

- `available_at = now`

### 7.3 等待对象排序

然后把“在新来的未预约用户之前，必须先被消化的需求”排成队列。

优先级建议如下：

1. 已到店预约等待单

- `source_type = appointment`
- 状态属于等待态

这些单已经有到店承诺，应优先于新来的未预约用户。

2. 已绑定技师、待开始的现场/预约会话

- 例如 `start_pending / delay_pending / appointment_waiting`
- 已有 `technician_id`

这些会话虽然还没正式开始，但已经占住了即将释放的服务能力。

3. 未绑定技师的现场等待单

- `source_type = walk_in`
- 按 Redis 队列号 `queue.Default.GetNo(...)` 排序
- 若取不到号，则按 `created_at asc` 兜底

### 7.4 新用户虚拟插入

在上述等待序列最后，追加一个“虚拟新未预约用户”，用它来反推：

- 如果用户现在出发
- 轮到他的理论开始服务时间是什么时候

### 7.5 项目时长口径

已有会话优先使用会话自身：

- `service_sessions.duration_minutes`

虚拟新用户使用门店基准时长：

1. 优先取启用项目的中位数 `merchant_projects.duration`
2. 如果没有项目配置：
   - 叫号模式 fallback 为 `15`
   - 非叫号/客服模式 fallback 为 `50`

这个 fallback 直接复用当前 `createServiceSessionForUsage(...)` 的默认值，保证和现有系统时长口径一致。

### 7.6 建议到店时间

定义一个“可接受等待阈值”：

- 一期默认 `10` 分钟

如果 `estimated_wait_minutes <= 10`：

- `recommended_arrival_at = now`

如果 `estimated_wait_minutes > 10`：

- `recommended_arrival_at = now + (estimated_wait_minutes - 10) 分钟`

这样给用户的是“什么时候去，等待大概率会回落到 10 分钟以内”的建议，而不是单纯把预计等待时间原样再说一遍。

### 7.7 忙闲等级

建议统一阈值：

- `idle`：`0 ~ 5` 分钟
- `light`：`6 ~ 15` 分钟
- `busy`：`16 ~ 30` 分钟
- `crowded`：`> 30` 分钟
- `unavailable`：无可服务技师 / 无可用房间 / 打烊

## 8. 后端落地方案

### 8.1 路由

修改：

- `backend/routes/routes.go`

新增公共路由：

```go
user.GET("/merchants/:id/live-queue", handlers.GetMerchantLiveQueue)
```

### 8.2 处理器建议

建议新增文件：

- `backend/handlers/live_queue.go`

建议拆分函数：

- `GetMerchantLiveQueue(c *gin.Context)`
- `buildMerchantLiveQueueSnapshot(tx *gorm.DB, merchant models.Merchant, now time.Time) (...)`
- `loadLiveQueueActiveSessions(...)`
- `loadLiveQueueTechnicianSlots(...)`
- `estimateWalkInWaitMinutes(...)`
- `buildLiveQueueAdvice(...)`

### 8.3 取数顺序

建议按下面顺序聚合：

1. 读取 `merchant`
2. 判断营业状态和营业时段
3. 读取当前活跃 `service_sessions`
4. 读取在岗技师及签到状态
5. 如果启用房间，读取活跃房间数
6. 若是现场单，尝试补齐 Redis 队列号
7. 计算人数、等待、建议文案

### 8.4 一期不新增数据库表

一期不新增：

- `merchant_live_queue_snapshots`
- `queue_metrics`

理由：

- 当前需求是只读展示
- 当前项目已有足够事实源
- 先验证算法和展示是否稳定，再决定是否沉淀异步快照表

### 8.5 一期缓存策略

建议一期先不落 Redis 缓存，直接实时聚合。

原因：

- 用户门店页流量有限
- 计算量主要是单店聚合，不是全局报表
- 先把口径跑顺

如果后续出现 QPS 或慢查询问题，再加：

- `merchant_live_queue:{merchant_id}`
- TTL 10~15 秒

## 10. 分阶段实施建议

### 阶段一：可上线最小版本

目标：先让未预约用户能看到可靠的“门店忙闲 + 预计等待”。

范围：

- 新增公共接口 `GET /user/merchants/:id/live-queue`
- `Shop.vue` 新增实时排队模块
- 一期算法按“技师槽位 + 活跃会话 + 现场队列顺序”计算
- 不新增表，不做埋点后台，不做商户端改版

### 阶段二：精度增强

目标：让估算更稳。

增强项：

- 房间瓶颈纳入更精细计算
- 按项目类型提供更准确时长
- 支持通过 `project_id` 估算特定项目等待
- 增加 10~15 秒 Redis 缓存

### 阶段三：商户端联动

目标：让商户和用户看到同一套负载事实。

增强项：

- 商户首页增加“实时门店负载”卡片
- 同步显示：
  - 预约到店等待人数
  - 现场等待人数
  - 技师释放时间
  - 是否建议开启先预约引导

## 11. 风险点与处理

### 11.1 历史脏数据导致人数虚高

风险：

- 历史遗留的活跃会话未收口，可能把门店人数抬高

处理：

- 一期加入陈旧会话过滤
- 输出 warn 日志
- 结合现有调度器健康检查继续治理

### 11.2 单窗口与多窗口口径混淆

风险：

- `support_multi_customer_service = false` 时，如果直接按技师人数算并发，会把等待低估

处理：

- 一期明确单窗口门店并发槽位固定按 `1`

### 11.3 房间约束未计入会低估等待

风险：

- 有房间约束的门店，如果只看技师，不看房间，会偏乐观

处理：

- 一期就把并发上限取 `min(技师数, 房间数)`
- 二期再做更精细的房间释放时间预测

### 11.4 没有项目信息时的等待估算偏差

风险：

- 未预约用户未指定项目，等待时长只能按门店基准时长估算

处理：

- 一期使用中位数时长 + 现有默认值兜底
- 文案上使用“预计等待”而非“准确等待”

## 12. 测试建议

### 12.1 后端单测

建议覆盖：

- 门店打烊返回 `closed`
- 无在岗技师返回 `unavailable`
- 单窗口门店并发按 `1`
- 多窗口门店按多个技师并发
- 预约到店等待优先于新现场客
- Redis 队列号缺失时按 `created_at` 兜底
- 陈旧活跃会话被过滤

### 12.2 联调场景

建议至少走完以下门店真实场景：

1. 没有人等待，1 个空闲技师
2. 2 个现场客待服务，1 个技师服务中
3. 1 个预约用户已到店等待，现场客再进入
4. 单窗口门店有多个技师但只允许单线推进
5. 房间数少于技师数

## 13. 建议的实施顺序

建议下一步按以下顺序直接开工：

1. 新增 `backend/handlers/live_queue.go`
2. 在 `backend/routes/routes.go` 挂出公共接口
3. 写后端单测，先把人数口径和等待算法跑通
4. 在 `frontend/src/api/index.js` 增加 `shopApi.getLiveQueue`
5. 在 `frontend/src/views/user/Shop.vue` 接入实时排队卡片和轮询
6. 联调真实门店数据，校准阈值与文案

## 14. 最终结论

基于当前项目代码，一期最合适的落地路径是：

- 不改预约履约主链
- 不复用当前商户端 `GetQueueStatus`
- 新增一个用户公共“门店实时排队”读接口
- 以 `service_sessions` 为核心事实，以 `technician_attendances` 为产能事实，以 `queue.Default` 为现场顺序补充
- 在 `Shop.vue` 增加轮询卡片展示

这样改动面最小，但能直接满足“未预约用户判断现在要不要去店里、什么时候去更快”的核心目标，也方便下一步按这个文档拆解成后端、前端、测试三类任务执行。
