## 第二轮：深度分析 — 运行时故障清单

> **核心前提**：核销入口（card.go）已正确写入带前缀状态（如 `cs_staff_selecting`、`qs_delay_pending`）。因此后续所有 `WHERE status = '裸状态'` 的精确匹配都**无法命中**带前缀记录，UPDATE 返回 0 rows affected，会话卡死。

### F1 🔴 cs_ delay_pending → serving 推进卡死

**文件**：`scheduler/service_session_scheduler.go` L778-791

```go
"status":     "serving",                    // ❌ 应为 ApplyStatusPrefix(s.Status, "serving")
Where("id = ? AND status = ?", s.ID, "delay_pending")  // ❌ 无法匹配 cs_delay_pending
```

**触发路径**：cs_ 客服模式 → 核销 → 选房 → 选技师 → 起单 → `cs_delay_pending` → scheduler 到达 scheduled_start_at

**运行时表现**：
- WHERE 匹配不到 → UPDATE 0 rows → 会话永远卡在 `cs_delay_pending`
- 服务永远不会自动启动
- 技师一直显示 busy，无法接新单

---

### F2 🔴 cs_ serving → auto_finishing 推进卡死

**文件**：`scheduler/service_session_scheduler.go` L817-825

```go
"status":      "auto_finishing",            // ❌ 应为 ApplyStatusPrefix
Where("id = ? AND status = ?", s.ID, "serving")  // ❌ 无法匹配 cs_serving
```

**触发路径**：假设 F1 被绕过 → `cs_serving` → 服务时间到达

**运行时表现**：
- WHERE 匹配不到 → 会话永远卡在 `cs_serving`
- 无法自动结单，技师/房间永远不释放

## 第二轮补充：过号插队规则审计

### 规则对比

| 项目 | 设计文档 | 代码实现 | 一致性 |
|------|----------|----------|--------|
| 状态名称 | qs_missed_waiting / qs_missed_failed | qs_timeout_waiting / qs_timeout_failed | ⚠️ 名称不同但语义等价 |
| 超时进入等待 | qs_called 超时 → qs_missed_waiting | delay_pending 超时 → timeout_waiting | ⚠️ 触发状态不同（见下文） |
| 插队窗口计算 | "三个号之前" | `myNo + 2 + 2*(cnt-1)` | ⚠️ 可能 off-by-one |
| 连续过号顺延 | 10,11过号→到15失败 | cnt=2: endNo=14, expired=currentNo>=15 | ✅ 一致 |
| 插队操作 | UnmarkDone + Uncall + CallNextUncalled | ✅ 完整实现 | ✅ |
| 窗口过期 | → qs_missed_failed + 退卡 | → qs_timeout_failed + 退卡 | ✅ 逻辑一致 |
| 共享函数 | QsTimeoutWindowEndNo / QsTimeoutWaitingExpired | ✅ 已实现 | ✅ |

### 问题 E1：过号插队窗口 off-by-one（🟡 中等）

**设计文档**：
- "在实际后续服务推进到的**三个号**之前允许插队"
- 测试用例：`10过号后可在12、13前插队；到14失败`

**代码实现**：
- `QsTimeoutWindowEndNo(10, 1)` = 10 + 2 = **12**
- `QsTimeoutWaitingExpired` = `currentNo >= 13` → 到13失败

**分析**：
- 设计文档的"三个号"（11,12,13）不含自己，窗口应到 currentNo=13（到14失败）
- 代码的窗口只到 currentNo=12（到13失败），少了1个号
- 但代码注释说"3个号（myNo=10 则允许到 currentNo<=12）"，注释与代码一致

**验证连续过号**：
- 设计文档：cnt=2 时到15失败
- 代码：`endNo = 10 + 2 + 2 = 14`，`expired = currentNo >= 15` ✅ 一致

**结论**：单次过号时窗口比设计文档少1个号。公式应为 `myNo + 3 + 2*(cnt-1)` 才能与设计文档完全一致。但连续过号用例是一致的，说明可能是设计文档的单次用例描述有歧义。**建议与产品确认**。

### 问题 E2：状态名称与设计文档不一致（🟢 低）

设计文档使用 `qs_missed_waiting` / `qs_missed_failed`，代码使用 `qs_timeout_waiting` / `qs_timeout_failed`。语义等价，但名称不一致可能导致沟通混乱。

### 问题 E3：设计文档中 qs_waiting / qs_called 状态未实现（🟢 低/设计差异）

设计文档定义了 `qs_waiting`（排队中）和 `qs_called`（已叫号等待上号）两个状态，但代码中：
- 排队中 = `qs_staff_selecting`（复用了客服模式的状态名）
- 已叫号等待上号 = `qs_delay_pending`（复用了客服模式的状态名）

这不影响功能，但与设计文档的状态集合定义不一致。

## 第二轮补充：TechnicianAttendance 状态分析

`TechnicianAttendance` 的 `status` 字段（idle/busy/paused/rest）**不使用**模式前缀，属于独立的业务实体状态。所有 `WHERE status = 'busy'` / `Updates("status": "idle")` 等操作是**正确的**，不需要前缀扩展。

同理，`Appointment.Status`（pending/confirmed/completed/canceled）和 `Usage.Status`（in_progress/success/failed）也不使用模式前缀。
