# 预约碎片保护与项目间歇时间落地方案

## 1. 本次落地目标

基于当前项目现状与最新业务约束，本次预约能力下一步直接执行的落地目标统一为：

1. 在项目设置中新增“服务间歇时间（分钟）”，默认值为 `3`，每个项目可自定义。
2. 不复用现有 `start_delay_seconds` 字段，该字段继续保留“开始服务前延迟秒数”的原语义。
3. 预约排期、预约保护、预约碎片判断，统一按：
   - `项目服务时长`
   - `项目服务间歇时间`
   - `商户预约预测缓冲`
   来计算占用时长。
4. 采用策略 B：
   - 碎片保护不是按“最短项目时长”判断
   - 而是按“核心预约项目集合”判断
5. 让 `available-slots`、创建预约、确认预约、预约改签四处逻辑使用同一套规则，避免展示、提交、确认、改签四处口径不一致。

## 3. 新业务口径

本次统一如下业务定义。

### 3.1 服务时长

- 字段：`duration`
- 含义：用户实际接受服务的时长，单位分钟

### 3.2 服务间歇时间

- 新字段：`service_gap_minutes`
- 默认值：`3`
- 含义：本次服务结束后，为准备、收尾、清理、客服短暂休息等保留的分钟数

### 3.3 开始服务延迟时间

- 现有字段：`start_delay_seconds`
- 含义：从核销或进入待开始，到系统正式记为“开始服务”的前置延迟秒数
- 本次不改变该字段语义

### 3.4 预约占用时长

预约排期、预约保护、碎片保护统一使用：

- `occupied_minutes = duration + service_gap_minutes + merchant_appointment_prediction_buffer_minutes`

注意：

- `service_gap_minutes` 是项目级固定间歇
- `merchant_appointment_prediction_buffer_minutes` 是商户级风险预测缓冲
- 两者都应计入预约产能占用

## 4. 本次采用的碎片保护策略

本次明确采用策略 B：核心预约项目集合匹配法。

### 4.1 核心预约项目集合定义

第一版直接落地时，核心预约项目集合定义为：

- 当前商户下
- `is_active = true`
- 可参与预约的项目

每个项目进入集合时使用的不是裸 `duration`，而是：

- `duration + service_gap_minutes`

也就是“项目实际预约占用长度”。

### 4.2 为什么不用“最短项目时长法”

因为本次已经明确：

- 极短项目只是测试数据，不代表真实预约项目结构

所以第一版不应该再把碎片规则绑到“某个极小值项目”上，而应该按核心预约项目集合判断，这正是策略 B 的适用场景。

## 5. 候选时段生成的新规则

### 5.1 改为统一粒度生成候选时段

不再按当前项目 `duration` 递增生成候选时段。

改为新增商户级固定粒度：

- `appointment_slot_granularity_minutes`

推荐默认值：

- `15`

原因：

- 如果继续按 `duration + gap` 递增，45 分钟项目加 3 分钟会变成 48 分钟，前端会出现 `10:00 / 10:48 / 11:36` 这种不友好的时间点。
- 统一 15 分钟粒度后，时段展示更符合用户认知，也更利于后续做碎片保护。

### 5.2 候选时段判断顺序

对每个候选开始时间，依次做：

1. 营业时间可容纳校验
2. 预约冲突校验
3. 预约保护校验
4. 碎片保护校验

只有全部通过，才加入 `time_slots` 返回。

## 6. 碎片保护规则

### 6.1 判定目标

某个候选预约如果落下去，会把当前可用时间段切成多个剩余区间。

若其中任一剩余区间：

- `> 0`
- 且不能容纳核心预约项目集合中的任一项目占用长度

则该候选时段视为“制造不可复用碎片”，不展示。

### 6.2 示例

假设某客服空闲区间是：

- `10:00 - 12:00`

核心预约项目占用长度集合是：

- 48 分钟
- 63 分钟
- 93 分钟

其中 48 分钟来自：

- `45 分钟服务时长 + 3 分钟服务间歇`

如果一个候选时段落下后，剩余区间变成：

- 前段 12 分钟
- 后段 24 分钟

因为这两段都无法容纳 48 / 63 / 93 中的任何一个，所以该候选时段应隐藏。

## 9. 口径统一原则

以下四个地方必须共享同一套项目占用口径：

1. 用户查询可预约时段
2. 用户提交创建预约
3. 商户确认预约
4. 用户或商户发起改签与最终确认改签

否则会出现：

- 列表看起来能约
- 提交时报冲突
- 或提交成功但确认时才发现排不下
- 或普通预约能选到的时段，改签却选不到
- 或改签提议能创建，但接受改签时才发现目标时间实际不成立

## 12. 最终建议

这次不要做成“只多一个项目字段”的小改。

正确做法是一次性把这四件事并起来：

1. 项目级 `service_gap_minutes`
2. 统一候选时段粒度
3. 策略 B 碎片保护
4. `available-slots / create / confirm` 三处统一口径
4. `available-slots / create / confirm / reschedule` 四处统一口径

这样改完后，系统才会真正从“按项目时长机械排 slot”，升级成“按经营可用性输出预约时段”。

## 13. 改签接入要求

改签不能单独维护一套较旧或较宽松的排期规则，必须与普通预约完全共用同一套可预约判断。

### 13.1 改签要共用的规则

改签查询时段、创建改签提议、接受改签时，都必须共用：

- 项目预约占用时长计算
- 统一粒度候选时段生成
- 预约冲突校验
- 预约保护校验
- 策略 B 碎片保护校验

### 13.2 改签落地位置

至少需要覆盖：

- 改签资格后的时段查询接口
- 改签提议创建时的目标时间校验
- 改签提议接受时的事务级二次校验

### 13.3 最终目标

最终要保证：

- 普通预约能选到的时段，改签在相同条件下也能选到
- 普通预约不能选到的时段，改签不能绕过
- 改签提议创建后到最终确认前，如资源状态变化，最终确认时仍按同一规则重新判定
