# 双边确认改签提议机制计划与实施对照清单

## 目标
把原来的“谁点改签谁就直接改掉预约”改成“双边确认”的提议机制：
- 用户发起改签后，必须等商户确认
- 商户发起改签后，必须等用户确认
- 只有确认后，才真正执行“关闭原预约 + 创建新预约”

## 方案设计

### 核心原则
- 谁发起改签，就由对方确认。
- 改签提议和预约主记录分离，避免还没确认就直接覆盖原预约。
- 拒绝提议时，原预约保持不变。
- 接受提议时，才执行现有正式改签事务。

### 数据结构
- 新增表：`appointment_reschedule_requests`
- 关键字段：
  - `appointment_id`
  - `current_project_id`
  - `current_technician_id`
  - `current_appointment_time`
  - `new_project_id`
  - `new_technician_id`
  - `new_appointment_time`
  - `status`
  - `reason`
  - `proposed_by_type`
  - `proposed_by_id`
  - `confirmed_by_type`
  - `confirmed_by_id`
  - `confirmed_at`
  - `result_appointment_id`

### 状态定义
- `pending_user`
  - 商户已发起改签，等待用户确认
- `pending_merchant`
  - 用户已发起改签，等待商户确认
- `accepted`
  - 改签提议已确认并执行完成
- `rejected`
  - 改签提议被拒绝
- `canceled`
  - 预留给后续“发起方撤回提议”能力

### 执行流程
1. 发起方提交改签提议。
2. 系统校验当前预约状态，禁止对已结束预约继续改签。
3. 若当前已有待确认改签提议，拒绝再创建新的提议。
4. 对方在自己的端上看到“待我确认”的提议。
5. 对方接受后：
   - 校验旧预约仍可改签
   - 若旧预约已到店但未开始服务，先回滚占用
   - 创建新预约
   - 关闭旧预约
   - 记录新旧预约关联
   - 将提议标记为 `accepted`
6. 对方拒绝后：
   - 提议标记为 `rejected`
   - 原预约保持不变

## 已完成

### 后端
- 新增 `appointment_reschedule_requests` 模型和迁移。
- 商户端支持发起改签提议。
- 用户端支持发起改签提议。
- 商户端支持确认/拒绝用户改签提议。
- 用户端支持确认/拒绝商户改签提议。
- 接受提议后复用正式改签事务，执行：
  - 原预约关闭
  - 新预约生成
  - 新旧预约关联
  - 已到店未开始服务时撤销占用
- 预约查询接口已返回改签提议，供两端渲染待确认状态。

### 前端
- 商户端：
  - “改签”改为“发起改签”
  - 用户发起改签后，显示 `确认改签` / `拒绝`
  - 商户自己发起后，显示“已向用户发起改签提议”
- 用户端：
  - 新增 `申请改签`
  - 商户发起改签后，卡片详情显示确认提示
  - 支持 `同意改签` / `拒绝改签`
  - 用户自己发起后，显示“待商户确认”

### 测试与验证
- 已新增后端测试：
  - 商户发起 -> 用户确认
  - 用户发起 -> 商户确认
  - 补偿补次数
- 已通过验证：
  - `go test ./handlers`
  - `go test ./...`
  - `npm run build:merchant`
  - `npm run build:user`

## 当前限制
- 同一预约当前只允许存在一条待确认改签提议。
- 还没有“发起方撤回改签提议”的接口。
- 提议详情当前以时间、原因和客服 ID 级别展示为主，尚未补更完整的项目/客服名称富展示。
