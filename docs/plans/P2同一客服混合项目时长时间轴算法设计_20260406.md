# P2 同一客服混合项目时长时间轴算法设计

日期：2026-04-06  
执行者：Codex

> 仅在业务确认保留 P2 模式时实施。默认模式仍为 P1 的“客服按时长组拆分”，P2 不是默认路径。

## 1. 方案目标

P2 解决的问题不是“商户整体存在多个项目时长”，而是更具体的高复杂度场景：

- 同一商户开启客服模式
- 同一客服允许绑定多个不同时长项目
- 仍希望系统自动生成可预约时段、改签候选时段和修复推荐时段
- 且不希望短项目持续吞噬长项目窗口，导致后续长项目几乎无位可约

本方案的目标是：

1. 保持预约时间展示仍然规整，继续使用商户级展示粒度。
2. 在同一客服时间轴上支持多个真实占用时长。
3. 把“可约判断”升级为“硬约束过滤 + 未来填充能力评分 + 稀缺窗口保护 + 排序”。
4. 统一普通预约、改签、保护性修复推荐三条链路的时间候选生成逻辑。

本方案不解决：

1. 商户排班 UI 改版。
2. 项目结算规则变化。
3. 客服结算口径变化。
4. 商户跨天产能规划。

## 2. 产品前提与模式开关

### 2.1 模式定义

为避免把 P2 混进默认模式，新增商户预约模式枚举：

- `technician_grouped`
- `technician_mixed_timeline`

默认值：

- `technician_grouped`

模式语义：

1. `technician_grouped`
   - 默认模式
   - 同一客服只允许开放同一时长组项目
   - 继续走 P1 方案
2. `technician_mixed_timeline`
   - 高复杂度模式
   - 允许同一客服绑定多个不同时长项目
   - 启用本文档定义的 P2 时间轴算法

### 2.2 启用条件

只有同时满足以下条件时，系统才允许进入 P2：

1. 商户开启客服模式。
2. 商户为客服配置了“可预约项目集合”。
3. 商户预约模式显式设置为 `technician_mixed_timeline`。

若不满足，则必须回落到：

- `technician_grouped`

### 2.3 P2 不改变的业务边界

P2 只替换候选时段生成与排序算法，不改变以下规则：

1. 营业时间限制。
2. 已发布预约排班限制。
3. 请假、停用状态限制。
4. 预约前保留缓冲、预约后宽限、预测缓冲等保护规则。
5. 保护性改签仅允许在既定业务范围内触发。
6. 改签资格、改签日期范围、改签责任归属规则。

### 2.4 变更后重算与重排边界

在允许用户取消或改签的前提下，P2 必须明确区分两件事：

1. 剩余可预约时段的动态重算。
2. 既有预约的自动重排。

结论固定如下：

1. 必须动态重算剩余可预约时段。
2. 默认不自动重排既有预约。
3. 仅在商户显式发起异常修复或保护性改签时，才允许对单个既有预约给出替代方案。
4. 不允许因为某一单被取消或改签，就连锁自动移动其他正常预约。

原因：

1. 既有预约本质上是已经承诺给用户的时间与客服资源。
2. 一旦自动重排，会触发连锁通知、用户确认、补偿、结算快照迁移等问题。
3. 当前系统已有取消、改签、保护性修复三条独立业务链路，不适合被一个“全局最优重排器”隐式改写。

因此 P2 的优化目标不是：

- 全局重排当天所有预约

而是：

- 在当前已承诺预约固定不动的前提下，对“剩余可售时段”做到动态更新和局部近优
- 在必须修复异常时，只对受影响预约给出候选改签方案，而不是自动改写全局

## 3. 时间轴模型

### 3.1 基本刻度

时间轴使用两套不同含义的时间单位：

1. 展示网格单位
   - `g = appointment_slot_granularity_minutes`
   - 默认 `5`
   - 仅用于候选开始时间枚举和用户前台展示
2. 真实占用单位
   - `occupied_minutes = duration + service_gap_minutes`
   - 不向上取整
   - 直接用于冲突判断、空闲段切分和残段评估

因此 P2 使用的是：

- 网格起点 + 真实占用分钟

而不是：

- 网格起点 + 网格化占用分钟

### 3.2 日时间轴对象

每个客服在每个自然日都生成一个 `TechnicianDayTimeline`。

建议对象结构：

```go
type TechnicianDayTimeline struct {
    MerchantID                    uint
    TechnicianID                  uint
    Date                          string
    GranularityMinutes            int
    SupplyIntervals               []TimeInterval
    OccupiedIntervals             []TimeInterval
    FreeIntervals                 []TimeInterval
    AllowedProjectOccupiedMinutes []int
}
```

其中：

- `SupplyIntervals`
  - 营业时间 ∩ 该客服已发布可预约排班
- `OccupiedIntervals`
  - 已存在预约占用
  - 已开始服务会话占用
  - 保护性修复锁位占用
- `FreeIntervals`
  - `SupplyIntervals - OccupiedIntervals - 不可用区间`
- `AllowedProjectOccupiedMinutes`
  - 该客服允许承接项目集合对应的全部 `occupied_minutes` 去重后的结果

### 3.3 区间来源定义

时间轴由四类区间叠加计算：

1. 供给区间
   - 营业时间与已发布预约排班的交集
2. 不可用区间
   - 请假
   - 停用
   - 未发布
   - 非营业时间
3. 已占用区间
   - 待到店、已确认预约
   - 已开始但未结束服务会话
   - 保护性修复保留位
4. 可候选区间
   - 供给区间减去不可用区间和已占用区间后的空闲段

所有区间在进入时间轴前必须完成：

1. 按开始时间排序。
2. 重叠合并。
3. 端点标准化。

## 4. 候选时段生成算法

### 4.1 输入

候选时段生成器输入固定为：

1. 商户。
2. 目标日期。
3. 目标项目。
4. 可预约客服集合。
5. 可选排除预约 ID。

这里的目标项目用于得到当前选择项目的真实占用：

```text
d_selected = duration + service_gap_minutes
```

### 4.2 逐客服候选生成

对每个客服分别处理：

1. 读取该客服次日允许承接的项目集合。
2. 计算这批项目的真实占用分钟集合 `D`。
3. 构建该客服的 `TechnicianDayTimeline`。
4. 在每个 `FreeInterval` 内按展示粒度 `g` 枚举候选开始点 `t`。

候选成立的硬条件如下：

1. `t` 必须落在展示网格点上。
2. `[t, t + d_selected)` 必须完整落在该客服某个 `FreeInterval` 内。
3. 必须满足现有预约保护规则。
4. 必须满足现有改签保护规则。
5. 必须满足服务预测缓冲等已存在的硬约束。

此时生成的是：

- “每客服、每项目”的初始可行候选集合

这一步还不直接返回给前端。

### 4.3 候选对象

建议候选对象结构：

```go
type MixedTimelineCandidate struct {
    TechnicianID      uint
    Start             time.Time
    End               time.Time
    OccupiedMinutes   int
    GapStart          time.Time
    GapEnd            time.Time
    LeftWasteMinutes  int
    RightWasteMinutes int
    FragmentCost      int
    ScarcityPenalty   int
    WaitPenalty       int
    StartBias         int
    PlacementScore    int
    FitSummary        string
}
```

## 5. 未来填充能力评分算法

### 5.1 设计目标

P2 的核心不是判断“这个时间能不能放下当前项目”，而是判断：

- 把当前项目放在这里后，这个客服后续还能不能继续高质量承接其他项目

因此评分目标固定为：

1. 优先保留后续还能承接长项目和稀缺项目的空间。
2. 降低无法继续利用的小碎片。
3. 让系统推荐“整体时间轴更健康”的候选，而不是只推荐最早候选。

### 5.2 残段定义

对任一候选 `(technician, start=t, occupied=d_selected)`：

1. 找到该候选所在的原始空闲段 `gap = [a, b)`。
2. 放入当前项目后，得到：
   - 左残段 `left = [a, t)`
   - 右残段 `right = [t + d_selected, b)`

后续的碎片评估全部只在这两个残段上完成。

### 5.3 最大可填充分钟数

对左右残段分别计算：

- `best_fill(segment, D, g)`

其中：

1. `segment`
   - 一个连续空闲段
2. `D`
   - 当前客服允许承接的全部真实占用时长集合
3. `g`
   - 展示网格单位

算法不是简单判断：

- “某个项目能不能放进去”

而是使用动态规划求：

- “在这个残段内，从展示网格点出发，最多还能填充多少分钟的项目占用”

### 5.4 动态规划规则

先把残段内所有可用网格点离散化：

- `P = {p0, p1, p2, ...}`

定义：

- `dp[i]`：从网格点 `pi` 开始，在当前残段内最多还能填充的总分钟数

转移：

1. 不放任何项目：
   - `dp[i] = dp[i+1]`
2. 尝试放一个时长 `d in D` 的项目：
   - 若 `[pi, pi+d)` 完整落在残段内，则跳到“第一个不早于 `pi+d` 的网格点 `pj`”
   - 转移值：
     - `d + dp[j]`
3. 取最大值：
   - `dp[i] = max(dp[i+1], max(d + dp[j]))`

最终：

- `best_fill(segment, D, g) = dp[0]`

该 DP 的意义是：

- 不要求项目结束时间也落在展示网格点上
- 只要求开始时间落在展示网格点上
- 与当前系统“开始时间网格化、占用真实分钟化”的逻辑一致

### 5.5 碎片成本定义

对左右残段分别计算：

```text
left_waste = left_length - best_fill(left_segment, D, g)
right_waste = right_length - best_fill(right_segment, D, g)
fragment_cost = left_waste + right_waste
```

解释：

1. `left_length`
   - 左残段总分钟数
2. `best_fill(left_segment, D, g)`
   - 左残段理论上还能高质量利用的最大分钟数
3. 差值就是该残段会留下的“真实不可利用分钟”

`fragment_cost` 越小，说明该候选对整条时间轴的伤害越小。

## 6. 稀缺窗口保护规则

### 6.1 保护目标

仅用 `fragment_cost` 还不够，因为它可能让短项目占掉未来稀缺的长项目窗口。

因此 P2 需要单独增加：

- 稀缺窗口保护

### 6.2 稀缺窗口统计

对每个客服、每个项目时长 `d in D`，在生成候选前先统计：

- 当天剩余可容纳 `d` 的窗口数 `remaining_slots(d)`

统计规则：

1. 在该客服全部 `FreeIntervals` 中按展示网格枚举起点。
2. 只要 `[t, t+d)` 能完整落下，即记为一个窗口。
3. 同一空闲段内的不同起点都分别计数。

### 6.3 稀缺判定阈值

阈值固定如下：

1. `remaining_slots(d_long) <= 2`
   - 视为稀缺窗口
2. `remaining_slots(d_long) == 0`
   - 视为该时长完全失去承接能力

### 6.4 稀缺惩罚规则

当某候选放入后，若导致某个长时长 `d_long` 的剩余窗口显著下降，则增加：

- `scarcity_penalty`

具体规则：

1. 若候选导致任意 `d_long` 从 `>2` 下降到 `<=2`
   - 增加一级惩罚
2. 若候选导致任意 `d_long` 从 `>=1` 下降到 `0`
   - 增加重惩罚
3. 若候选使最长时长项目当天完全无位可排
   - 不对用户前台展示
   - 但允许保留为内部“手动强约候选”，用于商户人工兜底

### 6.5 稀缺性优先级

若多个时长都受影响，优先保护：

1. 更长的项目时长。
2. 可预约项目数更少的时长。
3. 当天剩余窗口更少的时长。

## 7. 最终评分与排序

### 7.1 固定评分公式

候选最终得分固定为：

```text
score = fragment_cost * 1000 + scarcity_penalty * 100 + wait_penalty * 10 + start_bias
```

其中：

1. `fragment_cost`
   - 核心权重最高
2. `scarcity_penalty`
   - 保护长项目稀缺窗口
3. `wait_penalty`
   - 复用现有客服可用性模型中的等待分钟数
4. `start_bias`
   - 同分时更早开始时间更优
   - 仍同分时优先当前推荐客服

分值越低越优。

### 7.2 时间点合并规则

返回前按“开始时间”聚合候选。

对同一开始时间 `t`：

1. 找到该时间点下分值最低的候选分数 `best_score(t)`。
2. 只保留分值等于 `best_score(t)` 的客服集合。
3. 若多个客服同分，则都保留到 `technician_ids` 中。
4. 其余客服不进入该时间点返回结果。

这样可以保证前台仍看到：

- 一个时间点
- 若干可选客服

而不是把同一时间点下全部较差客服也暴露出来。

### 7.3 当前预约变更后的优化边界

当以下事件发生时：

1. 用户取消预约。
2. 用户申请改签并被接受。
3. 商户取消预约。
4. 商户发起保护性改签。
5. 系统因超时、撤回排班等原因关闭预约。

P2 的处理原则固定如下：

1. 立即把变更后的最新占用状态视为新的事实状态。
2. 后续任何“查可预约时段 / 查改签时段 / 查推荐时段”请求，都基于最新事实状态重新构建时间轴。
3. 已存在但未被本次操作直接修改的预约，默认保持原位不动。
4. 因此 P2 是“事件后动态重算剩余供给”，不是“事件后全局重排所有预约”。

这一定义与当前系统的事务语义一致：

1. 取消会释放原预约占用。
2. 改签会生成新预约并关闭旧预约。
3. 后续时段查询本来就是基于最新预约占用重新计算。

P2 只是在此基础上把：

- 候选过滤与排序

从当前的简单碎片否决升级为：

- 时间轴评分 + 稀缺窗口保护 + 局部近优排序

### 7.4 为什么不做自动全局重排

理论上，若在某一单取消后允许把当天后续预约全部重排，系统有机会得到更高的总体利用率。

但该方向不应纳入 P2 第一版，原因如下：

1. 全局重排会改动已确认预约，违反“已承诺预约默认稳定”的产品原则。
2. 会产生链式影响：
   - 用户确认
   - 商户确认
   - 客服变更
   - 结算迁移
   - 补偿责任归属
3. 优化目标会从“局部候选排序”升级为“带约束的多预约重排问题”，复杂度和解释成本都会显著上升。
4. 在当前系统中，改签推荐本来就是显式确认链路，不适合改成后台自动搬移。

因此 P2 第一版明确只承诺：

1. 剩余可售时段动态调整。
2. 对新预约选择给出局部近优结果。
3. 对单个待修复预约给出高质量替代候选。

不承诺：

1. 已有预约的自动全局最优重排。
2. 当天整体排布的绝对全局最优。

## 8. 与现有接口和链路的衔接

### 8.1 保留不变的对外接口

以下对外接口 URL 保持不变：

1. 普通预约查可用时段。
2. 改签查可用时段。
3. 系统优化性改签推荐。
4. 保护性修复推荐。

前端现有主消费字段也保持不变：

1. `time_slots[].time`
2. `time_slots[].technician_ids`
3. `time_slots[].technician_candidates`

### 8.2 后端内部新增字段

为支持排序和调试，后端候选对象内部新增：

1. `placement_score`
2. `fragment_cost`
3. `scarcity_penalty`
4. `fit_summary`

这些字段第一版默认只在后端内部使用，不要求前端展示。

### 8.3 统一候选生成器

P2 启用后，以下链路必须统一复用同一套候选生成器和评分器：

1. 普通预约查时段。
2. 用户改签查时段。
3. 系统优化性改签推荐。
4. 保护性修复推荐。

不允许继续保留：

- 各自独立的碎片判断或推荐排序逻辑

否则会导致：

1. 前台可约时段与改签推荐不一致。
2. 修复推荐与普通预约结果口径不一致。
3. 商户人工处理异常时难以解释系统排序依据。

### 8.4 取消与改签后的链路要求

取消、改签和修复三类操作发生后，下一次相关查询必须满足：

1. 普通预约查时段：
   - 直接基于最新占用状态重算，不读取旧候选缓存。
2. 用户改签查时段：
   - 排除当前预约自身后，基于最新占用状态重算。
3. 系统优化性改签推荐：
   - 以当前预约的既有排布为基线，和新候选做同源比较。
4. 保护性修复推荐：
   - 只对受影响预约生成推荐，不触发其他正常预约自动迁移。

这意味着 P2 需要的不是：

- “重排任务队列”

而是：

- “统一候选生成器 + 统一评分器 + 事实状态重算”

## 9. 性能与缓存策略

### 9.1 范围限制

P2 第一版的计算范围限制为：

- 单商户
- 单天
- 单项目请求

不做跨天联动计算。

### 9.2 请求内缓存

允许使用请求内缓存，但不做跨请求持久化缓存。

缓存项：

1. `TechnicianDayTimeline`
   - Key：`merchant_id + technician_id + date`
2. `best_fill(segment, D, g)`
   - Key：`technician_id + date + segment_start + segment_end + duration_set_hash`

原因：

1. 同一次请求内，普通候选、改签比较、推荐排序会重复访问相同时间轴。
2. 跨请求缓存会被排班发布、请假、改签、修复锁位快速打脏，维护成本高。

### 9.3 复杂度控制

允许的目标复杂度为：

```text
O(客服数 × 网格点数 × 时长种类数)
```

在以下约束下应可接受：

1. 展示粒度 `5` 分钟。
2. 单日营业 16 小时。
3. 单客服约 `192` 个候选起点。
4. 单客服可预约项目时长种类控制在 `4` 组左右。

必须避免：

1. 指数级回溯。
2. 同一残段重复无 memo 的深度搜索。

### 9.4 缓存失效规则

由于 P2 采用事实状态重算，因此缓存失效规则必须简单明确：

1. 只允许请求内缓存。
2. 任何取消、改签、修复锁位变化、排班变化、请假变化，都会自然在下一次请求中重新装载最新时间轴。
3. 不引入跨请求候选缓存，避免出现“旧可售时段仍被复用”的问题。

这样做虽然放弃了一部分缓存命中，但能保证：

1. 变更后剩余时段立即动态调整。
2. 不需要额外维护复杂失效广播。

## 10. 失败模式与降级策略

### 10.1 算法失败时的降级

若 P2 评分器计算异常，降级顺序固定如下：

1. 记录错误日志。
2. 当前请求回退到“硬约束过滤 + 旧碎片判断”。
3. 不允许因为评分失败直接返回空时段。

### 10.2 稀缺窗口全部耗尽时的表现

若某个候选会使长项目窗口全部归零：

1. 不在用户前台返回。
2. 允许在商户侧内部能力中保留为“手动强约候选”。
3. 必须给出明确原因说明，例如：
   - `该时段会占用当天最后一个90分钟窗口，已自动降级`

### 10.3 模式切换要求

若商户从 `technician_mixed_timeline` 切回 `technician_grouped`：

1. 时间轴算法立即回退到 P1。
2. 不要求保留 P2 评分缓存。
3. 已存在预约不回溯重算，只影响后续时段生成与推荐。

## 11. 测试方案

### 11.1 核心功能用例

1. 单客服混排 `45/60/90` 分钟项目时，短项目不会优先吃掉当天仅剩的长项目窗口。
2. 同一空闲段存在多个可行开始点时，结果优先返回低 `fragment_cost` 候选，而不是仅按开始时间先后。
3. 同一时间点多个客服都可约时，只保留该时间点下得分最优的客服集合。
4. 已存在预约、进行中服务、保护性修复锁位同时存在时，时间轴合并结果无重叠、无漏算。

### 11.2 链路一致性用例

1. 普通预约查时段与改签查时段对同一输入必须得到同源候选排序。
2. 系统优化性改签推荐必须复用同一评分器，不能和普通预约排序冲突。
3. 保护性修复推荐在同一输入下必须和普通可约时段保持同源评分口径。

### 11.3 模式隔离用例

1. 在 `technician_grouped` 模式下不得进入 P2 算法。
2. 在 `technician_mixed_timeline` 模式下，客服允许多时长项目时必须进入 P2 算法。
3. 模式切换后，新请求应立即走对应算法。

### 11.4 性能用例

1. 5 分钟粒度、10 个客服、每客服 4 个可预约项目时，接口耗时应保持在当前系统可接受范围内。
2. 重复请求同一天、同项目时，请求内 memo 应显著减少重复计算。
3. 不允许出现指数级增长或超长卡顿。

### 11.5 变更后动态调整用例

1. 某个 90 分钟预约被取消后，下一次查询应立即释放该窗口，并重新计算后续所有可售时段排序。
2. 某个 45 分钟预约改签到更晚时间后，原窗口应立即回到可售池，新窗口应占用对应时间轴。
3. 在上述两种情况下，其他未被直接修改的预约不得被系统自动迁移。
4. 若某次取消使长项目窗口重新恢复，后续候选排序应体现这种恢复，而不是沿用旧稀缺惩罚结果。

## 12. 算法效果评估

### 12.1 对“动态调整能力”的结论

在“允许取消或改签”的前提下，P2 可以做到：

1. 已预约发生变化后，剩余可售时段动态调整。
2. 新增查询基于最新占用事实重新计算。
3. 对新的预约选择结果做到局部近优。

P2 不做到：

1. 已有预约的自动全局重排。
2. 所有剩余预约的绝对全局最优重组。

因此准确表述应为：

- P2 能做到“动态重算 + 局部近优”
- 不能也不应在默认模式下做到“自动全局最优重排”

### 12.2 对混合项目时长碎片的改进程度

相对当前实现，P2 对混合项目时长下碎片时段的改进属于：

- 显著改善，但不是彻底消除

原因在于当前实现主要还是：

1. 检查是否留下明显不可复用碎片。
2. 以较轻量的排布分数做比较。
3. 没有显式保护长项目稀缺窗口。
4. 没有把“变更后重新计算剩余供给”定义为统一评分问题。

P2 上线后，改进主要体现在三层：

1. 对不可复用碎片的压制：
   - 从“二元否决”升级为“残段可填充能力评分”
   - 改进程度：高
2. 对长项目窗口的保护：
   - 新增稀缺窗口惩罚，避免短项目持续侵蚀长项目供给
   - 改进程度：高
3. 对总体利用率的提升：
   - 通过局部近优排序提升剩余可售时间轴质量
   - 改进程度：中到高

但 P2 仍有明确上限：

1. 因为不自动重排既有预约，所以无法达到“理论上的全天全局最优”。
2. 若商户项目时长种类过多、分布极不均匀，碎片仍会存在，只是显著减少。
3. P2 的最终效果仍会低于 P1 的“客服按时长组拆分”，因为 P1 从产品结构上避免了混排。

因此最终判断为：

1. 相比当前混合项目时长实现，P2 对碎片治理是一次明显升级。
2. 相比 P1，P2 仍然是“成本更高、效果次优”的保底高级模式。
3. 若追求最稳定、最可解释、最少碎片，仍应优先实施 P1。

## 13. 下一步一次执行落地方案

下一步若要“一次执行落地”，建议只落以下必要闭环，不同时做全局重排：

### 13.1 落地目标

一次交付完成以下能力：

1. 商户模式开关接入：
   - `technician_grouped`
   - `technician_mixed_timeline`
2. 客服“可预约项目集合”作为 P2 输入前提。
3. 新增统一 `MixedTimelineEngine`：
   - 时间轴构建
   - 候选生成
   - `best_fill` 动态规划
   - 稀缺窗口保护
   - 统一排序
4. 普通预约、改签、推荐、保护性修复四条链路统一接入该引擎。
5. 取消/改签后自动依赖事实状态重算剩余时段，不做全局自动重排。

### 13.2 明确不纳入本次

以下内容不纳入这次一次性交付：

1. 自动批量改签既有预约。
2. 全局最优重排任务。
3. 商户端复杂可视化时间轴界面。
4. 跨天联合优化。

### 13.3 实施顺序

实施顺序固定为：

1. 抽象统一候选生成器接口。
2. 抽象 `TechnicianDayTimeline` 与区间归并逻辑。
3. 实现 `best_fill(segment, D, g)`。
4. 实现 `fragment_cost + scarcity_penalty + wait_penalty` 排序器。
5. 接入普通预约时段查询。
6. 接入改签时段、推荐时段、保护性修复推荐。
7. 补齐取消/改签后的动态调整测试。
8. 增加模式隔离与性能测试。

### 13.4 验收标准

一次交付验收标准固定为：

1. 同一客服混排 `45/60/90` 项目时，长项目窗口不会被短项目系统性吞掉。
2. 取消和改签发生后，下一次查询能立即看到重新计算后的剩余时段。
3. 未被直接修改的既有预约不会被系统自动移动。
4. 普通预约、改签、推荐、修复四条链路结果同源。
5. 性能在 5 分钟粒度下保持可接受。

## 14. 实施建议

P2 只能作为：

- 明确知情、明确开启、成本可接受的高级模式

不应成为默认模式。

推荐实施顺序：

1. 先完成“客服可预约项目集合”能力。
2. 再完成模式开关和时间轴对象抽象。
3. 然后实现候选生成器与 `best_fill` 动态规划。
4. 最后统一接入普通预约、改签、推荐、修复四条链路。

若没有明确业务压力，不建议优先进入 P2 开发，而应优先推进 P1。
