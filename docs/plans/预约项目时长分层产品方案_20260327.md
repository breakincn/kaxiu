# 预约项目时长分层产品方案

日期：2026-03-27

## 1. 方案结论

为减少预约碎片、降低用户对异常时间点的理解成本，并让排班发布规则更稳定，预约产品按商户预约项目时长形态分为两套方案：

- 单一项目时长预约方案
- 混合项目时长预约方案

两套方案的核心区别不在于“营业时间”或“排班发布”是否变化，而在于：

- 候选预约时间如何生成
- 每个客服可开放哪些项目
- 是否允许同一客服同时承接不同时长项目

本方案建议默认收口为：

1. 单一项目时长商户：预约开始时间按 `5` 分钟刻度生成；单次占用时间按“服务时长 + 间隔时间”向上取整到 `5` 分钟倍数。
2. 混合项目时长商户：按“客服维度”限制可预约项目集合，一个客服只能被预约服务时长相同的项目。
3. 移除“同一客服混合项目时长预约模式”，不再支持同一客服同时开放不同时长项目。

## 2. 核心产品判断

### 2.1 是否要给每个客服指定可以预约的项目

是，需要。

如果不对客服做“可预约项目”限制，只按商户维度开放多个项目，那么用户在同一客服时间轴上混排不同服务时长项目，会直接带来三个问题：

1. 可预约时间越来越碎。
2. 用户会看到很多“看似能约、实际不该放开”的时间点。
3. 排班管理、请假修复、改签推荐都会越来越依赖复杂算法兜底。

因此排班管理应从“发布客服次日可预约时段”升级为：

- 发布客服次日可预约时段
- 同时确认该客服次日允许承接的预约项目

### 2.2 是否不允许一个客服可以预约服务时长不同的项目

建议默认不允许。

更准确的产品规则是：

- 默认：同一客服同一天只允许开放同一时长组的预约项目。
- 不提供“同一客服混合项目时长预约模式”。

这里的“同一时长组”可以有两种实现方式：

1. 严格按项目时长分钟值分组。
2. 按商户配置的“预约时长组”分组，例如 `45分钟组`、`60分钟组`。

建议优先采用第 2 种。产品表达更清晰，也便于以后扩展多个同时长项目共用同一预约时间轴。

## 3. 单一项目时长预约方案

### 3.1 适用场景

满足以下任一条件即可归入该方案：

- 商户所有公开预约项目的服务时长一致。
- 虽然项目名称不同，但排班到某个客服上的可预约项目都属于同一时长组。

这时系统不再需要为了多个项目时长混排去维护复杂的候选时段集合。

### 3.2 时间段算法

定义：

- `service_minutes`：项目服务时长
- `gap_minutes`：项目间隔时间
- `occupied_minutes = service_minutes + gap_minutes`
- `slot_unit = 5`
- `rounded_occupied_minutes = occupied_minutes` 向上取整到 `5` 的倍数

公式：

```text
rounded_occupied_minutes = ceil((service_minutes + gap_minutes) / 5) * 5
```

候选预约开始时间规则：

1. 所有候选预约开始时间必须落在 `5` 分钟刻度上：
   - `N:00`
   - `N:05`
   - `N:10`
   - `N:15`
   - `N:20`
   - `N:25`
   - `N:30`
   - `N:35`
   - `N:40`
   - `N:45`
   - `N:50`
   - `N:55`
2. 每次预约放下去后，会占用 `rounded_occupied_minutes`。
3. 下一次预约开始时间不得早于“上一单开始时间 + rounded_occupied_minutes”。
4. 同时仍需满足：
   - 在营业时间内
   - 在已发布预约排班内
   - 不与已有预约冲突

### 3.3 例子

1. `45` 分钟服务 + `3` 分钟间隔

- 实际占用：`48`
- 向上取整：`50`
- 若本次从 `09:00` 开始，则下一次最早从 `09:50` 开始

2. `45` 分钟服务 + `6` 分钟间隔

- 实际占用：`51`
- 向上取整：`55`
- 若本次从 `09:00` 开始，则下一次最早从 `09:55` 开始

3. `48` 分钟服务 + `5` 分钟间隔

- 实际占用：`53`
- 向上取整：`55`
- 若本次从 `09:00` 开始，则下一次最早从 `09:55` 开始

### 3.4 方案优点

1. 时间点规整，用户和门店都容易理解。
2. 相比固定 `15` 分钟粒度，浪费的空档显著减少。
3. 不会出现 `09:48`、`10:41` 这种难沟通时间。
4. 单一时长下几乎不需要复杂碎片保护，规则简单稳定。

### 3.5 方案约束

1. 该方案只适合单一时长组。
2. 若同一客服开放不同服务时长项目，则这套算法会失去稳定性。
3. 多出来的 `1-4` 分钟是对齐成本，不是实际服务间隔变化。

## 4. 混合项目时长预约方案

### 4.1 适用场景

当商户公开预约项目存在多个服务时长，但这些项目会被分配到不同客服或不同客服组上时，进入混合项目时长方案。

例如：

- `45` 分钟项目
- `60` 分钟项目
- `90` 分钟项目

这套方案的前提是：

- 商户整体可以存在多种项目时长
- 但同一个客服只能开放同一时长组的项目
- 不允许同一个客服同时承接不同时长项目

### 4.2 默认产品设计

混合项目时长商户的关键不是让同一客服混排多种时长，而是先做资源分层：

1. 排班管理中，每个客服必须配置“次日可预约项目”。
2. 系统校验该客服的次日可预约项目是否属于同一时长组。
3. 若不属于同一时长组，则该客服标记为“混合时长客服”。
4. 默认规则下，不允许发布“混合时长客服”的预约排班。
5. 商户必须调整项目分配，使每个客服只保留同一时长组项目后，才能发布预约排班。

### 4.3 时间段算法

混合项目时长商户不再使用“同一客服混合时长”算法，而是按客服拆分为多个单一时长组时间轴：

1. 客服 A 只承接 `45` 分钟组项目。
2. 客服 B 只承接 `60` 分钟组项目。
3. 每个客服各自按单一项目时长预约方案生成时间段。

因此：

- 商户整体是“混合项目时长商户”
- 但客服维度仍然是“单一时长时间轴”

这意味着系统不需要再为同一客服做复杂的混合时长碎片保护。

### 4.4 方案优点

1. 商户整体仍然可以提供多种项目时长。
2. 每个客服的预约时间轴仍然简单稳定。
3. 用户理解成本低，不会看到同一客服时间段算法忽松忽紧。
4. 排班、请假、撤销发布、改签修复都更容易处理。

### 4.5 方案约束

1. 商户必须提前决定每个客服次日承接哪一类时长项目。
2. 同一客服若需要切换服务时长，应通过次日排班配置调整，而不是同一天混挂。
3. 若商户人手少、希望所有客服什么都能接，这套方案的灵活性会下降。

## 5. 排班管理产品改造方案

### 5.1 改造目标

当前排班管理只表达：

- 哪个客服明天可预约
- 哪个客服请假不可预约

改造后应表达：

- 哪个客服明天可预约
- 该客服明天允许承接哪些预约项目
- 这些项目是否属于同一时长组
- 若不属于同一时长组，则不能发布

### 5.2 每个客服的排班卡片新增字段

在预约排班管理中，每个客服卡片新增：

1. `可预约项目`
   - 例如：`塑形私教课`
   - 或：`45分钟组：塑形私教课、燃脂私教课`

2. `时长组状态`
   - `单一时长组`
   - `混合时长组`

### 5.3 交互规则

1. 点击客服卡片中的“设置可预约项目”按钮，打开项目选择弹窗。
2. 商户选择该客服次日可承接的项目。
3. 系统自动检测这些项目的时长是否一致：
   - 一致：标记为 `单一时长组`
   - 不一致：标记为 `混合时长组`
4. 不允许保存“混合时长组”配置。
5. 商户必须调整为同一时长组后，才能完成发布。

### 5.4 发布前校验

发布预约排班前，对每个客服做校验：

1. 是否处于请假状态。
2. 是否已配置可预约项目。
3. 可预约项目是否属于同一时长组。
4. 若不是同一时长组，则直接禁止发布。

发布结果应明确反馈：

- `客服#js0001 大漂亮：单一时长组，按5分钟刻度发布`
- `客服#js0002 小美：存在不同服务时长项目，必须先调整为同一时长组后才能发布`

## 6. 推荐默认策略

默认产品策略建议如下：

1. 商户默认进入“单一项目时长优先”模式。
2. 每个客服必须绑定次日可预约项目。
3. 默认不允许同一客服同时开放不同时长项目。
4. 混合项目时长商户也必须通过“不同客服承接不同时长组”来实现。
5. 系统不再提供“同一客服混合项目时长预约模式”。

这样做的好处是：

1. 大部分商户仍然使用简单稳定的单一时长预约方案。
2. 复杂商户可以按需开启混合模式。
3. 产品规则清晰，排班管理也更容易解释。

## 7. 结论

结论如下：

1. 是的，预约排班管理应给每个客服指定可预约项目。
2. 默认不应允许同一客服开放服务时长不同的项目。
3. 单一项目时长商户采用：
   - 预约开始时间按 `5` 分钟刻度生成
   - 单次占用时间按“服务时长 + 间隔时间”向上取整到 `5` 分钟倍数
4. 混合项目时长商户不再允许单个客服混挂不同时长项目，而是按客服拆分为多个单一时长组时间轴。
5. 从产品整体可解释性、用户体验、排班稳定性看，“先按客服做项目时长分层，再决定时间算法”明显优于为单个客服设计混合时长预约模式。
