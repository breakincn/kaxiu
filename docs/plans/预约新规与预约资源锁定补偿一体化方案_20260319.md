# 预约新规与预约资源锁定补偿一体化方案

日期：2026-03-19

## 1. 方案结论

基于当前项目实现现状和你给出的新业务口径，最优方案不是继续在现有“可条件压预约”的规则上打补丁，而是整体切换为：

- `预约资源锁定制`
- `D-1 10:00 开放 + 16:00 截止 + 16:00-18:00 未满补开`
- `全时段分级改签：用户主动改签 / 商户保护性改签 / 系统优化性改签`
- `按卡型分层预约结算`
- `到店只做签到建单，不再做资产扣减`
- `商户未服务 / 商户拖堂` 两条自动补偿闭环

这套方案的核心目标是同时满足四件事：

1. 预约一旦成功，必须能按时服务，不能再被现场单或其他用户挤占。
2. 晚间空余产能还能继续出售，提升次日产能利用率。
3. 改签不是人工拍脑袋，而是受统一算法和碎片优化规则控制。
4. 商户违约成本结构化落库，补偿不再依赖线下口头协商。

### 1.1 2026-03-29 对照实现更新

结合本轮代码改动，以下口径补充冻结为当前实现要求：

- 预约到店窗口不再使用“预约开始后固定 `15` 分钟仍可签到/核销”的旧设计。
- 统一改为：若用户到店后，剩余服务时长仍达到该项目时长的 `1/2` 向下取整分钟数，则仍允许到店。
- 在满足上述条件时，前端应继续正常展示该预约，且用户可出示预约到店码，由客服扫码后建单进入服务。
- 超过该阈值后，预约自动收敛为用户失约；用户页和商户页都必须继续保留该预约记录，不得直接从可见列表中消失。
- 对于失约且资产已按预约规则占用的预约，页面展示口径应明确为：
  - 次卡：`用户失约，预约已完成扣次`
  - 额度卡：`用户失约，预约已完成扣额`
- 与该预约关联的消费/使用记录也必须继续保留在用户可查询历史中，不得因超时清理、失败态折叠或前端过滤而消失。

## 2. 当前项目综合评估

### 2.1 当前系统不适合直接承接新规则

当前代码已具备预约、改签、补偿、预约保护的基础，但仍有 7 个关键口径与新规则冲突：

1. 当前现场单对预约客服仍存在“条件性挤占”语义，不是绝对锁定。
2. 当前用户手动选客服与系统自动派单不是同一套预约保护规则，存在绕过保护的缺口。
3. 当前核销链路把“到店”和“扣次”耦合在一起，不满足“预约成功即扣次”的新要求。
4. 当前用户主动改签资格是“今天/昨天/明天阈值模型”，不符合 `D-1 16:00 / D-1 18:00 / D 营业前` 的新窗口。
5. 当前补偿能力以人工补录为主，还没有“拖堂分钟账本 -> 自动折算补偿”的机制。
6. 当前只有当天 `technician_attendances` 签到状态，没有“次日可预约排班发布”能力。
7. 当前客服请假、离岗、改签、补偿之间还没有正式闭环，更多依赖人工处理。

### 2.2 当前项目可直接复用的能力

以下能力可以直接纳入新方案，不需要推翻重写：

- 商户营业时间和预约粒度
- 项目时长与项目间歇时间
- 预约时段碎片保护
- 预约改签记录链路
- 预约补偿记录表
- 预约到店接入 `ServiceSession` 主链

### 2.3 必须明确废弃的旧语义

本方案下，以下旧语义必须明确下线：

- 现场单允许在阈值内挤占后续预约
- 预约用户到店后进入 `appointment_waiting` 等前序现场单结束
- 到店核销才正式扣次
- 预约后的取消、用户主动改签、商户保护性改签、补偿继续靠人工备注兜底

原因很简单：只要仍允许“压预约”，就无法满足“预约成功一定按时服务”这个新前提。

### 2.4 当前代码实现的真实业务画像

结合当前代码，现状更准确的定义不是“严格预约制”，而是：

- `预约 + 现场混合调度制`

其核心特征是：

1. 预约创建、确认、用户主动改签已经有统一校验主链，且具备碎片保护能力。
2. 现场用户在手动选客服时，会参考后续预约保护，但仍允许在一定阈值内压后一个预约。
3. 预约用户到店后，如果原预约客服仍忙，系统允许进入 `appointment_waiting`，本质上接受“预约不一定准点开始”。
4. 到店核销才真正扣次，不是预约成功即扣次。
5. 补偿能力主要是结构化补录，还不是自动履约账本。

这说明当前代码更偏向：

- 提高门店当下流转弹性
- 兼容现场客和预约客混跑
- 用“预计等待可接受”来换取更高的当班利用率

而不是：

- 严格保证预约准点
- 严格锁定预约资源
- 严格做预约结算与违约补偿闭环

### 2.5 当前代码实现的优点

当前实现不是没有价值，它在以下方面是成熟且应继续保留的：

1. 候选时段、创建预约、确认预约、用户主动改签已基本共用同一套排布判断。
2. 已经有碎片保护和排布评分基础，不是简单的时间重叠判断。
3. 允许一定弹性插单，在高现场客门店中短期吞吐更高。
4. 对老门店改造成本较低，不需要立刻重构“预约成功即扣次”的资产链路。

### 2.6 当前代码实现的根本短板

但对“真实预约制线下场景”而言，当前实现有 7 个根本短板：

1. 预约不等于准点承诺。
2. 手动选客服与系统自动派单规则不完全一致。
3. 允许有限压预约，会把后续履约风险向后传导。
4. 用户主动改签窗口设计仍偏补救逻辑，不是主动优化产能。
5. 扣次时点偏晚，无法表达“预约成功即占用用户权益”。
6. 补偿没有分钟账本，无法自动折算履约损失。
7. 没有次日排班发布机制，导致“预约可售”和“客服次日是否一定可上班”之间缺少正式前置条件。

## 3. 新方案的总原则

### 3.0 改签术语统一

本方案中的“改签”统一拆成三类，后文如无特别说明，均按此口径理解：

1. `用户主动改签`
   - 由用户主动发起
   - 默认受改签次数限制
2. `商户保护性改签`
   - 由商户或客服发起
   - 仅用于商户责任或资源异常修复
   - 不占用用户主动改签次数
3. `系统优化性改签`
   - 由系统生成推荐
   - 默认关闭
   - 只能推荐，不能直接替用户改
   - 不占用用户主动改签次数

### 3.1 原则一：预约成功即锁定真实资源

预约一旦成功，系统必须同时锁定：

- 具体客服
- 具体开始时间
- 具体结束时间
- 对应项目占用长度

在该预约时段内，该客服不得再分配给任何其他用户。

### 3.2 原则二：预约规则优先于现场效率

在客服模式下，预约时段属于硬锁定资源，不再允许通过现场单“优化利用率”的方式侵占预约时段。

产能效率提升要通过这三种方式获得，而不是靠压预约：

- `16:00-18:00` 未满补开
- 提前开放的分级改签
- 碎片最优排布

### 3.3 原则三：资产扣减前移，服务签到后置

新方案把“预约承诺”和“实际履约”拆开：

- 预约成功：完成资产扣减或冻结
- 到店签到：创建服务会话
- 服务完成：完成履约闭环

这样才能同时满足：

- 用户不来店也要承担预约成本
- 商户未服务时能精确补偿

### 3.4 原则四：用户主动改签只允许成功一次，失败申请可在截止前重复发起，且不做级联挤压

每次预约默认只有一次`用户主动改签成功`机会。

但在该次成功发生前：

- 如果用户发起改签申请后未通过系统算法校验
- 或用户提交的目标时段不可执行
- 则视为“申请失败”
- 只要仍在用户主动改签窗口内（第一版统一截止到 `D` 营业开始前），用户即可继续重新申请

但以下两类改签不受这条限制：

- `商户保护性改签`
- `系统优化性改签`

其中：

- 商户保护性改签必须满足：
  - 商户责任或资源异常
  - 自动补偿
  - 留痕审计
- 系统优化性改签默认关闭：
  - 仅在 `balanced / flex` 档位下开启
  - 且只能推荐，不能直接替用户改

一旦某次用户主动改签已成功生效，则该预约根单不可再次发起用户主动改签。

系统只允许把该预约改签到一个“严格空闲且更优”的新时段，不允许通过移动 A 去挤压 B，再让 B 去挤压 C。

原因：

- 级联挤压会极大增加解释成本
- 会破坏“预约成功一定按时服务”
- 会让改签变成隐式重排全部预约

因此本方案采用：

- `单单移动`
- `不影响其他已预约用户`
- `允许优化碎片`

而不采用：

- 多订单连锁交换
- 全局强制重排

### 3.5 原则五：改签应早于取消开放

如果系统在 `16:00` 前允许取消，却不允许改签，会产生两个直接问题：

1. 用户原本只想把 A 时段换到 B 时段，却只能先取消 A，再重新抢 B，过程更抖。
2. 系统失去了更早做“空洞搬移”和“碎片收敛”的机会，反而更容易制造临时空档。

因此更优原则应是：

- 只要允许取消，就应至少允许改签。
- 且改签应优先于取消被推荐给用户。

## 4. 预约窗口新规则

下文统一以：

- `D` = 服务日
- `D-1` = 预约日

### 4.1 基础规则

- 用户每天只能预约 `D`，即第二天。
- 预约创建窗口：
  - `D-1 00:00-10:00` 不开放次日新预约，商户需先完成次日预约排班发布
  - `D-1 10:00-16:00` 正常开放
  - `D-1 16:00-18:00` 若次日未约满则继续开放
- 取消窗口：
  - 截止到 `D-1 16:00`
- 改签窗口：
  - 从预约成功后即开放
  - 一直持续到 `D` 营业开始前
  - 但分三个阶段，越晚规则越严格
- `D-1 18:00` 之后到 `D` 营业开始前：
  - 不再开放新预约
  - 不允许取消
  - 用户主动改签继续受次数限制
  - 商户保护性改签仍可用
  - 系统优化性改签仅可推荐，不可自动执行

### 4.2 “未约满”定义

“未约满”不能用总人数判断，必须用严格产能判断：

- 对次日每个客服
- 按项目占用长度
- 按营业时间
- 按已确认预约
- 按碎片保护结果

只要还存在至少一个可售时段，就视为“未约满”，允许在 `16:00-18:00` 继续卖。

### 4.3 取消规则

取消窗口统一定义为：

- `cancel_deadline_at = D-1 16:00:00`

规则如下：

- 在 `cancel_deadline_at` 之前：
  - 可以取消
  - 若预约已完成资产扣减，则原路返还或解冻
- 在 `cancel_deadline_at` 之后：
  - 不可取消
  - 用户只能申请用户主动改签
  - 商户仍可发起保护性改签

注意：

- `16:00` 之后新下的预约，也不能取消；用户只能发起用户主动改签，商户仍可发起保护性改签。
- 这样可以保证 `16:00` 后门店的次日产能开始稳定收敛，不再被来回取消打穿。

### 4.4 为什么 `16:00` 前必须允许改签

更优设计下，`16:00` 前不仅应该允许改签，而且应该把改签作为默认推荐动作。

原因：

- 对用户而言，改签比取消重约成本更低。
- 对商户而言，改签比取消更有利于保留已成交订单。
- 对系统而言，越早移动预约，越容易把离散空洞并成可复用完整时段。

因此前端建议改为：

- 用户点击“取消预约”时
- 优先展示“推荐用户主动改签到这些更优时段”
- 用户确认放弃改签后，再允许取消

### 4.5 商户单方面取消规则

商户侧取消分两段处理，但“是否允许取消”和“是否需要补偿”分开判断：

- 离预约服务开始前 `5` 小时以上：
- 商户可单方面取消
- 但必须填写正当取消理由
- 取消生效时系统立即退款或解冻
- 若取消原因属于商户侧无法按原预约履约（如客服请假、项目不可服务、资源撤回、排班错误等），则取消生效后仍需立即进入商户侧补偿结算，不存在“取消成功即免补偿”的例外
- 用户保留抗辩权
- 离预约服务开始前 `5` 小时及以内：
- 商户不可单方面取消
- 但可向用户申请取消预约
- 用户同意则取消成功
- 用户不同意则不能取消，只能继续履约或发起保护性改签
- 保护性改签仍必须经用户同意后方可生效
- 若用户同意取消且商户已确认无法按原预约履约，则取消生效后同样按对应补偿策略结算

取消记录规则：

- 凡非用户主动取消成功的预约，都必须保留预约记录
- 用户端必须可查看该预约记录
- 商户单方面取消的预约记录，需增加“用户抗辩意见”字段
- 用户填写的抗辩意见不阻止 `5` 小时前的单方面取消生效
- 但可作为后续用户查看、申诉或投诉至平台的依据

说明：

- 第一版只落系统留痕和状态记录，不直接实现平台投诉裁决。
- 后续可增加平台级投诉处理功能。

## 5. 预约确认与资源锁定规则

### 5.1 新的预约确认语义

预约成功必须同时完成 4 件事：

1. 选定具体客服
2. 锁定预约时段
3. 完成对应的预约结算动作
4. 生成预约结算凭证

标准目标口径下，这里的“预约成功”指：

- 商户已先发布次日可预约排班
- 用户命中可售库存后
- 系统自动确认成功

商户逐单确认只保留给兼容期或异常处理场景，不再作为长期主流程。

### 5.2 预约锁定区间

预约锁定区间采用严格硬占用，不再允许软挤压：

- `reserved_start_at = appointment_time`
- `reserved_end_at = appointment_time + project.duration`

项目间歇时间不属于用户可服务时长，但属于客服产能占用：

- `occupied_end_at = appointment_time + project.duration + project.service_gap_minutes`


### 5.5 次日可预约排班发布机制

 推荐规则：

1. 商户在 `D-1` 某一截止时间前发布 `D` 的可预约客服名单和工作区间。
   - 第一版固定要求在 `D-1 10:00` 前完成发布；`10:00` 后用户侧开始开放次日预约。
2. 只有发布后处于可预约状态的客服和时段，才会出现在 `D` 的预约候选结果里。
3. 排班一旦发布，系统预约确认直接基于该排班自动完成，不再等待客服逐单同意。
4. 若商户未发布次日排班，则该客服次日不对外开放预约。

 建议状态：

 - `draft`
 - `published`
 - `withdrawn`
 - `leave_applied`
 - `leave_confirmed`

 口径冻结：

 - `published` 是排班发布记录的正式状态
 - 文中 `bookable` 统一指“处于可预约状态”的派生语义，而不是新增状态
 - 只有 `status = published` 且目标时段落在 `[bookable_start_at, bookable_end_at)` 内、且未被 `withdrawn` / `leave_confirmed` / 其他禁用区间覆盖时，才视为该时段 `bookable`
 - 后文若写“已发布 `bookable` 排班”或“客服在该时段处于 `bookable`”，均按上述派生语义理解

### 5.6 当前代码与目标方案在确认模型上的差异

 当前代码更接近：

- 商户确认预约
- 预约确认后仍可能由调度器继续回补客服

这说明现状里“预约确认”和“客服资源最终落位”还没有完全合一。

目标方案应改为：

- 先发布次日可预约排班
- 再允许用户预约
- 用户预约成功即拿到确定客服和确定时段

这样才能满足“预约成功一定按时服务”的业务承诺。

## 6. 可预约时段与改签时段算法

### 6.1 统一目标

时段算法统一服务于三个入口：

- 新预约查询
- 新预约提交
- 用户主动改签可选时段查询

三处必须共用一套规则，避免“看得到、提得上、确认不了”。

### 6.2 候选时段生成规则

候选时段仍按固定粒度生成，推荐继续使用：

- `appointment_slot_granularity_minutes = 15`

对每个候选时段依次执行：

1. 营业时间容纳校验
2. 指定客服硬冲突校验
3. 客服锁定资源校验
4. 碎片保护校验
5. 晚间窗口校验
6. 用户主动改签次数与改签资格校验

### 6.3 碎片保护规则

继续采用当前项目已落地的“减少不可复用碎片”原则，但收紧口径：

- 候选预约落下去后
- 前后剩余区间如果都不能容纳该商户任一可预约项目的 `occupied_minutes`
- 则该时段不可售

### 6.4 最优排布评分

新方案下，评分目标不再是“允许有限挤占”，而是“在严格不挤占的前提下最大化产能利用率”。

建议评分函数统一为：

- `score = fragment_penalty + idle_gap_penalty + late_window_fill_bonus + same_staff_bonus`

含义：

- `fragment_penalty`
  - 若产生不可复用碎片，直接判负无穷，拒绝
- `idle_gap_penalty`
  - 优先填补更接近已有预约边界的空洞
- `late_window_fill_bonus`
  - 在 `16:00-18:00` 卖尾盘时，优先卖能填平剩余空洞的时段
- `same_staff_bonus`
  - 用户主动改签或商户保护性改签时，若还能保持原客服，给予稳定性加分

当某客服已发布可预约排班后又被确认请假，并且系统已识别出受影响预约时，调度必须切换为“异常修复模式”。该模式下：

- 系统必须先计算受影响预约的可修复候选容量，并标记为 `protected_repair_slots`
- 普通新预约自动确认、普通用户主动改签、系统优化性改签推荐都不得占用 `protected_repair_slots`
- 只有在受影响预约已完成修复，或系统确认当前剩余容量足以同时覆盖修复与新增需求时，普通自动确认算法才可继续使用对应日期的剩余时段
- 因请假触发的调度目标必须从“提升利用率、减少碎片”切换为“优先修复受影响预约并避免二次受影响”，碎片优化只能作为同优先级候选之间的次级排序条件
- “已发布后确认请假”必须同时满足以下条件：该客服对应日期排班已处于可预约状态、用户已可见并可创建预约、后续又确认请假、且请假区间与已发布可预约区间存在交集
- 一旦进入异常修复模式，调度优先级必须固定为：受影响预约修复 > 商户保护性改签 > 普通用户主动改签 > 普通新预约自动确认
- 在异常修复模式下，不得为了减少碎片、提升利用率或保留黄金时段，而降低受影响预约的修复成功率

### 6.5 改签批准原则

三类改签共用同一套排布与冲突校验，但权限和触发条件不同。

#### 用户主动改签

系统应按以下顺序判断：

1. 是否仍在可改签窗口内
2. 是否已用过用户主动改签机会
3. 目标时段是否严格空闲
4. 是否会制造不可复用碎片
5. 是否优于或不劣于当前排布

只有全部满足，系统才自动同意并直接生效，不需要商户或客服二次确认。

前提：

- 目标时段属于原服务日 `D` 的已发布可预约排班，第一版普通用户主动改签不得跨日
- 目标客服在该时段处于可预约状态（即 `status = published` 且目标时段命中 `bookable` 区间）

#### 商户保护性改签

系统应按以下顺序判断：

1. 是否属于商户责任或资源异常
2. 是否已生成补偿方案
3. 目标时段是否严格空闲
4. 是否不会引入第二个受影响预约
5. 是否已写入审计说明

满足后只可生成保护性改签提议，需经用户确认后才生效，且不消耗用户主动改签次数。

默认不允许商户单方面把已确认预约直接改走。

补充约束：

- 对`非特殊资源违约`场景，用户拒绝后不允许对后续已预约用户做级联重排。
- 不允许为了保当前单去压后续预约。
- 最多只允许继续保留原预约，或对“当前这一单”继续给出不影响他人的替代候选。

#### 请假触发后的处置分流

当已发布可预约排班的客服被确认请假，且预约与请假区间发生重叠时，系统必须先为每笔受影响预约执行“高质量修复方案”判定。只有同时满足以下条件，某个候选方案才可被视为高质量修复方案：

1. 目标时段严格空闲，且属于已发布、仍可履约的正式排班
2. 不会引入第二个受影响预约，也不会挤占其他已确认预约
3. 旧占用释放、新占用锁定、结算归属迁移可在同一事务内原子完成
4. 扰动成本不超过系统阈值；该成本至少应综合考虑跨天、换客服、用户体验下降和碎片化风险
5. 已写入补偿说明、审计说明与异常原因

分流规则必须固定为：

- 一旦某笔预约被认定为受请假直接影响，该预约后续改签流程必须切换到商户保护性改签分支，不得继续按普通用户主动改签或系统优化性改签路径处理
- 若 `now < reserved_start_at - 5h`：系统必须优先走商户保护性改签；只有在不存在高质量修复方案时，商户才可走单方面取消
- 若 `now >= reserved_start_at - 5h`：系统必须优先走商户保护性改签；若不存在高质量修复方案，商户只可发起取消申请，不得单方面取消
- 商户单方面取消在请假场景下只能作为“高质量修复方案不存在”时的兜底路径，不得作为默认优先策略
- 用户接受保护性改签后，系统必须原子完成旧占用释放、新占用锁定、结算归属迁移、异常状态收敛与审计写入
- 用户拒绝保护性改签后，系统可继续尝试当前预约的其他可行候选；若不存在可行候选，必须立即转入取消申请、商户违约补偿或其他已定义异常归责闭环，不得长期悬空
- 当保护性改签失败、取消未成功或用户拒绝后，系统必须立即重新评估是否进入 `merchant_breach_pending`，不得让预约长期停留在待人工判断状态
- 以减少碎片为目标时，也不得直接跳过保护性改签而优先单方面取消；仅当取消的总排程代价明确低于所有可行改签方案，且不会损害前述用户权益约束时，才允许选择取消兜底

#### 系统优化性改签

系统只做推荐，不直接改写预约。

推荐条件：

1. 当前策略档位允许
2. 推荐目标时段优于当前排布
3. 不会制造不可复用碎片
4. 不会引入连锁延迟

### 6.6 三类调度算法的开发规格骨架

本节把方案 A 中最核心的三类调度算法收敛为可直接实现的开发规格骨架。三类算法必须共用 `6.2`、`6.3`、`6.4`、`6.5` 已定义的候选生成、碎片判定、排布评分、异常修复模式与权限约束，不得各自维护独立判断口径。

#### 6.6.0 异常修复模式下的联动顺序

正常模式下，系统仍以“先接单，再调度”为主：普通新预约自动确认优先，改签审核次之，局部重排主要用于生成更优推荐。

当触发“已发布后确认请假”并进入异常修复模式后，三类算法的联动顺序必须切换为“先修复，再接单”：

1. 先由局部重排能力为受影响预约生成可执行修复候选，并输出是否存在高质量修复方案。
2. 再由改签自动审核链路对商户保护性改签提议做合法性审核与分流，不得绕过用户确认直接改写预约。
3. 最后才允许普通新预约自动确认继续处理剩余可售容量，且不得占用 `protected_repair_slots`，也不得降低已受影响预约的修复成功率。

因此，正常模式与异常修复模式的总目标必须分别固定为：

- 正常模式：提高利用率、减少碎片、稳定自动确认
- 异常修复模式：最小扰动修复已受影响预约、保留修复容量、避免二次受影响

#### 6.6.1 防碎片预约自动确认算法


- 在不挤占已确认预约、不制造不可复用碎片的前提下，自动确认普通新预约
- 在异常修复事件存在时，优先保护受影响预约的修复容量

输入：

- `merchant_id`
- `service_item_id`
- `target_date`
- `candidate_slots`
- `service_duration`
- `slot_granularity`
- 已发布且处于可预约状态的排班（即 `status = published` 且目标时段命中 `bookable` 区间）
- 已确认预约、锁定资源与 `protected_repair_slots`
- 当前策略档位与营业窗口约束
- 当前日期受影响预约规模与修复容量快照

输出：

- `confirmable_slot`
- `assigned_technician_id`
- `auto_confirm`
- `score_breakdown`
- 若无可确认结果，则返回结构化拒绝原因

硬约束：

- 候选时段必须命中已发布且仍可履约的正式排班
- 候选时段必须能完整容纳 `service_duration`
- 候选时段不得落入 `leave_confirmed` 或其他禁用区间
- 候选时段不得与已确认预约、已开始服务、锁定资源产生硬冲突
- 在异常修复模式下，普通新预约不得占用 `protected_repair_slots`
- 候选提交前必须通过最终并发校验；无法原子提交的候选视为无效

候选生成与评分补充：

- 系统应对每个有效 `free_block` 按 `slot_granularity` 生成候选开始时刻，并只保留能完整容纳服务时长的候选
- 评分因子除 `6.4` 已定义项外，还应显式考虑“是否贴边排布”“是否保留可用于修复的长时段”“是否逼近受保护修复容量边界”
- 在异常修复模式下，任何会降低受影响预约修复成功率的候选，都不得因为更优碎片得分而获选

执行步骤：

1. 先按 `6.2` 生成候选时段，并过滤未发布排班、硬冲突、资源冲突和超窗口候选。
2. 对每个候选执行 `6.3` 碎片保护校验；一旦产生不可复用碎片，立即剔除。
3. 若对应日期处于异常修复模式，先剔除所有会占用 `protected_repair_slots` 的候选。
4. 对剩余候选按 `6.4` 评分函数计算得分，并按“是否贴边填洞”“是否消化尾盘空档”“是否减少剩余碎片”排序。
5. 选择得分最高且满足事务提交条件的候选，原子完成预约确认、资源锁定和结算归属写入。
6. 若提交时发现并发占用变化，则重新计算，不得沿用过期候选。
7. 若系统确认当前剩余可售容量不足以同时覆盖已识别受影响预约修复与新增需求，则必须停止该日期普通自动确认，或降级为仅返回有限推荐候选，不得继续抢占修复能力。

拒绝条件：

- 不存在通过碎片保护校验的候选
- 唯一可行候选会占用 `protected_repair_slots`
- 候选在事务提交前已被并发占用
- 当前剩余容量不足以同时保障受影响预约修复与新增需求

实现约束：

- 自动确认不得因为追求产能而牺牲已确认预约稳定性
- 自动确认算法与候选查询接口必须返回同一批可售结果，不能出现“可见但不可下单”或“不可见却可下单”

#### 6.6.2 改签自动审核算法

目标：

- 为用户主动改签、商户保护性改签提供统一的自动审核主链
- 保证改签批准结果与碎片保护、异常修复优先级和用户权益约束一致

输入：

- 原预约记录
- 改签发起类型
- 原时段与目标候选时段集合
- 当前阶段窗口、改签次数、补偿方案、审计说明
- 当前日期是否处于异常修复模式

输出：

- `approved`
- `rejected`
- `proposal_only`
- 对应结构化原因、目标时段与补偿信息

分类型处理补充：

- 用户主动改签：仅当候选时段满足窗口、次数、碎片保护、硬冲突与排布不劣化约束时，才允许自动批准；在异常修复模式下，不得抢占 `protected_repair_slots`
- 商户保护性改签：候选时段应优先来自 `protected_repair_slots` 或其他专门保留的修复容量；通过审核后只创建提议，不直接替用户确认
- 系统优化性改签：在正常模式下只做推荐；在异常修复模式下默认进一步降级，不得与保护性改签争抢容量，也不得自动推进
- 若某预约已被认定为受请假直接影响，则普通改签规则必须让位于保护性改签规则，不得并行适用两套批准口径

执行步骤：

1. 先判断发起类型属于用户主动改签、商户保护性改签或系统优化性推荐，选择对应权限分支。
2. 对目标候选逐一执行：窗口校验、次数校验、硬冲突校验、碎片保护校验、排布评分校验。
3. 若处于异常修复模式，优先允许受影响预约使用 `protected_repair_slots`，普通用户主动改签必须避让该容量。
4. 对用户主动改签，只有在 `score(target) >= score(current)` 或阶段性更严格规则满足时，才可自动批准。
5. 对商户保护性改签，必须先通过“是否属于商户责任或资源异常”“是否不会引入第二个受影响预约”“是否已生成补偿与审计说明”校验；满足后只生成提议，不直接生效。
6. 对请假触发场景，必须先执行“高质量修复方案”判定，并按 `5` 小时阈值决定是继续保护性改签、单方面取消兜底或取消申请。
7. 改签真正生效时，必须原子完成旧占用释放、新占用锁定、结算归属迁移与审计写入。
8. 若当前预约已被认定为受请假直接影响，则审核流程必须直接切换到商户保护性改签分支；普通用户主动改签和系统优化性改签只可作为未受影响预约的常规分支。

拒绝条件：

- 目标时段不满足窗口、次数或碎片保护约束
- 改签会引入第二个受影响预约
- 商户保护性改签缺少补偿方案或审计说明
- 请假场景下不存在高质量修复方案，且当前路径不满足取消放行条件

实现约束：

- 自动审核结果必须可解释，拒绝时需输出命中的第一优先级拒绝原因
- 商户保护性改签与用户主动改签必须共用同一套冲突和评分结果，不得出现两套算法口径

#### 6.6.3 预约与改签局部重排推荐算法

目标：

- 在不做全局链式搬移的前提下，为单笔预约或单笔受影响预约生成更优替代候选
- 让系统优化性改签和异常修复候选都基于同一套局部重排能力输出

输入：

- 当前预约
- 原时段、可选时段集合、同日可承接客服集合
- 当前已确认预约分布
- `protected_repair_slots`
- 排布评分参数与扰动成本参数

输出：

- 按优先级排序的推荐候选列表
- 每个候选的 `score_delta`
- 每个候选是否属于“高质量修复方案”
- 每个候选的扰动成本拆解

搜索范围与成本补充：

- 第一优先：同商户、同日、其他可承接客服的等价或更优时段
- 第二优先：同商户、同日、邻近且可接受的替代时段
- 第三优先：仅对商户保护性改签 / 异常修复开放，同商户、跨日但仍在业务可接受范围内的时段
- 普通用户主动改签与系统优化性改签第一版均不得跨日
- 默认不允许自动搬移其他已确认预约，不允许链式改动多个预约，也不允许为了整体利用率牺牲单笔已确认预约稳定性
- 扰动成本至少应综合考虑用户体验下降、换客服成本、跨天成本、碎片影响和冲突风险，且分值越低越优

执行步骤：

1. 以“只移动当前预约、不搬移其他已确认预约”为硬约束，生成局部候选集。
2. 先过滤掉会挤占已确认预约、会制造不可复用碎片、会占用不允许使用的 `protected_repair_slots` 的候选。
3. 对每个候选计算 `score_delta = score(target) - score(current)`，并同时计算扰动成本。
4. 若用于系统优化性改签，只保留 `score_delta > 0` 且扰动成本在阈值内的候选。
5. 若用于异常修复，则在满足不引入第二个受影响预约的前提下，优先选择同商户、同日、同客服或低扰动成本候选，并输出“高质量修复方案”判定。
6. 按“是否可修复当前异常”“是否减少碎片”“是否降低扰动成本”的顺序排序后返回推荐结果。
7. 若用于异常修复且局部候选已穷尽，系统不得继续对其他已确认预约做自动链式腾挪；应直接返回无高质量修复方案，并转入后续异常归责或补偿分流。

禁止事项：

- 不得自动链式改动其他已确认预约
- 不得为了优化局部碎片而降低受影响预约修复成功率
- 不得输出在线接口无法实际提交的伪候选

实现约束：

- 第一版只实现局部重排，不实现多订单交换、跨多单连锁腾挪和全局最优求解
- 推荐算法必须与最终提交校验复用同一套候选生成与评分函数，避免“推荐可行但提交失败”成为常态

### 6.7 算法边界与实现要点

- `available-slots`、`reschedule-slots`、`reschedule-recommendations` 必须共用同一套候选生成、冲突检测、碎片保护与评分口径，不能分别维护各自的可用性判断。
- 新预约自动确认与改签生效都必须在最终提交前再次校验资源占用变化；一旦并发状态变化，应立即重算，不得沿用过期候选。
- 改签真正生效时，必须在同一事务内原子完成旧占用释放、新占用锁定、结算归属迁移与审计写入，任一步失败整体回滚。
- `appointments` 上的 `reserved_start_at`、`reserved_end_at`、`occupied_end_at`、`settlement_status_snapshot` 仅承载快照；正式结算与补偿记录分别由 `appointment_settlements`、`appointment_compensations`、`appointment_delay_ledgers` 承载。
- 本章对应的实现承载位置见 `13.1 新预约`、`13.3 改签` 与 `13.8.1` 中的“预约确认与资源锁定模块”“可售时段与候选时段计算模块”。

## 7. 分阶段改签机制

### 7.1 更优的改签时间窗

原文档把改签从 `16:00` 才打开，这个设计并不最优。

更优方案应改为：

- `预约成功后` 到 `D-1 16:00`
- `D-1 16:00-18:00`
- `D-1 18:00` 至 `D` 营业开始前

也就是：

- 三类改签相关能力全程存在
- 但分阶段收紧

这样的好处是：

1. 更早开始消化碎片，而不是等到 `16:00` 后才被动修补。
2. 用户更少使用“取消后重下”这种更伤库存的操作。
3. 系统能在新预约持续进入前，先把已有预约往更优位置收敛。

### 7.2 三阶段改签策略

#### 阶段 A：自由调仓窗口

时间：

- `预约成功后` 至 `D-1 16:00`

规则：

- 允许取消
- 允许用户主动改签
- 允许商户保护性改签
- 允许系统优化性改签推荐
- 允许新预约
- 改签目标只要满足：
  - 严格无冲突
  - 不制造不可复用碎片
  - 排布评分不劣于当前时段
  - 即可自动批准

这个阶段的目标是：

- 尽早搬移边缘时段
- 提前填平孤岛空洞
- 优先用用户主动改签替代取消

#### 阶段 B：尾盘收敛窗口

时间：

- `D-1 16:00-18:00`

规则：

- 不允许取消
- 若未约满，允许新增预约
- 用户主动改签、商户保护性改签仍可用
- 系统优化性改签可推荐
- 但用户主动改签目标必须：
  - `score(target) > score(current)`
  - 即必须严格优于当前排布

这个阶段的目标是：

- 利用最后两小时把离散空洞向可售完整时段收敛
- 让改签和新增预约共同收口次日产能

#### 阶段 C：冻结前修复窗口

时间：

- `D-1 18:00` 至 `D` 营业开始前

规则：

- 不允许新预约
- 不允许取消
- 仅允许一次`用户主动改签`
- 商户保护性改签仍可用
- 改签目标必须满足：
  - 严格无冲突
  - 不制造碎片
  - `score(target) > score(current)`，或
  - 属于门店运营强制修复场景

运营强制修复场景示例：

- 原预约客服临时请假
- 原预约项目不可服务
- 门店主动发起保护性改签

这个阶段的目标是：

- 不再做大规模调仓
- 只做最后的优化和异常修复

### 7.3 哪种设计更能减少碎片

如果目标是“更有效减少预约时间段碎片”，三阶段方案优于“两段式晚间改签”的原因是：

1. 碎片不是在 `16:00` 之后才出现，而是在全天预约流入过程中持续产生。
2. 越早移动预约，越容易把多个小空洞合并为完整可售时段。
3. 若直到 `16:00` 才允许改签，很多本可提前修复的碎片已经失去再利用机会。

所以更优的原则是：

- `越早开放改签，越有利于碎片治理`
- `越接近服务日，越要限制改签自由度`

### 7.4 用户主动改签机会的定义

“一次改签机会”只针对`用户主动改签成功`，并且以预约根单为单位，而不是以预约记录行为单位。

建议引入：

- `booking_root_id`
- `reschedule_count`
- `reschedule_used_at`

规则：

- 初始预约：`reschedule_count = 0`
- 成功执行一次用户主动改签后：`reschedule_count = 1`
- 此后用户再次主动改签，直接拒绝
- 但在成功发生前，若申请未通过系统算法校验，则不累计 `reschedule_count`
- 只要仍在用户主动改签窗口内（第一版统一截止到 `D` 营业开始前），用户即可继续重新申请

但以下两类改签不消耗 `reschedule_count`：

- `商户保护性改签`
- `系统优化性改签`

说明：

- 商户保护性改签是商户为修复自己责任或资源异常而发起，不应占用用户机会。
- 系统优化性改签只能做推荐，不会直接改写预约，因此也不应消耗用户机会。

### 7.5 改签执行方式

当前项目已有“旧预约关闭 + 新预约生成 + 建立替代关系”的链路，这条链路可以保留。

新规则下需要增加两点：

1. 改签不会再次扣减资产。
2. 改签后原预约的预约结算凭证整体迁移到新预约，或由根单级结算记录继续关联。

适用说明：

- `用户主动改签`
  - 走系统校验后自动生效的正式改签提交流程
- `商户保护性改签`
  - 走“提议 -> 用户确认 -> 生效”的正式流程，但必须附带补偿和审计字段
- `系统优化性改签`
  - 只产出推荐，不直接提交改签结果

## 8. 按卡型分层预约结算

### 8.1 必须把资产扣减从核销链路中拆出来

当前项目是“到店核销 -> 扣次 -> 建单”。

新规则要求变为：

- `预约成功 -> 次卡扣次 / 额度卡冻结`
- `到店签到 -> 建单`

因此必须把“预约资产结算”从现有 `verify/commit` 流程中拆出，形成独立结算能力。

### 8.2 新的资产语义

预约成功后：

- 次卡：立即扣减 1 次
- 额度卡：优先采用“先冻结、后转实扣”

如后续在 `16:00` 之前取消：

- 次卡原路返还
- 额度卡解冻

如后续未取消，哪怕用户没有到店：

- 次卡扣减仍然有效
- 额度卡在超过取消窗口且最终未到店时，自动从冻结转为扣减

### 8.3 新的结算对象

建议新增正式表：

- `appointment_settlements`

字段建议：

- `id`
- `appointment_id`
- `booking_root_id`
- `merchant_id`
- `user_id`
- `card_id`
- `asset_type`
  - `times`
  - `amount`
- `consumed_value`
- `status`
  - `consumed`
  - `refunded`
  - `transferred`
- `refunded_at`
- `transferred_to_appointment_id`
- `created_at`

设计意图：

- 次卡支持预约成功即消费一笔
- 额度卡支持预约成功先冻结
- 取消时可退款或解冻
- 改签时不重复扣减，只转移归属

### 8.4 到店后的处理

到店后不再走“扣次型核销”语义，而是走“签到建单”语义：

- 用户在可到店窗口内生成预约签到码
- 商户必须扫码用户预约签到码
- 系统校验预约状态和到店时间
- 创建 `ServiceSession`
- 不再重复扣减卡资产

  这意味着：

  - 预约用户的签到入口应和普通现场核销入口分开
  - 或者在现有核销入口中识别 `appointment_settlement_id`，避免再次扣减

### 8.5 用户是否到店的判定口径

商户违约补偿、拖堂补偿、用户迟到、用户未到店等判断，都依赖统一的“到店事实”定义。

推荐统一以“预约签到成功”作为用户到店的唯一强事实来源：

- 用户到店后，由商户扫码预约签到码
- 系统校验预约状态和到店时间
- 成功创建 `ServiceSession`
- 同时写入 `actual_arrived_at`
- 该笔预约才视为“用户已到店”

因此统一口径如下：

- 已到店：存在有效 `actual_arrived_at`
- 未到店：直到 `reserved_end_at` 仍不存在有效 `actual_arrived_at`

补充说明：

- 口头到店、线下沟通、电话说明，不作为系统自动归责的强事实依据
- 商户端不得对 `confirmed` 预约提供“裸点即签到建单”的直达入口
- 商户端可以提供“去扫码签到”入口，但最终必须以扫码预约签到码成功为准
- 若商户主张用户已到店但系统无签到记录，则只能走人工申诉或补录审计，不进入自动补偿主链
- 若后续需要支持“到店但扫码失败”的兜底场景，应单独增加人工补签到留痕流程，而不应放宽自动判定口径

### 8.6 事务边界与结算迁移要点

- 本节真正需要统一的，不是单纯的扣减规则，而是“预约确认即结算/冻结、改签生效即迁移归属”的整套结算链路。
- 新预约确认成功时，次卡应立即扣次，额度卡应立即冻结；若预约在允许取消窗口内取消，则原路返还或解冻。
- 改签生效时不得重复扣减资产，而应迁移原结算归属，并同步回写 `appointment_settlement_id` 与 `settlement_status_snapshot`。
- 新预约确认、取消生效、改签生效都应在清晰事务边界内推进，避免出现资源已切换但结算未迁移、或结算已迁移但占用未切换的部分成功状态。
- 本章对应的实现承载位置见 `13.1 新预约`、`13.3 改签` 与 `13.8.1` 的“预约结算模块”。

## 9. 到店与迟到规则

### 9.1 预约服务窗口固定，不顺延

如果用户预约的是：

- `10:00 - 11:00`

用户 `10:20` 到店，则服务窗口仍然是：

- `10:20 - 11:00`

而不是：

- `10:20 - 11:20`

这是新方案下“预约资源锁定”的核心前提。

### 9.2 最低可服务时长阈值

定义：

- `min_serviceable_minutes = floor(project.duration / 2)`

命名关系说明：

- `min_serviceable_minutes` 表示规则层的最低可服务时长判定阈值
- `late_arrival_min_service_minutes` 表示该阈值在 `appointments` 表中的落库字段，用于固化预约创建当时的判定口径
- 若无特别说明，文中出现的 `min_serviceable_minutes` 默认指代其业务规则含义；实现落库时可映射到 `late_arrival_min_service_minutes`

若用户到店后的剩余可服务时长：

- `remaining_minutes = reserved_end_at - actual_arrived_at`

满足：

- `remaining_minutes >= min_serviceable_minutes`

则允许服务。

否则：

- 不再提供服务
- 预约关闭原因为 `service_denied_late`
- 不触发商户违约补偿

因为该情形属于用户迟到导致无法履约，不是商户违约。

示例：

- 项目时长 `45` 分钟
- `min_serviceable_minutes = floor(45 / 2) = 22`
- 若到店后剩余 `22` 分钟，仍可继续提供剩余服务
- 若到店后剩余不足 `22` 分钟，则不再提供服务，改走用户违约流程

### 9.3 迟到但仍可服务时的履约规则

当用户迟到但仍超过最低阈值时：

- 允许服务
- 服务结束时间仍以 `reserved_end_at` 为准
- 不因用户迟到延后后续预约
- 商户不得因此挤占下一位预约用户

### 9.4 迟到判定实现要点

- 本节的核心判定，是基于 `remaining_minutes` 与 `min_serviceable_minutes` 的迟到后可服务性计算，而不是现场人工裁量。
- `actual_arrived_at` 必须以签到成功作为唯一强事实来源；若不存在有效签到记录，则不能进入“已到店但迟到”的自动判定链路。
- `min_serviceable_minutes` 的规则口径应在预约创建时固化到 `late_arrival_min_service_minutes`，避免项目时长、规则配置后续变化造成历史预约判定漂移。
- 当 `remaining_minutes < min_serviceable_minutes` 时，应统一关闭为 `service_denied_late`，并明确不触发商户违约补偿。
- 本章对应的实现承载位置见 `13.4 到店签到` 与 `13.8.2` 中 `actual_arrived_at`、`actual_start_at`、`late_arrival_min_service_minutes` 的字段定义。

## 10. 商户未服务与拖堂补偿

### 10.1 补偿拆成两类

本方案把补偿拆为两类：

1. `商户违约补偿`
2. `拖堂占用补偿`

两类都要结构化落库，但结算方式不同。

### 10.2 商户违约补偿

 统一原则改为：
 
 - 只要属于商户侧无法按原预约承诺履约
 - 就必须进入结构化归责链路
 - 系统最终只会收敛到 `merchant_breach` 或 `merchant_failure_offset`
 - 商户已先取消、已先报备或已先发起改签，都不构成自动免责
 
 但“最终无法履约”的判定，不能在 `reserved_start_at` 一到就立即下结论，而应采用：
 
 - `风险锁定 + 服务窗口结束判定`

原因：

- 若只看 `reserved_start_at`，无法区分“商户短时异常后恢复资源”与“用户随后迟到/未到店”
- 也无法区分“最终未履约”与“只是延迟开始、应走拖堂补偿”

因此建议新增两个核心概念：一个结构化风险标记、一个最终判定时点：

- `merchant_breach_pending`
  - 表示：商户责任风险已出现，但尚未完成最终归责
  - 类型：预约异常归责链路中的风险标记或中间状态，不属于预约正常履约主流程状态
- `breach_decision_at = reserved_end_at`
  - 表示：商户违约补偿的默认最终判定时点，取该预约服务窗口结束时刻

商户违约补偿的具体规则如下：

- 次卡：返还本次并补 1 次
- 额度卡：返还本次并补 1 次等价额度或等价值补偿

这类补偿统一属于“商户违约补偿”，建议写入现有 `appointment_compensations`，并新增原因类型：

- `merchant_breach`

对于“用户未到店，但商户已正式提出取消或保护性改签，用户未接受，最终只恢复用户本次损失而不追加额外补偿”的场景，建议单独增加原因类型：

- `merchant_failure_offset`

该原因类型用于表示：

- 商户侧已出现明确无法按原预约履约的异常
- 但由于用户最终未到店，事实链不足以支持完整 `merchant_breach`
- 因此只做“恢复性对冲结算”，不做“返还 + 额外补 1 次”的完整商户违约补偿

### 10.3 商户违约补偿适用场景与触发时机

包括但不限于：

- 商户保护性改签被用户拒绝且原预约已无法履约
- 客服临时请假或离岗导致最终无法履约
- 商户未按原预约提供服务
- 非特殊资源违约导致原预约无法继续履约

#### 10.3.1 风险锁定时机

当出现以下组合条件时，系统先把预约标记为 `merchant_breach_pending`，但此时不立即发放补偿：

- 商户已确认原预约客服临时请假、离岗、项目不可服务或其他商户侧资源异常
- 且取消未成功
- 且保护性改签未成功或被用户拒绝
- 且原预约仍暂时保留，等待观察最终是否还能履约

该阶段只做：

- 锁定商户责任风险
- 预生成补偿方案
- 记录商户异常说明、用户反馈和审计留痕

适用边界：

- `merchant_breach_pending` 只适用于“原预约仍保留、系统仍需观察是否最终履约”的场景
- 若商户侧取消已正式生效，且商户已确认无法按原预约履约，则不再等待 `breach_decision_at`；系统应在取消生效事务内直接完成退款/解冻、补偿落账与终态收敛
- `merchant_failure_offset` 仅适用于预约未提前取消成功、但商户已正式披露无法履约且用户最终未到店的观察后场景

该标记在以下任一情形下退出：

- 预约已在窗口内实际开始服务，则退出风险标记，不触发商户违约补偿
- 商户已恢复到可履约状态，且最终归责落到用户未到店或用户迟到，则退出风险标记，不触发商户违约补偿
- 到达 `breach_decision_at` 后满足完整商户违约条件，则转入 `merchant_breach`
- 到达 `breach_decision_at` 后满足恢复性对冲结算条件，则转入 `merchant_failure_offset`

实现约束：

- `merchant_breach_pending` 一旦进入，必须在当前预约服务窗口闭合前或闭合时收敛到最终结果，不得在 `breach_decision_at` 之后长期停留
- 最终结果只允许为以下三类之一：风险解除并清除标记、转入 `merchant_breach`、转入 `merchant_failure_offset`
- 状态推进必须具备幂等语义；重复执行判定或补偿任务时，不得重复发放补偿，也不得生成冲突的最终归责结果
- 商户异常上报、取消申请处理、保护性改签处理、预约签到成功、最终补偿结算这几类动作发生后，服务端都必须重新评估当前预约是否仍处于 `merchant_breach_pending`，并在满足退出条件时立即推进到对应最终结果
- 若前述在线动作未完成最终收敛，服务端必须在 `breach_decision_at` 到达后通过补偿任务再次执行最终判定，确保不存在“窗口已结束但仍停留在风险标记”的预约

#### 10.3.2 最终判定窗口

商户违约补偿不在 `reserved_start_at` 立即触发，而是默认观察整个预约服务窗口：

- 观察区间：`[reserved_start_at, reserved_end_at)`
- 默认最终判定时点：`breach_decision_at = reserved_end_at`

在这个观察窗口内，系统持续记录 3 类事实：

- 商户资源是否恢复到可履约状态
- 用户是否到店，以及到店时剩余可服务时长是否仍满足 `min_serviceable_minutes`
- 预约是否已实际开始服务，即是否生成有效 `actual_start_at`

其中，“商户资源已恢复到可履约状态”必须按结构化事实判定，至少同时满足以下条件：

- 对应预约在当前时点存在可执行的服务资源，而不是仅有商户侧口头说明或主观判断
- 该资源可以在当前预约剩余窗口内实际开始服务
- 开始后仍满足 `remaining_minutes >= min_serviceable_minutes`
- 恢复结果已形成系统内可审计记录，可用于后续归责与对账

这样设计的目的，是把以下几种情形清晰区分开：

- 商户短时异常后恢复，但用户后来迟到或未到店
- 商户虽晚开始，但最终仍完成履约
- 商户在整个服务窗口内始终未恢复到可履约状态

#### 10.3.3 到 `reserved_end_at` 时的最终归责规则

到达 `breach_decision_at` 后，按以下顺序判定：

1. 若预约已在窗口内实际开始服务：
   - 不触发商户违约补偿
   - 若 `actual_start_at > reserved_start_at` 且延迟原因为商户责任，则改记`拖堂占用补偿`
2. 若用户首次到店时，`remaining_minutes < min_serviceable_minutes`：
   - 视为用户迟到导致无法履约
   - 关闭原因为 `service_denied_late`
   - 不触发商户违约补偿
3. 若商户在观察窗口内已恢复到可履约状态，但用户始终未到店，或到店时已低于最低可服务阈值：
   - 视为用户未到店或用户迟到责任
   - 不触发商户违约补偿
4. 若用户在窗口内曾到店，且到店时仍满足 `remaining_minutes >= min_serviceable_minutes`，但商户直到 `reserved_end_at` 仍未能开始服务：
   - 视为商户违约
   - 自动触发 `merchant_breach` 补偿
5. 若用户在整个窗口内始终未到店：
   - 默认不直接认定为 `merchant_breach`
   - 因缺少用户实际到店事实，无法可靠证明商户在用户真实到店时点仍不可履约
6. 但若同时满足以下条件：
   - 商户已在预约前或服务窗口内明确申报无法按原预约履约，并完成留痕
   - 商户已发起取消申请
   - 若存在可行替代时段，商户也已发起保护性改签提议
   - 用户对上述取消申请和保护性改签提议均未接受
   - 用户最终仍未到店
   - 则进入“恢复性对冲结算”，而不是完整 `merchant_breach` 补偿

恢复性对冲结算规则：

- 保留用户预约成功时已发生的原始扣减或冻结转实扣结果
- 同时由商户侧生成 `1` 次等值恢复性补偿，用于冲回本次用户损失
- 最终用户净结果为“本次未被实际扣损”，但不额外多得 `1` 次
- 商户承担的是“恢复用户本次损失”的责任，而不是“额外赔付一份惩罚性补偿”

这样处理更公平，原因是：

- 用户未到店时，系统无法对“商户在用户真实到店时是否仍不可履约”做强事实判断
- 若直接判完整商户违约并执行“返还 + 额外补 1 次”，会过度有利于未到店用户
- 若完全按用户未到店处理并保留扣次，又会忽略商户已提前声明无法履约的事实
- 因此在“商户已明确申请取消/改签、用户拒绝、最终未到店”的交叉场景下，以“只恢复本次损失、不追加额外补偿”最平衡

#### 10.3.4 用户未到店场景的证据边界

对于用户在整个预约服务窗口内未到店的场景，系统不得仅依据“商户整窗均未恢复到可履约状态”这一事实，自动判定完整商户违约。

规则说明：

- 用户未到店时，平台缺少“用户真实到店时点”这一关键事实，无法自动证明商户在该时点仍不可履约
- 即使商户内部记录显示整窗资源异常，也不足以替代用户实际到店这一强事实
- 若将商户事后补充的线下说明、聊天截图、口头证明等非结构化材料纳入自动规则，会显著提高系统复杂度，并削弱正式留痕约束

自动归责结论统一收敛为：

- 用户到店且商户未服务：可以判定完整商户违约
- 用户未到店，但商户已正式发起取消申请或保护性改签提议且用户未接受：仅执行恢复性对冲结算
- 用户未到店，且商户不存在充分的前置留痕：按单纯用户未到店场景处理，不触发商户补偿

自动规则的证据边界限定为：

- `merchant_failure_offset` 仅采纳系统内已留痕的取消申请、保护性改签提议、用户拒绝结果等结构化强事实
- 不采纳商户在事后补交的线下说明、聊天截图、口头证明等非结构化材料作为自动补偿触发条件
- 法定不可抗力或平台级事故如需救济，应走独立流程，不纳入本规则的常规自动归责链路

实施约束：

- “恢复性对冲结算”建议写入 `appointment_compensations`，原因类型使用 `merchant_failure_offset`
- 不使用 `merchant_breach` 记录该类场景
- 后续在报表、责任统计、客服/月度违约考核中，应将“完整商户违约”与“证据不足但需恢复用户本次损失的对冲场景”明确区分

#### 10.3.5 商户已实际无法履约，但未向用户提出取消或改签申请时如何处理

若商户内部已发生客服临时请假、离岗、项目不可服务等异常，但商户未正式向用户提出取消申请或保护性改签提议，则系统按以下规则处理：

1. 用户已到店：
   - 若到店时仍满足 `remaining_minutes >= min_serviceable_minutes`，但商户无法开始服务
   - 仍按完整商户违约处理
   - 触发 `merchant_breach`
2. 用户未到店：
   - 默认不触发 `merchant_breach`
   - 也不进入 `merchant_failure_offset`
   - 按单纯用户未到店场景处理

规则说明：

- 商户未发起取消申请或保护性改签提议，说明系统侧不存在“商户已提前正式披露无法履约”的有效通知链
- 在用户未到店前提下，平台既无法证明商户最终一定不能服务，也无法证明用户是因商户通知而放弃到店
- 旧规则在局部 `no_show` 场景下，确实存在“商户未报备且用户未到店时，商户结果可能更有利”的收益偏差
- 但该收益偏差是否足以构成主导激励，仍取决于多个现实因素，包括：用户到店概率、商户对用户行为的预期，以及商户对完整违约赔付的厌恶程度
- 从真实业务看，商户在异常发生时通常并无法准确预知用户是否会到店；一旦用户正常到店且商户仍无法履约，商户将承担更重的完整违约成本，因此该收益偏差未必会主导商户行为
- 若进一步将“未报备但事后可举证”的情形纳入常规人工仲裁或自动恢复，会显著增加争议处理成本，并削弱商户按流程提前报备的约束力

实施约束：

- 只有商户先完成正式取消申请或保护性改签提议留痕，后续才有资格进入 `merchant_failure_offset` 的恢复性对冲结算
- 若商户未做该动作，则用户未到店场景一律不自动补偿
- 第一版不额外保留“未报备但事后举证”的常规人工仲裁层；极端不可抗力或平台级事故按独立救济流程处理

### 10.4 拖堂占用补偿

若商户因上一个服务或其他商户责任原因，导致预约客户实际开始服务时间晚于预约开始时间，则计算占用补偿。

补偿分钟定义：

- 若 `delay_minutes <= 1`，不补偿
- 若 `delay_minutes > 1`，补偿分钟数记为完整的 `delay_minutes`

示例：

- 晚 1 分钟：不记账
- 晚 5 分钟：记 5 分钟

### 10.5 拖堂补偿账本

现有 `appointment_compensations` 不适合直接承载“分钟累计阈值发奖”，建议新增：

- `appointment_delay_ledgers`

字段建议：

- `id`
- `appointment_id`
- `booking_root_id`
- `merchant_id`
- `user_id`
- `card_id`
- `project_id`
- `service_session_id`
- `technician_id`
- `scheduled_start_at`
- `actual_start_at`
- `delay_minutes`
- `credited_minutes`
- `service_duration_minutes`
- `unit_compensation_value`
- `created_at`

其中：

- `delay_minutes` = 实际晚点分钟
- `credited_minutes` = 实际计入补偿账本的分钟

### 10.6 累计发放规则

建议按 `card_id + merchant_id + project_id` 维度累计补偿桶。

默认推荐模型：

- 次卡项目：
  - 当累计补偿分钟 `>= project.duration`
  - 自动补 1 次
  - 并从补偿桶中扣掉一个 `project.duration`
- 额度项目：
  - 每次拖堂折算货币补偿值：
    - `credited_amount = ceil(unit_amount * credited_minutes / project.duration)`
  - 当累计金额 `>= unit_amount`
  - 自动补 1 个服务单位额度

但优化版方案下，这里不再写死为唯一规则，而是允许由项目配置决定：

- `minutes_bucket`
- `amount_bucket`
- `fixed_unit`

### 10.7 卡耗尽后的 60% 规则

`60%` 规则保留为默认推荐值，而不是唯一强制值。

默认建议：

- 当卡已经消费完成后：
  - 若剩余补偿桶 `>= 60%` 的一个服务单位
  - 系统仍自动补 1 次或 1 单位额度
- 若不足 `60%`：
  - 系统只保留账本和统计
  - 不再自动补
  - 交由商户与用户线下协商

如果项目级配置显式覆盖，则以项目级配置为准。

### 10.8 客服临时请假的内部责任承担规则

虽然用户侧统一按“商户违约补偿”处理，但对于客服临时请假或离岗导致的违约，内部责任承担仍按月度规则区分：

#### 第 1 次

- 该客服每自然月有 `1` 次免责机会
- 该次违约造成的补偿损失由商户承担
- 仍需完整记录到 `merchant_id + technician_id` 内部责任账本

#### 第 2 次及之后

- 该客服当月超过 `1` 次后
- 该次违约造成的补偿损失由该客服承担
- 系统继续按 `merchant_breach` / `merchant_failure_offset` 的最终归责结果向用户结算
- 但内部责任账本标记为 `technician_chargeable`

说明：

- 上述“次数”只统计“临时请假/离岗 + 改签失败 + 最终未履约”的事件。
- 若保护性改签成功，不计入本月次数。
- 责任承担差异只影响商户与客服内部对账，不影响用户侧补偿口径。

### 10.9 不可抗力下的违约补偿撤销

当出现法定不可抗力，或商户因公共设施突发故障如停水、停电等导致一方违约时，系统允许发起“撤销违约补偿申请”流程。

规则：

- 可由商户或用户向对方发起申请
- 只有双方确认一致属于不可抗力时
- 才可撤销对应一方的违约补偿

第一版建议：
- 先落申请、确认、留痕能力
- 不直接接入平台裁决
- 后续再增加平台级投诉或裁决功能

### 10.10 违约裁决与任务调度要点

- 本节的核心判定，是围绕 `merchant_breach_pending` 与 `breach_decision_at` 展开的最终归责链路，而不是在 `reserved_start_at` 即时下结论。
- 在线动作与异步任务必须共用同一归责口径：商户异常上报、取消申请、保护性改签、签到成功、开始服务、窗口结束后的补偿任务，都应推动同一条归责链路收敛。
- `runMerchantBreachCompensation` 应负责对已到达 `breach_decision_at` 但尚未完成最终归责的预约做兜底收敛，并通过幂等键防止重复补偿或重复写终态。
- 自动归责只应采纳系统内结构化强事实，例如取消申请、保护性改签提议、用户接受/拒绝、签到与开始服务时间；线下说明、聊天截图、口头证明不应进入常规自动补偿主链。
- 本章对应的实现承载位置见 `13.5 补偿` 与 `13.8.1` 的“补偿与责任结算模块”“任务与重试模块”。

## 11. 对当前调度与会话链路的重构建议

本章对预约与服务会话状态的设计采用“最小状态集”原则。新增状态必须先满足以下硬标准，且该标准作为后续所有状态扩张讨论的统一约束条件：

1. 新状态必须对应一个稳定、可重复判定、可审计的业务事实，而不能只是对同一事实的展示细分、操作习惯差异或临时人工感知。
2. 新状态必须显著改变后续系统行为，至少影响以下事项之一：权限控制、计时规则、资源占用规则、补偿归责规则、自动流转规则、对账统计口径。
3. 新状态必须具备明确且可实现的进入条件、退出条件、超时处理、失败回退和幂等语义，不能形成长期停留的模糊中间态。
4. 新状态必须证明无法被“现有状态 + 字段补充 + 审计事件 + 操作留痕”以更低复杂度表达；若仅用于描述准备动作、人工介入过程或局部执行细节，则原则上不得升级为主流程状态。

只有当上述条件同时满足时，才允许把某一业务情形升级为新的正式状态。若任一条件不满足，则不得新增状态，而应优先通过以下方式表达：

- 复用现有状态机
- 补充结构化字段
- 增加审计事件与用户确认留痕
- 在异常闭环中处理，而不是扩张主流程状态

以上硬标准同时适用于两类状态：

- 预约或服务会话的主流程状态
- 独立业务记录的生命周期状态

但两者必须严格区分：主流程状态应从严控制数量；独立记录状态只有在该记录本身需要形成正式闭环、且状态转移语义明确时才允许设计。不得以新增记录状态为名，变相扩张预约主流程状态。

因此，本方案对“到店后待开服务”“人工介入协调”“中途接力处理”等场景，不默认新增状态；除非后续证明这些场景满足上述全部硬标准，否则一律按现有状态、字段与异常留痕机制承载。

### 11.1 废弃 `appointment_waiting` 作为预约常态分支

在新方案下，预约成功意味着预约时段内客服不可被其他单占用，因此：

- `appointment_waiting` 不应再作为“预约客户到店后正常等待前序现场单”的主路径

保留它只用于异常兼容场景：

- 历史脏数据
- 人工误操作
- 非预约资源占用修复

正常情况下，预约到店应直接进入：

- `room_selecting`
- `start_pending`
- `serving`

其中 `room_selecting`、`start_pending`、`serving` 应视为服务会话的既有执行状态或等价执行阶段，用于表达“已到店但未开始服务”和“已开始服务”的处理链路，不构成新增预约主流程状态；若现网已有等价状态，应直接复用，不再新增新的预约等待状态。

而不是进入 `appointment_waiting`。

### 11.2 自动派单必须复用预约锁定规则

当前项目里，系统自动派单和用户手动选客服存在规则不一致的问题。

新方案必须强制收敛为一套：

- 只要客服在预约占用窗口内有预约
- 自动派单就不能把该客服分配给其他用户

不存在：

- 手动不行，自动可以
- 前端看不到，调度器还能分过去

### 11.3 预约签到和现场核销分流

建议在服务会话工厂层面区分两条入口：

1. `walk_in_checkin`
2. `appointment_checkin`

其中：

- `walk_in_checkin` 才会触发资产扣减
- `appointment_checkin` 只校验预约结算记录和到店时效

这里的 `walk_in_checkin` 与 `appointment_checkin` 属于入口类型和处理链路划分，不属于新增状态；其目的在于分流结算与校验责任，而不是把入口差异建模为新的主流程状态。

### 11.4 客服请假、离岗与预约异常闭环

新方案必须显式处理三类异常：

1. `D-1` 已知次日请假
2. `D` 营业前临时请假
3. 服务中途离岗或提前下班

统一原则：

- 不再依赖客服逐单确认预约
- 依赖“次日可预约排班发布”作为预约前置条件
- 一旦发布后又发生请假或离岗，必须走保护性改签或取消补偿闭环
- 保护性改签失败后，用户侧统一走商户违约补偿
- 客服临时请假导致的责任承担，再按该客服当月免责次数区分商户承担或客服承担
- 对人工介入、中途接力、请假协调等场景，优先通过 `disruption_status`、审计事件和用户确认留痕收口，不新增“待接力”“人工处理中”等执行主状态
- “已发布后确认请假”统一指：排班已发布为可预约、用户已可见并可下单、后续又确认请假、且请假区间与已发布可预约区间重叠
- 对该场景，系统必须先止血、再修复、最后收敛，不得一边继续放新预约、一边延迟处理已受影响预约

#### 已发布后确认请假异常修复流程

触发条件：

- 某客服的次日排班已处于可预约状态
- 用户已经可以看到并创建该日期预约
- 之后该客服明确确认请假
- 请假时段与已发布可预约时段存在交集

处理目标：

- 立即停止新增风险，不再让新预约落入受影响时段
- 优先修复已受影响预约，先处理已确认预约，再考虑普通新预约
- 尽量最小扰动，优先同日、同商户、等价或更优替代
- 保留责任闭环；若无法修复，最终必须进入商户侧异常归责或补偿链路

标准流程：

1. 排班侧立即收口：在客服确认请假后，系统应立刻将对应 `technician_schedule_publishings` 标记为 `leave_confirmed`，记录 `leave_reason` 与 `updated_at`，并将请假区间内的可预约时段从候选可售结果中下线；这一步的目标是先止血，而不是先补偿。
2. 锁定受影响预约范围：系统必须扫描请假区间内所有未来预约，筛出服务日期命中请假日期、预约状态仍可履约、预约时段与请假区间重叠、且尚未取消或完成的预约，形成 `AFFECTED_APPOINTMENTS`。
3. 冻结修复容量：系统应在同商户、同日、可承接该服务的其他客服或时段中，先计算 `repair_capacity_pool`，再按优先级冻结一批 `protected_repair_slots`；在这些槽位释放前，普通新预约自动确认、普通用户主动改签与系统优化性改签不得占用。
4. 逐单尝试修复：系统必须按“同商户同日其他客服等价时段 -> 同商户同日邻近时段 -> 同商户跨日可接受时段”的顺序，为每笔受影响预约生成修复候选；若候选可执行且不会引入第二个受影响预约，则创建保护性改签提议。
5. 用户响应分流：若用户接受保护性改签，系统必须原子完成旧占用释放、新占用锁定、结算归属迁移与异常状态收敛；若用户拒绝，则继续尝试该预约的其他可行候选；若不存在可行候选，则立即转入取消申请、商户违约补偿或其他已定义异常归责闭环。
6. 最终收敛：该流程最终只允许收敛到“修复成功”“预约取消并完成退款/解冻/补偿”“进入商户违约或失败补偿闭环”等可解释终态，不得长期停留在待人工判断或口头承诺状态。

#### 场景一：`D-1` 已知次日请假

处理方式：

1. 商户撤回该客服次日未开始的 `bookable` 时段。
2. 系统定位所有受影响的已确认预约。
3. 系统必须先按“同商户、同日、可承接服务且不引入第二受影响预约”的顺序，为受影响预约预留 `protected_repair_slots`；在这些槽位释放前，普通新预约自动确认、普通用户主动改签和系统优化性改签不得占用。
4. 系统为每笔受影响预约生成保护性改签候选时段，并对每个候选输出是否属于“高质量修复方案”的结构化判定结果。
5. 若 `now < reserved_start_at - 5h`，系统必须优先发起保护性改签；只有在不存在高质量修复方案时，商户方可走单方面取消。
6. 若 `now >= reserved_start_at - 5h`，系统必须优先发起保护性改签；只有在不存在高质量修复方案时，商户方可发起取消申请，不得单方面取消。
7. 商户发起`商户保护性改签`提议并附带补偿。
8. 用户确认后生效；若用户拒绝且无可替代时段，则按前述 `5` 小时阈值规则进入单方面取消、取消申请或商户违约补偿闭环。
9. 若局部重排与保护性改签候选均已穷尽，系统不得继续自动搬移其他已确认预约制造链式影响，而必须直接进入已定义的异常归责或补偿闭环。

#### 场景二：`D` 营业前临时请假

处理方式与场景一相同，但优先级更高：

1. 立即冻结该客服当日未开始预约的继续签到能力。
2. 立即冻结受影响区间对普通新预约自动确认、普通用户主动改签和系统优化性改签的占用能力，直至受影响预约完成修复或确认无解。
3. 立即触发保护性改签提议，并优先使用已保留的 `protected_repair_slots`。
4. 若 `now < reserved_start_at - 5h` 且不存在高质量修复方案，商户方可走单方面取消；若 `now >= reserved_start_at - 5h`，则不得单方面取消，只可发起取消申请。
5. 若距预约开始时间已很近且用户未及时确认，商户不得静默改派。
6. 若无法在服务前取得用户确认，且取消也未成功，则转入商户违约补偿闭环。

#### 场景三：服务中途离岗或提前下班

分两类处理：

1. `当前正在服务中的预约`
   - 默认不做强制换人继续服务
   - 若业务允许中途接力，必须用户明确同意并留痕
   - 若无法继续服务，按未服务或部分未服务规则补偿
2. `后续尚未开始的预约`
   - 立即转入保护性改签或取消补偿闭环

#### 闭环要求

以上三类异常最终只能落入以下结果之一：

- `用户确认保护性改签并成功改期`
- `预约取消并完成退款/解冻/补偿`
- `用户同意换人接续并留痕`

不允许长期停留在“线下口头承诺、系统状态不变”的中间态。

### 11.5 保护性改签失败后的补偿决策

当商户保护性改签失败且预约无法按原承诺履约时，系统必须按以下顺序收口：

1. 优先尝试保护性改签到其他客服
2. 若失败，则判断原预约是否还能按原承诺履约
3. 若不能履约，则由系统取消当前预约
4. 用户侧统一走商户违约补偿
5. 若原因是客服临时请假或离岗，再查询该客服当月免责次数并写入内部责任账本
6. 同步更新预约异常状态、用户端提示、责任账本和对账数据

### 11.6 非特殊资源违约的保护性改签处理规则

非特殊资源违约，指商户希望调整预约，但不属于客服请假、离岗、人员不可服务这类客观资源失效。

常见场景包括：

- 商户主动优化排布，想减少碎片或收紧空洞
- 项目服务能力或服务顺序调整，但仍具备履约可能
- 房间、工位、设备临时变化，但并非人员缺勤
- 历史排班或库存发布错误后的运营修正

这类场景的处理原则是：

- 不做级联重排
- 不压后续预约
- 不为修一张单破坏其他已确认预约的稳定性

#### 用户拒绝后的处理

当商户发起`非特殊资源违约`保护性改签，且用户拒绝时：

1. 系统先判断原预约是否仍可按原承诺正常履约。
2. 若仍可正常履约：
   - 原预约继续有效
   - 不重排后续预约
   - 给该预约打上高风险或人工关注标记
3. 若已不能正常履约：
   - 不对后续预约做算法重排
   - 由系统取消当前预约
   - 按`商户违约补偿`路径处理

#### 对排布和碎片的影响

用户拒绝后，系统允许保留局部碎片，但不允许引入全局链式碎片。

也就是说：

- 可以接受“当前这一块空洞没被修掉”
- 不接受“为了修这块空洞把后面一串预约全部打乱”

### 11.7 保护性改签的最终收口规则

不论保护性改签属于特殊资源违约还是非特殊资源违约，系统最终都按下面的统一顺序收口：

1. 商户发起保护性改签提议
2. 用户确认或拒绝
3. 若用户确认：
   - 改签生效
4. 若用户拒绝：
   - 先判断原预约是否还能正常履约
   - 能履约：保留原预约
   - 不能履约：系统取消并进入对应补偿流程

补偿分流规则：

- 用户侧：
  - 统一走商户违约补偿
- 内部责任侧：
  - 若属于客服临时请假或离岗
    - 第 `1` 次由商户承担
    - 第 `2` 次及之后由客服承担
  - 其他商户违约原因由商户承担

写入/收敛口径：

- 商户发起保护性改签提议时，写入 `disruption_status = reschedule_proposed`，并同步写入 `disruption_reason` 与补偿/审计说明
- 用户确认商户保护性改签后，写入 `disruption_status = reschedule_accepted`

- 最终补偿归责确定时，写入 `compensation_strategy`，并确保异常闭环字段同步收敛到可解释终态

这里的 `disruption_status` 属于预约异常闭环字段，用于表达改签/取消/补偿处理进度，不等同于预约正常履约主流程状态。其设计直接影响异常流转、补偿归责与审计留痕，且状态边界清晰，因此符合前述新增状态硬标准。

实现约束：

- `disruption_status` 仅用于表达异常处置进度，不得替代预约正常履约主流程状态
- 当预约已进入最终结果，如改签成功、取消完成、`merchant_breach` 或 `merchant_failure_offset` 已确定时，异常闭环字段也必须同步收敛到可解释终态，不得长期停留在 `reschedule_proposed`、`reschedule_rejected` 等中间值
- 主流程结果、补偿结果与 `disruption_status` 之间不得出现相互矛盾的组合

  - 自动锁定具体客服和时段
  - 成功确认时立即完成对应的预约结算记录
  - 同时写入 `booking_root_id`、`late_arrival_min_service_minutes` 与初始 `reschedule_count = 0`
  - 若生成预约结算记录，则同步写入 `appointment_settlement_id` 与 `settlement_status_snapshot`
  - 服务端必须在同一事务内再次校验排班发布状态、预约窗口、资源未被并发占用后方可确认成功

### 13.2 取消

- `POST /user/appointments/:id/cancel`
  - 只允许 `now < cancel_deadline_at`
  - 取消后原路退款或解冻
  - 同步更新 `settlement_status_snapshot`
  - 服务端必须强制拒绝超窗取消请求，不能仅依赖前端隐藏入口
- `POST /merchant/appointments/:id/cancel`
  - 仅允许在预约开始前 `5` 小时以上由商户单方面取消
  - 必填正当取消理由
  - 取消生效时立即退款或解冻，并同步更新 `settlement_status_snapshot`
  - 若取消原因属于商户侧无法按原预约履约，则必须在同一事务内继续完成对应补偿落账或归责收敛，不得出现“已取消但未归责”
  - 用户可保留抗辩记录
  - 取消成功后写入 `disruption_status = merchant_canceled`、`merchant_cancel_reason`、`canceled_by_type`、`canceled_by_id`，并同步更新 `settlement_status_snapshot`
- `POST /merchant/appointments/:id/cancel-request`
  - 仅允许在预约开始前 `5` 小时及以内由商户向用户申请取消
  - 与商户单方面取消互斥，同一预约在同一时点只能存在一种取消路径
- `POST /user/appointments/cancel-requests/:id/accept`
  - 用户同意商户取消申请
  - 若取消最终生效，则同步将异常闭环收敛到 `merchant_canceled`，并更新 `settlement_status_snapshot`
  - 若商户已正式确认无法按原预约履约，则必须在同一事务内完成对应补偿落账或归责收敛
- `POST /user/appointments/cancel-requests/:id/reject`
  - 用户拒绝商户取消申请
- `POST /user/appointments/:id/rebuttal`
  - 用户补充对商户单方面取消的抗辩意见
  - 写入或更新 `user_rebuttal_note`

- `GET /user/appointments/:id/reschedule-eligibility`
  - 改为“三阶段改签窗口”模型
- `GET /user/appointments/:id/reschedule-slots`
  - 用户主动改签：
    - 阶段 A：返回“优于当前”与“不劣于当前”的时段，默认优先展示更优时段
    - 阶段 B/C：只返回“严格优于当前”的时段
  - 商户保护性改签：
    - 返回可执行且不引入第二受影响预约的修复时段
  - 系统优化性改签：
    - 只返回推荐时段，不提供自动提交能力
- `POST /user/appointments/:id/reschedule`
  - 仅用于用户主动改签
  - 事务内再次校验
  - 校验通过后直接生效
  - 仅“成功生效”计入一次改签机会
  - 若未成功，只要仍在用户主动改签窗口内，即可继续重新申请
  - 不重复扣减资产
  - 迁移结算归属
  - 成功生效后保持 `booking_root_id` 不变，并递增 `reschedule_count`
  - 若结算归属发生迁移，必须同步更新 `appointment_settlement_id` 与 `settlement_status_snapshot`
  - 改签生效必须原子完成旧占用释放、新占用锁定、结算归属迁移和审计记录写入，任一步失败都不得留下部分成功状态
- `POST /merchant/appointments/:id/protective-reschedule`
  - 仅用于商户保护性改签
  - 必填补偿和审计说明
  - 写入 `disruption_status = reschedule_proposed` 及相关异常原因/审计信息
  - 只创建提议，不直接生效
- `POST /user/appointments/reschedule-requests/:id/accept`
  - 用户确认商户保护性改签
  - 生效后写入 `disruption_status = reschedule_accepted`
- `POST /user/appointments/reschedule-requests/:id/reject`
  - 用户拒绝商户保护性改签
  - 写入 `disruption_status = reschedule_rejected`
- `GET /user/appointments/:id/reschedule-recommendations`
  - 仅用于系统优化性改签推荐
  - 默认关闭
  - 只返回推荐，不返回可直接执行结果

实现约束：

- `GET /user/appointments/:id/reschedule-slots` 在保护性改签场景下，必须优先返回 `protected_repair_slots` 中的可执行修复方案，并给出是否属于“高质量修复方案”的结构化字段
- `POST /user/appointments/:id/reschedule` 处理用户主动改签时，必须避让已保留给受影响预约修复使用的 `protected_repair_slots`
- `GET /user/appointments/:id/reschedule-recommendations` 在存在异常修复事件时，只能在不影响受影响预约修复成功率的前提下返回推荐时段，不得抢占修复容量
- 自动确认、改签自动审核与重排推荐三类算法必须共享同一套冲突检测、碎片判定和“是否引入第二受影响预约”的判断结果，不得出现在线接口和后台任务算出不同候选集的情况
- 第一版重排只允许局部重排：仅能为当前受影响预约生成替代候选，不得自动链式搬移其他已确认预约

### 13.4 到店签到

建议新增：

- `POST /merchant/appointments/:id/check-in`

语义：

- 只校验预约是否可签到
- 创建 `ServiceSession`
- 不重复扣减卡资产
- 签到成功时必须写入有效 `actual_arrived_at`，作为用户已到店的结构化强事实
- 实际开始服务后由服务会话开单/上钟动作写入 `actual_start_at`；`actual_arrived_at` 与 `actual_start_at` 不得混用

### 13.5 补偿

建议新增系统任务或服务端自动触发：

- `runMerchantBreachCompensation`
- `runAppointmentDelayLedgerSettlement`
- `runLeaveDisruptionLiabilitySettlement`

实现约束：

- `runMerchantBreachCompensation` 必须负责对已到达 `breach_decision_at` 且尚未完成最终归责的预约执行最终判定，并将结果收敛到“风险解除”“`merchant_breach`”或“`merchant_failure_offset`”之一
- 每个任务都必须定义明确的触发条件、重复执行策略与幂等键
- 同一预约、同一补偿原因、同一结算周期内，不得因任务重试、并发执行或补偿回放而重复发放补偿
- 补偿任务落账后，必须与最终归责结果、异常闭环字段和责任账本保持一致

### 13.6 排班发布与请假

建议新增：

- `POST /merchant/schedules/publish-next-day`
  - 发布次日可预约排班
- `POST /merchant/schedules/:id/withdraw`
  - 撤回未开始的可预约排班
- `POST /merchant/schedules/:id/leave`
  - 标记客服请假并触发受影响预约扫描
- `GET /merchant/schedules/affected-appointments`
  - 查看受影响预约列表和保护性改签候选
- `GET /merchant/technicians/:id/monthly-disruptions`
  - 查看该客服当月临时请假导致未履约次数和责任汇总

实现约束：

- `POST /merchant/schedules/:id/leave` 在确认请假后，必须在同一处理链内完成以下动作：更新排班状态为 `leave_confirmed`、撤回受影响 `bookable` 时段、扫描受影响预约、计算 `protected_repair_slots`
- 对每笔受影响预约，系统都必须产出“是否存在高质量修复方案”的结构化结果，该结果用于驱动后续保护性改签、单方面取消、取消申请与补偿归责分流
- 当 `now < reserved_start_at - 5h` 且不存在高质量修复方案时，系统才允许商户单方面取消；当 `now >= reserved_start_at - 5h` 时，系统不得放行单方面取消，只可进入取消申请或商户违约补偿闭环
- 在受影响预约完成修复或确认无解之前，普通新预约自动确认、普通用户主动改签和系统优化性改签都必须避让 `protected_repair_slots`
- `POST /merchant/schedules/:id/leave` 的处理结果中，必须显式返回或持久化“是否进入异常修复模式”“受影响预约集合”“剩余可售容量是否足以同时覆盖修复与新增需求”等关键判定结果，供自动确认、改签审核与候选查询接口共用
- 同一日期一旦进入异常修复模式，自动确认接口、改签审核接口、候选查询接口必须共用同一份 `protected_repair_slots` 与修复优先级判断，不得出现展示层、审核层、提交层三套口径

  - 商户发起不可抗力撤销违约补偿申请

  - 用户发起不可抗力撤销违约补偿申请
- `POST /appointments/force-majeure-relief/:id/accept`

## 13.8 实现附录：后端实现清单 / 数据结构清单 / 接口字段清单

本节不重复业务规则本身，只把前文已确定的口径收敛为后端可直接拆任务的实现附录。第一版必须坚持一个统一原则：同一预约、同一日期、同一请假异常事件的判定结果，必须在自动确认、改签审核、候选查询、补偿归责四类链路间保持一致，不允许各自产生独立口径。

### 13.8.1 后端实现清单

建议后端按以下模块拆分实现：

1. `预约确认与资源锁定模块`
   - 负责新预约确认、资源占用写入、`reserved_start_at` / `reserved_end_at` / `occupied_end_at` 固化
   - 负责预约确认时生成或关联正式预约结算记录
   - 负责最终提交时并发校验，避免候选查询可下单但事务提交失败成为常态

2. `可售时段与候选时段计算模块`
   - 负责 `available-slots`、`reschedule-slots`、`reschedule-recommendations` 共用候选生成与评分
   - 负责碎片保护、窗口限制、排布评分、冲突检测、并发前最终校验
   - 负责在异常修复模式下统一避让 `protected_repair_slots`

3. `三阶段改签引擎`
   - 负责 `阶段 A / B / C` 的资格判定、时间窗判定、取消放行判定
   - 负责用户主动改签次数校验与 `reschedule_count` 更新
   - 负责商户保护性改签提议、用户接受/拒绝后的状态收敛

4. `异常修复判定与请假处理模块`
   - 负责识别“已发布后确认请假”是否成立
   - 负责扫描 `AFFECTED_APPOINTMENTS`
   - 负责计算 `repair_capacity_pool` 与 `protected_repair_slots`
   - 负责输出“是否进入异常修复模式”“是否存在高质量修复方案”“剩余容量是否足以同时覆盖修复与新增需求”等统一判定结果

5. `保护性改签与异常闭环模块`
   - 负责保护性改签提议创建、接受、拒绝、取消申请、单方面取消放行条件
   - 负责 `disruption_status`、异常原因、审计说明、补偿说明的统一写入
   - 负责在候选穷尽后，把预约收敛到“修复成功 / 取消退款或解冻 / 商户违约补偿 / 恢复性对冲结算”之一

6. `预约结算模块`
   - 负责 `appointment_settlements` 的生成、退款、解冻、迁移、状态快照回写
   - 负责用户主动改签与商户保护性改签生效时的结算归属迁移
   - 负责确保改签不重复扣减资产

7. `签到与服务会话接入模块`
   - 负责 `appointment_checkin` 与 `walk_in_checkin` 分流
   - 负责签到成功时写入 `actual_arrived_at`
   - 负责实际开始服务时写入 `actual_start_at`
   - 负责避免预约签到再次触发扣次或扣额

8. `补偿与责任结算模块`
   - 负责 `merchant_breach_pending` 到最终归责结果的收敛
   - 负责 `merchant_breach`、`merchant_failure_offset`、拖堂账本累积和补偿兑现
   - 负责客服月度免责次数与内部责任承担结果写入

9. `任务与重试模块`
   - 负责 `runMerchantBreachCompensation`、`runAppointmentDelayLedgerSettlement`、`runLeaveDisruptionLiabilitySettlement`
   - 负责重复执行幂等键、周期性补偿任务与窗口结束后的兜底收敛

第一版实施顺序建议按依赖收敛为：

- 先完成预约锁定、三阶段改签、统一候选计算
- 再完成预约结算拆分与签到建单分流
- 再完成异常修复判定、保护性改签与补偿闭环
- 最后补齐拖堂账本、不可抗力救济与报表侧汇总

### 13.8.2 数据结构清单

本方案中的实现对象，建议区分为三类：正式业务表、预约主表扩展字段、运行时统一判定结构。

#### A. 正式业务表

1. `appointment_settlements`
   - 用途：承载预约成功时的扣次、冻结、退款、解冻、迁移
   - 关键字段：`appointment_id`、`booking_root_id`、`merchant_id`、`user_id`、`card_id`、`asset_type`、`consumed_value`、`status`、`refunded_at`、`transferred_to_appointment_id`、`created_at`

2. `appointment_delay_ledgers`
   - 用途：承载拖堂分钟原始账本与后续折算
   - 关键字段：`appointment_id`、`booking_root_id`、`merchant_id`、`user_id`、`card_id`、`project_id`、`service_session_id`、`technician_id`、`scheduled_start_at`、`actual_start_at`、`delay_minutes`、`credited_minutes`、`service_duration_minutes`、`unit_compensation_value`、`created_at`

3. `technician_schedule_publishings`
   - 用途：承载次日可预约排班发布状态与请假收口结果
   - 关键字段：`merchant_id`、`technician_id`、`service_date`、`status`、`published_at`、`withdrawn_at`、`leave_reason`、`updated_at`

#### B. `appointments` 表需要统一维护的字段

- `booking_root_id`
- `reserved_start_at`
- `reserved_end_at`
- `occupied_end_at`
- `cancel_deadline_at`
- `booking_close_deadline_at`
- `late_arrival_min_service_minutes`
- `actual_arrived_at`
- `actual_start_at`
- `reschedule_count`
- `appointment_settlement_id`
- `settlement_status_snapshot`

其中必须重点保证：

- `booking_root_id` 在整条改签链上保持不变
- `reschedule_count` 只在“用户主动改签成功生效”后递增
- `appointment_settlement_id` 与 `settlement_status_snapshot` 必须始终反映当前有效结算归属
- `actual_arrived_at` 与 `actual_start_at` 必须分别代表“签到成功”与“实际开始服务”，不得混用

#### C. 运行时统一判定结构

第一版不强制这些对象必须单独建表，但服务端至少要为它们定义稳定、可复用的内部结构，支持在线接口与后台任务共用。

1. `AFFECTED_APPOINTMENTS`
   - 含义：当前请假事件直接影响到、仍需处理的预约集合
   - 最少字段：`event_id`、`appointment_id`、`merchant_id`、`technician_id`、`service_date`、`reserved_start_at`、`reserved_end_at`、`disruption_reason`、`repair_status`、`has_high_quality_repair_plan`

2. `repair_capacity_pool`
   - 含义：同商户、同日、其他可承接客服或时段中可用于修复的原始容量池
   - 最少字段：`event_id`、`merchant_id`、`service_date`、`candidate_technician_id`、`slot_start_at`、`slot_end_at`、`service_item_id`、`capacity_type`、`is_reserved_for_repair`

3. `protected_repair_slots`
   - 含义：从 `repair_capacity_pool` 中冻结出来、优先供受影响预约修复使用的受保护时段集合
   - 作用：自动确认避让、普通用户主动改签避让、系统优化性改签避让、商户保护性改签优先使用
   - 最少字段：`event_id`、`merchant_id`、`service_date`、`slot_start_at`、`slot_end_at`、`technician_id`、`service_item_id`、`reserved_for_appointment_id`、`protection_reason`、`expires_at`、`status`

4. `leave_disruption_event`
   - 含义：一次“已发布后确认请假”触发出来的统一异常事件上下文
   - 第一版可落表，也可作为聚合根内部对象，但必须有稳定主键以串起同一次异常处理
   - 最少字段：`event_id`、`merchant_id`、`technician_id`、`service_date`、`leave_start_at`、`leave_end_at`、`event_type`、`is_abnormal_repair_mode`、`affected_appointment_count`、`repair_capacity_sufficient`、`created_at`、`updated_at`

5. `abnormal_repair_mode_decision`
   - 含义：某商户某日期是否进入异常修复模式的统一判定结果
   - 最少字段：`merchant_id`、`service_date`、`triggered`、`trigger_event_id`、`trigger_reason`、`affected_appointment_count`、`repair_capacity_sufficient`、`can_continue_auto_confirm`、`priority_order_snapshot`、`evaluated_at`

#### D. 异常修复模式判定口径

服务端必须把“是否进入异常修复模式”收敛为统一函数或统一判定器，不允许接口各自判断。

建议判定条件固定为：

- 已存在次日已发布为 `bookable` 的排班
- 用户已可见并可基于该排班创建预约
- 之后商户或系统将该排班标记为 `leave_confirmed`
- 请假区间与已发布可预约时段有交集
- 同时扫描到至少一笔仍可履约但与请假区间重叠的受影响预约

建议统一输出：

- `triggered`
- `trigger_reason = leave_confirmed_after_publish`
- `affected_appointment_count`
- `repair_capacity_sufficient`
- `can_continue_auto_confirm`
- `priority_order = [affected_repair, protective_reschedule, user_reschedule, new_booking]`

### 13.8.3 接口字段清单

本节只列需要在第一版显式返回、或至少可被统一内部复用的关键字段，不要求所有字段都首版对外暴露，但服务端内部必须具备这些结构。

#### A. 通用返回字段

- `is_abnormal_repair_mode`
- `abnormal_repair_event_id`
- `trigger_reason`
- `affected_appointment_count`
- `repair_capacity_sufficient`
- `can_continue_auto_confirm`
- `protected_repair_slots_count`
- `has_high_quality_repair_plan`
- `first_reject_reason`

### 13.8.4 研发落地时必须统一的几个口径

1. `protected_repair_slots` 不是前端展示概念，而是后端强约束容量

### 13.8.5 各核心算法的实现承载位置索引

- 可预约时段生成与资源锁定算法：对应“预约确认与资源锁定模块”“可售时段与候选时段计算模块”，并由 `13.1 新预约`、`13.3 改签` 共享同一候选与提交校验口径。

- 商户违约最终归责算法：对应“补偿与责任结算模块”“任务与重试模块”，并由 `runMerchantBreachCompensation`、`runAppointmentDelayLedgerSettlement`、`runLeaveDisruptionLiabilitySettlement` 负责在线与离线链路收敛。
- 综上，当前文档已经给出各核心算法的业务规则、字段承载、模块边界与任务入口，但尚未展开为最终可运行代码或完整伪代码实现。

1. `backend/handlers/appointment.go` 是当前最核心的改造入口。

## 15. 最终推荐口径

如果本项目要同时满足“预约可信度高”和“产能利用率高”，推荐采用以下优化版最终口径：

1. 预约一旦成功，预约时段内客服资源默认锁定。
2. 次日产能只卖到 `D-1 16:00`，若未满则补开到 `18:00`。
3. 改签从预约成功后即开放，但按 `16:00` 和 `18:00` 分三阶段逐步收紧。
4. `16:00` 之后不允许取消。
5. `18:00` 之后到次日营业前，不再卖新预约。
6. 改签统一拆成三类：
   - 用户主动改签
   - 商户保护性改签
   - 系统优化性改签
7. 预约结算按卡型分层处理：
   - 次卡优先采用预约成功即扣次
   - 额度卡优先采用预约成功即冻结、签到后转实扣
8. 到店迟到不顺延，只能消费剩余预约窗口。
9. 商户未服务补 1 个完整服务单位。
10. 商户拖堂超过 1 分钟记入补偿账本，但兑换规则按项目配置执行。
11. 系统保留极窄口径的“局部优化能力”，但不得引入连锁延迟。

这套方案相较当前实现的优势是：

- 规则稳定，可解释
- 商户与用户预期一致
- 不再出现“预约成功但仍被现场单压掉”的违和体验
- 仍然通过晚间补开和碎片优化保住产能效率

相较当前实现的代价是：

- 现场调度弹性会下降
- 必须重构“预约扣次”和“到店签到”的职责边界
- 需要新增预约结算、排班发布、修复容量预留、拖堂账本等正式业务对象
 
 但这是更合理的代价。因为如果继续允许预约被挤占，或把所有规则都做成一刀切的纯刚性，也都不是最优解。

## 16. 现有代码实现 vs 新规方案 对比评估

### 16.1 对比结论先行

如果评价标准是：

- `更适合真实线下预约制场景`
- `更能稳定提升预约用户体验`
- `更能减少预约碎片`
- `更能形成长期可运营的补偿与结算闭环`

则：

- `预约新规方案` 明显优于 `现有代码实现`

如果评价标准仅仅是：

- `当班现场吞吐最大化`
- `短期内尽量不改现有扣次与核销链路`

则：

- `现有代码实现` 在短期弹性上更占优

所以两者不是谁“绝对全维度碾压”，而是目标函数不同。

### 16.2 分维度详细对比

#### 一、真实线下场景适配度

现有代码实现：

- 更适合“预约只是参考、现场流转优先”的门店。
- 适合高 walk-in 占比、用户对准点预期较低的业态。

预约新规方案：

- 更适合“预约就是承诺”的门店。
- 更适合美业、理疗、问诊、顾问型服务等强预约场景。

评判：

- 若面向真实预约制线下门店，新规方案更适合。

#### 二、预约准点性和可解释性

现有代码实现：

- 允许条件性压预约。
- 到店后可能进入 `appointment_waiting`。
- 用户理解成本高，容易出现“明明预约成功，为何还要等”的争议。

预约新规方案：

- 预约成功即锁客服时段。
- 到店后正常情况下不应再排队等前序现场单。
- 规则更容易向商户和用户解释。

评判：

- 新规方案显著更优。

#### 三、产能利用率

现有代码实现：

- 通过弹性插单、条件压预约，短期利用率更高。
- 在高波动门店里，当班空闲时间更少。

预约新规方案：

- 通过分阶段改签、晚间补开、碎片优化来提效。
- 不靠压预约换吞吐，峰值利用率可能略低于现有实现。

评判：

- 若只看“即时吞吐”，现有代码更高。
- 若看“稳定履约 + 可复用排程”，新规方案更健康。

#### 四、预约碎片治理

现有代码实现：

- 已有碎片保护，但仍允许条件性重叠和现场挤压。
- 因为改签开启较晚、资源锁定不彻底，碎片治理是局部和被动的。

预约新规方案：

- 改签从预约成功后即开放。
- 越早移动预约，越容易把边角空洞并回完整可售段。
- 16:00 后和 18:00 后逐步收紧，只保留“更优改签”，更利于收口。

评判：

- 若目标是“更有效减少预约碎片”，新规方案更优。

#### 五、运营效率

现有代码实现：

- 商户需要更多人工解释和线下协调。
- 用户到店后等待、改派、备注处理的运营负担更重。

预约新规方案：

- 前期规则更重，但后期争议更少。
- 自动结算、自动补偿、固定窗口能降低运营沟通成本。

评判：

- 中长期看，新规方案更高效。

#### 六、实施成本和改造风险

现有代码实现：

- 成本最低，基本保持现状即可。

预约新规方案：

- 要改预约结算、签到、补偿账本、改签窗口、派单规则。
- 改造明显更重。

评判：

- 短期实施成本上，现有代码更优。

### 16.3 哪种方式更能提高产能、提高效率且减少碎片

这个问题必须拆开回答。

#### 1. 提高即时产能

现有代码实现更强。

原因：

- 它允许更激进地利用客服未来时段。
- 能把本来会被预约保留的部分空闲时间拿去接现场单。

代价：

- 会稀释预约承诺
- 会放大后续等待和补偿成本
- 会引入连锁延迟风险

#### 2. 提高稳定效率

预约新规方案更强。

这里的“稳定效率”指：

- 更少扯皮
- 更少人工改派
- 更少到店争议
- 更少预约失信
- 更少后补协调

从真实经营结果看，这种效率往往比“多塞进几单”更重要。

#### 3. 更有效减少预约碎片

预约新规方案更强。

原因不是“它更刚性”，而是：

- 它把改签从晚间补救动作，前移成全天收敛动作。
- 它要求越晚的改签越必须更优。
- 它不再允许用后续预约承担前序插单成本。

所以从碎片治理上看，新规方案是主动优化，现有代码更像被动容忍。

### 16.4 最终评判

综合评估后，结论如下：

1. 若目标是做“严格预约制门店”，新规方案优于现有代码实现。
2. 若目标是做“现场优先、预约次优先”的混合门店，现有代码实现更接近业务现实。
3. 若同时追求：
   - 预约可信
   - 产能不明显下降
   - 碎片更少
   - 运营成本更低
   则最优答案不是完全回退到现有代码，也不是机械照搬旧文档，而是采用：
   - `新规主框架`
   - `吸收现有代码里的碎片评分与候选时段算法`
   - `保留 16:00-18:00 未满补开`
   - `采用三阶段改签收敛`

## 17. 最终推荐方案

### 17.1 推荐结论

最终推荐：

- `采用优化版预约新规作为主方案`
- `不建议继续以现有代码实现作为最终业务形态`
- `也不建议原样落地纯刚性版新规`

原因：

现有代码实现的优势主要是“短期现场吞吐更高”，但这建立在牺牲预约确定性和规则可解释性的前提上。对于真实线下预约门店，这种收益不稳定，也很容易被用户投诉、补偿成本和运营协调成本吃掉。

相比之下，优化版新规虽然改造更重，但更符合线下预约业务的核心承诺：

- 约了就能按时服务
- 改签分三类且边界清晰，越晚越严格
- 取消和改签窗口清晰
- 到店与扣次分责明确
- 商户违约有正式账本

### 17.2 推荐采用的“收敛版方案”

最终不建议生硬采用“纯理论最刚性方案”，而建议采用以下收敛版：

1. 保留现有代码中的：
   - 候选时段统一校验
   - 碎片保护
   - 排布评分
   - 改签复用主规则
2. 切换为新规中的：
   - 预约成功即锁定客服时段
   - 自动派单不得绕过预约锁定
   - `D-1 16:00` 后禁止取消
   - `16:00-18:00` 未满补开
   - 三阶段改签窗口
   - 用户主动改签 / 商户保护性改签 / 系统优化性改签 三分法
   - 按卡型分层预约结算
   - 拖堂分钟账本与自动补偿
3. 把当前 `appointment_waiting` 从正常主路径降级为异常兼容路径。

### 17.3 最终一句话判断

若只问“哪个更像真实线下预约制，并且更能长期提高效率、减少碎片”，答案是：

- `预约新规方案更优`

若只问“哪个更容易继续沿用当前代码，并在短期内把现场单尽量塞满”，答案才是：

- `现有代码实现更优`

但本项目若要走预约能力升级路线，应选择前者，而不是后者。

## 18. 可直接执行落地的优化版方案

### 18.1 方案定义

本节给出的是下一步可以直接拆任务落地的执行版本，不再停留在“方向性原则”层面。

其核心定义是：

- `统一预约主引擎`
- `单一业务机制，不保留两套并行预约制度`
- `保留少量策略参数，不保留机制分叉`
- `在强预约底座上，允许极窄口径的局部优化`

### 18.2 统一预约主引擎

所有入口统一走一套排程和校验内核：

- 可预约时段查询
- 创建预约
- 确认预约
- 改签查询
- 改签提交
- 现场派单
- 自动派单
- 到店签到

统一内核必须同时输出：

- `reserved_start_at`
- `reserved_end_at`
- `occupied_end_at`
- `placement_score`
- `fragment_delta`
- `policy_decision`

这里的 `policy_decision` 只允许三类结果：

- `allow`
- `allow_with_recommendation`
- `deny`

不再使用会把后续预约拖入不确定状态的“条件性压预约”语义。

### 18.3 统一策略档位

机制保持一套，但预留策略档位。

建议后端先支持：

- `strict`
- `balanced`
- `flex`

但第一阶段只开放：

- `balanced`

给商户使用。

含义如下：

#### `strict`

- 预约成功后完全硬锁定
- 不允许任何局部重排
- 只允许用户主动改签和商户保护性改签

适合：

- 强预约、强准点场景

#### `balanced`

- 预约资源默认硬锁定
- 允许极窄口径的局部优化
- 不允许引入第二个受影响预约

适合：

- 大多数线下预约门店

#### `flex`

- 仅作为未来保留档
- 当前阶段不建议开放

原因：

- 它很容易重新滑回现有代码的“混合调度”路径

### 18.4 `balanced` 档的局部优化边界

`balanced` 档不是重新允许压预约，而是只允许以下两类受控动作：

1. `同客服相邻空洞重排`
   - 只能在同一客服、相邻时段内发生
   - 不能新增第二位受影响预约用户
   - 只允许作用于当前正在生成候选的单笔预约，不得自动改变其他已确认预约的开始时间

2. `保护性改签`
   - 仅在商户责任或系统资源异常时触发
   - 必须带补偿和审计记录

明确禁止：

- 为了接现场单去压后任意预约
- 因 A 单挤压导致 B、C、D 连锁后移
- 为了短期利用率打破既有预约承诺

### 18.5 改签的执行版本

三类改签共用三阶段时间窗，但权限不同：

#### 阶段 A：自由调仓

- 时间：预约成功后至 `D-1 16:00`
- 允许取消
- 允许用户主动改签
- 允许商户保护性改签
- 系统优化性改签可推荐
- 允许新预约
- 改签条件：
  - 严格无冲突
  - 不制造不可复用碎片
  - `score(target) >= score(current)`

#### 阶段 B：尾盘收敛

- 时间：`D-1 16:00-18:00`
- 不允许取消
- 未约满可继续卖
- 用户主动改签、商户保护性改签仍可用
- 系统优化性改签可推荐
- 用户主动改签条件：
  - `score(target) > score(current)`

#### 阶段 C：冻结前修复

- 时间：`D-1 18:00` 至 `D` 营业开始前
- 不允许新预约
- 不允许取消
- 用户只允许一次主动改签
- 商户保护性改签仍可用
- 系统优化性改签只可推荐
- 用户主动改签条件：
  - `score(target) > score(current)`，或
  - 商户责任 / 资源异常

### 18.6 结算的执行版本

不建议第一版继续坚持“一刀切全部预约成功即实扣”。

更优执行版本如下：

#### 次卡

- 预约确认成功即扣次
- `D-1 16:00` 前取消返还
- 改签不重复扣次

#### 额度卡

- 预约确认成功先冻结额度
- 到店签到后转为实扣
- `D-1 16:00` 前取消解冻
- 超过取消窗口未取消且最终未到店，则自动转为扣减

这样做的原因是：

- 次卡天然适合强承诺扣减
- 额度卡更适合先冻结、后结算，财务口径更稳

### 18.7 补偿的执行版本

补偿直接拆成两条产品链：

#### A. 商户违约补偿

- 完整商户违约收敛到 `merchant_breach`
- 用户侧执行“恢复本次损失 + 额外补偿一份同等次数或同等额度”
- 观察后仅满足恢复性对冲条件的，收敛到 `merchant_failure_offset`
- `merchant_failure_offset` 只恢复本次损失，不追加额外补偿
- 若原因是客服临时请假或离岗：
  - 第 `1` 次由商户承担
  - 第 `2` 次及之后由客服承担

#### B. 延迟补偿

- 拖堂超过 `1` 分钟
- 进入 `appointment_delay_ledgers`
- 是否兑现、何时兑现，不再统一写死为“满一个时长补一次”

建议新增项目级配置：

- `delay_tolerance_minutes`
- `delay_compensation_mode`
  - `minutes_bucket`
  - `amount_bucket`
  - `fixed_unit`
- `delay_redeem_threshold_percent`

原因：

- 不同项目时长、客单价、补偿习惯差异很大
- 统一分钟桶只适合作为默认模型，不适合作为唯一模型

### 18.8 到店链路的执行版本

预约到店后不再默认走现有“核销即扣次”主语义，而是拆成：

1. `appointment_checkin`
2. `walk_in_verify`

其中：

- `appointment_checkin`
  - 校验预约状态、时间窗、结算记录
  - 创建 `ServiceSession`
  - 不重复扣减
- `walk_in_verify`
  - 继续保留现有核销扣减逻辑

### 18.9 可以直接开工的 P0 / P1 / P2

#### P0

- 统一自动派单和手动选人规则
- 去掉现有会引入连锁延迟的压预约路径
- 上线三阶段改签窗口
- 保留当前碎片评分与候选时段算法

#### P1

- 新增 `appointment_settlements`
- 实现次卡实扣、额度卡冻结
- 新增预约签到入口
- 上线商户违约最终归责任务
- 把 `appointment_waiting` 降级为异常兼容

#### P2

- 新增 `appointment_delay_ledgers`
- 接入项目级补偿规则
- 跑通自动兑现与审计报表

### 18.10 最终执行建议

如果现在就要进入实施，最推荐的落地顺序是：

1. 先做 `P0`
   - 先把最危险的连锁延迟和规则不一致收住
2. 再做 `P1`
   - 把预约承诺和资产结算做实
3. 最后做 `P2`
   - 把补偿从人工处理升级成正式账本

这就是当前项目下一步最科学、最可执行、也最容易分阶段交付的优化版方案。

### 20.5 对核心算法、规则与技术以及实现层级的归纳判断

结合全文内容，并与第 `6`、`8`、`9`、`10`、`13.8` 章的对应实现要点相互印证，可归纳为以下结论。

#### 20.5.1 最核心的不是单一公式，而是一套预约决策算法 / 规则引擎

从全文结构看，本方案最核心的不是某一个孤立的数学算法，而是一套统一的`预约决策算法 / 规则引擎`。

它统一负责决定：

- 某个预约能否创建
- 创建后锁定哪段客服资源
- 预约确认后如何完成结算或冻结
- 用户迟到后是否仍允许履约
- 商户出现异常后最终归责给谁
- 最终落到正常履约、用户责任、`merchant_breach` 或 `merchant_failure_offset`

换句话说，这份文档的核心不是“排序算法”本身，也不是“排队算法”本身，而是一个同时覆盖以下闭环的统一规则系统：

- `预约成立`
- `资源锁定`
- `改签分流`
- `迟到判定`
- `异常归责`
- `补偿收敛`

如果继续向下拆，全文实际上已经把这套规则引擎拆成 `4` 个核心子算法：

1. `可预约时段生成与资源锁定算法`
   - 对应 `5`、`6`、`13.1`、`13.8.1`
   - 负责可售时段生成、排班命中、冲突校验、碎片保护、资源锁定和自动确认
2. `预约确认与结算算法`
   - 对应 `5`、`8`、`13.1`、`13.8.1`
   - 负责把预约成功、扣次或冻结、结算凭证生成、改签归属迁移统一到一个事务语义里
3. `迟到仍可服务判定算法`
   - 对应 `9`
   - 负责基于 `remaining_minutes` 与 `min_serviceable_minutes` 判断迟到后还能否继续履约
4. `商户违约最终归责算法`
   - 对应 `10`、`13.5`、`13.8.1`
   - 负责在服务窗口内持续观察事实，并在 `breach_decision_at` 收敛到最终归责结果

若只选一个“最核心算法”，应定义为：

- `基于预约服务窗口的预约决策与归责算法`

因为它贯穿了“能否预约 -> 如何锁定 -> 如何改签 -> 是否履约 -> 如何补偿”的完整主链。

#### 20.5.2 这套算法必须同时考虑哪些规则

从文档现有口径看，这套算法至少必须统一考虑以下 `6` 类规则：

1. `预约成立规则`
   - 已发布排班
   - 次日预约窗口
   - `D-1 16:00-18:00` 未满补开
   - 严格资源无冲突
2. `资源锁定规则`
   - `reserved_start_at`
   - `reserved_end_at`
   - `occupied_end_at`
   - 改签时旧资源释放、新资源锁定、结算迁移必须原子完成
3. `迟到规则`
   - `actual_arrived_at`
   - `remaining_minutes`
   - `min_serviceable_minutes`
   - `service_denied_late`
4. `商户异常与归责规则`
   - 商户是否已明确无法履约
   - 是否发起取消申请
   - 是否发起保护性改签
   - 用户是否接受、拒绝、到店
   - 商户是否恢复到可履约状态
   - 是否已经实际开始服务
5. `补偿与责任规则`
   - `merchant_breach`
   - `merchant_failure_offset`
   - 用户侧补偿与内部责任承担分离
   - `liability_level`
   - `salary_settlement_reference_status`
6. `异常闭环规则`
   - `disruption_status`
   - `disruption_reason`
   - `merchant_cancel_reason`
   - `user_rebuttal_note`
   - `canceled_by_type`
   - `canceled_by_id`

这些规则在全文中的对应关系已经比较清楚：

- `4`、`5`、`6`、`7` 负责预约、改签、资源与时段算法
- `8` 负责预约结算
- `9` 负责迟到判定
- `10` 负责商户违约、恢复性对冲和拖堂补偿
- `11`、`12`、`13.8` 负责状态、字段、模块边界和实现承载

#### 20.5.3 除业务规则外，还必须考虑哪些技术点

从工程实现角度，这不是一个只写几个 if/else 就能稳定落地的算法，至少还必须同时处理以下技术问题：

1. `事务一致性`
   - 预约确认、改签生效、取消、签到、补偿落账都涉及多对象联动
   - 预约记录、资源占用、结算归属、异常状态、补偿记录必须在清晰事务边界内推进
2. `并发控制`
   - 必须处理并发抢同一时段、并发改签、并发取消、并发补偿任务
   - 文档已明确在线提交前要再次校验，并要求任务具备幂等语义
3. `统一判定器 / 规则执行器`
   - 同一预约、同一日期、同一异常事件的判断结果，必须在候选查询、自动确认、改签审核、补偿归责间保持一致
   - 不能让前台接口、后台任务、调度器各算一套口径
4. `异步任务调度`
   - `runMerchantBreachCompensation`
   - `runAppointmentDelayLedgerSettlement`
   - `runLeaveDisruptionLiabilitySettlement`
   - 都要求明确触发条件、重复执行策略、幂等键和窗口结束后的兜底收敛
5. `审计与留痕`
   - 用户是否到店、商户是否报备、谁拒绝改签、谁发起取消、为何落到某种归责，都必须是结构化强事实
6. `快照字段与正式记录分层`
   - `appointments` 上的快照字段不能替代正式结算与补偿记录
   - 正式记录、快照字段、运行时统一判定结构三者的职责在 `12`、`13.8.2` 中已经开始收口

## 21. 新方案重构后预约功能完整使用说明

### 21.1 用户端使用说明

#### 预约

1. 用户选择商户、卡和项目。
2. 系统只展示“已发布次日排班”中，且符合营业时间、资源锁定和碎片规则的可预约时段。
3. 用户提交预约后，系统按统一算法自动判断是否可预约成功，不需要客服本人逐单确认。
4. 预约确认后：
   - 次卡立即扣次
   - 额度卡先冻结额度
5. 用户在预约详情中可查看：
   - 预约时间
   - 锁定客服
   - 是否可取消
   - 是否可发起用户主动改签
   - 是否存在保护性改签入口
   - 结算状态

#### 取消

1. `D-1 16:00` 前可取消。
2. 取消前系统优先推荐更优改签时段。
3. 若用户仍选择取消：
   - 次卡返还
   - 额度卡解冻
4. `D-1 16:00` 后不可取消。
5. 商户仅可在预约开始前 `5` 小时以上单方面取消，且必须填写正当理由。
6. 若商户在预约开始前 `5` 小时及以内想取消，只能向用户申请取消；用户同意后方可取消成功。
7. 若属于非用户主动取消成功的预约，用户仍可查看该预约记录。
8. 对商户单方面取消的预约，用户可填写抗辩意见，作为后续申诉或投诉依据。

#### 用户主动改签

1. 预约成功后即可发起用户主动改签。
2. 系统按当前阶段返回可主动改签时段：
   - 阶段 A：可改到不劣于当前的时段
   - 阶段 B/C：只能改到更优时段
3. 每次预约默认只有一次用户主动改签成功机会。
4. 若本次申请未通过系统算法校验，只要仍在用户主动改签窗口内，即可继续重新申请。
5. 用户提交后，系统再次校验目标时段；校验通过则自动生效，不需要商户或客服确认。
6. 用户主动改签不会重复扣减或冻结。

#### 商户保护性改签

1. 若属于门店责任或资源异常，商户可发起保护性改签。
2. 保护性改签不占用用户主动改签次数。
3. 保护性改签必须附带补偿和审计说明。
4. 保护性改签必须经用户确认后才生效。
5. 若改签失败，则按最终事实分别收敛到 `merchant_breach` 或 `merchant_failure_offset`。
6. 若原因是客服临时请假或离岗，内部再按该客服当月免责次数区分商户承担或客服承担。
7. 若属于非特殊资源违约，用户拒绝后：
   - 原预约还能履约则继续保留
   - 原预约不能履约则系统取消，并按商户违约补偿走
   - 不对后续已预约用户做级联重排

#### 商户违约补偿

1. 完整商户违约收敛到 `merchant_breach`，执行“恢复本次损失 + 额外补偿一份”。
2. 仅满足恢复性对冲条件的，收敛到 `merchant_failure_offset`，只恢复本次损失，不追加额外补偿。
3. 若因客服临时请假或离岗导致违约：
   - 用户侧补偿口径不变
   - 仅内部责任承担按客服当月免责次数区分商户承担或客服承担
4. 用户可在预约详情查看补偿结果。

#### 系统优化性改签推荐

1. 默认关闭。
2. 开启后，系统只会推荐更优时段，不会自动替用户改签。
3. 用户或商户确认后，仍然走正式改签提交流程。

#### 到店

1. 用户到店后由商户执行预约签到。
2. 若到店后剩余服务时长仍达到该项目时长的 `1/2` 向下取整分钟数，则客服扫码后建单进入服务。
3. 若剩余时长不足该阈值，则不提供服务，并转入用户违约流程。
4. 若最终转入用户违约流程，用户端仍必须保留该预约和对应使用记录，并明确展示“预约已完成扣次/扣额”结果。

### 21.2 商户端使用说明

#### 查看预约

商户可在预约列表看到：

- 预约时间
- 预约客服
- 锁定区间
- 结算状态
- 用户主动改签次数
- 补偿状态
- 客服当月免责次数状态
- 商户取消理由
- 用户抗辩意见状态
- 对于已失约预约，仍必须继续展示该预约记录及其结算结果，不得因超窗自动从商户可见列表中直接消失

#### 发布次日排班

1. 商户需先发布次日可预约排班。
   - 第一版固定要求在当天 `10:00` 前完成发布；`10:00` 前不开放次日预约。
2. 只有被发布为可预约的客服和时段，才会对用户开放预约。
3. 若客服次日不确定能上班，则不应发布到可预约库存中。

#### 确认预约

1. 标准模式下，预约不依赖客服本人逐单确认，而是依赖次日排班先行发布。
2. 用户命中已发布库存后，系统自动确认预约并锁定客服时段。
3. `PUT /merchant/appointments/:id/confirm` 仅保留给兼容期或异常处理场景，不应再作为长期主流程。

#### 处理改签

1. 商户可查看用户是否还有主动改签机会。
2. 若属于门店责任或资源异常，可发起保护性改签。
3. 保护性改签必须留痕并带补偿，且需用户确认。
4. 若后续开启系统优化性改签，商户只能查看推荐，不可让系统自动落单。
5. 若属于非特殊资源违约，用户拒绝后默认不重排后续预约：
   - 原预约还能履约则继续保留
   - 原预约不能履约则系统取消并转商户违约补偿

#### 处理请假与离岗

1. 若客服次日请假，商户应立即撤回对应可预约排班并触发受影响预约扫描。
2. 系统给出保护性改签候选后，商户向用户发起保护性改签提议。
3. 若用户拒绝或无可替代时段，则按取消补偿闭环处理：
   - 用户侧统一返还/解冻 + 直接补一次/同额
   - 内部再按该客服当月免责次数区分商户承担或客服承担
4. 若客服当日中途离岗，后续未开始预约立即转入保护性改签或取消补偿闭环。

#### 到店签到

1. 用户在可到店窗口内生成预约签到码。
2. 商户扫码该预约签到码，对预约单执行签到。
3. 若签到时剩余服务时长仍达到项目时长的 `1/2` 向下取整分钟数，则系统创建 `ServiceSession`，即客服扫码后建单进入服务。
4. 预约单不再重复走普通核销扣减流程。
5. 若超出该阈值未到店，则系统按用户失约收敛，但预约记录、结算结果和对应使用记录仍需保留可查。

#### 处理取消

1. 商户在预约开始前 `5` 小时以上可单方面取消，但必须填写正当理由。
2. 商户在预约开始前 `5` 小时及以内不可单方面取消，只能发起取消申请或保护性改签。
3. 非用户主动取消成功的预约记录必须保留。
4. 用户可对商户单方面取消填写抗辩意见。

### 21.3 系统自动处理说明

系统会自动处理以下事项：

- 基于已发布排班生成可预约库存
- `16:00` 后禁止取消
- `16:00-18:00` 未满补开
- `18:00` 后关闭新预约
- 自动派单避开预约锁定窗口
- 客服请假后的受影响预约扫描
- 客服当月免责次数统计
- 商户取消申请流转
- 非特殊资源违约保护性改签被拒后的履约判断
- 无法履约时自动取消并转补偿
- 用户主动改签失败后的再次申请资格判断
- 额度冻结转实扣
- 超窗未到店的关闭与结算推进
- 商户违约补偿
- 不可抗力撤销违约补偿申请流转
- 拖堂账本累计与兑现

### 21.4 典型业务流程说明

#### 流程一：普通成功预约

1. 用户预约明天 `10:00`
2. 系统自动确认预约
3. 系统锁定客服时段
4. 次卡扣次或额度冻结
5. 用户次日到店出示预约签到码，商户扫码签到
6. 创建服务会话并服务完成

#### 流程二：用户提前改签

1. 用户预约后发现原时段不方便
2. 在 `D-1 16:00` 前发起用户主动改签
3. 系统返回不劣于当前排布的目标时段
4. 用户确认改签
5. 原预约关闭，新预约承接原结算记录

#### 流程三：超窗不可取消但可改签

1. 到了 `D-1 16:00` 后
2. 用户不能取消
3. 若存在更优时段，仍可在规则内发起用户主动改签

#### 流程四：合法到店但商户未服务

1. 用户准时或在可接受迟到范围内到店
2. 商户最终未提供服务
3. 系统生成商户违约补偿
4. 用户获得返还 + 1 个完整服务单位补偿

#### 流程五：客服临时请假且改签失败

1. 商户标记客服请假或离岗
2. 系统扫描受影响预约并生成保护性改签候选
3. 若用户拒绝或无可替代时段，则进入取消补偿闭环
4. 若该客服当月为第 `1` 次：
   - 用户侧返还/解冻本次预约并直接补一次/同额
   - 内部记为商户承担
5. 若该客服当月为第 `2` 次及之后：
   - 返还/解冻本次预约
   - 直接补一次同等次数或同等额度
   - 记入该客服责任台账

#### 流程六：非特殊资源违约的保护性改签被拒绝

1. 商户因排布优化、设备变化或运营修正发起保护性改签
2. 用户拒绝改签
3. 系统判断原预约是否还能按原承诺履约
4. 若能履约：
   - 保留原预约
   - 不重排后续预约
5. 若不能履约：
   - 系统取消该预约
   - 按商户违约补偿处理

#### 流程七：商户拖堂

1. 用户预约 `10:00`
2. 实际开始服务为 `10:08`
3. 系统记入 `8` 分钟拖堂账本
4. 达到项目配置阈值后自动兑现补偿

#### 流程八：不可抗力撤销违约补偿

1. 商户或用户发起不可抗力撤销违约补偿申请
2. 对方确认属于不可抗力
3. 系统撤销对应违约补偿
4. 记录双方确认留痕
