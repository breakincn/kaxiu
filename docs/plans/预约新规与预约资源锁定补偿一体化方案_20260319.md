# 预约新规与预约资源锁定补偿一体化方案

日期：2026-03-19

## 1. 方案结论

基于当前项目实现现状和你给出的新业务口径，最优方案不是继续在现有“可条件压预约”的规则上打补丁，而是整体切换为：

- `预约资源锁定制`
- `D-1 16:00 截止 + 16:00-18:00 未满补开`
- `全时段分级改签：用户主动改签 / 商户保护性改签 / 系统优化性改签`
- `按卡型分层预约结算`
- `到店只做签到建单，不再做资产扣减`
- `商户未服务 / 商户拖堂` 两条自动补偿闭环

这套方案的核心目标是同时满足四件事：

1. 预约一旦成功，必须能按时服务，不能再被现场单或其他用户挤占。
2. 晚间空余产能还能继续出售，提升次日产能利用率。
3. 改签不是人工拍脑袋，而是受统一算法和碎片优化规则控制。
4. 商户违约成本结构化落库，补偿不再依赖线下口头协商。

## 2. 当前项目综合评估

### 2.1 当前系统不适合直接承接新规则

当前代码已具备预约、改签、补偿、预约保护的基础，但仍有 5 个关键口径与新规则冲突：

1. 当前现场单对预约客服仍存在“条件性挤占”语义，不是绝对锁定。
2. 当前用户手动选客服与系统自动派单不是同一套预约保护规则，存在绕过保护的缺口。
3. 当前核销链路把“到店”和“扣次”耦合在一起，不满足“预约成功即扣次”的新要求。
4. 当前用户主动改签资格是“今天/昨天/明天阈值模型”，不符合 `D-1 16:00 / D-1 18:00 / D 营业前` 的新窗口。
5. 当前补偿能力以人工补录为主，还没有“拖堂分钟账本 -> 自动折算补偿”的机制。
6. 当前只有当天 `technician_attendances` 签到状态，没有“次日可预约排班发布”能力。
7. 当前客服请假、离岗、改签、补偿之间还没有正式闭环，更多依赖人工处理。

### 2.2 当前项目可直接复用的能力

以下能力可以直接纳入新方案，不需要推翻重写：

- 商户营业时间和预约粒度
- 项目时长与项目间歇时间
- 预约时段碎片保护
- 预约改签记录链路
- 预约补偿记录表
- 预约到店接入 `ServiceSession` 主链

### 2.3 必须明确废弃的旧语义

本方案下，以下旧语义必须明确下线：

- 现场单允许在阈值内挤占后续预约
- 预约用户到店后进入 `appointment_waiting` 等前序现场单结束
- 到店核销才正式扣次
- 预约后的取消、用户主动改签、商户保护性改签、补偿继续靠人工备注兜底

原因很简单：只要仍允许“压预约”，就无法满足“预约成功一定按时服务”这个新前提。

### 2.4 当前代码实现的真实业务画像

结合当前代码，现状更准确的定义不是“严格预约制”，而是：

- `预约 + 现场混合调度制`

其核心特征是：

1. 预约创建、确认、用户主动改签已经有统一校验主链，且具备碎片保护能力。
2. 现场用户在手动选客服时，会参考后续预约保护，但仍允许在一定阈值内压后一个预约。
3. 预约用户到店后，如果原预约客服仍忙，系统允许进入 `appointment_waiting`，本质上接受“预约不一定准点开始”。
4. 到店核销才真正扣次，不是预约成功即扣次。
5. 补偿能力主要是结构化补录，还不是自动履约账本。

这说明当前代码更偏向：

- 提高门店当下流转弹性
- 兼容现场客和预约客混跑
- 用“预计等待可接受”来换取更高的当班利用率

而不是：

- 严格保证预约准点
- 严格锁定预约资源
- 严格做预约结算与违约补偿闭环

### 2.5 当前代码实现的优点

当前实现不是没有价值，它在以下方面是成熟且应继续保留的：

1. 候选时段、创建预约、确认预约、用户主动改签已基本共用同一套排布判断。
2. 已经有碎片保护和排布评分基础，不是简单的时间重叠判断。
3. 允许一定弹性插单，在高现场客门店中短期吞吐更高。
4. 对老门店改造成本较低，不需要立刻重构“预约成功即扣次”的资产链路。

### 2.6 当前代码实现的根本短板

但对“真实预约制线下场景”而言，当前实现有 6 个根本短板：

1. 预约不等于准点承诺。
2. 手动选客服与系统自动派单规则不完全一致。
3. 允许有限压预约，会把后续履约风险向后传导。
4. 用户主动改签窗口设计仍偏补救逻辑，不是主动优化产能。
5. 扣次时点偏晚，无法表达“预约成功即占用用户权益”。
6. 补偿没有分钟账本，无法自动折算履约损失。
7. 没有次日排班发布机制，导致“预约可售”和“客服次日是否一定可上班”之间缺少正式前置条件。

## 3. 新方案的总原则

### 3.0 改签术语统一

本方案中的“改签”统一拆成三类，后文如无特别说明，均按此口径理解：

1. `用户主动改签`
   - 由用户主动发起
   - 默认受改签次数限制
2. `商户保护性改签`
   - 由商户或客服发起
   - 仅用于商户责任或资源异常修复
   - 不占用用户主动改签次数
3. `系统优化性改签`
   - 由系统生成推荐
   - 默认关闭
   - 只能推荐，不能直接替用户改
   - 不占用用户主动改签次数

### 3.1 原则一：预约成功即锁定真实资源

预约一旦成功，系统必须同时锁定：

- 具体客服
- 具体开始时间
- 具体结束时间
- 对应项目占用长度

在该预约时段内，该客服不得再分配给任何其他用户。

### 3.2 原则二：预约规则优先于现场效率

在客服模式下，预约时段属于硬锁定资源，不再允许通过现场单“优化利用率”的方式侵占预约时段。

产能效率提升要通过这三种方式获得，而不是靠压预约：

- `16:00-18:00` 未满补开
- 提前开放的分级改签
- 碎片最优排布

### 3.3 原则三：资产扣减前移，服务签到后置

新方案把“预约承诺”和“实际履约”拆开：

- 预约成功：完成资产扣减或冻结
- 到店签到：创建服务会话
- 服务完成：完成履约闭环

这样才能同时满足：

- 用户不来店也要承担预约成本
- 商户未服务时能精确补偿

### 3.4 原则四：用户主动改签只允许一次，且不做级联挤压

每次预约默认只有一次`用户主动改签`机会。

但以下两类改签不受这条限制：

- `商户保护性改签`
- `系统优化性改签`

其中：

- 商户保护性改签必须满足：
  - 商户责任或资源异常
  - 自动补偿
  - 留痕审计
- 系统优化性改签默认关闭：
  - 仅在 `balanced / flex` 档位下开启
  - 且只能推荐，不能直接替用户改

系统只允许把该预约改签到一个“严格空闲且更优”的新时段，不允许通过移动 A 去挤压 B，再让 B 去挤压 C。

原因：

- 级联挤压会极大增加解释成本
- 会破坏“预约成功一定按时服务”
- 会让改签变成隐式重排全部预约

因此本方案采用：

- `单单移动`
- `不影响其他已预约用户`
- `允许优化碎片`

而不采用：

- 多订单连锁交换
- 全局强制重排

### 3.5 原则五：改签应早于取消开放

如果系统在 `16:00` 前允许取消，却不允许改签，会产生两个直接问题：

1. 用户原本只想把 A 时段换到 B 时段，却只能先取消 A，再重新抢 B，过程更抖。
2. 系统失去了更早做“空洞搬移”和“碎片收敛”的机会，反而更容易制造临时空档。

因此更优原则应是：

- 只要允许取消，就应至少允许改签。
- 且改签应优先于取消被推荐给用户。

## 4. 预约窗口新规则

下文统一以：

- `D` = 服务日
- `D-1` = 预约日

### 4.1 基础规则

- 用户每天只能预约 `D`，即第二天。
- 预约创建窗口：
  - `D-1 00:00-16:00` 正常开放
  - `D-1 16:00-18:00` 若次日未约满则继续开放
- 取消窗口：
  - 截止到 `D-1 16:00`
- 改签窗口：
  - 从预约成功后即开放
  - 一直持续到 `D` 营业开始前
  - 但分三个阶段，越晚规则越严格
- `D-1 18:00` 之后到 `D` 营业开始前：
  - 不再开放新预约
  - 不允许取消
  - 用户主动改签继续受次数限制
  - 商户保护性改签仍可用
  - 系统优化性改签仅可推荐，不可自动执行

### 4.2 “未约满”定义

“未约满”不能用总人数判断，必须用严格产能判断：

- 对次日每个客服
- 按项目占用长度
- 按营业时间
- 按已确认预约
- 按碎片保护结果

只要还存在至少一个可售时段，就视为“未约满”，允许在 `16:00-18:00` 继续卖。

### 4.3 取消规则

取消窗口统一定义为：

- `cancel_deadline_at = D-1 16:00:00`

规则如下：

- 在 `cancel_deadline_at` 之前：
  - 可以取消
  - 若预约已完成资产扣减，则原路返还或解冻
- 在 `cancel_deadline_at` 之后：
  - 不可取消
  - 用户只能申请用户主动改签
  - 商户仍可发起保护性改签

注意：

- `16:00` 之后新下的预约，也不能取消；用户只能发起用户主动改签，商户仍可发起保护性改签。
- 这样可以保证 `16:00` 后门店的次日产能开始稳定收敛，不再被来回取消打穿。

### 4.4 为什么 `16:00` 前必须允许改签

更优设计下，`16:00` 前不仅应该允许改签，而且应该把改签作为默认推荐动作。

原因：

- 对用户而言，改签比取消重约成本更低。
- 对商户而言，改签比取消更有利于保留已成交订单。
- 对系统而言，越早移动预约，越容易把离散空洞并成可复用完整时段。

因此前端建议改为：

- 用户点击“取消预约”时
- 优先展示“推荐用户主动改签到这些更优时段”
- 用户确认放弃改签后，再允许取消

## 5. 预约确认与资源锁定规则

### 5.1 新的预约确认语义

预约成功必须同时完成 4 件事：

1. 选定具体客服
2. 锁定预约时段
3. 完成对应的预约结算动作
4. 生成预约结算凭证

标准目标口径下，这里的“预约成功”指：

- 商户已先发布次日可预约排班
- 用户命中可售库存后
- 系统自动确认成功

商户逐单确认只保留给兼容期或异常处理场景，不再作为长期主流程。

### 5.2 预约锁定区间

预约锁定区间采用严格硬占用，不再允许软挤压：

- `reserved_start_at = appointment_time`
- `reserved_end_at = appointment_time + project.duration`

项目间歇时间不属于用户可服务时长，但属于客服产能占用：

- `occupied_end_at = appointment_time + project.duration + project.service_gap_minutes`

系统对资源使用区分两层：

- 用户承诺服务窗口：`[reserved_start_at, reserved_end_at)`
- 客服产能占用窗口：`[reserved_start_at, occupied_end_at)`

### 5.3 客服不可再分配规则

对已经被预约成功锁定的客服，在其预约占用窗口内：

- 不允许分配给现场单
- 不允许分配给其他预约
- 不允许超时自动派单绕过保护
- 不允许商户手动改派给其他非预约用户

这条规则是新方案的硬约束，不允许存在 `conditional` 例外。

### 5.4 预约是否需要客服本人逐单确认

推荐方案下，不需要客服本人对每一笔预约逐单确认。

更合理的确认模型是：

- 商户先发布次日可预约排班
- 系统只对已发布排班内的客服和时段开放预约
- 用户提交后，系统按统一算法自动确认是否可预约成功

也就是说，预约确认的对象不应是“客服逐单点同意”，而应是“商户对次日可售产能先行发布”。

原因：

- 逐单让客服确认，效率低且无法稳定支撑线上预约。
- 真正决定可售资源的，不是单笔预约时刻的临时意愿，而是前一日已经发布的次日排班。
- 只有这样，用户看到的可预约时段才是可信库存。

### 5.5 次日可预约排班发布机制

新方案增加一个前置动作：

- `次日可预约排班发布`

推荐规则：

1. 商户在 `D-1` 某一截止时间前发布 `D` 的可预约客服名单和工作区间。
2. 只有被发布为 `bookable` 的客服，才会出现在 `D` 的预约候选时段里。
3. 排班一旦发布，系统预约确认直接基于该排班自动完成，不再等待客服逐单同意。
4. 若商户未发布次日排班，则该客服次日不对外开放预约。

建议状态：

- `draft`
- `published`
- `withdrawn`
- `leave_applied`
- `leave_confirmed`

### 5.6 当前代码与目标方案在确认模型上的差异

当前代码更接近：

- 商户确认预约
- 预约确认后仍可能由调度器继续回补客服

这说明现状里“预约确认”和“客服资源最终落位”还没有完全合一。

目标方案应改为：

- 先发布次日可预约排班
- 再允许用户预约
- 用户预约成功即拿到确定客服和确定时段

这样才能满足“预约成功一定按时服务”的业务承诺。

## 6. 可预约时段与改签时段算法

### 6.1 统一目标

时段算法统一服务于三个入口：

- 新预约查询
- 新预约提交
- 用户主动改签可选时段查询

三处必须共用一套规则，避免“看得到、提得上、确认不了”。

### 6.2 候选时段生成规则

候选时段仍按固定粒度生成，推荐继续使用：

- `appointment_slot_granularity_minutes = 15`

对每个候选时段依次执行：

1. 营业时间容纳校验
2. 指定客服硬冲突校验
3. 客服锁定资源校验
4. 碎片保护校验
5. 晚间窗口校验
6. 用户主动改签次数与改签资格校验

### 6.3 碎片保护规则

继续采用当前项目已落地的“减少不可复用碎片”原则，但收紧口径：

- 候选预约落下去后
- 前后剩余区间如果都不能容纳该商户任一可预约项目的 `occupied_minutes`
- 则该时段不可售

### 6.4 最优排布评分

新方案下，评分目标不再是“允许有限挤占”，而是“在严格不挤占的前提下最大化产能利用率”。

建议评分函数统一为：

- `score = fragment_penalty + idle_gap_penalty + late_window_fill_bonus + same_staff_bonus`

含义：

- `fragment_penalty`
  - 若产生不可复用碎片，直接判负无穷，拒绝
- `idle_gap_penalty`
  - 优先填补更接近已有预约边界的空洞
- `late_window_fill_bonus`
  - 在 `16:00-18:00` 卖尾盘时，优先卖能填平剩余空洞的时段
- `same_staff_bonus`
  - 用户主动改签或商户保护性改签时，若还能保持原客服，给予稳定性加分

### 6.5 改签批准原则

三类改签共用同一套排布与冲突校验，但权限和触发条件不同。

#### 用户主动改签

系统应按以下顺序判断：

1. 是否仍在可改签窗口内
2. 是否已用过用户主动改签机会
3. 目标时段是否严格空闲
4. 是否会制造不可复用碎片
5. 是否优于或不劣于当前排布

只有全部满足，系统才自动同意并直接生效，不需要商户或客服二次确认。

前提：

- 目标时段属于已发布的次日可预约排班
- 目标客服在该时段处于 `bookable`

#### 商户保护性改签

系统应按以下顺序判断：

1. 是否属于商户责任或资源异常
2. 是否已生成补偿方案
3. 目标时段是否严格空闲
4. 是否不会引入第二个受影响预约
5. 是否已写入审计说明

满足后只可生成保护性改签提议，需经用户确认后才生效，且不消耗用户主动改签次数。

默认不允许商户单方面把已确认预约直接改走。

#### 系统优化性改签

系统只做推荐，不直接改写预约。

推荐条件：

1. 当前策略档位允许
2. 推荐目标时段优于当前排布
3. 不会制造不可复用碎片
4. 不会引入连锁延迟

## 7. 分阶段改签机制

### 7.1 更优的改签时间窗

原文档把改签从 `16:00` 才打开，这个设计并不最优。

更优方案应改为：

- `预约成功后` 到 `D-1 16:00`
- `D-1 16:00-18:00`
- `D-1 18:00` 至 `D` 营业开始前

也就是：

- 三类改签相关能力全程存在
- 但分阶段收紧

这样的好处是：

1. 更早开始消化碎片，而不是等到 `16:00` 后才被动修补。
2. 用户更少使用“取消后重下”这种更伤库存的操作。
3. 系统能在新预约持续进入前，先把已有预约往更优位置收敛。

### 7.2 三阶段改签策略

#### 阶段 A：自由调仓窗口

时间：

- `预约成功后` 至 `D-1 16:00`

规则：

- 允许取消
- 允许用户主动改签
- 允许商户保护性改签
- 允许系统优化性改签推荐
- 允许新预约
- 改签目标只要满足：
  - 严格无冲突
  - 不制造不可复用碎片
  - 排布评分不劣于当前时段
  - 即可自动批准

这个阶段的目标是：

- 尽早搬移边缘时段
- 提前填平孤岛空洞
- 优先用用户主动改签替代取消

#### 阶段 B：尾盘收敛窗口

时间：

- `D-1 16:00-18:00`

规则：

- 不允许取消
- 若未约满，允许新增预约
- 用户主动改签、商户保护性改签仍可用
- 系统优化性改签可推荐
- 但用户主动改签目标必须：
  - `score(target) > score(current)`
  - 即必须严格优于当前排布

这个阶段的目标是：

- 利用最后两小时把离散空洞向可售完整时段收敛
- 让改签和新增预约共同收口次日产能

#### 阶段 C：冻结前修复窗口

时间：

- `D-1 18:00` 至 `D` 营业开始前

规则：

- 不允许新预约
- 不允许取消
- 仅允许一次`用户主动改签`
- 商户保护性改签仍可用
- 改签目标必须满足：
  - 严格无冲突
  - 不制造碎片
  - `score(target) > score(current)`，或
  - 属于门店运营强制修复场景

运营强制修复场景示例：

- 原预约客服临时请假
- 原预约项目不可服务
- 门店主动发起保护性改签

这个阶段的目标是：

- 不再做大规模调仓
- 只做最后的优化和异常修复

### 7.3 哪种设计更能减少碎片

如果目标是“更有效减少预约时间段碎片”，三阶段方案优于“两段式晚间改签”的原因是：

1. 碎片不是在 `16:00` 之后才出现，而是在全天预约流入过程中持续产生。
2. 越早移动预约，越容易把多个小空洞合并为完整可售时段。
3. 若直到 `16:00` 才允许改签，很多本可提前修复的碎片已经失去再利用机会。

所以更优的原则是：

- `越早开放改签，越有利于碎片治理`
- `越接近服务日，越要限制改签自由度`

### 7.4 用户主动改签机会的定义

“一次改签机会”只针对`用户主动改签`，并且以预约根单为单位，而不是以预约记录行为单位。

建议引入：

- `booking_root_id`
- `reschedule_count`
- `reschedule_used_at`

规则：

- 初始预约：`reschedule_count = 0`
- 成功执行一次用户主动改签后：`reschedule_count = 1`
- 此后用户再次主动改签，直接拒绝

但以下两类改签不消耗 `reschedule_count`：

- `商户保护性改签`
- `系统优化性改签`

说明：

- 商户保护性改签是商户为修复自己责任或资源异常而发起，不应占用用户机会。
- 系统优化性改签只能做推荐，不会直接改写预约，因此也不应消耗用户机会。

### 7.5 改签执行方式

当前项目已有“旧预约关闭 + 新预约生成 + 建立替代关系”的链路，这条链路可以保留。

新规则下需要增加两点：

1. 改签不会再次扣减资产。
2. 改签后原预约的预约结算凭证整体迁移到新预约，或由根单级结算记录继续关联。

适用说明：

- `用户主动改签`
  - 走系统校验后自动生效的正式改签提交流程
- `商户保护性改签`
  - 走“提议 -> 用户确认 -> 生效”的正式流程，但必须附带补偿和审计字段
- `系统优化性改签`
  - 只产出推荐，不直接提交改签结果

## 8. 按卡型分层预约结算

### 8.1 必须把资产扣减从核销链路中拆出来

当前项目是“到店核销 -> 扣次 -> 建单”。

新规则要求变为：

- `预约成功 -> 次卡扣次 / 额度卡冻结`
- `到店签到 -> 建单`

因此必须把“预约资产结算”从现有 `verify/commit` 流程中拆出，形成独立结算能力。

### 8.2 新的资产语义

预约成功后：

- 次卡：立即扣减 1 次
- 额度卡：优先采用“先冻结、后转实扣”

如后续在 `16:00` 之前取消：

- 次卡原路返还
- 额度卡解冻

如后续未取消，哪怕用户没有到店：

- 次卡扣减仍然有效
- 额度卡在超过取消窗口且最终未到店时，自动从冻结转为扣减

### 8.3 新的结算对象

建议新增正式表：

- `appointment_settlements`

字段建议：

- `id`
- `appointment_id`
- `booking_root_id`
- `merchant_id`
- `user_id`
- `card_id`
- `asset_type`
  - `times`
  - `amount`
- `consumed_value`
- `status`
  - `consumed`
  - `refunded`
  - `transferred`
- `refunded_at`
- `transferred_to_appointment_id`
- `created_at`

设计意图：

- 次卡支持预约成功即消费一笔
- 额度卡支持预约成功先冻结
- 取消时可退款或解冻
- 改签时不重复扣减，只转移归属

### 8.4 到店后的处理

到店后不再走“扣次型核销”语义，而是走“签到建单”语义：

- 商户扫码用户预约码或预约签到码
- 校验预约状态和到店时间
- 创建 `ServiceSession`
- 不再重复扣减卡资产

这意味着：

- 预约用户的签到入口应和普通现场核销入口分开
- 或者在现有核销入口中识别 `appointment_settlement_id`，避免再次扣减

## 9. 到店与迟到规则

### 9.1 预约服务窗口固定，不顺延

如果用户预约的是：

- `10:00 - 11:00`

用户 `10:20` 到店，则服务窗口仍然是：

- `10:20 - 11:00`

而不是：

- `10:20 - 11:20`

这是新方案下“预约资源锁定”的核心前提。

### 9.2 最低可服务时长阈值

定义：

- `min_serviceable_minutes = ceil(project.duration * 10%)`

若用户到店后的剩余可服务时长：

- `remaining_minutes = reserved_end_at - actual_arrived_at`

满足：

- `remaining_minutes >= min_serviceable_minutes`

则允许服务。

否则：

- 不再提供服务
- 预约关闭原因为 `service_denied_late`
- 不触发商户未服务补偿

因为该情形属于用户迟到导致无法履约，不是商户违约。

### 9.3 迟到但仍可服务时的履约规则

当用户迟到但仍超过最低阈值时：

- 允许服务
- 服务结束时间仍以 `reserved_end_at` 为准
- 不因用户迟到延后后续预约
- 商户不得因此挤占下一位预约用户

## 10. 商户未服务与拖堂补偿

### 10.1 补偿拆成三类

本方案把补偿拆为三类：

1. `未服务补偿`
2. `拖堂占用补偿`
3. `特殊资源违约补偿`

三类都要结构化落库，但结算方式不同。

### 10.2 未服务补偿

若用户满足以下条件：

- 预约已成功
- 到店时间合法
- 剩余可服务时长仍达到最低阈值
- 商户最终未提供服务

则系统自动补偿用户：

- 次卡：补 1 次
- 额度卡：补 1 次等价额度或等价值补偿

这类补偿属于“商户未履约补偿”，建议直接写入现有 `appointment_compensations`，并新增原因类型：

- `merchant_no_service`

### 10.3 拖堂占用补偿

若商户因上一个服务或其他商户责任原因，导致预约客户实际开始服务时间晚于预约开始时间，则计算占用补偿。

补偿分钟定义：

- 若 `delay_minutes <= 1`，不补偿
- 若 `delay_minutes > 1`，补偿分钟数记为完整的 `delay_minutes`

示例：

- 晚 1 分钟：不记账
- 晚 5 分钟：记 5 分钟

### 10.4 拖堂补偿账本

现有 `appointment_compensations` 不适合直接承载“分钟累计阈值发奖”，建议新增：

- `appointment_delay_ledgers`

字段建议：

- `id`
- `appointment_id`
- `booking_root_id`
- `merchant_id`
- `user_id`
- `card_id`
- `project_id`
- `service_session_id`
- `technician_id`
- `scheduled_start_at`
- `actual_start_at`
- `delay_minutes`
- `credited_minutes`
- `service_duration_minutes`
- `unit_compensation_value`
- `created_at`

其中：

- `delay_minutes` = 实际晚点分钟
- `credited_minutes` = 实际计入补偿账本的分钟

### 10.5 累计发放规则

建议按 `card_id + merchant_id + project_id` 维度累计补偿桶。

默认推荐模型：

- 次卡项目：
  - 当累计补偿分钟 `>= project.duration`
  - 自动补 1 次
  - 并从补偿桶中扣掉一个 `project.duration`
- 额度项目：
  - 每次拖堂折算货币补偿值：
    - `credited_amount = ceil(unit_amount * credited_minutes / project.duration)`
  - 当累计金额 `>= unit_amount`
  - 自动补 1 个服务单位额度

但优化版方案下，这里不再写死为唯一规则，而是允许由项目配置决定：

- `minutes_bucket`
- `amount_bucket`
- `fixed_unit`

### 10.6 卡耗尽后的 60% 规则

`60%` 规则保留为默认推荐值，而不是唯一强制值。

默认建议：

- 当卡已经消费完成后：
  - 若剩余补偿桶 `>= 60%` 的一个服务单位
  - 系统仍自动补 1 次或 1 单位额度
- 若不足 `60%`：
  - 系统只保留账本和统计
  - 不再自动补
  - 交由商户与用户线下协商

如果项目级配置显式覆盖，则以项目级配置为准。

### 10.7 特殊资源违约补偿

该补偿专门用于以下场景：

- 客服次日临时请假
- 服务前临时离岗
- 中途离岗导致后续预约无法履约

前提：

- 系统已优先尝试保护性改签到其他客服
- 最终改签失败或用户拒绝改签

### 10.8 特殊资源违约补偿的月度分层规则

客服临时请假/离岗导致无法履约时，不再统一采用单一路径，而是按该客服当月已发生的“未履约且改签失败”次数分层：

#### 第 1 次

走`免责型特殊资源违约补偿`：

- 本次预约原路返还或解冻
- 不直接额外补一次
- 生成一笔`用户违约抵扣点`
- 抵扣点仅在该用户未来发生“同商户任意预约违约”时自动抵扣一次同等次数或额度
- 该事件记入：
  - 商户侧用户补偿记录
  - `merchant_id + technician_id` 内部责任账本

#### 第 2 次及之后

走`升级赔付型特殊资源违约补偿`：

- 本次预约原路返还或解冻
- 直接补偿用户一次同等次数，或一次同等额度
- 不再发放`用户违约抵扣点`
- 该赔付直接记入该客服责任台账
- 该记录纳入每月对账，可供薪资发放与结算参考

说明：

- 上述“次数”只统计“临时请假/离岗 + 改签失败 + 最终未履约”的事件。
- 若保护性改签成功，不计入本月次数。
- 该月度规则不影响用户侧统一看到的“商户责任”口径，只影响内部追责和补偿方式。

## 11. 对当前调度与会话链路的重构建议

### 11.1 废弃 `appointment_waiting` 作为预约常态分支

在新方案下，预约成功意味着预约时段内客服不可被其他单占用，因此：

- `appointment_waiting` 不应再作为“预约客户到店后正常等待前序现场单”的主路径

保留它只用于异常兼容场景：

- 历史脏数据
- 人工误操作
- 非预约资源占用修复

正常情况下，预约到店应直接进入：

- `room_selecting`
- `start_pending`
- `serving`

而不是进入 `appointment_waiting`。

### 11.2 自动派单必须复用预约锁定规则

当前项目里，系统自动派单和用户手动选客服存在规则不一致的问题。

新方案必须强制收敛为一套：

- 只要客服在预约占用窗口内有预约
- 自动派单就不能把该客服分配给其他用户

不存在：

- 手动不行，自动可以
- 前端看不到，调度器还能分过去

### 11.3 预约签到和现场核销分流

建议在服务会话工厂层面区分两条入口：

1. `walk_in_checkin`
2. `appointment_checkin`

其中：

- `walk_in_checkin` 才会触发资产扣减
- `appointment_checkin` 只校验预约结算记录和到店时效

### 11.4 客服请假、离岗与预约异常闭环

新方案必须显式处理三类异常：

1. `D-1` 已知次日请假
2. `D` 营业前临时请假
3. 服务中途离岗或提前下班

统一原则：

- 不再依赖客服逐单确认预约
- 依赖“次日可预约排班发布”作为预约前置条件
- 一旦发布后又发生请假或离岗，必须走保护性改签或取消补偿闭环
- 保护性改签失败后，补偿路径由“该客服当月第几次临时请假导致未履约”决定

#### 场景一：`D-1` 已知次日请假

处理方式：

1. 商户撤回该客服次日未开始的 `bookable` 时段。
2. 系统定位所有受影响的已确认预约。
3. 系统为每笔受影响预约生成保护性改签候选时段。
4. 商户发起`商户保护性改签`提议并附带补偿。
5. 用户确认后生效；若用户拒绝且无可替代时段，则取消并按规则退款/解冻/补偿。

#### 场景二：`D` 营业前临时请假

处理方式与场景一相同，但优先级更高：

1. 立即冻结该客服当日未开始预约的继续签到能力。
2. 立即触发保护性改签提议。
3. 若距预约开始时间已很近且用户未及时确认，商户不得静默改派。
4. 若无法在服务前取得用户确认，则转入特殊资源违约补偿闭环。

#### 场景三：服务中途离岗或提前下班

分两类处理：

1. `当前正在服务中的预约`
   - 默认不做强制换人继续服务
   - 若业务允许中途接力，必须用户明确同意并留痕
   - 若无法继续服务，按未服务或部分未服务规则补偿
2. `后续尚未开始的预约`
   - 立即转入保护性改签或取消补偿闭环

#### 闭环要求

以上三类异常最终只能落入以下结果之一：

- `用户确认保护性改签并成功改期`
- `预约取消并完成退款/解冻/补偿`
- `用户同意换人接续并留痕`

不允许长期停留在“线下口头承诺、系统状态不变”的中间态。

### 11.5 保护性改签失败后的补偿决策

当客服临时请假或离岗导致预约无法按原承诺履约时，系统必须按以下顺序收口：

1. 优先尝试保护性改签到其他客服
2. 若失败，则查询该客服当月已发生的“请假/离岗导致未履约且改签失败”次数
3. 按次数决定补偿路径：
   - 第 `1` 次：走`免责型特殊资源违约补偿`
   - 第 `2` 次及之后：走`升级赔付型特殊资源违约补偿`
4. 同步更新预约异常状态、用户端提示、责任账本和对账数据

## 15. 最终推荐口径

如果本项目要同时满足“预约可信度高”和“产能利用率高”，推荐采用以下优化版最终口径：

1. 预约一旦成功，预约时段内客服资源默认锁定。
2. 次日产能只卖到 `D-1 16:00`，若未满则补开到 `18:00`。
3. 改签从预约成功后即开放，但按 `16:00` 和 `18:00` 分三阶段逐步收紧。
4. `16:00` 之后不允许取消。
5. `18:00` 之后到次日营业前，不再卖新预约。
6. 改签统一拆成三类：
   - 用户主动改签
   - 商户保护性改签
   - 系统优化性改签
7. 预约结算按卡型分层处理：
   - 次卡优先采用预约成功即扣次
   - 额度卡优先采用预约成功即冻结、签到后转实扣
8. 到店迟到不顺延，只能消费剩余预约窗口。
9. 商户未服务补 1 个完整服务单位。
10. 商户拖堂超过 1 分钟记入补偿账本，但兑换规则按项目配置执行。
11. 系统保留极窄口径的“局部优化能力”，但不得引入连锁延迟。

这套方案相较当前实现的优势是：

- 规则稳定，可解释
- 商户与用户预期一致
- 不再出现“预约成功但仍被现场单压掉”的违和体验
- 仍然通过晚间补开和碎片优化保住产能效率

相较当前实现的代价是：

- 现场调度弹性会下降
- 必须重构“预约扣次”和“到店签到”的职责边界
- 需要新增两张正式业务表

但这是更合理的代价。因为如果继续允许预约被挤占，或把所有规则都做成一刀切的纯刚性，也都不是最优解。

## 16. 现有代码实现 vs 新规方案 对比评估

### 16.1 对比结论先行

如果评价标准是：

- `更适合真实线下预约制场景`
- `更能稳定提升预约用户体验`
- `更能减少预约碎片`
- `更能形成长期可运营的补偿与结算闭环`

则：

- `预约新规方案` 明显优于 `现有代码实现`

如果评价标准仅仅是：

- `当班现场吞吐最大化`
- `短期内尽量不改现有扣次与核销链路`

则：

- `现有代码实现` 在短期弹性上更占优

所以两者不是谁“绝对全维度碾压”，而是目标函数不同。

### 16.2 分维度详细对比

#### 一、真实线下场景适配度

现有代码实现：

- 更适合“预约只是参考、现场流转优先”的门店。
- 适合高 walk-in 占比、用户对准点预期较低的业态。

预约新规方案：

- 更适合“预约就是承诺”的门店。
- 更适合美业、理疗、问诊、顾问型服务等强预约场景。

评判：

- 若面向真实预约制线下门店，新规方案更适合。

#### 二、预约准点性和可解释性

现有代码实现：

- 允许条件性压预约。
- 到店后可能进入 `appointment_waiting`。
- 用户理解成本高，容易出现“明明预约成功，为何还要等”的争议。

预约新规方案：

- 预约成功即锁客服时段。
- 到店后正常情况下不应再排队等前序现场单。
- 规则更容易向商户和用户解释。

评判：

- 新规方案显著更优。

#### 三、产能利用率

现有代码实现：

- 通过弹性插单、条件压预约，短期利用率更高。
- 在高波动门店里，当班空闲时间更少。

预约新规方案：

- 通过分阶段改签、晚间补开、碎片优化来提效。
- 不靠压预约换吞吐，峰值利用率可能略低于现有实现。

评判：

- 若只看“即时吞吐”，现有代码更高。
- 若看“稳定履约 + 可复用排程”，新规方案更健康。

#### 四、预约碎片治理

现有代码实现：

- 已有碎片保护，但仍允许条件性重叠和现场挤压。
- 因为改签开启较晚、资源锁定不彻底，碎片治理是局部和被动的。

预约新规方案：

- 改签从预约成功后即开放。
- 越早移动预约，越容易把边角空洞并回完整可售段。
- 16:00 后和 18:00 后逐步收紧，只保留“更优改签”，更利于收口。

评判：

- 若目标是“更有效减少预约碎片”，新规方案更优。

#### 五、运营效率

现有代码实现：

- 商户需要更多人工解释和线下协调。
- 用户到店后等待、改派、备注处理的运营负担更重。

预约新规方案：

- 前期规则更重，但后期争议更少。
- 自动结算、自动补偿、固定窗口能降低运营沟通成本。

评判：

- 中长期看，新规方案更高效。

#### 六、实施成本和改造风险

现有代码实现：

- 成本最低，基本保持现状即可。

预约新规方案：

- 要改预约结算、签到、补偿账本、改签窗口、派单规则。
- 改造明显更重。

评判：

- 短期实施成本上，现有代码更优。

### 16.3 哪种方式更能提高产能、提高效率且减少碎片

这个问题必须拆开回答。

#### 1. 提高即时产能

现有代码实现更强。

原因：

- 它允许更激进地利用客服未来时段。
- 能把本来会被预约保留的部分空闲时间拿去接现场单。

代价：

- 会稀释预约承诺
- 会放大后续等待和补偿成本
- 会引入连锁延迟风险

#### 2. 提高稳定效率

预约新规方案更强。

这里的“稳定效率”指：

- 更少扯皮
- 更少人工改派
- 更少到店争议
- 更少预约失信
- 更少后补协调

从真实经营结果看，这种效率往往比“多塞进几单”更重要。

#### 3. 更有效减少预约碎片

预约新规方案更强。

原因不是“它更刚性”，而是：

- 它把改签从晚间补救动作，前移成全天收敛动作。
- 它要求越晚的改签越必须更优。
- 它不再允许用后续预约承担前序插单成本。

所以从碎片治理上看，新规方案是主动优化，现有代码更像被动容忍。

### 16.4 最终评判

综合评估后，结论如下：

1. 若目标是做“严格预约制门店”，新规方案优于现有代码实现。
2. 若目标是做“现场优先、预约次优先”的混合门店，现有代码实现更接近业务现实。
3. 若同时追求：
   - 预约可信
   - 产能不明显下降
   - 碎片更少
   - 运营成本更低
   则最优答案不是完全回退到现有代码，也不是机械照搬旧文档，而是采用：
   - `新规主框架`
   - `吸收现有代码里的碎片评分与候选时段算法`
   - `保留 16:00-18:00 未满补开`
   - `采用三阶段改签收敛`

## 17. 最终推荐方案

### 17.1 推荐结论

最终推荐：

- `采用优化版预约新规作为主方案`
- `不建议继续以现有代码实现作为最终业务形态`
- `也不建议原样落地纯刚性版新规`

原因：

现有代码实现的优势主要是“短期现场吞吐更高”，但这建立在牺牲预约确定性和规则可解释性的前提上。对于真实线下预约门店，这种收益不稳定，也很容易被用户投诉、补偿成本和运营协调成本吃掉。

相比之下，优化版新规虽然改造更重，但更符合线下预约业务的核心承诺：

- 约了就能按时服务
- 改签分三类且边界清晰，越晚越严格
- 取消和改签窗口清晰
- 到店与扣次分责明确
- 商户违约有正式账本

### 17.2 推荐采用的“收敛版方案”

最终不建议生硬采用“纯理论最刚性方案”，而建议采用以下收敛版：

1. 保留现有代码中的：
   - 候选时段统一校验
   - 碎片保护
   - 排布评分
   - 改签复用主规则
2. 切换为新规中的：
   - 预约成功即锁定客服时段
   - 自动派单不得绕过预约锁定
   - `D-1 16:00` 后禁止取消
   - `16:00-18:00` 未满补开
   - 三阶段改签窗口
   - 用户主动改签 / 商户保护性改签 / 系统优化性改签 三分法
   - 按卡型分层预约结算
   - 拖堂分钟账本与自动补偿
3. 把当前 `appointment_waiting` 从正常主路径降级为异常兼容路径。

### 17.3 最终一句话判断

若只问“哪个更像真实线下预约制，并且更能长期提高效率、减少碎片”，答案是：

- `预约新规方案更优`

若只问“哪个更容易继续沿用当前代码，并在短期内把现场单尽量塞满”，答案才是：

- `现有代码实现更优`

但本项目若要走预约能力升级路线，应选择前者，而不是后者。

## 18. 可直接执行落地的优化版方案

### 18.1 方案定义

本节给出的是下一步可以直接拆任务落地的执行版本，不再停留在“方向性原则”层面。

其核心定义是：

- `统一预约主引擎`
- `单一业务机制，不保留两套并行预约制度`
- `保留少量策略参数，不保留机制分叉`
- `在强预约底座上，允许极窄口径的局部优化`

### 18.2 统一预约主引擎

所有入口统一走一套排程和校验内核：

- 可预约时段查询
- 创建预约
- 确认预约
- 改签查询
- 改签提交
- 现场派单
- 自动派单
- 到店签到

统一内核必须同时输出：

- `reserved_start_at`
- `reserved_end_at`
- `occupied_end_at`
- `placement_score`
- `fragment_delta`
- `policy_decision`

这里的 `policy_decision` 只允许三类结果：

- `allow`
- `allow_with_recommendation`
- `deny`

不再使用会把后续预约拖入不确定状态的“条件性压预约”语义。

### 18.3 统一策略档位

机制保持一套，但预留策略档位。

建议后端先支持：

- `strict`
- `balanced`
- `flex`

但第一阶段只开放：

- `balanced`

给商户使用。

含义如下：

#### `strict`

- 预约成功后完全硬锁定
- 不允许任何局部重排
- 只允许用户主动改签和商户保护性改签

适合：

- 强预约、强准点场景

#### `balanced`

- 预约资源默认硬锁定
- 允许极窄口径的局部优化
- 不允许引入第二个受影响预约

适合：

- 大多数线下预约门店

#### `flex`

- 仅作为未来保留档
- 当前阶段不建议开放

原因：

- 它很容易重新滑回现有代码的“混合调度”路径

### 18.4 `balanced` 档的局部优化边界

`balanced` 档不是重新允许压预约，而是只允许以下两类受控动作：

1. `同客服相邻空洞重排`
   - 只能在同一客服、相邻时段内发生
   - 不能新增第二位受影响预约用户
   - 不能让任何已确认预约的开始时间变晚超过商户设定阈值

2. `保护性改签`
   - 仅在商户责任或系统资源异常时触发
   - 必须带补偿和审计记录

明确禁止：

- 为了接现场单去压后任意预约
- 因 A 单挤压导致 B、C、D 连锁后移
- 为了短期利用率打破既有预约承诺

### 18.5 改签的执行版本

三类改签共用三阶段时间窗，但权限不同：

#### 阶段 A：自由调仓

- 时间：预约成功后至 `D-1 16:00`
- 允许取消
- 允许用户主动改签
- 允许商户保护性改签
- 系统优化性改签可推荐
- 允许新预约
- 改签条件：
  - 严格无冲突
  - 不制造不可复用碎片
  - `score(target) >= score(current)`

#### 阶段 B：尾盘收敛

- 时间：`D-1 16:00-18:00`
- 不允许取消
- 未约满可继续卖
- 用户主动改签、商户保护性改签仍可用
- 系统优化性改签可推荐
- 用户主动改签条件：
  - `score(target) > score(current)`

#### 阶段 C：冻结前修复

- 时间：`D-1 18:00` 至 `D` 营业开始前
- 不允许新预约
- 不允许取消
- 用户只允许一次主动改签
- 商户保护性改签仍可用
- 系统优化性改签只可推荐
- 用户主动改签条件：
  - `score(target) > score(current)`，或
  - 商户责任 / 资源异常

### 18.6 结算的执行版本

不建议第一版继续坚持“一刀切全部预约成功即实扣”。

更优执行版本如下：

#### 次卡

- 预约确认成功即扣次
- `D-1 16:00` 前取消返还
- 改签不重复扣次

#### 额度卡

- 预约确认成功先冻结额度
- 到店签到后转为实扣
- `D-1 16:00` 前取消解冻
- 超过取消窗口未取消且最终未到店，则自动转为扣减

这样做的原因是：

- 次卡天然适合强承诺扣减
- 额度卡更适合先冻结、后结算，财务口径更稳

### 18.7 补偿的执行版本

补偿直接拆成三条产品链：

#### A. 未服务补偿

- 用户合法到店
- 商户未服务
- 直接补 1 个服务单位

#### B. 延迟补偿

- 拖堂超过 `1` 分钟
- 进入 `appointment_delay_ledgers`
- 是否兑现、何时兑现，不再统一写死为“满一个时长补一次”

#### C. 特殊资源违约补偿

适用于：

- 客服临时请假
- 服务前临时离岗
- 中途离岗导致后续预约无法履约

规则：

- 先尝试保护性改签到其他客服
- 仅在改签失败后触发
- 按该客服当月已发生次数分层：
  - 第 `1` 次：
    - 返还或解冻本次预约
    - 不直接补一单
    - 生成`用户违约抵扣点`
  - 第 `2` 次及之后：
    - 返还或解冻本次预约
    - 直接补偿一次同等次数或同等额度
    - 不再生成抵扣点
    - 直接记入该客服责任台账

建议新增项目级配置：

- `delay_tolerance_minutes`
- `delay_compensation_mode`
  - `minutes_bucket`
  - `amount_bucket`
  - `fixed_unit`
- `delay_redeem_threshold_percent`

原因：

- 不同项目时长、客单价、补偿习惯差异很大
- 统一分钟桶只适合作为默认模型，不适合作为唯一模型

### 18.8 到店链路的执行版本

预约到店后不再默认走现有“核销即扣次”主语义，而是拆成：

1. `appointment_check_in`
2. `walk_in_verify`

其中：

- `appointment_check_in`
  - 校验预约状态、时间窗、结算记录
  - 创建 `ServiceSession`
  - 不重复扣减
- `walk_in_verify`
  - 继续保留现有核销扣减逻辑

### 18.9 可以直接开工的 P0 / P1 / P2

#### P0

- 统一自动派单和手动选人规则
- 去掉现有会引入连锁延迟的压预约路径
- 上线三阶段改签窗口
- 保留当前碎片评分与候选时段算法

#### P1

- 新增 `appointment_settlements`
- 实现次卡实扣、额度卡冻结
- 新增预约签到入口
- 把 `appointment_waiting` 降级为异常兼容

#### P2

- 新增 `appointment_delay_ledgers`
- 接入项目级补偿规则
- 跑通自动兑现与审计报表

### 18.10 最终执行建议

如果现在就要进入实施，最推荐的落地顺序是：

1. 先做 `P0`
   - 先把最危险的连锁延迟和规则不一致收住
2. 再做 `P1`
   - 把预约承诺和资产结算做实
3. 最后做 `P2`
   - 把补偿从人工处理升级成正式账本

这就是当前项目下一步最科学、最可执行、也最容易分阶段交付的优化版方案。

## 20. 方案复核与直接执行性确认

### 20.1 复核结论

经过对整份方案复核，当前优化版方案在业务上是自洽的，可以直接进入开发落地。

原因：

1. 目标明确：
   - 解决连锁延迟
   - 保住预约承诺
   - 兼顾产能和碎片治理
2. 机制统一：
   - 不保留两套并行预约制度
   - 只保留一套主引擎和少量策略参数
3. 分期清晰：
   - `P0` 先控风险
   - `P1` 再做结算重构
   - `P2` 最后补齐补偿账本

### 20.2 已确认自洽的关键点

- 改签窗口与取消窗口不冲突：
  - `16:00` 前可取消，也允许用户主动改签 / 商户保护性改签 / 系统优化性改签推荐
  - `16:00` 后取消关闭，但改签窗口继续开放
- 预约承诺与即时产能不再直接冲突：
  - 通过晚间补开和提前改签优化，而不是压预约
- 预约确认与人员排班职责清晰：
  - 商户负责先发布次日可预约排班
  - 系统负责基于已发布排班自动确认预约
- 三类改签的生效边界清晰：
  - 用户主动改签校验通过后直接生效
  - 商户保护性改签必须用户确认
  - 系统优化性改签只做推荐
- 结算与履约职责清晰：
  - 预约确认处理结算
  - 到店签到只建单
- 补偿与违约职责清晰：
  - 未服务补偿
  - 拖堂账本补偿
  - 临时请假特殊资源违约补偿

### 20.3 需要作为实现前提的约束

以下约束应在开发前明确，否则容易出现实现分叉：

1. 第一阶段不开放 `strict` 和 `flex` 给商户，只落地 `balanced`。
2. 第一阶段不实现“系统主动为用户自动改签到新时段”，只提供推荐和受控提交。
3. 第一阶段系统优化性改签默认关闭，即使代码预留接口也不对商户开放。
4. 第一阶段不做跨客服、多预约全局重排，只做局部相邻优化。
5. 第一阶段额度卡统一采用“先冻结、后转实扣”，不与次卡共用扣减路径。
6. 第一阶段必须先落地“次日可预约排班发布”，否则不应直接切换到自动确认预约。
7. 第一阶段即需落地客服当月免责次数计数器，否则无法正确区分“第 1 次抵扣点”与“第 2 次直接赔付”。

确认可以直接进入开发。

推荐执行顺序：

1. 先按 `19.1-19.3` 完成 `P0`
2. 验证预约锁定、取消、改签、自动派单一致性
3. 再进入 `P1`
4. 最后做 `P2`

## 21. 新方案重构后预约功能完整使用说明

### 21.1 用户端使用说明

#### 预约

1. 用户选择商户、卡和项目。
2. 系统只展示“已发布次日排班”中，且符合营业时间、资源锁定和碎片规则的可预约时段。
3. 用户提交预约后，系统按统一算法自动判断是否可预约成功，不需要客服本人逐单确认。
4. 预约确认后：
   - 次卡立即扣次
   - 额度卡先冻结额度
5. 用户在预约详情中可查看：
   - 预约时间
   - 锁定客服
   - 是否可取消
   - 是否可发起用户主动改签
   - 是否存在保护性改签入口
   - 结算状态

#### 取消

1. `D-1 16:00` 前可取消。
2. 取消前系统优先推荐更优改签时段。
3. 若用户仍选择取消：
   - 次卡返还
   - 额度卡解冻
4. `D-1 16:00` 后不可取消。

#### 用户主动改签

1. 预约成功后即可发起用户主动改签。
2. 系统按当前阶段返回可主动改签时段：
   - 阶段 A：可改到不劣于当前的时段
   - 阶段 B/C：只能改到更优时段
3. 每次预约默认只有一次用户主动改签机会。
4. 用户提交后，系统再次校验目标时段；校验通过则自动生效，不需要商户或客服确认。
5. 用户主动改签不会重复扣减或冻结。

#### 商户保护性改签

1. 若属于门店责任或资源异常，商户可发起保护性改签。
2. 保护性改签不占用用户主动改签次数。
3. 保护性改签必须附带补偿和审计说明。
4. 保护性改签必须经用户确认后才生效。
5. 若改签失败，系统按该客服当月免责次数决定走“违约抵扣点”还是“直接补一次/同额”。

#### 客服临时请假的补偿

1. 若因客服临时请假或离岗导致最终无法履约，系统先尝试保护性改签。
2. 若改签失败：
   - 该客服当月第 `1` 次：返还/解冻本次预约，并给用户一笔违约抵扣点
   - 第 `2` 次及之后：返还/解冻本次预约，并直接补一次同等次数或同等额度
3. 用户可在预约详情查看补偿结果。

#### 系统优化性改签推荐

1. 默认关闭。
2. 开启后，系统只会推荐更优时段，不会自动替用户改签。
3. 用户或商户确认后，仍然走正式改签提交流程。

#### 到店

1. 用户到店后由商户执行预约签到。
2. 若仍满足最低可服务时长，则建单进入服务。
3. 若用户迟到导致剩余时长不足最低阈值，则不提供服务。

### 21.2 商户端使用说明

#### 查看预约

商户可在预约列表看到：

- 预约时间
- 预约客服
- 锁定区间
- 结算状态
- 用户主动改签次数
- 补偿状态
- 客服当月免责次数状态

#### 发布次日排班

1. 商户需先发布次日可预约排班。
2. 只有被发布为可预约的客服和时段，才会对用户开放预约。
3. 若客服次日不确定能上班，则不应发布到可预约库存中。

#### 确认预约

1. 标准模式下，预约不依赖客服本人逐单确认，而是依赖次日排班先行发布。
2. 用户命中已发布库存后，系统自动确认预约并锁定客服时段。
3. `PUT /merchant/appointments/:id/confirm` 仅保留给兼容期或异常处理场景，不应再作为长期主流程。

#### 处理改签

1. 商户可查看用户是否还有主动改签机会。
2. 若属于门店责任或资源异常，可发起保护性改签。
3. 保护性改签必须留痕并带补偿，且需用户确认。
4. 若后续开启系统优化性改签，商户只能查看推荐，不可让系统自动落单。

#### 处理请假与离岗

1. 若客服次日请假，商户应立即撤回对应可预约排班并触发受影响预约扫描。
2. 系统给出保护性改签候选后，商户向用户发起保护性改签提议。
3. 若用户拒绝或无可替代时段，则按取消补偿闭环处理：
   - 该客服当月第 `1` 次：返还/解冻 + 违约抵扣点
   - 第 `2` 次及之后：返还/解冻 + 直接补一次/同额
4. 若客服当日中途离岗，后续未开始预约立即转入保护性改签或取消补偿闭环。

#### 到店签到

1. 商户对预约单执行签到。
2. 系统创建 `ServiceSession`。
3. 预约单不再重复走普通核销扣减流程。

### 21.3 系统自动处理说明

系统会自动处理以下事项：

- 基于已发布排班生成可预约库存
- `16:00` 后禁止取消
- `16:00-18:00` 未满补开
- `18:00` 后关闭新预约
- 自动派单避开预约锁定窗口
- 客服请假后的受影响预约扫描
- 客服当月免责次数统计
- 额度冻结转实扣
- 超窗未到店的关闭与结算推进
- 商户未服务补偿
- 特殊资源违约补偿分层：
  - 第 `1` 次生成违约抵扣点
  - 第 `2` 次及之后直接补一次/同额
- 拖堂账本累计与兑现

### 21.4 典型业务流程说明

#### 流程一：普通成功预约

1. 用户预约明天 `10:00`
2. 商户确认
3. 系统锁定客服时段
4. 次卡扣次或额度冻结
5. 用户次日到店签到
6. 创建服务会话并服务完成

#### 流程二：用户提前改签

1. 用户预约后发现原时段不方便
2. 在 `D-1 16:00` 前发起用户主动改签
3. 系统返回不劣于当前排布的目标时段
4. 用户确认改签
5. 原预约关闭，新预约承接原结算记录

#### 流程三：超窗不可取消但可改签

1. 到了 `D-1 16:00` 后
2. 用户不能取消
3. 若存在更优时段，仍可在规则内发起用户主动改签

#### 流程四：合法到店但商户未服务

1. 用户准时或在可接受迟到范围内到店
2. 商户最终未提供服务
3. 系统生成未服务补偿
4. 用户获得 1 个完整服务单位补偿

#### 流程五：客服临时请假且改签失败

1. 商户标记客服请假或离岗
2. 系统扫描受影响预约并生成保护性改签候选
3. 若用户拒绝或无可替代时段，则进入取消补偿闭环
4. 若该客服当月为第 `1` 次：
   - 返还/解冻本次预约
   - 给用户记一笔违约抵扣点
5. 若该客服当月为第 `2` 次及之后：
   - 返还/解冻本次预约
   - 直接补一次同等次数或同等额度
   - 记入该客服责任台账

#### 流程六：商户拖堂

1. 用户预约 `10:00`
2. 实际开始服务为 `10:08`
3. 系统记入 `8` 分钟拖堂账本
4. 达到项目配置阈值后自动兑现补偿
