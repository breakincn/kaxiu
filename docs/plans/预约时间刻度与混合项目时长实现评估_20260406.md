# 预约时间刻度与混合项目时长实现评估

日期：2026-04-06  
执行者：Codex

## 1. 结论

当前项目里，`预约时段展示粒度` 就是控制预约时间刻度的配置项，对应字段为 `appointment_slot_granularity_minutes`。

当前代码并没有真正实现《预约项目时长分层产品方案》里描述的“两套预约算法”：

- 单一项目时长商户：不是独立一套 5 分钟取整算法
- 混合项目时长商户：也不是“客服维度拆成多个单一时长组时间轴”

当前线上实现本质上只有一套统一规则：

1. 预约开始时间统一按商户粒度 `appointment_slot_granularity_minutes` 生成。
2. 单次预约占用时间按 `项目服务时长 + 项目间隔时间` 直接计算。
3. 再基于已发布排班、营业时间、预约冲突、碎片保护规则筛选可用时段。

因此：

- 单一项目时长：`统一刻度 + 固定占用长度`
- 混合项目时长：`统一刻度 + 可变占用长度`

## 2. 当前实现对应代码

### 2.1 时间刻度来源

后端读取商户粒度的入口：

- `backend/handlers/appointment_policy.go`
- `merchantAppointmentSlotGranularityMinutes`

当前逻辑：

- 商户有配置值时，使用商户值
- 商户未配置或非法时，使用默认值
- 本次已将默认值从 `15` 分钟调整为 `5` 分钟

候选开始时间生成入口：

- `backend/handlers/appointment.go`
- `buildAvailableTimeSlotsPayload`

生成方式：

- `for t := interval.Start; !t.After(latestStart); t += granularity`

说明：

- 这意味着当前开始时间候选完全取决于 `appointment_slot_granularity_minutes`
- 不是按项目时长动态决定刻度

### 2.2 占用时间来源

项目预约占用时间入口：

- `backend/handlers/project_timing.go`
- `resolveProjectBookingConfig`
- `projectBookingOccupiedMinutes`

当前逻辑：

- `occupied_minutes = duration + service_gap_minutes`

说明：

- 当前没有把占用分钟数再向上取整到 5 分钟倍数
- 也没有区分“单一时长商户”和“混合时长商户”的不同占用规则

### 2.3 混合项目时长下的客服限制

当前代码没有实现以下能力：

- 客服绑定“可预约项目集合”
- 发布排班前校验“同一客服是否属于单一时长组”
- 禁止“同一客服同时开放多个不同时长项目”

证据：

- `listAppointmentBookableTechnicians` 只返回可预约客服，不按项目或时长组过滤
- 当前没有“客服可预约项目”数据结构参与预约时段生成

因此当前混合项目时长商户的真实策略是：

- 商户整体可以有多种项目时长
- 同一客服也可能被用于不同项目时长
- 但所有项目仍然共用同一个商户级时间刻度

## 3. 单一项目时长与混合项目时长的实现区别

### 3.1 单一项目时长

单一项目时长商户下：

- 所有项目的 `duration + gap` 一样
- 统一刻度下，所有候选时段的占用长度一致
- 用户看到的预约节奏更稳定

例子：

- 商户粒度 `5`
- 项目统一占用 `48`
- 则用户会看到 `09:00/09:05/09:10...`
- 但真正能放下的可用时段，会按 `48` 分钟占用结果筛选

这种情况下，虽然不是文档里“向上取整到 5”，但因为占用长度固定，整体表现仍然比较规整。

### 3.2 混合项目时长

混合项目时长商户下：

- 所有项目共享一个统一刻度
- 不同项目有不同的 `duration + gap`
- 候选开始时间仍然从同一套网格上生成

例子：

- 商户粒度 `5`
- 项目 A 占用 `48`
- 项目 B 占用 `63`
- 两个项目都从 `09:00/09:05/09:10...` 这套网格里挑开始时间

这意味着当前混合时长不是“不同客服不同时间轴”，而是“统一时间轴上承载不同长度的占用块”。

## 4. 时间刻度差异

### 4.1 当前代码下是否存在两套刻度

不存在。

当前代码里：

- 单一项目时长商户：用商户粒度
- 混合项目时长商户：也用商户粒度

差别不在刻度，而在占用长度是否固定。

### 4.2 当前混合项目时长商户采用什么刻度

当允许同一客服开放服务时长不同的项目时，当前混合项目时长商户采用的仍然是：

- `appointment_slot_granularity_minutes`

也就是商户级统一时间刻度。

不是：

- 客服级刻度
- 项目级刻度
- 时长组级刻度

## 5. 是否会产生碎片

### 5.1 单一项目时长 + 5 分钟刻度

若单一项目时长商户改为 `5` 分钟粒度：

- 碎片风险通常较低
- 因为占用长度固定，全天时间轴重复模式稳定
- 用户看到的时段也更细，但不会因为多项目时长混排而快速碎裂

需要注意：

- 当前实现没有做“占用长度向上取整到 5 分钟倍数”
- 所以即使刻度是 5，若项目占用是 `48` 分钟，下一个可放位置是由冲突判断决定的，而不是自然落在 `50` 分钟节奏上
- 这比文档目标略差，但仍然比 15 分钟粒度更细致

结论：

- 单一时长项目采用 `5` 分钟粒度，当前实现下通常不会产生很多不可控碎片
- 但仍不如文档方案里“开始时间 5 分钟刻度 + 占用向上取整到 5 倍数”那么规整

### 5.2 混合项目时长 + 5 分钟刻度

混合项目时长采用 `5` 分钟粒度时：

- 候选开始时间会显著增多
- 不同时长项目在同一客服时间轴上交错时，更容易形成短碎片
- 当前虽然有 `evaluateAppointmentFragmentImpact` 做碎片保护
- 但它只是“避免明显不可复用碎片”，不是从产品规则层面解决“混合时长同轴”的问题

结论：

- 混合项目时长采用 5 分钟粒度，碎片风险会高于单一时长
- 尤其在“同一客服可接 45/60/90 分钟项目”时最明显
- 当前实现能兜底一部分，但无法从根上消除碎片增长

## 6. 更优方案

### 6.1 短期可落地方案

建议分两层处理：

1. 平台默认粒度改为 `5` 分钟
2. 单一项目时长商户优先推荐使用 `5` 分钟
3. 混合项目时长商户允许继续使用 `5` 分钟，但在商户端提示“若同一客服开放不同时长项目，碎片风险更高”

这一层已经完成的代码调整：

- 后端默认兜底值改为 `5`
- 模型默认值改为 `5`
- 前端预约设置默认值改为 `5`
- 数据库列默认值迁移改为 `5`

### 6.2 中期产品改造方案

建议按文档真正落地“时长组”：

1. 每个客服增加“次日可预约项目集合”
2. 发布预约排班时校验这些项目是否属于同一时长组
3. 若同一客服存在多个不同时长组，默认禁止发布
4. 混合项目时长商户通过“不同客服承接不同项目时长组”实现，而不是在同一客服时间轴上混排

这样可以把混合项目时长问题从：

- 算法兜底问题

转成：

- 资源配置问题

这是更稳定的产品路线。

### 6.3 长期算法方案

若未来坚持支持“同一客服同时开放多种时长项目”，建议单独做：

1. 客服级时间轴建模
2. 项目级候选时段生成
3. 碎片成本评分
4. 候选时段排序而不是简单可用/不可用

但这会显著提高：

- 排班发布复杂度
- 改签复杂度
- 请假修复复杂度
- 用户理解成本

不建议作为默认模式。

## 7. 推荐实施计划

### P0

- 默认预约展示粒度改为 `5` 分钟
- 单一时长商户优先使用 `5` 分钟粒度
- 商户端文案明确区分“单一时长更适合 5 分钟粒度，混合时长需要谨慎”

### P1

- 排班配置增加“客服可预约项目”
- 发布前校验“同一客服单一时长组”
- 混合时长客服禁止发布

### P2

- 若业务坚持支持“同一客服混合时长项目”，再单独设计高复杂度时间轴算法
- 该模式不应作为默认能力
