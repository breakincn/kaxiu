# 用户主动改签回归预约系统实施方案

**日期**：2026-04-08
**执行者**：Codex

## 背景与现状问题

当前用户主动改签继承了自动排产导向的“更优过滤”逻辑，并且历史上曾混入“跨日改签到明天”的旧窗口判断：

- 用户端改签时段列表会先通过营业时间、已发布排班、硬冲突、碎片保护等硬约束筛选。
- 筛选后还会继续按 `PlacementScore` 与当前预约做比较。
- 在旧的跨日窗口里，仅保留“更优于当前”的时段。

这个口径更像自动排产系统，而不是预约系统。实际结果是：

- 空闲客服的可执行时段可能完全不展示。
- 用户改签成功率被“是否更优”强约束压低。
- 用户主动改签被做成“提交申请，待商户确认”，与预约系统的自助改签语义不一致。

## 本次目标

把用户主动改签收敛为更偏预约系统的产品语义：

- 展示全部硬约束可执行的时段。
- 排布评分仅保留为推荐和标注，不再作为用户主动改签列表的硬门槛。
- 用户主动改签提交后直接生效，不再走待商户确认流。
- 用户主动改签只允许留在原预约服务日内，不允许跨日改签。
- 用户主动改签默认截止到服务开始前 `60` 分钟。
- 商户保护性改签、请假异常修复、推荐接口保持现有职责，不混改。

## 新旧口径对比

### 旧口径

- 用户端 `reschedule-slots` 返回的是“更优过滤后的列表”。
- 旧实现允许跨到明天，且会受旧阶段口径影响。
- 用户提交改签后生成 `pending_merchant` 请求。
- 商户确认后才真正执行改签。

### 新口径

- 用户端 `reschedule-slots` 返回“全部硬约束可执行时段”。
- `comparison_kind` 继续返回，但只做展示与推荐。
- 用户提交改签后直接在事务内执行。
- 同时落一条 `accepted` 改签审计记录。
- 后端资格统一返回 `same_day_only`，只放行原预约服务日。
- 超过截止时间后直接返回不可改签原因。

## 后端行为设计

落点文件：`backend/handlers/appointment.go`

### 用户端时段查询

- `GET /user/appointments/:id/reschedule-slots`
- 保留 `buildAvailableTimeSlotsPayload(...)` 的硬约束能力：
  - 已发布排班
  - 营业时间
  - 硬冲突
  - 碎片保护
  - 项目适配
  - 请假保护修复限制
- 改签资格先校验：
  - 目标日期必须等于原预约服务日
  - 当前时间必须早于 `appointment_time - appointment_reschedule_deadline_minutes_before_start`
- 不再对用户端时段调用“按更优过滤”的逻辑。
- 改为仅写入：
  - `comparison_kind`
  - `comparison_label`

### 用户主动改签提交

- `POST /user/appointments/:id/reschedule-requests`
- 在普通用户主动改签场景下：
  - 不再创建 `pending_merchant`
  - 直接执行改签事务
  - 事务内完成预约关闭、新预约创建、结算迁移、审计落账
- 同时保留一条改签请求记录作为审计：
  - `status = accepted`
  - `proposed_by_type = user`
  - `confirmed_by_type = user`
  - `confirmed_at = now`
  - `result_appointment_id = 新预约ID`

### 其他链路保持不变

- 商户/员工发起的保护性改签仍然走待确认提议流。
- `GET /user/appointments/:id/reschedule-recommendations` 继续只返回推荐候选。
- 商户端 `reschedule-slots` 继续保留现有更优过滤口径。

## 前端交互设计

落点文件：`frontend/src/views/user/CardDetail.vue`

### 改签弹窗

- 显示全部可改签时段。
- 顶部提示改为：
  - `当前规则仅允许改签到原预约日内的其他营业时段`
- 保留时段标签：
  - `better` => `更优于当前`
  - `not_worse` => `不劣于当前`
  - `worse` => 不隐藏，保持普通可选

### 客服选择

- 不再主动剔除原客服。
- 用户可以：
  - 原客服改时间
  - 换客服改签

### 提交结果

- 普通用户主动改签成功后：
  - 关闭弹窗
  - 刷新详情
  - 提示 `改签成功，新的预约已生效`
- 仅当接口返回 `mode = pending` 时，才显示待确认语义。

## 风险与边界

- 本次只放宽“更优过滤”，不放宽硬约束。
- 不再支持跨日补救改签。
- 中间时段变多后，用户可见选择会增多，但不会突破碎片保护和硬冲突底线。
- 用户主动改签即时生效后，旧的“商户确认”心智会被移除；商户保护性改签仍然保留双向确认。
- 当前不扩展跨预约链路历史展示；用户主动改签完成后，新预约页不再携带旧预约的 pending 记录，这一行为保持现状。

## 测试与验收口径

后端验证重点：

- 用户端 `reschedule-slots` 返回中存在 `worse` 但硬约束可行的时段。
- 用户主动改签提交后直接生效。
- 审计请求记录为 `accepted` 且 `confirmed_by_type = user`。
- 旧预约被关闭为 `rescheduled`。
- 新预约生效、结算迁移正确。
- 请假保护性改签仍要求商户发起。
- 推荐接口仍只返回推荐集合。
