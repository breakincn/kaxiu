# 改签及补偿计划方案与实施对照清单

## 目标
在既有“预约确认 -> 占产能 -> 到店核销 -> ServiceSession”闭环基础上，补齐商户端正式的改签与补偿能力，避免继续依赖单纯备注处理预约冲突。

本次实现聚焦三个核心能力：
- 双边确认的改签到新时间
- 补偿类型选择并执行
- 原预约关闭 + 新预约生成并形成可追溯关系

## 功能方案

### 一、动作边界

#### 取消
- 含义：本次预约终止，不再继续服务。
- 适用状态：`pending`、`confirmed`。
- 当前实现：保留原有取消能力。

#### 改签
- 含义：本次预约继续，但改到新的时间，必要时改客服或项目。
- 适用状态：`confirmed`、`arrived`、`failed`。
- 实施规则：
  - 改签先生成“改签提议”，由对方确认后才执行。
  - 用户发起改签，状态进入 `pending_merchant`，等待商户确认。
  - 商户发起改签，状态进入 `pending_user`，等待用户确认。
  - 只有提议被接受后，才执行“关闭旧预约 + 创建新预约”。
  - 新预约仍走预约保护规则，校验营业时间和客服可用性。
  - 若旧预约已经到店但还未开始正式服务，先撤销本次到店占用，再完成改签。

#### 补偿
- 含义：因门店未兑现预约承诺，对客户做正式补回。
- 展示原则：
  - `confirmed / 待到店` 不提前显示补偿。
  - `arrived` 且已产生等待/服务冲突时显示补偿。
  - `completed`、`failed` 允许补录补偿。
- 当前补偿类型：
  - `extra_times`：补次数，立即增加卡片总次数与剩余次数
  - `extend_minutes`：补时长，立即延长当前关联服务会话
  - `discount_note`：优惠减免记录，形成正式补偿单与备注
  - `other_note`：其他补偿记录，形成正式补偿单与备注

### 二、改签流程
1. 用户或商户在预约卡片发起改签。
2. 发起方选择新的日期、时间段、客服，并填写改签原因。
3. 系统创建 `appointment_reschedule_requests` 提议记录。
4. 对方在自己的端上看到“待我确认”的改签提议。
5. 对方确认后在事务内执行：
   - 锁定旧预约
   - 校验旧预约状态是否允许改签
   - 若已到店但未开始服务，撤销 usage / service_session 占用
   - 创建新预约
   - 关闭旧预约并写入 `closed_reason=rescheduled`
   - 互相回写 `replaces_appointment_id / replaced_by_appointment_id`
   - 将改签提议更新为 `accepted`
6. 若对方拒绝，则改签提议更新为 `rejected`，原预约保持不变。

### 三、补偿执行流程
1. 商户在预约卡片点击“补偿”。
2. 弹窗选择补偿类型、数值、原因和备注。
3. 系统创建正式补偿记录 `appointment_compensations`。
4. 按补偿类型立即执行：
   - `extra_times`：回充卡次数
   - `extend_minutes`：延长关联服务会话时长和预计结束时间
   - `discount_note / other_note`：保留正式记录与预约处理备注
5. 补偿记录状态推进为 `applied`，并回写预约的 `resolution_note`。

## 保留兼容
- 历史 `resolution_note` 仍保留，继续作为预约处理摘要展示。
- `discount_note` 与 `other_note` 当前落为正式补偿记录 + 备注，不直接联动营销或财务系统。
- 原取消接口与既有预约列表接口保持兼容。
