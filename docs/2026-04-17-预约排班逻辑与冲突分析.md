# 问答记录

**时间**：2026-04-17  
**执行者**：Codex  
**提问**：结合文档分析介绍 预约排班逻辑，及用户什么时候可以预约，可以撤销，及现有预约排班与，文档中的用户预约有没有冲突，如何解决冲突

**回答**：

当前预约体系分为三层：

1. 预约排班发布：客服或商户把某一天可预约的时间段发布出去，数据落在 `technician_schedule_publishings`。
2. 用户预约：用户只能基于已发布排班选择可用时段，创建 `Appointment`。
3. 履约与异常：预约到店后进入 `ServiceSession`，改签、取消、补偿、失约等作为预约履约异常处理。

文档的核心口径是“预约不是排队”。预约表示未来时段承诺，排队表示现场服务流转。预约会占用未来产能，也会影响现场单是否能插入，但不应该再用“前面排队几人”这类排队语义解释预约。

现有代码中的用户预约规则：

- 商户必须开启预约。
- 卡必须属于当前用户和当前商户，且卡不能锁定。
- 用户只能预约明天。
- 用户预约明天的开放时间是今天 10:00 之后。
- 预约时间必须在营业时间内。
- 预约时段必须命中已发布排班。
- 项目必须在线可预约，且项目时长有效。
- 同一卡、同商户、同用户只能有一个 `pending/confirmed` 活跃预约。
- 创建时会在事务里重新检查客服、项目时长、时间占用、碎片保护、混合时间轴等硬约束，避免并发超卖。
- 创建成功后当前实现直接置为 `confirmed`，不是待商户确认。

用户撤销/取消规则：

- 用户可以取消 `pending/confirmed` 预约。
- 普通次日预约创建时，直接取消截止时间是预约当天的 16:00。
- 超过直接取消截止时间后，用户端会改为发起取消申请，状态为 `pending_merchant`，待商户确认。
- 用户主动改签只允许原预约服务日内，并且默认要求距离预约开始至少 60 分钟；提交后即时生效。
- 商户或客服距预约开始不足 5 小时不能直接取消，只能走取消申请；若有高质量修复方案，应优先保护性改签。

截图中的“我的预约排班”不是用户预约入口，而是客服端排班发布入口。它的含义是：客服在指定时间前发布自己当天或次日可被预约的工作安排。截图日期是 2026-04-17，说明当前页面正在展示 2026-04-17 的排班发布状态。

冲突判断：

1. 主链不冲突。文档要求预约回归“预约状态/履约”，现有用户端已经展示为“预约状态”，后端也用预约占用未来产能，不再把预约当现场排队。
2. 文案存在混淆。客服端叫“预约排班”，用户端叫“预约状态”，如果不解释，很容易让人误以为用户是在看“今天可预约排队”。应明确改成“我的可预约时间”或“发布可预约时段”。
3. 排班撤销存在业务冲突。当前撤销已发布排班时，会同时取消该日期 `pending/confirmed` 预约。这与文档中“预约是履约承诺，异常应走改签/取消/补偿闭环”的方向存在冲突，尤其是已被用户预约后直接撤销。

建议解决方式：

1. 页面命名拆清：客服端用“我的可预约时间 / 发布预约时段”，用户端继续用“预约状态 / 预约履约”。
2. 规则拆清：排班发布负责开放产能，用户预约负责占用产能，现场排队只负责到店后的实时等待。
3. 撤销逻辑分层：没有用户预约时允许撤销排班；已有用户预约时不应静默直接取消，应该进入请假/异常修复流程，先生成受影响预约列表，再优先保护性改签，确实无方案时才发起取消申请和补偿。
4. 时间窗口统一：用户预约开放前，排班可以自由发布/撤销；用户预约产生后，排班变更应走异常履约流程，不再当成普通撤销。
5. 文案修正：截图非今日场景中的“发布后日预约排班”应按实际目标日期改成“发布该日期预约排班”，避免和用户只能预约明天的规则混淆。
