# 问答记录
**时间**：2026-04-20 11:55:20 +0800
**提问**：现在如果该项目配置的服务人员是 A 和 B, 那么核销时是 A, 则核销后自动进入待服务开始状态，而且 A 也自动进入已扫码待开始服务状态，那么 B 的状态是什么，B 是否还有单独扫其他任何一个已核销的 该项目服务用户后，才能进入以扫码待开始服务状态？
**回答**：结论：B 不会因为 A 核销或 A 已扫码，就自动进入“已扫码待开始服务”状态；B 仍然是普通空闲/未确认状态。只有当 B 自己去扫码某个已核销、且属于该项目默认服务人员集合内的服务单后，系统才会把 B 记入该服务单的“已扫码待开始服务”人员列表。

依据如下：

1. 核销创建服务会话时，如果项目配置了默认服务人员 A、B：
   - 会话会写入 `service_technician_ids = [A, B]`
   - 兼容主服务人员字段 `technician_id` 默认只会先绑定第一个人（通常是 A）
   - 初始状态是 `cs_start_pending`
   - 此时还没有把 B 自动写进 `start_confirmed_technician_ids`

2. 如果核销人本身是该项目默认服务人员之一（例如 A），并且当前是“核销即确认待开始”的那条路径：
   - 会话会进入 `cs_delay_pending`
   - `start_confirmed_technician_ids` 只会先记录当前确认的人，例如 `[A]`
   - 不会自动变成 `[A, B]`

3. 后续 B 再扫码这个项目下的服务单时：
   - 只要 B 在该项目默认服务人员名单内，并且该单里还没记录过 B
   - 系统会把 B 追加到 `start_confirmed_technician_ids`
   - 例如从 `[A]` 变成 `[A, B]`
   - 这表示 B 也进入了“已扫码待开始服务”

4. 从现有测试可确认：
   - 单个待开始服务单，第二位服务人员扫码后，会话仍保持待开始/延迟中的服务阶段，但确认人员列表会变成包含第二位扫码人员
   - 如果是一组同一项目、同一开始时间的团课/课程单，某位服务人员扫码会批量把该组单据都记为该人员已确认；另一位服务人员之后再扫同组任一单，也会把自己追加进去

因此，针对你的问题，直接回答是：

- B 的状态：不会自动进入“已扫码待开始服务”，仍是未对这笔服务单做扫码确认的状态。
- B 是否还需要单独扫码：是，需要。
- B 扫哪个单才行：
  - 如果这是同项目同开始时间的一组课程/团课单，B 扫这组里的任意一个已核销服务单即可，系统会把同组单一起补记。
  - 如果不是同组联动场景，那就需要对对应那笔服务单单独扫码，B 才会进入该单的“已扫码待开始服务”列表。
