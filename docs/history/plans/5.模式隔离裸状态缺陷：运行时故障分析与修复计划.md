# 模式隔离裸状态缺陷：运行时故障分析与修复计划

逐一追踪当前代码中每个裸状态写入/比较问题的实际触发路径，给出具体的错误表现和用户可感知的故障现象，并重新审视修复计划的准确性和完整性。

---

## 核心前提

核销入口（`card.go` VerifyCard/ScanVerifyCard）在创建 `ServiceSession` 时，**已正确写入带前缀状态**：
- 客服模式：`cs_staff_selecting` / `cs_room_selecting` / `cs_delay_pending`
- 叫号模式：`qs_staff_selecting` / `qm_staff_selecting` / `qms_staff_selecting` / `qmm_staff_selecting`

因此，数据库中所有新创建的会话状态**一定带有前缀**。后续代码中任何 `WHERE status = '裸状态'` 的精确匹配都**无法命中**这些记录，导致更新操作静默失败（0 rows affected），会话卡死在某个状态无法推进。

## 一、客服模式（cs_）故障清单

### 故障 F1：客服模式 delay_pending → serving 自动推进失败（严重 🔴）

**触发路径**：客服模式 → 核销 → 选房间 → 选技师 → 工作人员扫码起单 → 进入 `cs_delay_pending` → scheduler 轮询

**问题代码**：`scheduler/service_session_scheduler.go` L778-791
```go
// 客服模式或非叫号模式：到达 scheduled_start_at 后自动进入 serving
if s.ScheduledStartAt != nil && !now.Before(*s.ScheduledStartAt) {
    updates := map[string]interface{}{
        "status":     "serving",        // ❌ 写裸状态，应为 cs_serving
        "started_at": now,
    }
    return tx.Model(&models.ServiceSession{}).
        Where("id = ? AND status = ? AND ...", s.ID, "delay_pending").  // ❌ 精确匹配裸状态
        Updates(updates).Error
}
```

**实际表现**：
- `WHERE status = 'delay_pending'` 无法匹配 `cs_delay_pending` → **UPDATE 0 rows**
- 会话**永远卡在 `cs_delay_pending` 状态**，无法进入 `serving`
- 用户看到"等待服务开始"但服务永远不会开始
- 技师已被占用（busy），无法接新单

**影响范围**：**所有客服模式会话**（cs_ 前缀）的自动服务启动全部失效

### 故障 F2：客服模式 serving → auto_finishing 自动结单推进失败（严重 🔴）

**触发路径**：假设 F1 被绕过（如手动修改数据库），会话进入 `cs_serving` → 服务时间到达 → scheduler 轮询

**问题代码**：`scheduler/service_session_scheduler.go` L817-825
```go
// 客服模式：进入 auto_finishing 状态，延迟结单
updates := map[string]interface{}{
    "status":      "auto_finishing",    // ❌ 写裸状态，应为 cs_auto_finishing
    "finished_at": finishAt,
}
return tx.Model(&models.ServiceSession{}).
    Where("id = ? AND status = ? AND ...", s.ID, "serving").  // ❌ 精确匹配裸状态
    Updates(updates).Error
```

**实际表现**：
- `WHERE status = 'serving'` 无法匹配 `cs_serving` → **UPDATE 0 rows**
- 会话**永远卡在 `cs_serving` 状态**，无法进入 `auto_finishing`
- 服务时间到了但不会自动结单
- 技师一直显示"服务中"，无法释放
- 房间一直显示"占用中"

**影响范围**：**所有客服模式会话**的自动结单全部失效

### 故障 F3：选房间后状态写入丢失前缀（严重 🔴）

**触发路径**：客服模式 → 核销 → 用户在前端选择房间 → 调用 `ChooseServiceSessionRoom`

**问题代码**：`handlers/service_session.go` L574, L589-590
```go
if s.Status == "finished" || s.Status == "canceled" {  // ❌ 精确比较裸状态
    return apiErr{...}
}
// ...
if m.SupportCustomerServiceMode {
    updates["status"] = "room_locked"    // ❌ 写裸状态，应为 cs_room_locked
}
```

**实际表现**：
- `s.Status == "finished"` 对 `cs_finished` 返回 false → **已结束的会话可以被重新选房**（逻辑漏洞）
- `updates["status"] = "room_locked"` → 数据库中状态从 `cs_room_selecting` 变为裸 `room_locked`
- **前缀丢失**：后续所有依赖 `cs_` 前缀的逻辑（如 scheduler 的 `NormalizeSessionStatus` + `ApplyStatusPrefix`）会写出不一致的状态
- 具体后果：`ApplyStatusPrefix("room_locked", "staff_selecting")` → `"staff_selecting"`（无前缀），整条链路的前缀全部丢失

**影响范围**：**所有客服模式 + 支持房间的会话**选房操作

---

### 故障 F4：选技师后状态写入丢失前缀（严重 🔴）

**触发路径**：客服模式 → 核销 → 选房间 → 用户在前端选择技师 → 调用 `ChooseServiceSessionTechnician`

**问题代码**：`handlers/service_session.go` L651, L670
```go
if s.Status == "finished" || s.Status == "canceled" {  // ❌ 精确比较裸状态
    return apiErr{...}
}
updates := map[string]interface{}{
    "technician_id": input.TechnicianID,
    "status":        "start_pending",    // ❌ 写裸状态，应为 cs_start_pending
    // ...
}
```

**实际表现**：
- 同 F3，已结束会话的校验失效
- 状态从 `cs_staff_selecting` 变为裸 `start_pending` → **前缀丢失**
- 后续 scheduler 的 `start_pending` 分支中 `ApplyStatusPrefix("start_pending", "staff_selecting")` → `"staff_selecting"`（无前缀）
- 整条链路的前缀全部丢失，模式隔离被破坏

**影响范围**：**所有客服模式会话**的技师选择操作

**触发路径**：客服模式 → 核销 → 进入 `cs_room_selecting` → 选房超时 → scheduler 调用 `autoAssignRoom`

**问题代码**：`handlers/usage_revoke.go` L75, L117, L124

## 四、对之前分析计划的审视与修正

### 之前分析的准确性

1. **P1-P11 问题清单**：基本准确，但需要区分"真正会在运行时触发"和"理论上有问题但实际不会触发"的情况
2. **遗漏**：之前未充分分析 `autoAssignRoom` L926-930 的触发条件——该分支仅在 `!SupportCustomerServiceMode || !SupportRoom` 时执行，对于正常客服模式不会触发，但商户配置变更场景下会触发
3. **严重程度评估修正**：
   - F1/F2 是**最严重**的问题，直接导致客服模式核心流程完全不可用
   - F3/F4 是**次严重**的问题，导致前缀丢失后整条链路崩溃
   - F9 对 qm_/qmm_ 的影响比之前评估的更严重

### 之前计划的完整性

1. **Phase A（裸状态修复）**：完整且准确，覆盖了所有需要修复的点
2. **Phase B（客服子模式）**：需要与产品确认优先级，当前阶段可暂缓
3. **Phase C（防串用校验）**：优先级应提升，因为 F13 暴露了安全漏洞
4. **Phase D（回归测试）**：应增加针对 F1-F14 每个故障的专项回归用例

### 新增发现

- `ChooseServiceSessionRoom` 中非客服模式分支（L591-599）也写了裸状态 `"delay_pending"`，但这个分支的触发条件是 `!SupportCustomerServiceMode`，此时会话可能是叫号模式的带前缀状态，同样会丢失前缀
