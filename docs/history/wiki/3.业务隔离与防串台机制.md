# 3. 业务隔离、调用链分析与防串台机制

本章节着重解析 Kabao 系统在复杂的多模式、高并发场景下，如何保证系统正常运行，做到各个功能分支互不影响（不串台）、资源不被超分配的核心机制。

## 3.1 模式隔离的核心机制

在 Kabao 系统中，商户可以根据经营需要开启不同的功能组合（如预约、房间、手牌、结单等）。需要特别说明：在当前代码实现下，商户的**客服模式（`support_customer_service_mode`）与叫号模式（`support_queue` + `queue_mode`）在运行时互斥**，不会在同一商户配置下同时生效两条入口链路，从而减少了“平行状态机”同时推进同一业务的风险。

**受控重构的解法：状态收敛总线**
所有的前置动作（预约 `Appointment`，排队取号 `QueueTicket`）都被视为“漏斗”，其最终目的都是导向唯一的、标准化的业务承载体——`ServiceSession`（服务会话）。
- **单向降维/升维**：预约单一旦核销，即结束其 `Appointment` 生命周期，转化为排队票据或直接转化为 `ServiceSession`。
- **杜绝并发推进**：在 `ServiceSession` 的代码实现（`models/service_session.go`）中，所有的状态推进方法都强制要求通过 `WHERE id = ? AND status IN (...)` 的前置条件约束，防止多线程同时将状态向前推进。

## 3.2 核心高并发控制与防串台设计

为了防止不同用户同时请求同一名技师，或者同一时间抢占同一个房间，系统在关键资源入口应用了严格的并发控制：

### A. 技师服务互斥校验（防超接）
当多路入口（例如：客服模式入口、叫号模式入口、预约到店核销转化入口）指向同一名技师时，系统执行二次校验：
```go
// 伪代码逻辑示意：
func ValidateTechnicianAvailability(techID) error {
    // 1. 检查基础考勤与静态状态
    if tech.Status == "busy" {
        // 2. 二次深查：该技师名下是否已经存在未结束的活跃会话
        activeSessionCount := db.Where("technician_id = ? AND status IN ('serving', 'auto_finishing')", techID).Count()
        if activeSessionCount > 0 {
            return ErrTechnicianBusy
        }
    }
    return nil
}
```
通过实时检索活跃 `ServiceSession` 表，取代仅仅依赖 `Technician.status` 字段，彻底解决了状态延迟导致的超接问题。

### B. 资源抢占的行锁策略 (FOR UPDATE)
物理资源（如 `Room` 房间 和 `HandCard` 手牌）是不可再分的独占资源。在分配接口中，系统强制使用数据库事务行锁：
1. 开启事务 `BEGIN`。
2. `SELECT * FROM rooms WHERE status = 'available' AND merchant_id = ? LIMIT 1 FOR UPDATE` 
3. 若获取成功，立即更新 `UPDATE rooms SET status = 'occupied' WHERE id = ?`
4. 将 Room ID 绑定到 `ServiceSession`。
5. 提交事务 `COMMIT`。
此机制确保即使商户端两个收银员同时点击“分配房间”，MySQL 也会阻塞其中一个请求，保证防串台安全。

### C. 事务边界与租户隔离
系统是多租户（Merchant）架构。所有对于业务表的操作，强制在 `WHERE` 条件中带上 `merchant_id = ?` 上下文拦截。
- **隔离性**：即使代码在状态机推进时发生严重 Bug，事务回滚或脏数据污染也绝不会越界影响到数据库中其他商户的数据。

## 3.3 异步调度器 (Scheduler) 的隔离与容错

Kabao 的 Scheduler 负责自动推进超时会话（例如超过预定服务时长，自动转入 `auto_finishing` 预结单状态）。这部分属于极易出现“全表扫描性能崩溃”和“交叉污染”的重灾区。

**防串台保障措施：**
1. **带条件批处理 (Batch limit)**：`scheduler` 禁止执行 `SELECT *` 拿回内存中遍历。必须使用类似 `UPDATE service_sessions SET status = 'auto_finishing' WHERE status = 'serving' AND end_time <= NOW()` 的基于条件语句的原子级推演。
2. **幂等性要求**：保证如果 Scheduler 在短时间内被重复唤醒执行两次，或与商户前台人工手动点击“结单”并发发生时，系统状态最终一致。人工触发的 `status = auto_finishing` 成功后，异步任务的 Where 条件自然失效，不会抛出异常。
3. **隔离执行**：通过在定时任务查询中引入 `merchant_id` 或基于 Redis 分布式锁，避免多节点 Scheduler 重复争抢同一批数据。
