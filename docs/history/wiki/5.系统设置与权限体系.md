# 5. 系统设置与权限体系

本系统为典型的多租户（Merchant）架构，每个商户拥有独立的门店设置与人员架构。为了保证系统的灵活性和安全性，系统内部实现了一套完备的**商家配置拦截**与**角色权限控制（RBAC）**机制。

## 5.1 商家配置生效链路与开关拦截

系统支持通过前端控制面板动态开启或关闭特定功能模块（如预约、手牌、房间、叫号模式等）。为了防止 API 层的越权调用（例如商户关闭了房间功能，但通过抓包强行请求分配房间），后端实现了严格的配置鉴权链路。

### A. 配置存储层
*   商家的所有全局开关记录在 `Merchant` 及相关的 `MerchantProject` 或 `MerchantRolePermissionOverride` 模型中。
*   核心开关包括（对应前端截图）：
    *   `enable_appointment` (开启预约)
    *   `enable_project` (开启项目)
    *   `enable_customer_service` (开启客服模式)
    *   `enable_queue` (开启叫号模式)
    *   `enable_hand_card` (开启手牌)
    *   `enable_room` (开启房间)
    *   `enable_direct_card` (开启直购售卡)

### B. Handler 层的拦截逻辑
后端在各对应功能的 Handler 入口处，注入了检查逻辑。
*   **示例 (`room.go`)**：在商户请求创建或分配房间前，系统会调用配置校验函数：
    ```go
    if !merchant.EnableRoom {
        return c.JSON(http.StatusForbidden, gin.H{"error": "该商户未开启房间管理功能"})
    }
    ```
*   **解耦设计**：部分公共配置或权限覆盖规则，通过 `merchant_permission_override.go` 在商户级别进行了重载，从而使个别商户可以不遵循系统默认策略。

## 5.2 角色与权限体系 (Role-Based Access Control)

Kabao 包含三个分离的前端项目（Admin 平台端、Merchant 商户端、User 用户端）。针对商户端的复杂人员结构，系统内置了角色管理与鉴权机制。

### A. 核心角色划分
在 `service_role.go` 及相关表中，定义了以下基础角色：
1. **超级管理员 (Platform Admin)**：登录 Admin 端，拥有全局商户审核、系统参数配置权限（相关逻辑在 `role_permission_admin.go` 中）。
2. **商户店长/老板 (Merchant Owner)**：拥有该商户下的所有最高权限（查看流水、配置营业时间、开关模式等）。
3. **收银员/前台 (Cashier/Receptionist)**：可进行排队叫号、房间分配、发收手牌与日常结单操作，但无法修改商家基础配置。
4. **技师 (Technician)**：部分功能中技师拥有受限的登录权限（账号为 `js0001` 等）。主要仅用于查看自己的接单状态、操作自动结单或下钟。

### B. 鉴权中间件与路由隔离
*   **商户上下文绑定**：`middleware` 中拦截请求的 Token。解析成功后，将对应的 `merchant_id` 注入到当前请求 Context（`c.Set("merchant_id", id)`）中。
*   **API 组隔离**：
    *   `/api/admin/*`：仅限平台管理员访问。
    *   `/api/merchant/*`：商户端接口，内部根据 Context 中的角色 ID 再进行细粒度的 `RolePermission` 判断。
    *   `/api/user/*`：C 端用户接口，主要基于微信 OpenID 或 Token 进行鉴权，无越界获取其他商户敏感数据的权限。

## 5.3 数据行级隔离 (Data Row-Level Security)
所有的 SQL 查询操作，如果是从商户端发起的，**必须**带上 `WHERE merchant_id = ?`，以此实现严格的租户行级隔离。
```go
// 正确的做法
db.Where("id = ? AND merchant_id = ?", ticketID, currentMerchantID).First(&ticket)
```
避免出现商户 A 的员工，通过篡改 `id` 参数核销或删除了商户 B 的订单流水。
