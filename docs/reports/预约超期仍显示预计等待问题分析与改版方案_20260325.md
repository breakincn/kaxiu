# 预约超期仍显示“预计等待”问题分析与改版方案

## 1. 问题背景

用户反馈场景如下：

- 当前日期已经是 `2026-03-25`
- 页面中仍展示一条预约时间为 `2026-03-19 10:45` 的预约
- 卡片提示文案为：`前序服务未结束，预计还需等待 46 分钟，系统已按预约优先等待处理`

该展示会让用户自然理解为：

1. 一个 `3 月 19 日` 的预约在 `3 月 25 日` 仍处于进行中
2. 系统正在提供一个“实时剩余等待 46 分钟”的可信倒计时

从产品认知上看，这两个理解会直接导致强烈冲突，因此这是一个设计问题，不是单纯的文案优化问题。

## 2. 结论

当前问题本质上是三类信息被混在了一起展示：

- `预约时间`：历史事实
- `predicted_wait_minutes`：签到当下写入的一次性预测值
- `当前状态`：预约是否仍有效、是否已超时、是否仍在等待原客服

结果是页面把一个历史预约上的“静态预测值”展示成了“当前实时剩余等待时间”，从而形成误导。

## 3. 现有代码链路

### 3.1 前端文案如何展示

商户端卡片直接读取 `predicted_wait_minutes`，只要状态是 `arrived` 且该值大于 `0`，就显示：

`前序服务未结束，预计还需等待 X 分钟，系统已按预约优先等待处理`

对应代码：

- [frontend/src/views/merchant/Dashboard.vue:4719](/Users/will/Projects/Go/kabao/frontend/src/views/merchant/Dashboard.vue#L4719)

关键点：

- 前端没有校验预约时间是否早已过去
- 前端也没有校验这个 `X 分钟` 是否是实时重新计算结果
- 只要数据库里还保留该值，就会继续显示

### 3.2 `predicted_wait_minutes` 在什么时候写入

预约签到后，后端会创建 `service_session`，并把 `session.PredictedAppointmentDelayMinutes` 回写到预约表的 `predicted_wait_minutes` 字段：

- [backend/handlers/appointment.go:2072](/Users/will/Projects/Go/kabao/backend/handlers/appointment.go#L2072)
- [backend/models/models.go:239](/Users/will/Projects/Go/kabao/backend/models/models.go#L239)

关键点：

- 这是签到时落库的值
- 不是每次页面打开时重新按“当前时刻”计算

### 3.3 这个值是如何算出来的

预约签到创建服务会话时，如果发现预约绑定客服当前不可立即接待，则会进入 `appointment_waiting`，并调用：

- [backend/handlers/service_session_factory.go:70](/Users/will/Projects/Go/kabao/backend/handlers/service_session_factory.go#L70)

核心计算发生在：

- [backend/handlers/appointment_policy.go:536](/Users/will/Projects/Go/kabao/backend/handlers/appointment_policy.go#L536)
- [backend/handlers/appointment_policy.go:127](/Users/will/Projects/Go/kabao/backend/handlers/appointment_policy.go#L127)
- [backend/handlers/project_timing.go:70](/Users/will/Projects/Go/kabao/backend/handlers/project_timing.go#L70)

公式可以整理为：

```text
predicted_wait_minutes
= ceil(predicted_finish - appointment_time)

predicted_finish
= checkin_time + occupied_minutes + prediction_buffer

occupied_minutes
= project_duration + service_gap_minutes
```

其中：

- `checkin_time`：用户签到时刻
- `project_duration`：项目服务时长
- `service_gap_minutes`：项目间歇时间
- `prediction_buffer`：商户预约预测缓冲时间
- `appointment_time`：预约开始时间

## 4. “46 分钟”是怎么来的

仅凭截图无法还原数据库里的真实签到时刻、项目间歇时间和商户缓冲配置，因此不能 100% 断言当时的精确输入值。但从代码看，`46` 大概率是按下面这类方式算出来的：

```text
示例：
预约时间 = 10:45
签到时间 = 10:38
项目时长 = 45 分钟
项目间歇 = 3 分钟
预测缓冲 = 5 分钟

occupied_minutes = 45 + 3 = 48
predicted_finish = 10:38 + 48 + 5 = 11:31
predicted_wait_minutes = 11:31 - 10:45 = 46
```

这说明当前的 `46` 更像是：

- 用户签到当下
- 按项目占用时长和缓冲时间
- 粗略推导出的“预约相对被压后的等待分钟数”

而不是：

- 到 `2026-03-25` 这一刻为止
- 系统重新计算得到的“现在还剩 46 分钟”

## 5. 为什么这个设计会误导

### 5.1 文案语义与数据语义不一致

文案写的是 `预计还需等待 46 分钟`，这在中文语境里默认表示“从现在开始的实时剩余时间”。

但代码里的值实际上更接近：

- `签到时预测延迟`
- 或 `相对预约开始时间的预计压单分钟数`

两者不是一回事。

### 5.2 历史预约与当前等待未做分层

`3 月 19 日` 是历史预约时间；`预计等待 46 分钟` 又被写成当前时态。页面没有告诉用户：

- 这是历史未闭环订单
- 还是门店人工保留中的异常单
- 还是系统没有及时收敛的脏状态

### 5.3 到店后状态缺少异常分流

当前前端只认：

- `confirmed + predicted_wait_minutes > 0`
- `arrived + predicted_wait_minutes > 0`

但没有继续判断：

- 是否已超过预约日
- 是否已超过签到窗口很多天
- 是否应转成 `超时未服务`
- 是否应提示改派/改签/人工处理

### 5.4 `arrived` 不会被自动取消

自动取消仅作用于 `pending` / `confirmed`，不会处理 `arrived`：

- [backend/handlers/appointment.go:1439](/Users/will/Projects/Go/kabao/backend/handlers/appointment.go#L1439)

因此一旦用户签到，预约可以长期停留在 `arrived`，而页面仍继续沿用历史预测文案。

## 6. 现有设计的真实问题定义

这不是单点文案 bug，而是一个状态建模问题：

1. 系统把“预约保护/压单预测”的计算结果复用成了“用户当前等待展示”
2. 系统把“签到时写入值”复用成了“页面当前剩余值”
3. 系统缺少“预约已超时但仍未闭环”的异常状态层

因此只改一句文案并不能彻底解决。

## 7. 更合理的设计方案

## 7.1 设计原则

需要把三类信息拆开显示：

1. `预约承诺`
2. `当前执行状态`
3. `等待预测`

建议规则如下：

- `预约时间` 永远只表达历史承诺
- `当前状态` 永远表达订单是否仍有效
- `预计等待` 只在“当前仍处于有效等待中”时显示

## 7.2 建议的状态展示模型

### A. 正常预约未到店

展示：

- `预约时间：2026-03-26 10:45`
- `状态：待到店`

如有风险，可补充：

- `提示：若前序服务延长，预计到店后可能等待 15 分钟`

这里用“可能等待”，不要用“还需等待”。

### B. 已到店，正在等待原客服

展示：

- `状态：已到店待服务`
- `原因：原预约客服仍在服务上一位客户`
- `当前预计等待：46 分钟`
- `已保留预约优先处理`

这里的等待值必须是实时值，而不是签到时静态值。

### C. 已超过预约时间较久，但仍未开始服务

展示：

- `状态：预约已超时`
- `预约时间：2026-03-19 10:45`
- `说明：该预约尚未完成服务闭环，请人工处理`

如果业务允许继续承接，可写：

- `当前处理方式：已转为异常等待单`
- `建议操作：改派其他客服 / 发起改签 / 关闭并补偿`

此时不要再显示 `预计还需等待 X 分钟`。

### D. 历史异常单保留展示

展示：

- `状态：历史异常单`
- `预约时间：2026-03-19 10:45`
- `异常原因：到店后未完成服务闭环`
- `最近处理：改签说明 1`

这类单的重点应该是异常说明和处理动作，不是继续展示等待倒计时。

## 7.3 文案层建议

### 应废弃的文案

`前序服务未结束，预计还需等待 X 分钟，系统已按预约优先等待处理`

问题：

- 把静态预测值说成实时剩余值
- 对历史异常单仍然成立，误导很强

### 建议替换为两类文案

#### 场景 1：实时有效等待

`原预约客服暂未释放，当前预计等待 X 分钟`

附加说明：

`系统已保留预约优先顺序`

#### 场景 2：历史超时未闭环

`该预约已超过原预约时间，当前仍未完成服务闭环`

附加说明：

`请改派、改签或做异常结案处理`

## 7.4 交互层建议

当预约满足以下条件之一时，应强制进入异常样式：

- `status = arrived`
- 且 `now - appointment_time > 预约宽限阈值`
- 且尚未 `actual_start_at`
- 或服务会话仍未完成

建议阈值：

- `60 分钟` 进入黄色告警
- `跨日` 进入红色异常

异常卡片应提供明确动作：

- `改派其他客服`
- `发起改签`
- `异常结案`
- `补偿`

## 8. 是否需要改后端

需要，且至少分两层。

### 8.1 最小修复

只改前端展示规则：

- 当预约时间已远早于当前时间时，不再展示 `预计还需等待 X 分钟`
- 改成 `预约已超时，待人工处理`

优点：

- 上线快
- 立刻消除最明显的用户误解

缺点：

- `predicted_wait_minutes` 仍然是静态值
- 数据语义问题没有根治

### 8.2 正式修复

后端新增区分字段或实时计算逻辑，把以下概念拆开：

- `predicted_delay_minutes_at_checkin`
- `current_estimated_wait_minutes`
- `exception_state`

建议：

1. `predicted_wait_minutes` 改名或停止直接用于 UI 主文案
2. 对 `arrived` 且未开始服务的预约，在查询详情时按当前 `service_session` / `predicted_ready_at` 实时计算剩余等待
3. 对超时未闭环预约输出明确异常状态，例如：
   - `waiting_active`
   - `waiting_overdue`
   - `waiting_cross_day_exception`

## 9. 推荐落地方案

建议分两步实施。

### 第一步：快速止血

前端改展示规则：

- `arrived && predicted_wait_minutes > 0 && appointment_time 在有效等待窗口内`
  - 才显示 `当前预计等待 X 分钟`
- `arrived && appointment_time 已跨日或超时`
  - 显示 `预约已超时，待人工处理`

### 第二步：语义收敛

后端把 `预计等待` 拆成两类值：

- `签到时预测压单值`
- `当前实时剩余等待值`

同时为历史异常单输出独立状态。

## 10. 最终判断

针对用户问题“今天已经是 3 月 25 日，为什么 3 月 19 日的预约还显示预计还需等待 46 分钟，这是设计的问题吗”：

答案是：

- 是设计问题
- 更准确地说，是状态建模和展示语义共同导致的问题
- 当前的 `46 分钟` 并不等价于“现在还要再等 46 分钟”
- 它更可能是签到时一次性计算出的预测值，被错误地持续展示成了实时等待

因此更合理的方案不是单纯改文案，而是：

- 把历史预约、当前等待、异常未闭环三种语义拆开
- 只在“当前仍有效等待”时显示实时等待分钟数
- 对跨日/历史异常单改为异常状态和处理动作展示
