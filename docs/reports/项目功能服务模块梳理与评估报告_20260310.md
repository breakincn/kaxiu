# 项目功能服务模块梳理与评估报告

- 文档日期：2026-03-10
- 代码基线：`HEAD @ 9ed20cf`
- 适用范围：`kabao` 当前仓库实现

## 1. 报告说明

### 1.1 目标

本报告以当前仓库代码为准，对项目现有功能服务模块进行系统梳理，说明各模块的角色、入口、核心流程、状态流转与异常回收机制，评估其完整性和闭环程度，识别缺失能力，并给出补齐建议，形成一份可供产品、研发、管理层共同使用的现状评估文档。

### 1.2 覆盖范围

覆盖以下内容：

- 用户端、商户端、平台端前端入口
- `backend/routes/routes.go` 暴露的接口面
- 核心领域模型：`Merchant / Card / Usage / Appointment / ServiceSession / Technician / Room / ServiceRole / Permission`
- 调度器：`service_session_scheduler / appointment_scheduler / hand_card_scheduler`
- 服务开关、模式隔离、RBAC、租户隔离相关实现

不覆盖以下内容：

- 线上真实数据与运营效果
- 数据库实际存量质量
- 第三方支付真实性校验
- UI 视觉设计优劣

### 1.3 评估方法

本报告采用“前端入口 + 路由/API + 模型状态 + 调度器补偿”四层交叉核对法：

1. 从三端页面与路由识别用户可见能力
2. 从后端路由与 Handler 确认真实接口边界
3. 从模型与状态字段确认核心数据承载方式
4. 从调度器与异常分支判断是否形成流程闭环

历史文档仅作为旁证；若历史结论与当前代码不一致，以当前代码行为为准。

### 1.4 完整度评级标准

- `高闭环`：主流程、关键异常、回收补偿都已具备，模块可独立稳定运行
- `中闭环`：主流程已跑通，但异常场景、补偿流程或运营兜底不足
- `低闭环`：存在关键缺口、高风险副作用或与其他模块整合不足
- `未闭环`：只有入口或局部能力，核心流程未形成可用闭环

### 1.5 术语约定

- `ServiceSession`：服务会话主状态机，承接核销后到结单前的过程
- `Usage`：单次核销/消费记录
- `Appointment`：预约记录
- `Queue`：叫号/排队引擎，当前由 Redis 队列与业务状态共同驱动
- `SessionMode`：会话模式标记，当前使用 `cs / qs / qm / qms / qmm / oc / simple`

## 2. 系统总览

### 2.1 三端入口

#### 用户端

- 主要页面：`/user/cards`、`/user/cards/:id`、`/user/service-sessions/:id`、`/user/settings`、`/s/:slug`
- 主要能力：登录/注册、卡包、卡详情、核销码、预约、会话恢复、直购购卡、用户设置

#### 商户端

- 主要页面：`/merchant`、`/merchant/settings`、`/merchant/services`、`/merchant/project-settings`、`/merchant/customer-service`、`/merchant/queue-settings`、`/merchant/hand-card-settings`、`/merchant/service-sessions`
- 主要能力：服务开关配置、项目配置、技师/岗位管理、核销/扫码起单、叫号、房间、手牌、通知、直购模板与订单、看板

#### 平台端

- 主要页面：`/platform-admin/login`、`/platform-admin`
- 主要能力：平台岗位模板、权限枚举、专业客服基础权限、系统域名配置

### 2.2 核心实体

| 实体 | 作用 | 关键字段 |
| --- | --- | --- |
| `Merchant` | 商户租户与服务开关承载体 | `support_*`、`queue_mode`、营业时间、房间号牌/手牌号牌设置 |
| `Card` | 用户卡资产 | 次数、余额、锁卡、有效期 |
| `Usage` | 单次核销/消费记录 | `status`、`project_id`、`hand_card_no`、关联 `ServiceSession` |
| `Appointment` | 预约记录 | `status`、`appointment_time`、`technician_id` |
| `ServiceSession` | 服务状态机 | `session_mode`、`status`、`room_id`、`technician_id`、时间轴字段 |
| `Technician` | 工作人员账号 | `service_role_id`、`account`、`window_no`、`queue_paused` |
| `TechnicianAttendance` | 当日出勤与忙闲状态 | `checked_in_at`、`checked_out_at`、`status` |
| `Room` | 房间资源 | `name`、`is_active` |
| `ServiceRole` | 平台/商户岗位模板 | `role_type`、`account_prefix`、`require_attendance` |
| `Permission` / `RolePermission` | RBAC 权限体系 | `key`、`allowed` |

### 2.3 ServiceSession 状态机与模式体系

当前会话模式包括：

- `cs`：客服模式
- `qs`：自动叫号单窗口
- `qm`：自动叫号多窗口
- `qms`：手动叫号单窗口
- `qmm`：手动叫号多窗口
- `oc`：结单模式
- `simple`：简化模式

核心状态主体包括：

- `room_selecting`
- `room_locked`
- `staff_selecting`
- `start_pending`
- `delay_pending`
- `serving`
- `auto_finishing`
- `timeout_waiting`
- `timeout_failed`
- `finished`
- `canceled`

当前实现已经把 `session_mode` 与状态前缀结合使用，并通过 `ValidateSessionModeForEntry` 避免不同模式串用同一入口推进旧会话。

### 2.4 调度器职责

#### `service_session_scheduler`

- 定时推进会话状态
- 处理待选人、待上号、过号等待、自动结单、打烊收尾
- 释放已完成会话的技师资源
- 承担大部分流程补偿逻辑

#### `appointment_scheduler`

- 对超过 10 分钟仍未分配技师的预约执行自动指派
- 在客服模式下尝试绑定不冲突的专业客服
- 分配失败时将预约标记为 `failed`

#### `hand_card_scheduler`

- 对开启手牌功能的商户生效
- 当“已分配未归还手牌”超过 8 分钟时自动锁卡
- 写入锁卡原因，等待归还或人工解锁

### 2.5 服务开关体系

商户设置页对应的主要开关包括：

- `support_appointment`
- `support_project`
- `support_customer_service`
- `support_customer_service_mode`
- `support_queue`
- `support_order_complete`
- `support_hand_card`
- `support_room`
- `support_direct_sale`

当前实现的关键特征：

- 客服模式与叫号模式互斥
- 开启预约要求先配置营业时间
- 开启客服模式要求先开启客服账号体系
- 在存在未完成会话时，禁止切换会影响叫号运行语义的关键开关

这一点修正了历史文档中“运行中可裸切 queue / cs 模式”的高风险结论；当前代码已经加入显式保护。

## 4. 逐模块详评

### 4.1 认证与账号体系

#### 功能说明

系统存在三类主要登录主体：用户、商户、工作人员；平台管理员使用独立中间件。

#### 角色与入口

- 用户：`/user/login`、`/user/register`、`/user/sms/send`
- 商户：`/merchant/login`、`/merchant/register`
- 工作人员：`/merchant/s/:slug/login`
- 平台：`/platform-admin/login`

#### 核心接口与模型

- 中间件：`backend/middleware/auth.go`
- RBAC：`backend/middleware/rbac.go`
- 用户/商户/工作人员模型：`backend/models/models.go`、`backend/models/technician.go`

#### 正常流程

1. 登录后签发 JWT
2. 中间件识别 `type=user/merchant/staff`
3. 将 `user_id / merchant_id / technician_id / service_role_id` 注入上下文
4. 商户老板默认拥有商户端权限；工作人员再走权限校验

#### 异常与回滚

- 员工 `password_need_reset=true` 时，仅允许访问改密接口
- 用户仍兼容 `user_{id}_{timestamp}` 旧 token 分支
- 无权限时统一由 RBAC 拦截

#### 闭环判断

`中闭环`。三类账号流程可用，首登改密和 RBAC 已接通，但认证实现仍保留历史兼容分支，体系不够收敛。

#### 缺失点与建议

- 建议逐步停用 legacy user token
- 建议统一整理平台管理员鉴权与三端鉴权口径
- 建议补充“账号冻结/停用/强制退出”类运营能力

### 4.2 用户卡包与卡详情

#### 功能说明

用户端卡包是整个 C 端主入口，承载卡资产查看、置顶通知、预约入口、核销码、会话恢复和使用记录展示。

#### 入口与接口

- 页面：`frontend/src/views/user/CardList.vue`、`CardDetail.vue`
- 接口：`/user/cards`、`/user/cards/:id`、`/user/cards/:id/projects`、`/user/cards/:id/usages`、`/user/cards/:id/verify-code`

#### 核心流程

1. 用户进入卡包查看有效卡/失效卡
2. 点击卡片进入详情页
3. 查看项目、营业时间、商户地址、通知、使用记录
4. 需要到店消费时生成核销码
5. 若已有预约或服务会话，可继续查看进度

#### 异常与回滚

- 卡片锁定时禁止预约和核销
- 剩余次数不足、过期、核销码过期会在核销环节拦截
- 置顶通知与手牌状态会在卡片及使用记录中展示

#### 闭环判断

`高闭环`。用户侧资产展示、核销前信息准备、历史记录回看已具备完整链路。

#### 缺失点与建议

- 建议增加“卡片状态时间线”，统一展示锁卡、预约、服务、手牌、退款等事件
- 建议进一步收敛“卡类型=储值卡/次数卡”的展示逻辑分支

### 4.3 商户基础配置与服务开关

#### 功能说明

商户设置页负责决定门店启用哪些业务能力，是全系统运行语义的总开关。

#### 入口与接口

- 页面：`frontend/src/views/merchant/Settings.vue`、`Services.vue`、`MerchantInfo.vue`
- 接口：`PUT /merchant/services`、`PUT /merchant/info`、`PUT /merchant/business-status`

#### 核心流程

1. 商户读取当前配置
2. 在设置页勾选/关闭功能
3. 后端校验互斥关系、营业时间前置条件、运行中会话保护
4. 更新商户配置
5. 若启用房间功能且号牌范围变化，自动同步房间资源

#### 异常与回滚

- 客服模式与叫号模式互斥
- 开启预约要求已配置营业时间
- 开启客服模式要求先开启客服
- 有未完成服务会话时，禁止切换会改变 queue 运行语义的关键配置

#### 闭环判断

`高闭环`。配置保存、前置条件、运行时保护已基本成型。

#### 缺失点与建议

- 建议补一份“配置变更影响矩阵”，减少运营误操作
- 建议增加配置审计日志
- 建议为服务开关补充更系统的组合场景回归测试

### 4.4 项目设置

#### 功能说明

项目是预约、核销、会话时长、直购模板的基础配置单元。

#### 入口与接口

- 页面：`frontend/src/views/merchant/ProjectSettings.vue`
- 接口：`GET/POST/PUT/DELETE /merchant/projects`

#### 核心流程

1. 商户创建项目，配置名称、时长、价格、排序
2. 项目被预约、核销、卡模板引用
3. 核销建单时读取项目时长，写入会话

#### 异常与回滚

- 预约要求项目有效且时长大于 0
- 项目停用后不再用于新流程，但历史记录仍保留引用

#### 闭环判断

`高闭环`。项目 CRUD 与下游引用关系明确。

#### 缺失点与建议

- 建议增加“项目上下架影响提示”
- 建议增加项目级营业时段/技师适配规则，提升预约与队列精度

### 4.5 发卡/售卡/卡模板

#### 功能说明

包括商户后台发卡和用户侧直购两条线，最终都落到 `Card` 资产。

#### 入口与接口

- 商户发卡：`/merchant/cards`、`/merchant/next-card-no`
- 直购模板：`/merchant/card-templates`
- 用户购卡：`/s/:slug`、`/user/direct-purchase`
- 订单确认：`/user/direct-purchase/:order_no/confirm`、`/merchant/direct-purchases/:order_no/confirm`

#### 核心流程

1. 商户配置支付二维码和卡模板
2. 用户进入店铺页选择卡片
3. 创建 `DirectPurchase(pending)`
4. 用户付款后点击“已完成付款”，订单变为 `paid`
5. 商户确认后生成 `Card`，并把模板项目固化到 `card_projects`

#### 异常与回滚

- 商户未开启直购或未配置对应支付方式时拒绝下单
- 模板下架后拒绝购买
- 商户确认前不会开卡

#### 闭环判断

`中闭环`。业务闭环已经跑通，但“支付成功”依赖用户声明 + 商户人工确认，不做资金校验。

#### 缺失点与建议

- 建议增加订单超时取消与人工驳回能力
- 建议增加商户确认时的备注/审核记录
- 若未来接真实支付，建议保持“收款归商户、卡包只管资产”的边界不变

### 4.6 核销、起单、结单、反结单

#### 功能说明

该模块是门店履约核心，负责把“用户卡资产”转化为“正在发生的服务”。

#### 入口与接口

- 核销：`/merchant/verify`、`/merchant/verify/prepare`、`/merchant/verify/commit`
- 扫码上号/起单：会话码 `SS:*`
- 反结单：`/user/usages/:id/revoke`

#### 核心流程

1. 商户扫描用户核销码
2. `PrepareVerify` 校验核销码、卡片、项目、商户、手牌前置条件
3. `CommitPreparedVerify` 扣次并写入 `Usage`
4. 根据商户模式创建 `ServiceSession`
5. 服务结束后完成 Usage、Session、Card、Queue 的状态回写
6. 必要时支持撤销 Usage 进行回滚

#### 异常与回滚

- 卡片锁定、过期、余次不足直接阻断
- 手牌开启时要求输入或明确跳过分配
- 过号超时分支会退卡并把 Usage 标记失败
- 反结单负责退回次数并恢复部分状态

#### 闭环判断

`中闭环`。核销主链已经较完整，但不同模式的推进逻辑复杂，客服模式子场景仍未补齐。

#### 缺失点与建议

- 优先补齐客服模式下“手动结单 / 房间手动结单”
- 建议补充“多次核销并单结算”的标准视图
- 建议完善核销失败后的统一审计日志

### 4.7 ServiceSession 服务会话

#### 功能说明

`ServiceSession` 是所有履约模式的统一承载体，决定“核销后如何进入服务、如何结束服务、如何释放资源”。

#### 入口与接口

- 商户：`GET /merchant/service-sessions`、`GET /merchant/service-sessions/:id`
- 选房/选人/加钟：商户端与用户端都支持一部分

#### 核心流程

1. 核销或其他入口创建会话
2. 根据模式进入 `room_selecting / staff_selecting / delay_pending / start_pending`
3. 扫码上号后进入 `serving`
4. 到时自动结单或人工结单
5. 释放技师、房间、叫号资源

#### 异常与回滚

- `ValidateSessionModeForEntry` 防止跨模式推进
- 调度器承担超时取消、过号等待、自动完成、打烊收尾
- 队列模式下会和 Redis Queue 联动回收

#### 闭环判断

`中闭环`。状态机本身成熟，但创建入口仍分散在核销、预约、叫号推进中，商户端“直接创建服务会话”并非独立完整能力。

#### 缺失点与建议

- 建议补一份标准状态图放入长期 Wiki
- 建议为每种 `session_mode` 建立完整自动化场景测试

### 4.8 预约

#### 功能说明

预约允许用户基于卡片和项目预约明天的时段，商户确认后进入待履约状态。

#### 入口与接口

- 页面：用户卡详情页预约区域、商户首页预约 Tab
- 接口：`POST /user/appointments`、`PUT /merchant/appointments/:id/confirm`、`finish`、`cancel`

#### 核心流程

1. 用户选择项目、时间、可选技师，创建 `Appointment(pending)`
2. 校验卡片归属、营业时间、项目时长、仅支持预约明天
3. 商户确认后置为 `confirmed`，进入预约队列
4. 商户在服务窗口内完成预约，置为 `finished`

#### 异常与回滚

- 同一卡同商户仅允许一个活跃预约
- 超时预约会自动取消
- 预约创建超过 10 分钟且未指定技师时，调度器尝试自动分配专业客服；失败则标记 `failed`

#### 闭环判断

`低闭环`。预约自身 CRUD 可用，但与 `ServiceSession` 和现场队列并未真正融合；“预约到店 -> 核销 -> 进入统一履约主链”仍不充分。

#### 缺失点与建议

- 建议把预约到店转化为统一的服务会话/高优先级队列入口
- 建议引入迟到宽容期、改签、改派、预约转现场号等规则
- 建议补充预约与现场核销资源冲突的统一处理策略

### 4.9 叫号与队列

#### 功能说明

系统已支持四种叫号模式：自动单窗口、自动多窗口、手动单窗口、手动多窗口。

#### 入口与接口

- 页面：商户首页、看板、叫号设置
- 接口：`call-next`、`continue-call`、`continue-call-force`、`finish-call-next`、`trigger-auto-assign`

#### 核心流程

1. 核销建单后将现场服务写入队列
2. 手动或自动把下一位推进到可上号状态
3. 扫码上号进入 `serving`
4. 服务结束时结束当前号并继续推进下一号

#### 异常与回滚

- 手动模式支持继续叫号、强制继续、跳过待上号用户
- 自动模式支持超时退回、释放技师、自动补叫
- 调度器对过号窗口和超时失败进行回收

#### 闭环判断

`高闭环`。四种叫号模式主链路已闭环，入口守卫、调度补偿与结单触发下一号都已成型。

#### 缺失点与建议

- 已补一期：多客服叫号模式下，支持对当前 `start_pending` 待上号单执行自动重分配，并在商户首页“扫码核销”Tab 的“今日核销记录”中显示“当前客服不可服务”提示
- 二阶段仍可继续补：手工指定改派、立即跳过、批量异常待上号处理
- 建议补充更完整的大屏/投屏视图，而不是仅复用商户端页面

### 4.10 技师、岗位、考勤、签到

#### 功能说明

该模块承载门店人员组织结构、接单资格、签到状态和权限范围。

#### 入口与接口

- 页面：`CustomerService.vue`、`RolePermissionAdjust.vue`、`RoleStartPendingAdjust.vue`
- 接口：技师 CRUD、岗位 CRUD、签到、签退、状态切换、岗位权限微调、岗位签到配置、岗位待起单超时设置

#### 核心流程

1. 平台维护基础岗位模板与权限
2. 商户新增自定义专业岗/运营岗
3. 基于岗位前缀创建账号
4. 技师签到成为 `idle`
5. 接单或上号后转 `busy`
6. 可手动切 `paused` 或签退为 `rest`

#### 异常与回滚

- 无需签到岗位会自动补当天考勤记录
- 技师从 `idle -> busy` 使用数据库更新条件避免并发重复抢单
- 技师暂停或未签到时，不允许扫码上号

#### 闭环判断

`中高闭环`。岗位、账号、签到、权限已经打通；多客服叫号模式下，技师离岗前已支持自助转交自己当前待上号单，商户/运营也可在商户首页“扫码核销”Tab 的“今日核销记录”发起自动重分配。

#### 缺失点与建议

- 已补一期：商户/运营可在商户首页“扫码核销”Tab 的“今日核销记录”对“当前客服不可服务”的待上号单执行重新分配，专业客服在暂停叫号/下班前可自助转交自己当前待上号单
- 二阶段再评估：手工指定改派、立即跳过、批量异常处理
- 增加技师维度的审计日志与异常工单能力

### 4.11 房间管理

#### 功能说明

房间管理用于为会话分配物理资源，但当前房间状态更多通过会话推导，而不是单独维护复杂状态机。

#### 入口与接口

- 页面：`Rooms.vue`、看板、用户会话页选房
- 接口：`/merchant/rooms`、`/merchant/service-sessions/:id/room`、`/user/service-sessions/:id/room`

#### 核心流程

1. 商户配置房间或通过号牌范围自动生成房间
2. 会话需要房间时先选房或自动分房
3. 绑定 `room_id`
4. 会话结束后释放占用

#### 异常与回滚

- 开启房间功能但无可用房间时阻止起单或上号
- 房间选择超时由调度器取消会话或释放锁

#### 闭环判断

`中闭环`。基本资源占用逻辑可用，但当前没有显式持久化 `occupied/cleaning` 状态，也没有完善的异常运营工作流。

#### 缺失点与建议

- 建议引入显式房态或最少增加“脏房/清洁中”标记
- 建议支持人工释放、故障房间、跨日占用处理

### 4.12 手牌管理

#### 功能说明

手牌模块用于把线下实体手牌与一次核销/卡片责任关联起来。

#### 入口与接口

- 页面：`HandCardSettings.vue`
- 接口：绑定手牌、查询待归还、归还手牌、强制解锁卡

#### 核心流程

1. 核销时输入手牌号或明确跳过
2. 使用记录写入 `hand_card_no` 与分配时间
3. 超过窗口未归还，由调度器锁卡
4. 归还手牌后更新 `hand_card_returned_at`
5. 若同卡所有手牌都归还，则自动解锁

#### 异常与回滚

- 已归还手牌不可再次绑定
- 已绑定未归还的 usage 不允许更换手牌号
- 仍有未归还手牌时，锁卡原因会动态更新

#### 闭环判断

`中闭环`。主链已通，自动锁卡/归还解锁都可用。

#### 缺失点与建议

- 缺少挂失、补办、转移责任、跨日未归还运营处理
- 建议增加“未归还手牌清单”专门页面

### 4.13 通知与看板

#### 功能说明

通知面向用户传达门店信息；看板面向商户展示房间与员工状态。

#### 入口与接口

- 页面：商户首页通知 Tab、用户卡包置顶通知、`Table.vue`
- 接口：`/merchant/notices`、`/merchant/table/rooms`、`/merchant/table/staff`

#### 核心流程

1. 商户创建、删除、置顶通知
2. 用户在卡包和卡详情看到通知
3. 商户通过看板查看房间/员工状态

#### 异常与回滚

- 通知支持置顶和删除
- 看板能力主要是读视图，不承担事务写入

#### 闭环判断

`高闭环`。通知链条简单完整；看板作为展示层也已可用。

#### 缺失点与建议

- 建议增加“通知时效/定时失效”
- 建议增加独立门店大屏模式

### 4.14 平台端权限与角色模板

#### 功能说明

平台端当前不是完整运营中台，而是聚焦在角色模板、权限枚举和系统配置。

#### 入口与接口

- 页面：`frontend/src/views/platformAdmin/Dashboard.vue`
- 接口：`/admin/service-roles`、`/admin/permissions`、`/admin/system/config`

#### 核心流程

1. 平台维护固定岗位模板
2. 维护权限枚举
3. 配置专业客服基础默认权限
4. 配置系统域名
5. 商户侧读取平台模板并可做商户级微调

#### 异常与回滚

- 商户老板默认放行，工作人员按权限枚举与覆盖规则校验
- 专业岗可读取系统配置的基础权限列表

#### 闭环判断

`中闭环`。平台端在“权限模板平台”这一定位下是成立的，但不承担完整商户审核、租户运营、报表等平台能力。

#### 缺失点与建议

- 若未来要做完整平台后台，需补商户生命周期、数据审计、运营看板
- 若维持当前定位，建议在文档中明确“平台端仅负责权限模板与系统基础配置”

## 5. 跨模块闭环分析

### 5.1 预约 -> 核销 -> ServiceSession

当前链路并未完全漏斗化：

- 预约可创建、确认、取消、完成
- 预约也有独立队列概念
- 但预约完成并不等同于正式进入 `ServiceSession` 统一主链

结论：

- 预约模块仍然相对独立
- 它还没有像现场核销那样被彻底收敛进 `Usage + ServiceSession + Queue` 的统一履约链
- 这是当前全项目最明显的业务整合缺口之一

### 5.2 叫号 -> 技师 -> 房间

当前链路已经较成熟：

- 叫号模式下建单后可进入 `staff_selecting/start_pending/delay_pending`
- 技师签到、忙闲状态、权限与队列分配已联动
- 房间开启时，起单和上号前会校验房间条件

结论：

- 正常履约主链已闭环
- 剩余问题主要集中在“异常运营场景”，不是主链缺失

### 5.3 手牌 -> 锁卡 -> 归还 -> 解锁

当前实现已形成完整的“责任闭环”：

1. 核销绑定手牌
2. 长时间未归还自动锁卡
3. 归还后自动修复锁卡原因
4. 全部归还后自动解锁

结论：

- 手牌主链可用
- 仍缺挂失、补办、跨日追责等“门店异常处理链”

### 5.4 直购 -> 开卡 -> 用户卡包

当前链路清晰：

1. 用户店铺页选卡
2. 创建订单
3. 用户确认已付款
4. 商户确认后生成卡
5. 用户卡包可见

结论：

- 产品逻辑自洽
- 但资金真实性依赖人工确认，这是一种明确的业务取舍，不是技术 bug

### 5.5 权限 -> 配置 -> 运行时语义

历史文档曾指出“运行中切 queue / cs 配置会导致旧会话语义漂移”。当前代码已在 `UpdateCurrentMerchantServices` 中加入保护：

- 当存在未完成会话时，不允许切换关键 queue 运行参数
- 也不允许直接关闭 queue 或切到客服模式

结论：

- 这一高风险问题在当前代码已得到修正
- 未来重点应从“有没有保护”转向“保护是否覆盖足够全面、组合场景是否有回归测试”

## 6. 缺失模块与关键缺口清单

### 6.1 P0 级

#### P0-1 预约未融入统一履约主链

- 类型：流程不闭环
- 影响：预约和现场核销仍是两套偏并行链路，资源冲突处理不够自然
- 建议：把预约到店转化为统一的 `ServiceSession` 或高优先级队列票据

### 6.2 P1 级

#### P1-1 客服模式“手动结单 / 房间手动结单”子模式缺失

- 类型：功能未实现
- 影响：特定商户配置下，客服模式下的结单语义不完整
- 建议：细化 `ResolveSessionMode` 与对应状态推进、调度器收尾逻辑

#### P2-4 技师紧急离岗后的异常补偿仍有二阶段空间

- 类型：异常运营补偿增强
- 当前状态：一期已补齐“当前待上号单自动重分配”能力，支持商户/运营在商户首页“扫码核销”Tab 的“今日核销记录”重新分配，也支持专业客服在暂停叫号/下班前自助转交自己当前待上号单
- 剩余问题：仍未支持手工指定改派、立即跳过、批量处理异常待上号单
- 建议：如果后续门店规模和并发继续提升，再按二阶段需求补更强的调度操作
#### P1-3 房间与手牌异常工作流不足

- 类型：流程不闭环
- 影响：丢失、故障、跨日未归还等真实门店问题处理不完整
- 建议：补异常工单与责任转移链

#### P1-4 ServiceSession 统一入口语义仍不够清晰

- 类型：设计清晰度不足
- 影响：创建会话依赖核销、叫号、预约等多入口，维护成本高
- 建议：沉淀统一生命周期说明，并把创建与完成路径标准化

### 6.3 P2 级

#### P2-1 平台端定位偏窄

- 类型：能力边界未扩展
- 影响：平台端更像权限模板后台，不是完整租户运营后台
- 建议：要么明确定位，要么追加商户生命周期管理

#### P2-2 看板缺少独立大屏态

- 类型：产品能力缺失
- 影响：门店展示依赖复用商户页面
- 建议：拆出投屏/大屏专用视图

#### P2-3 认证体系仍保留 legacy 兼容路径

- 类型：技术债
- 影响：体系复杂度较高，不利于长期维护
- 建议：计划性清退 legacy token

### 6.4 测试覆盖缺口

- 队列模式与服务开关组合场景回归不足
- 客服模式未实现子场景缺少自动化用例
- 预约与会话、队列整合场景缺少端到端验证
- 房间/手牌异常补偿场景缺少自动化测试

## 7. 建议建设路线

### 7.1 短期止血

- 补齐客服模式手动结单子场景
- 跟进待上号重分配一期上线后的真实使用反馈，确认是否需要扩展到手工指定改派
- 补服务开关组合场景回归测试

### 7.2 中期补环

- 把预约到店转为统一履约入口
- 增加房间异常态与手牌异常工单流
- 梳理 ServiceSession 全状态图与模式矩阵

### 7.3 长期产品化

- 平台端按定位扩展为完整租户运营后台，或维持权限平台并明确边界
- 增加独立大屏看板
- 收敛认证体系，完成 legacy 能力下线

## 8. 结论摘要

### 8.1 总体判断

当前项目已经不是“原型系统”，而是一个具备明确业务主干的多端服务平台，尤其在以下方面完成度较高：

- 商户服务开关与模式控制
- 现场核销、会话状态机与四种叫号模式
- 用户卡包、卡详情与核销前展示
- 技师岗位、权限、签到与队列联动

### 8.2 当前最主要的短板

当前主要问题不在“完全没有功能”，而在“部分模块尚未完全并入统一主链”：

- 预约还没有真正与现场履约统一
- 客服模式某些子模式仍未落地
- 房间/手牌在极端门店异常场景下的运营链不完整
- 待上号异常补偿已补一期，但更强的调度能力仍属于二阶段增强

### 8.3 最终评级

如果以“服务体系是否形成较完整、逻辑基本自洽的经营闭环”来评估，本项目当前可给出如下结论：

- 核心主链：`中高完成度`
- 异常运营链：`中等完成度`
- 跨模块统一性：`仍需补环`

总体上，项目已经具备继续演进为“功能完备、逻辑自洽服务体系”的基础；下一阶段不应再分散新增外围功能，而应优先补齐预约融合、客服子模式、技师异常补偿、房间/手牌异常流这四类关键缺口。
总体上，项目已经具备继续演进为“功能完备、逻辑自洽服务体系”的基础；下一阶段不应再分散新增外围功能，而应优先补齐预约融合、客服子模式、房间/手牌异常流，以及待上号重分配二阶段增强这四类关键事项。
