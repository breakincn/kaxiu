# 预约与排队解耦及门店实时排队能力重设计方案

日期：2026-03-25

## 1. 结论

当前代码中，`预约` 与 `排队` 已经不再是同一个产品能力，只剩两类间接关联：

1. `预约` 会占用未来产能，影响现场单是否允许插入。
2. `预约用户到店后` 若原预约客服仍被占用，会进入 `appointment_waiting`，表现为预约优先等待。

这说明二者目前的真实关系是：

- `预约`：未来时段承诺与履约管理
- `排队`：现场服务流转与叫号推进

它们已经不是“一个预约列表顺便展示排队进度”的关系，更不是“预约排队 = 门店实时排队”的关系。

因此，应该正式解耦：

- `预约` 回归“预约履约”语义
- `排队` 回归“门店实时忙闲 / 到店等待决策”语义

## 2. 现状分析

### 2.1 配置层已经分开

现有系统已经把两者拆成独立开关和独立设置页：

- `support_appointment`
- `support_queue`
- `frontend/src/views/merchant/AppointmentSettings.vue`
- `frontend/src/views/merchant/QueueSettings.vue`

这说明产品配置层面已经默认它们是两套能力。

### 2.2 当前“预约排队”并不代表门店实时排队

用户端卡详情页当前展示的是“预约排队”：

- `frontend/src/views/user/CardDetail.vue`

但它拿到的数据来源并不是门店现场服务队列，而是：

1. 预约确认时，把预约写入一个单独的 Redis 队列 `QueueTypeAppointment`
2. 用户查看预约时，从这个预约队列快照里取自己的号序
3. `queue_before = no - 1`
4. `estimated_minutes = queue_before * 30`

对应代码：

- `backend/handlers/appointment.go`
- `backend/queue/queue.go`

这套实现存在几个关键问题：

1. 它反映的是“预约确认先后顺序”，不是“当前门店现场等待人数”。
2. `estimated_minutes` 是固定用 `前面人数 * 30` 粗算，不是根据当前技师、房间、服务进度实时计算。
3. `QueueTypeAppointment` 在代码里只有 `Enqueue` 和 `Snapshot` 的读取使用，没有形成真正的叫号、完成、推进闭环。
4. 用户看到“前面排队 0 人 / 预计等待 0 分钟”，并不能据此判断现在去店里能不能马上服务。

所以，当前“预约排队”本质上是一个命名误导。

### 2.3 真正仍然存在的关联，是资源保护而不是产品同一性

当前仍然有价值、且应该保留的关联有两类。

第一类：现场单不能随意压后续预约。

- `backend/handlers/appointment_policy.go`
- `evaluateWalkInTechnicianAvailability(...)`

系统会判断：

- 当前现场单是否会压后某个预约
- 预计让预约多等多久
- 是否超过 `appointment_max_wait_minutes`
- 是否改派其他客服更优

这是一种“预约保护规则”，不是“预约也属于现场排队”。

第二类：预约用户到店后，如果原预约客服还忙，会进入预约优先等待。

- `backend/handlers/service_session_factory.go`
- `backend/scheduler/service_session_scheduler.go`

此时系统创建的是：

- `source_type = appointment` 的 `ServiceSession`
- 状态进入 `appointment_waiting`

这是一种“履约执行状态”，不是“门店公开排队信息”。

### 2.4 因此可以下最终判断

当前预约与排队已经没有“设计初衷上的同一性”。

保留关联的正确方式应该是：

- 在调度层共享资源占用与产能判断
- 在产品层、页面层、数据语义层彻底分开

## 3. 解耦目标

### 3.1 预约模块的职责

预约模块只负责：

- 预约时段选择
- 预约确认与履约承诺
- 到店签到
- 预约改签 / 改派 / 取消 / 免责 / 补偿
- 到店后与 `ServiceSession` 绑定
- 异常闭环与责任结算

预约模块不再负责：

- 展示“前面排队几个人”
- 伪造一个面向用户的排队号
- 用预约确认顺序代替现场忙闲状态

### 3.2 排队模块的职责

排队模块只负责：

- 反映门店当前现场忙闲程度
- 反映当前在店待服务人数 / 服务中人数
- 给未预约用户提供“现在去是否值得”“预计等多久”“建议几点去”的决策信息
- 给商户提供现场叫号与等待推进能力

排队模块不再负责：

- 展示预约自己的履约状态
- 承载预约确认顺序
- 用预约对象冒充现场排队对象

## 4. 建议的结构性拆分

### 4.1 页面与命名拆分

用户端卡详情页当前的“预约排队”应改名为：

- `预约状态`
或
- `预约履约`

该卡片只展示：

- 预约时间
- 预约项目
- 预约客服
- 当前状态
- 当前等待说明
- 是否已到店
- 是否已绑定服务会话
- 改签 / 取消 / 补偿 / 结算信息

应移除字段：

- `前面排队`
- `estimated_minutes` 这类预约队列估算值

### 4.2 数据语义拆分

建议停止把预约写入 `QueueTypeAppointment` 作为用户侧展示基础。

保留的数据字段应只有：

- `predicted_wait_minutes`
- `display_wait_state`
- `display_wait_message`
- `current_estimated_wait_minutes`

这些字段表达的是：

- 预约风险
- 预约到店后的等待状态
- 异常履约说明

而不是门店排队号。

### 4.3 运行链路拆分

解耦后应形成两条主链：

1. 预约主链  
   `Appointment -> CheckIn -> ServiceSession(source=appointment) -> 完成/异常闭环`

2. 现场排队主链  
   `WalkIn/Verify -> ServiceSession(source=walk_in) -> Onsite Queue -> 叫号/上号 -> 完成`

两条主链只在“共享资源池”处发生耦合：

- 技师
- 房间
- 时间片
- 服务时长
- 营业时间

## 5. 新的排队初衷设计

排队能力应该围绕这句话重建：

`让未预约用户在去店前，知道这家店现在忙不忙、到店后大概要等多久、什么时候去更容易及时消费。`

### 5.1 设计原则

1. 排队展示必须基于“当前实时供需”，不能基于预约确认顺序。
2. 排队展示服务的是“到店决策”，不是“订单履约解释”。
3. 排队展示优先输出“忙闲结论”，其次才是人数和分钟数。
4. 预约占用未来产能，但不应该以“预约排队号”形式暴露给用户。
5. 同时支持商户运营视角和用户决策视角，两者指标不同。

## 6. 新排队能力的产品方案

### 6.1 用户侧目标

未预约用户打开门店页时，优先看到：

- 当前忙闲等级
- 当前到店等待人数
- 预计到店等待时长
- 最适合到店时间
- 是否建议先预约

核心不是“你前面有几个人”，而是“你现在去要不要等、要等多久、值不值得去”。

### 6.2 用户侧展示模型

建议在用户店铺页新增一个模块：`门店实时忙闲`

展示字段建议如下：

- `忙闲等级`：空闲 / 稍忙 / 忙碌 / 拥挤
- `当前在店人数`：当前已到店且未完成离店的人数
- `待服务人数`：当前未开始服务但已在店等待的人数
- `服务中人数`：当前正在服务中的人数
- `预计到店等待`：现在出发、到店后预计等待时长
- `建议到店时间`：如 `建议 14:30 后到店`
- `提示动作`：如 `较忙，建议先预约`

### 6.3 预约用户的展示模型

预约用户仍在卡详情页看自己的履约卡片，但卡片文案改为：

- `预约状态`
- `已到店待服务`
- `原预约客服仍在服务上一位客户`
- `当前预计等待 18 分钟`
- `系统已保留预约优先处理`

不再显示：

- `前面排队 X 人`

因为这不是预约用户真正关心的数据，也不是当前系统能准确表达的数据。

### 6.4 商户侧展示模型

商户首页新增或重构一个运营看板区块：`实时门店负载`

展示：

- 当前在店总人数
- 现场待服务人数
- 预约到店待服务人数
- 服务中人数
- 各技师当前状态
- 未来 30/60 分钟预约压力
- 推荐是否开启“建议先预约”提示

这样商户和用户看到的是同一套底层事实，但呈现层不同。

## 7. 新排队指标定义

### 7.1 指标分层

建议把指标拆成三层。

第一层：事实指标

- `present_count`：当前在店人数
- `walk_in_waiting_count`：现场待服务人数
- `appointment_waiting_count`：预约已到店待服务人数
- `serving_count`：服务中人数
- `idle_technician_count`：空闲可接待技师数

第二层：预测指标

- `estimated_walk_in_wait_minutes`
- `estimated_appointment_wait_minutes`
- `next_recommended_arrival_at`
- `capacity_pressure_score`

第三层：展示指标

- `load_level`：空闲 / 稍忙 / 忙碌 / 拥挤
- `advice_text`
- `recommend_booking`

### 7.2 指标口径建议

`当前在店人数`

- 来源于已形成到店事实、且尚未完成/取消/失败收口的服务对象
- 包含现场用户与预约已到店用户

`现场待服务人数`

- `source_type = walk_in`
- `started_at IS NULL`
- 状态属于 `room_selecting / staff_selecting / start_pending / delay_pending / appointment_waiting` 的有效等待态

`预约已到店待服务人数`

- `source_type = appointment`
- `started_at IS NULL`
- 状态属于等待态

`服务中人数`

- 状态属于 `serving / auto_finishing`

`预计到店等待`

- 不是简单 `人数 * 固定分钟`
- 应按当前可用技师、各技师预计释放时间、主流项目时长、预约保护占用综合估算

## 8. 新排队能力的计算方案

### 8.1 用户侧等待时间的推荐算法

给未预约用户看的等待时间，建议按“最早可承接能力”计算：

1. 找到当前所有可承接的技师
2. 计算每个技师的 `available_at`
3. 将已在等待中的现场单按规则排入
4. 将预约已到店优先等待单也计入供需压力
5. 取一个保守值作为 `estimated_walk_in_wait_minutes`

建议默认采用保守口径：

- `P70` 或 `中偏保守` 估算，而不是最乐观估算

这样用户感知更稳定。

### 8.2 建议到店时间

若当前等待较长，系统给出：

- `next_recommended_arrival_at`

生成规则：

- 找到未来第一个 `estimated_walk_in_wait_minutes <= 阈值` 的时间点
- 阈值可默认 `10~15 分钟`

这样比单纯展示“预计等待 38 分钟”更符合决策场景。

### 8.3 忙闲等级

建议用统一规则：

- `空闲`：预计等待 `0~5` 分钟
- `稍忙`：预计等待 `6~15` 分钟
- `忙碌`：预计等待 `16~30` 分钟
- `拥挤`：预计等待 `>30` 分钟

并结合：

- 当前空闲技师数
- 当前待服务人数
- 未来 30 分钟预约压力

做最终校正。

## 9. 数据来源设计

### 9.1 不再以 Appointment 作为排队主数据源

新的排队能力不应从 `appointments` 表直接推导，而应从统一履约事实推导：

- `service_sessions`
- `technician_attendances`
- `technicians`
- `merchant_projects`
- `appointments` 仅作为未来预约占用与已到店来源补充

### 9.2 事实来源优先级

建议按以下优先级取数：

1. `ServiceSession` 当前状态
2. 技师签到/忙闲状态
3. 预约未来占用窗口
4. 项目时长与间隙配置
5. 商户营业时间

### 9.3 缓存策略

该能力适合做“读模型 / 快照”：

- 每 15~30 秒刷新一次
- 或在关键事件发生时增量更新

建议提供一个独立快照对象：

- `merchant_live_queue_snapshots`

可先不落表，先由服务端实时聚合 + Redis 缓存。

## 10. 接口方案

### 10.1 用户侧接口

新增：

- `GET /user/merchants/:id/live-queue`

返回建议：

```json
{
  "load_level": "busy",
  "present_count": 8,
  "walk_in_waiting_count": 3,
  "appointment_waiting_count": 1,
  "serving_count": 4,
  "estimated_walk_in_wait_minutes": 18,
  "next_recommended_arrival_at": "2026-03-25 14:30:00",
  "recommend_booking": true,
  "advice_text": "当前较忙，建议先预约或 14:30 后到店"
}
```

### 10.2 商户侧接口

新增：

- `GET /merchant/live-queue`

返回：

- 全店负载摘要
- 各技师释放时间
- 各等待来源人数
- 未来预约压力

### 10.3 预约详情接口调整

`GET /user/cards/:id/appointment`

建议移除或废弃以下字段：

- `queue_before`
- `estimated_minutes`

保留：

- `display_wait_state`
- `display_wait_message`
- `current_estimated_wait_minutes`

## 11. 页面改版建议

### 11.1 用户店铺页

新增模块：

- `门店实时忙闲`

文案示例：

- `当前稍忙`
- `待服务 3 人，服务中 4 人`
- `现在到店预计等待 18 分钟`
- `建议 14:30 后到店，体验更稳定`

### 11.2 用户卡详情页

把“预约排队”改成“预约状态”。

正常场景示例：

- `预约时间：2026-03-26 10:45`
- `状态：待到店`
- `提示：若前序服务延长，到店后可能等待 10 分钟`

已到店等待示例：

- `状态：已到店待服务`
- `原因：原预约客服仍在服务上一位客户`
- `当前预计等待：18 分钟`
- `系统已保留预约优先处理`

异常跨日示例：

- `状态：历史异常单`
- `说明：客户已到店但服务未完成闭环，请商户处理`

### 11.3 商户首页

新增区块：

- `实时门店负载`

展示：

- 当前可接待技师数
- 在店等待人数
- 预约到店等待人数
- 服务中人数
- 预计现场客等待时长

## 12. 实施计划

### 阶段一：语义拆分

目标：先去误导，不先做大功能。

建议动作：

1. 用户端把 `预约排队` 改为 `预约状态/预约履约`
2. 下线预约卡片中的 `前面排队` 与 `estimated_minutes`
3. 停止新增预约写入 `QueueTypeAppointment`
4. 保留预约等待展示，仅使用 `display_wait_state/display_wait_message/current_estimated_wait_minutes`
5. 文档和表注释中不再把 `appointments` 称为“预约排队表”

### 阶段二：搭建实时排队读模型

目标：形成真正的“门店实时忙闲”能力。

建议动作：

1. 新增 `live-queue` 聚合服务
2. 从 `service_sessions + technician_attendances + appointments` 聚合实时负载
3. 提供用户侧/商户侧两个接口
4. 引入 `load_level / advice_text / next_recommended_arrival_at`

### 阶段三：前端落地

建议动作：

1. 用户店铺页新增“门店实时忙闲”
2. 卡详情页改成“预约履约卡片”
3. 商户首页新增“实时门店负载”

### 阶段四：优化与运营

建议动作：

1. 根据真实到店转化数据调优等待算法
2. 加入“建议先预约”阈值
3. 加入高峰预警和异常监控

## 13. 风险与注意事项

1. 不应把“预约保护等待”直接对外宣传为“门店排队人数”。
2. 不应继续用固定公式 `人数 * 30 分钟` 估算等待。
3. 不应把预约是否到店、是否异常闭环，与门店公开忙闲看板混在一个卡片里。
4. 新排队能力必须是聚合视图，不能暴露预约用户、技师或具体订单隐私。

## 14. 推荐决策

推荐按以下原则执行：

1. 立即确认：`预约` 与 `排队` 在产品层正式解耦。
2. 立即改名：用户端“预约排队”改为“预约状态/预约履约”。
3. 立即下线：预约卡片里的 `前面排队` 与伪 `estimated_minutes`。
4. 保留现有有效耦合：预约保护规则、预约到店后的优先等待规则。
5. 重新建设：基于统一履约事实的“门店实时忙闲 / 到店等待决策”能力。

这套方案能同时解决三个问题：

1. 消除“预约排队”概念误导
2. 保住预约保护与优先等待的真实业务价值
3. 真正实现排队设计最初想解决的“未预约用户到店决策”问题
