# 预约主链重构对齐预约新规实施说明

日期：2026-03-25

## 1. 目标

本次重构以以下文档为准：

- `docs/plans/预约新规与预约资源锁定补偿一体化方案_20260319.md`
- `docs/plans/预约新规与预约资源锁定补偿一体化方案_研发启动执行清单_20260322.md`

核心目标不是继续修补“预约等待/预约排队”，而是把预约主链收敛为：

1. 预约成功即代表资源已锁定。
2. 正常到店后直接进入服务执行链路。
3. 若预约客服仍被前序服务占用，系统记录为履约延迟/商户违约待判定，而不是把预约继续放入正常等待主链。
4. `appointment_waiting` 仅保留为历史兼容状态。

## 2. 实施结果

### 2.1 预约签到主链已改为执行链

已改造 `CheckInAppointment`、`performVerifyCommit`、`createServiceSessionForUsage`：

- 预约到店后不再通过 `evaluateWalkInTechnicianAvailability` 决定是否进入 `appointment_waiting`
- 改为直接进入：
  - `room_selecting`（启用房间时）
  - `start_pending`（未启用房间时）
- 同时用 `estimateAppointmentArrivalDelay` 估算原预约客服的真实释放时间

这意味着：

- 预约签到后的正常主链已经不再依赖 `appointment_waiting`
- `appointment_waiting` 不再是新预约到店的正常入口

### 2.2 条件性压预约已收口为严格预约保护

已改造 `evaluateWalkInTechnicianAvailability`：

- 旧规则：允许 `conditional`
- 新规则：只要现场派单会占用后续预约锁定时段，就直接返回 `unavailable`
- 决策模式统一为 `strict_reservation_lock`

这意味着：

- 运行代码里已不再存在 `safe / conditional / unavailable` 的预约保护语义
- 现场单不能再以“有限压预约”的方式穿透未来预约锁定

### 2.3 延迟保留，但语义已从“等待主链”改为“履约异常处理”

以下能力保留：

- `predicted_wait_minutes`
- `PredictedAppointmentDelayMinutes`
- `PredictedReadyAt`
- `merchant_breach_pending`
- `merchant_delay_pending`

但它们的语义已经改为：

- 风险预约提示
- 到店后检测到的实际延迟
- 商户履约异常待判定

不再表示：

- 预约排队号
- 预约前面还有几人
- 预约正常等待主链

### 2.4 前端与文案已对齐

已同步清理前端残留语义：

- 不再展示 `conditional`
- 商户端预约签到后的提示改为“已到店，预计等待 X 分钟”或“已进入服务闭环”
- `appointment_waiting` 的展示名改为“预约异常等待”
- 预约详情页延迟提示改为“系统已记录本次预约延迟并按履约异常持续跟进”

## 3. 兼容边界

本次没有删除 `appointment_waiting` 状态本身，原因是仍需兼容：

1. 历史遗留会话
2. 调度器对旧状态的收敛处理
3. 自愈/修复/异常结案链路
4. 对旧会话的手动改派

因此当前系统的准确状态是：

- 新建预约到店主链：不再进入 `appointment_waiting`
- 历史兼容与异常分支：仍允许识别和处理 `appointment_waiting`

新增/更新的关键回归覆盖点：

1. 预约签到后进入 `start_pending`，而不是 `appointment_waiting`
2. 预约客服忙时，签到仍走执行链，但会写入延迟与 `merchant_breach_pending`
3. 现场派单一旦占用未来预约锁定时段，立即返回 `strict_reservation_lock`

### 5.3 关键字复核

对运行代码执行关键字复核后，已确认不再存在以下旧语义残留：

- `conditional`
- `QueueTypeAppointment`
- `queue_before`
- `estimated_minutes`
- `预约排队`
- `预约优先等待`
- `max_wait_protection`
- `alternative_preferred`

## 6. 当前结论

重构完成后，当前运行代码可以定义为：

1. 预约已经没有独立排队实现。
2. 预约正常到店主链已经不再使用 `appointment_waiting`。
3. 预约仍保留延迟识别、责任判定、补偿闭环能力。
4. `appointment_waiting` 已降级为历史兼容状态，而不是预约正常主链。

这与 `2026-03-19` 和 `2026-03-22` 两份方案文档的目标是一致的。
