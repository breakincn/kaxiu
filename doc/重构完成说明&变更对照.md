# 重构完成说明 & 变更对照

## 目标

- 完成 ServiceSession 状态机的“模式隔离”：
  - 客服模式使用 `cs_` 前缀状态。
  - 叫号模式使用 `qs_ / qm_ / qms_ / qmm_` 前缀状态。
- 降低复杂度：所有逻辑以“基础状态（Normalize 后）+ SessionMode”驱动，避免不同模式的状态/流程互相污染。
- 补齐业务场景：
  - `qs_`（自动叫号单窗口）支持“过号等待 + 插队窗口”规则。
  - `qms_ / qmm_`（手动叫号单/多窗口）补齐“叫到号后会话推进”“扫码上号”“结单触发下一号”的一致性。
- 修复/避免漏判：后端所有涉及 `status IN (...)` 的查询统一扩展为“全前缀兼容”。

## 核心约定

### 1) 状态前缀

- 旧：直接写裸状态（如 `start_pending`、`serving`）。
- 新：
  - 客服模式：`cs_start_pending`、`cs_serving` 等。
  - 叫号模式：`qs_start_pending/qm_start_pending/qms_start_pending/qmm_start_pending` 等。
- 前端展示与逻辑统一通过 `normalizeSessionStatus`（去前缀）进行展示/筛选。

### 2) 后端工具函数

- `models.NormalizeSessionStatus(status)`：去前缀得到基础状态。
- `models.ApplyStatusPrefix(currentStatus, newBaseStatus)`：保持当前前缀写回新状态。
- `models.ExpandStatusWithKnownPrefixes(baseStatus)`：把单个基础状态扩展成全前缀集合，用于 `WHERE status IN ?`。
- `models.ExpandStatusesWithKnownPrefixes([]string{...})`：批量扩展。

> 所有涉及查询/更新条件的 `status IN (...)` 必须用 Expand*，所有写回状态必须用 ApplyStatusPrefix。

## 变更对照

### A. `qs_` 自动叫号单窗口：过号等待 + 插队窗口（重点）

#### A1. 旧行为

- `delay_pending` 超时后可能直接失败/退卡，且无法在窗口期内重新扫码“插队回到队列”。

#### A2. 新行为

- 超时后进入 `qs_timeout_waiting`（不立即失败）。
- 在“插队窗口”内再次扫码：
  - 撤销队列 done 标记
  - 取消该号的叫号状态
  - 重新触发 `CallNextUncalled` 使其回到 active 队列头
  - 允许直接进入 `serving`
- 插队窗口到期后：进入 `qs_timeout_failed`，并执行 `usage failed + 退卡`。

#### A3. 插队窗口计算

- 抽成共享函数，避免 scheduler/handler 公式漂移：
  - `models.QsTimeoutWindowEndNo(myNo, timeoutCount)`
  - `models.QsTimeoutWaitingExpired(currentNo, myNo, timeoutCount)`

#### A4. 相关文件

- `backend/scheduler/service_session_scheduler.go`
- `backend/handlers/service_session.go`
- `backend/queue/queue.go`
- `backend/queue/redis_store.go`
- `backend/models/session_mode.go`

### B. `qms_ / qmm_` 手动叫号：推进一致性 + 前缀兼容

#### B1. 旧行为

- 部分地方使用精确比较（如 `s.Status == "start_pending"` 或 `status = 'serving'`），导致前缀状态（如 `qmm_start_pending`）被漏判。
- 单窗口手动叫号在“叫到号”后，可能只调用队列 `CallNextUncalled`，但 ServiceSession 未推进到可扫码上号状态。

#### B2. 新行为

- 多窗口扫码上号：以 `NormalizeSessionStatus(s.Status) == "start_pending"` 判断，确保 `qms_/qmm_` 前缀可扫码进入 `serving`。
- 单窗口手动叫号：任何“叫到号”的入口都会把会话推进到 `delay_pending`（保持前缀），等待扫码上号。
  - 复用 helper：`promoteManualSingleCalledSession(...)`
  - 覆盖入口：
    - `TriggerNextCalling`
    - `TriggerNextCallingOnFinish`
    - `TriggerContinueCalling`
    - `TriggerContinueCallingForce`
- 多窗口手动叫号：分配与查询条件统一改为全前缀兼容：
  - `assignNextSessionToTechnicianManual` 使用 Expand/Apply
  - `finalizeSessionManual`/continue-call 相关 where 条件使用 Expand

#### B3. 相关文件

- `backend/handlers/queue_status.go`
- `backend/handlers/service_session.go`

### C. 超时常量统一（扫码上号超时）

#### C1. 旧行为

- 多处硬编码 `60 * time.Second` / `60 * 1000`，前后端不一致。

#### C2. 新行为

- 后端新增统一配置：`config.StartScanTimeout()`（env: `KABAO_START_SCAN_TIMEOUT_SECONDS`，默认 60s）。
- 下发给前端：
  - `/merchant/config` 增加 `startScanTimeoutSeconds`
  - `GetCard` 返回体增加 `start_scan_timeout_seconds`
- 前端用户页推算逻辑使用 `card.start_scan_timeout_seconds`，不再硬编码 `60*1000`。

#### C3. 相关文件

- `backend/config/conf.go`
- `backend/handlers/config.go`
- `backend/models/models.go`
- `backend/handlers/card.go`
- `backend/handlers/service_session.go`
- `backend/scheduler/service_session_scheduler.go`
- `frontend/src/views/user/CardDetail.vue`

### D. 全局扫漏：所有 status IN 列表全前缀兼容

#### D1. 改动原则

- 所有 `status IN ('...')` 必须改为 `status IN ?` 并用 `ExpandStatus(es)WithKnownPrefixes`。
- 所有写回状态必须用 `ApplyStatusPrefix`。

#### D2. 已处理的典型点

- 房间占用统计（避免只兼容 `cs_`）：
  - `backend/handlers/service_session.go` 的 `assignRoomIfPossible`
- scheduler 精确状态过滤：
  - `finalizeOverdueManualServingSessions`：`status = 'serving'` -> `status IN ?`
- 批量收尾时保持前缀：
  - `finalizeUsagesAfterQueueEnded` 批量把会话置 finished 时使用 `CASE WHEN status LIKE 'qms_%' THEN 'qms_finished' ...`

## 注意事项

- `migrations/` 中的 SQL 为数据迁移脚本，保留 `UPDATE service_sessions SET status=...` 属于历史兼容，不参与运行期的“前缀扩展”规则。
- `Appointment`、`TechnicianAttendance` 等表的 `status IN ('pending'...)` 不涉及 ServiceSession 前缀，属于业务实体状态，不需要前缀扩展。
