### 问题 P12：客服子模式未区分（设计缺口）

当前 `ResolveSessionMode` 对所有客服模式统一返回 `"cs"`，**未区分**用户要求的四种客服子模式：

| 子模式 | SupportCustomerServiceMode | SupportOrderComplete | SupportRoom | 当前实现 |
|--------|----------------------------|----------------------|-------------|----------|
| 客服-自动结单模式 | true | false | false | ✅ 已实现（cs_ 无房间自动） |
| 客服-手动结单模式 | true | true | false | ❌ 未实现 |
| 客服-房间自动模式 | true | false | true | ✅ 已实现（cs_ 房间自动） |
| 客服-房间手动模式 | true | true | true | ❌ 未实现 |

设计文档明确说明"当前阶段暂不支持客服-手动结单"，但用户需求中要求完整覆盖。

### 问题 P13：缺少模式防串用校验

设计文档要求"状态推进必须在所属模式状态机内进行"，但当前代码中：
- **无** `session_mode` 与 `status` 前缀一致性校验
- **无** 入口级别的模式路由守卫（如 cs_ 会话不应走 qs_ 推进接口）
- `handleQueueModeStartScan` 仅通过 `isQueueMode`（商户配置）判断，未校验 `session.SessionMode`

## 三、实施计划

### Phase A：修复裸状态写入/比较（高优先级）

#### A1. scheduler 裸状态修复
- `delay_pending` 分支：所有 `"status": "xxx"` 改为 `ApplyStatusPrefix(s.Status, "xxx")`
- `delay_pending` 分支：所有 `Where("status = ?", "xxx")` 改为 `Where("status IN ?", ExpandStatusWithKnownPrefixes("xxx"))`
- `serving` 分支：`"status": "auto_finishing"` → `ApplyStatusPrefix`
- `serving` 分支：`Where("status = ?", "serving")` → `Where("status IN ?", Expand...)`
- `autoAssignRoom`：裸状态写入和查询修复
- `failStartPendingAndAssignNext`：裸状态写入和查询修复
- `finalizeOverdueManualServingSessions`：`locked.Status != "serving"` → `NormalizeSessionStatus(locked.Status) != "serving"`

#### A2. handler 裸状态修复
- `ChooseServiceSessionRoom`：`s.Status == "finished"` → `NormalizeSessionStatus`；`"room_locked"/"delay_pending"` → `ApplyStatusPrefix`
- `ChooseServiceSessionTechnician`：同上；`"start_pending"` → `ApplyStatusPrefix`
- `ExtendServiceSession`/`ExtendServiceSessionDuration`：`s.Status == "xxx"` → `NormalizeSessionStatus`
- `usage_revoke.go`：所有裸状态比较和写入修复；`NOT IN ('finished','canceled')` → `NOT IN ?` + Expand
- `table.go`：`s.Status == "start_pending"` → `NormalizeSessionStatus(s.Status) == "start_pending"`
- `service_session.go` L460：`out.Status == "delay_pending"` → `NormalizeSessionStatus`

#### A3. merchant.go 迁移函数修复
- `statuses` 使用 `ExpandStatusesWithKnownPrefixes`
- 写入状态使用 `ApplyStatusPrefix`

### Phase B：客服子模式支持（中优先级）

#### B1. 扩展 `ResolveSessionMode` 支持客服子模式
```
cs       → SupportCustomerServiceMode && !SupportOrderComplete && !SupportRoom
cs_order → SupportCustomerServiceMode && SupportOrderComplete && !SupportRoom
cs_room  → SupportCustomerServiceMode && !SupportOrderComplete && SupportRoom
cs_full  → SupportCustomerServiceMode && SupportOrderComplete && SupportRoom
```

**注意**：状态前缀仍统一为 `cs_`，子模式通过 `session_mode` 字段区分流程分支。

#### B2. 客服手动结单流程
- `cs_order` / `cs_full` 模式下：`serving` 到达 `scheduled_finish_at` 后不自动进入 `auto_finishing`，而是等待商户手动结单
- 新增手动结单接口或复用现有 `finalizeSessionManual`
- scheduler `serving` 分支增加 `SupportOrderComplete` 判断

#### B3. 状态流程文档化
- `cs_basic`：核销 → 选技师 → 起单 → 自动结单
- `cs_order`：核销 → 选技师 → 起单 → **手动结单**
- `cs_room`：核销 → 选房间 → 选技师 → 起单 → 自动结单
- `cs_full`：核销 → 选房间 → 选技师 → 起单 → **手动结单**

### Phase C：模式防串用校验（中优先级）

#### C1. 入口级模式校验
- `handleServiceSessionStartScan`：校验 `session.SessionMode` 与当前商户模式一致
- `handleQueueModeStartScan`：校验 `session.SessionMode` 以 `qs`/`qm`/`qms`/`qmm` 开头
- 选房/选技师接口：校验 `session.SessionMode == "cs"` 系列

#### C2. 状态推进守卫
- 在 `ApplyStatusPrefix` 或新增 `ValidateStatusTransition` 中校验：
  - `session_mode` 与写入的 status 前缀一致
  - 状态转换在合法状态机路径内

### Phase D：回归测试（高优先级，与 Phase A 并行）

- 补充单元测试覆盖：
  - cs_ 会话走 qs_ 推进接口应被拒绝
  - cs_ 房间自动全流程
  - cs_ 无房间自动全流程
  - qs_ 过号插队窗口
  - qms_/qmm_ 手动叫号全流程
  - 裸状态写入回归（确保所有 status 写入带前缀）
